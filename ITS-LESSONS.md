# ITS-138 LESSONS FOR INTERACTIVE DAIMOS

STATUS: DESIGN DIRECTION; NOT YET AN IMPLEMENTATION REQUIREMENT

## 1. PURPOSE

ITS-138 IS A PARTICULARLY USEFUL COMPARISON FOR DAIMOS BECAUSE THE SURVIVING
MONITOR LISTING EXPOSES THE MECHANISMS USED TO MAKE INTERACTION WORK:
SCHEDULING, I/O WAIT, CORE ALLOCATION, USER INTERRUPTS, SUPERIOR/INFERIOR
PROCEDURES, TERMINAL OWNERSHIP, DISPLAY-CONSOLE SERVICE, AND DYNAMIC I/O
BUFFER MANAGEMENT.

DAIMOS SHOULD NOT BECOME ITS. ITS ASSUMES A DIFFERENT USER ENVIRONMENT,
SECURITY MODEL, PROGRAMMING CULTURE, DEVICE SET, AND RELATIONSHIP BETWEEN
MONITOR AND DEBUGGER. DAIMOS IS A SMALL GENERAL-PURPOSE MULTIUSER SYSTEM
OPTIMIZED FOR A WORKSTATION-LIKE LOAD: A FEW CONCURRENT USERS, INTERACTIVE
SHELLS AND EDITORS, DEVELOPMENT TOOLS, BACKGROUND BUILDS, AND OCCASIONAL
CPU-HEAVY OR REAL-TIME PROGRAMS.

THE USEFUL ITS LESSON IS:

> INTERACTIVE PROGRAMS SHOULD BE ABLE TO CONTROL, WAIT FOR, INTERRUPT, STOP,
> RESUME, AND HAND TERMINAL OWNERSHIP TO OTHER PROGRAMS USING SMALL GENERAL
> KERNEL PRIMITIVES.

THIS COMPLEMENTS 'JOSS-LESSONS.md'. JOSS PRIMARILY TEACHES RESPONSE-TIME
POLICY. ITS-138 PRIMARILY TEACHES HOW A SMALL MONITOR CAN SUPPORT A RICH
INTERACTIVE PROGRAMMING ENVIRONMENT WITHOUT MAKING EVERY INTERACTIVE FACILITY
A DISTINCT KERNEL SUBSYSTEM.

## 2. OBSERVED ITS-138 MECHANISMS

THE ITS-138 MONITOR LISTING SHOWS SEVERAL IMPORTANT MECHANISMS DIRECTLY.

THE CLOCK PATH DECREMENTS A CURRENT USER QUANTUM AND CALLS 'SEARCH' WHEN THE
QUANTUM EXPIRES. 'SEARCH' SCANS USERS AND EXPLICITLY TESTS SAVED I/O-WAIT
CONDITIONS SO A USER WHICH HAS BECOME READY CAN BE SELECTED. THE USER RECORD
HAS A SAVED 'UQUAN', RESTORED TO 'CUQUAN' ON A USER SWITCH.

THE PROCESS/PROCEDURE MODEL HAS A 'SUPPRO' SUPERIOR-PROCEDURE RELATIONSHIP.
THE MONITOR CAN DELIVER A USER CONTROL INTERRUPT TO A SUPERIOR PROCEDURE, AND
THE USER DEVICE ROUTINES CAN LOCATE AND CREATE INFERIOR PROCEDURES. THIS IS
THE BASIS FOR AN INTERACTIVE ENVIRONMENT IN WHICH ONE USER PROGRAM CAN
SUPERVISE ANOTHER.

TERMINAL OWNERSHIP IS NOT PERMANENTLY FUSED TO ONE USER RECORD. THE 'AATTY'
AND 'AGBLTTY' OPERATIONS TRANSFER OR RECOVER TERMINAL ASSOCIATION BETWEEN
RELATED PROCEDURES. TERMINAL STATE ALSO DISTINGUISHES NORMAL, IMAGE, AND DDT
MODES.

THE CORE ALLOCATOR CAN MOVE USER CORE AND ALSO KNOWS ABOUT I/O STORAGE WHICH
MAY BE IN USE. ACTIVE I/O BUFFERS ARE LOCKED WHILE THE ALLOCATOR MOVES OR
RECLAIMS STORAGE. THE MONITOR HAS A BOUNDED TABLE OF DYNAMICALLY ALLOCATED
I/O BUFFERS RATHER THAN DEDICATING THE MAXIMUM STORAGE TO EVERY CHANNEL.

THE GE DISPLAY-CONSOLE OUTPUT PATH SERVICES CONSOLES ROUND-ROBIN, KEEPS A
RETAINED REPRESENTATION, RECORDS WHICH CHARACTER POSITIONS DIFFER, AND IN
NORMAL COMMAND MODE GIVES COMMAND LINES PREFERENCE OVER ORDINARY SCREEN
LINES. THIS IS A DEVICE-SPECIFIC EXAMPLE OF FAVORING INTERACTIVE FEEDBACK
OVER BULK OUTPUT.

THE MONITOR ALSO HAS AN EXPLICIT NULL JOB/IDLE PATH. WHEN NO USER IS READY,
THE MACHINE DOES NOT NEED TO PRETEND THAT AN ORDINARY USER PROCESS IS RUNNING.

## 3. WHAT DAIMOS ALREADY GETS RIGHT

MUCH OF THE ARCHITECTURAL LESSON FROM ITS IS ALREADY PRESENT IN DAIMOS.

DAIMOS HAS:

- PARENT/CHILD PROCESS RELATIONSHIPS;
- PROCESS GROUPS;
- SESSIONS;
- DOMAINS AS A SEPARATE PROCESS-CONTROL SCOPE;
- A COMPACT NATIVE PROCESS-EVENT MODEL;
- STOP/CONTINUE;
- FOREGROUND PROCESS-GROUP TTY OWNERSHIP;
- SESSION-BASED CONTROLLING TERMINALS;
- RAW AND COOKED TERMINAL MODES;
- BOUNDED WORD PIPES;
- DYNAMIC CORE ALLOCATION;
- PDP-6 USER-EXTENT RELOCATION/COMPACTION;
- PROCESS SWAPPING;
- RECLAIMABLE CLEAN FILESYSTEM CACHE;
- MEMFS RECLAIM BEFORE PROCESS SWAP;
- BOUNDED/LAZY DISPLAY STORAGE.

THIS MEANS THE CORRECT RESPONSE TO ITS IS MOSTLY TO PRESERVE THE GENERALITY OF
THESE PRIMITIVES AND MAKE SURE USERSPACE CAN COMPOSE THEM EFFECTIVELY.

IN PARTICULAR, DAIMOS SHOULD NOT REPLACE PROCESS GROUPS/SESSIONS WITH AN
ITS-LIKE SUPERIOR-PROCEDURE TREE. THE DAIMOS MODEL IS BETTER SUITED TO
PIPELINES, MULTI-PROCESS JOBS, MULTIPLE LOGINS, AND A GENERAL SHELL.

## 4. READY I/O SHOULD BECOME RUNNABLE PROMPTLY

ITS 'SEARCH' DOES NOT TREAT I/O WAIT AS AN OPAQUE CONDITION WHICH IS ONLY
REVISITED AT A DISTANT SCHEDULER INTERVAL. IT TESTS WHETHER A USER'S SAVED
I/O-WAIT CONDITION HAS BECOME READY WHILE CHOOSING THE NEXT USER.

DAIMOS ALREADY HAS A CLEANER EVENT-WAKEUP MODEL, SO IT SHOULD NOT COPY THE ITS
TECHNIQUE OF SAVING AN EXECUTABLE WAIT INSTRUCTION IN THE PROCESS RECORD.
THE LESSON IS THE POLICY:

    I/O COMPLETION
        ->
    MARK THE PROCESS RUNNABLE IMMEDIATELY
        ->
    RECONSIDER CPU OWNERSHIP PROMPTLY WHEN THE WAKEUP IS LATENCY-SENSITIVE

'JOSS-LESSONS.md' PROPOSES USING LONG BLOCKING TIME AS A GENERAL INDICATION
THAT A WAKEUP MAY BE HUMAN-INTERACTIVE. ITS REINFORCES THE NEED FOR A CHEAP
WAKEUP-TO-SCHEDULER PATH, BUT ALSO SHOWS WHY DAIMOS MUST NOT KICK THE
SCHEDULER FOR EVERY HIGH-RATE DEVICE COMPLETION.

THE FIRST DAIMOS POLICY SHOULD THEREFORE REMAIN:

- ALL COMPLETIONS MAKE THEIR WAITERS RUNNABLE WITHOUT DELAY;
- LONG-BLOCK/HUMAN-SCALE WAKEUPS MAY REQUEST THE EXISTING SOFTWARE PI6
  RESCHEDULE;
- SHORT DEVICE WAITS NORMALLY WAIT FOR THE EXISTING SCHEDULER BOUNDARY;
- REAL-TIME OWNERSHIP REMAINS AUTHORITATIVE.

NO SECOND I/O-PRIORITY QUEUE IS NEEDED.

## 5. KEEP QUANTUM POLICY CHEAP

ITS-138 STORES A QUANTUM IN EACH USER RECORD AND RESTORES IT ON USER SWITCH.
THE LISTING PROVES THE REPRESENTATION; IT DOES NOT BY ITSELF JUSTIFY A LARGE
DYNAMIC-QUANTUM POLICY FOR DAIMOS.

DAIMOS SHOULD KEEP ONE NORMAL QUANTUM POLICY UNLESS MEASUREMENT SHOWS A
REPEATABLE INTERACTIVE PROBLEM WHICH THE LONG-BLOCK WAKEUP RULE DOES NOT
SOLVE. A FEW WORKSTATION USERS DO NOT JUSTIFY MULTIPLE SCHEDULER CLASSES OR
LARGE PER-PROCESS QUANTUM STATE.

IF FUTURE MEASUREMENT SHOWS THAT BURSTY INTERACTIVE TASKS BENEFIT FROM A
SHORTER FIRST QUANTUM OR CPU-BOUND JOBS FROM A LONGER FOLLOWING QUANTUM, THAT
SHOULD BE IMPLEMENTED BY REUSING EXISTING SCHEDULER FIELDS OR GLOBAL POLICY
FIRST. DO NOT ADD A WORD PER PROCESS MERELY TO COPY 'UQUAN'.

## 6. SUPERIOR/INFERIOR PROCEDURES: THE IMPORTANT ITS LESSON

ITS'S SUPERIOR/INFERIOR MODEL LETS ONE INTERACTIVE PROGRAM CONTROL ANOTHER.
THE SUPERIOR CAN RECEIVE CONTROL INDICATIONS FROM AN INFERIOR, AND THE SYSTEM
CAN ROUTE EXCEPTIONAL CONDITIONS THROUGH THAT RELATIONSHIP.

THIS IS IMPORTANT FOR WORKSTATION USE BECAUSE A DEVELOPMENT SYSTEM NEEDS
TOOLS SUCH AS:

- SHELLS;
- DEBUGGERS;
- TEST RUNNERS;
- EDITOR BUILD/RUN COMMANDS;
- PROGRAM MONITORS;
- EVENTUALLY PROFILERS OR TRACING TOOLS.

THE KERNEL SHOULD NOT IMPLEMENT THESE AS SPECIAL FACILITIES. IT SHOULD
PROVIDE ENOUGH GENERAL PROCESS CONTROL THAT USERSPACE CAN BUILD THEM.

DAIMOS ALREADY HAS MOST OF THE NECESSARY BASE:

    PARENT/CHILD
    PROCESS GROUP
    SESSION
    DOMAIN
    WAIT STATUS
    PROCESS EVENTS
    STOP / CONTINUE
    FOREGROUND TTY OWNERSHIP

THE DESIGN RULE IS TO EXTEND THESE EXISTING PRIMITIVES ONLY WHEN A REAL
USERSPACE DEBUGGER OR MONITOR REQUIRES SOMETHING THEY CANNOT EXPRESS.

FOR EXAMPLE, A FUTURE DEBUGGER MAY EVENTUALLY NEED REGISTER/MEMORY INSPECTION
AND CONTROLLED SINGLE-STEP/CONTINUE. THAT WOULD JUSTIFY A SMALL DEBUG
INTERFACE. IT WOULD NOT JUSTIFY COPYING THE ITS SUPERIOR-PROCEDURE ABI OR
ADDING A LARGE POSIX 'PTRACE'-LIKE REQUEST MATRIX BEFORE A DEBUGGER EXISTS.

## 7. PROCESS EVENTS SHOULD REMAIN SMALL AND COMPOSABLE

ITS USES USER INTERRUPT REQUESTS TO CONNECT ASYNCHRONOUS EVENTS TO USER
PROGRAMS AND TO SUPERIOR PROCEDURES.

DAIMOS'S COMPACT EVENT SET ALREADY COVERS THE CURRENT GENERAL NEED:

    INT
    TERM
    HUP
    TSTP
    CONT
    ALRM
    CHLD
    PIPE

THIS IS A GOOD FIT FOR THE ITS LESSON. THE EVENT MECHANISM SHOULD REMAIN A
SMALL PROCESS-CONTROL FACILITY RATHER THAN GROWING INTO A FULL SIGNAL
FRAME/USER-HANDLER ABI PREMATURELY.

DSH'S DEFERRED TRAP/EVENT LANGUAGE SHOULD BE BUILT ON THE STABLE NATIVE EVENT
MODEL. DO NOT CREATE A SECOND SHELL-LOCAL ASYNCHRONOUS CONTROL SYSTEM.

WHEN A FUTURE TOOL NEEDS A NEW EVENT, FIRST ASK WHETHER THE EXISTING
PARENT/WAIT STATUS, FILE-DESCRIPTOR READINESS, OR CURRENT EVENT SET ALREADY
REPRESENTS IT. ADD A NEW PERMANENT EVENT CODE ONLY FOR A SYSTEM-WIDE
SEMANTIC, NOT FOR ONE APPLICATION.

## 8. TERMINAL OWNERSHIP SHOULD FOLLOW THE ACTIVE JOB

ITS CAN GIVE A TERMINAL TO AN INFERIOR PROCEDURE AND LATER RECOVER IT. THIS
IS A STRONG VALIDATION OF DAIMOS'S DECISION TO MAKE TTY OWNERSHIP AND
FOREGROUND PROCESS GROUPS REAL KERNEL STATE.

THE SHELL MUST NOT PROXY ALL INTERACTIVE I/O FOR CHILDREN. A FOREGROUND JOB
SHOULD TALK TO ITS CONTROLLING TERMINAL DIRECTLY. DSH SHOULD:

1. CREATE OR JOIN THE JOB'S PROCESS GROUP;
2. GIVE THAT GROUP FOREGROUND TTY OWNERSHIP;
3. LET THE PROGRAM USE THE TTY DIRECTLY;
4. REGAIN FOREGROUND OWNERSHIP WHEN THE JOB STOPS OR EXITS;
5. RESTORE THE SAVED TTY MODE.

THIS IS THE GENERAL DAIMOS EQUIVALENT OF ITS TERMINAL TRANSFER, AND IT WORKS
FOR MULTI-PROCESS PIPELINES RATHER THAN ONLY A SUPERIOR/INFERIOR PAIR.

THE CURRENT RAW/COOKED/ECHO/SIGNALS TTY MODEL IS ALSO SUFFICIENT. ITS IMAGE
AND DDT MODES SHOW THAT INTERACTIVE SYSTEMS NEED A WAY TO BYPASS NORMAL
CHARACTER PROCESSING, BUT THEY DO NOT ARGUE FOR A LARGE 'TERMIOS'-STYLE ABI.

## 9. CORE PRESSURE: RECLAIM CHEAP STORAGE BEFORE USER WORKING SETS

ITS'S CORE ALLOCATOR IS A STRONG HISTORICAL EXAMPLE OF TREATING I/O BUFFERS AS
MEMORY WHICH MAY NEED TO BE RECLAIMED OR MOVED RATHER THAN AS UNTOUCHABLE
PERMANENT RESERVATIONS. THE ALLOCATOR DISTINGUISHES ACTIVE I/O STORAGE, LOCKS
BUFFERS WHICH CANNOT MOVE DURING A TRANSFER, AND CAN RELOCATE OTHER STORAGE
WHILE SEARCHING FOR CORE.

DAIMOS HAS ALREADY ADOPTED THE CORRECT GENERALIZATION:

    CLEAN BCACHE
        ->
    BACKED MEMFS RECLAIM
        ->
    PROCESS SWAP

THIS ORDER SHOULD REMAIN. A USER'S ACTIVE WORKING SET SHOULD NOT BE SWAPPED
MERELY TO PRESERVE REGENERABLE OR IDLE I/O CACHE.

THE ADDITIONAL ITS-DERIVED RULE IS:

> PIN ONLY THE MINIMUM STORAGE WHICH AN ACTIVE DEVICE TRANSFER ACTUALLY NEEDS.

AN IN-FLIGHT DEVICE OPERATION MAY REQUIRE A STABLE BUFFER OR DESCRIPTOR.
THAT DOES NOT JUSTIFY PINNING A LARGE CACHE, COMPLETE FILE, OR UNRELATED
PROCESS STORAGE.

FUTURE DMA/DATA-CHANNEL DRIVERS SHOULD FOLLOW THE SAME RULE.

## 10. BOUNDED DYNAMIC I/O BUFFERING

ITS HAS A FINITE DYNAMIC I/O-BUFFER TABLE. CHANNELS OBTAIN BUFFERS WHEN
NEEDED; THE MONITOR DOES NOT RESERVE A MAXIMUM-SIZED BUFFER SET FOR EVERY
POSSIBLE USER AND DEVICE.

DAIMOS SHOULD CONTINUE THE SAME GENERAL POLICY:

- FIXED PER-OBJECT RESIDENT STATE SHOULD BE TINY;
- BULK BUFFERS SHOULD EXIST ONLY WHILE NEEDED;
- BUFFER COUNTS MUST HAVE HARD BOUNDS;
- ALLOCATION MUST OCCUR IN SLEEPABLE PROCESS CONTEXT, NOT INTERRUPT CONTEXT;
- CLEAN/REGENERABLE BUFFERS SHOULD BE RECLAIMABLE;
- ACTIVE DEVICE TRANSFERS MAY PIN ONLY THEIR IMMEDIATE WORKING STORAGE.

THIS APPLIES TO TTY INPUT, FILESYSTEM TRANSFER WORKSPACE, DISPLAY STORAGE,
TAPE BUFFERS, AND FUTURE NETWORKING.

## 11. DISPLAY/CONSOLE PRIORITY: COPY THE GOAL, NOT THE MECHANISM

THE ITS GE CONSOLE CODE SERVICES MULTIPLE CONSOLES ROUND-ROBIN, TRACKS
DIFFERENCES BETWEEN DESIRED AND PRESENTED SCREEN STATE, AND IN COMMAND MODE
GIVES THE COMMAND-LINE AREA PREFERENCE OVER ORDINARY LINES.

THE GENERAL LESSON IS:

> WHEN OUTPUT BANDWIDTH IS LIMITED, FEEDBACK FOR THE CURRENT INTERACTION
> SHOULD WIN OVER BULK REDRAW.

DAIMOS SHOULD NOT COPY THE ITS DIFFERENCE-SENDING ALGORITHM INTO THE
TYPE-340 DRIVER. A TYPE-340 IS A REFRESH DISPLAY: VISIBLE CONTENT MUST BE
REPLAYED CONTINUOUSLY, WHILE THE ITS GE CONSOLE PATH IS OPERATING A DIFFERENT
DISPLAY/TRANSPORT MODEL. SENDING ONLY CHANGED CHARACTERS WOULD NOT PRESERVE A
TYPE-340 IMAGE.

THE CURRENT DAIMOS TYPE-340 DESIGN IS THEREFORE CORRECT TO KEEP A RETAINED,
DIRECTLY REPLAYABLE FRAME AND DRIVE IT ASYNCHRONOUSLY WITH BLKO.

HOWEVER, IF MEASUREMENT EVER SHOWS THAT A COMPLETE FRAME CANNOT FINISH
COMFORTABLY INSIDE THE REFRESH BUDGET, THE FIRST POLICY EXPERIMENT SHOULD BE
TO MAKE THE ACTIVE INPUT/CURSOR REGION VISIBLE EARLY IN THE FRAME RATHER THAN
TO ADD A COMPLEX DIRTY-REGION SYSTEM. DO THIS ONLY IF DISPLAY TIMING
MEASUREMENTS JUSTIFY IT.

THE ITS ROUND-ROBIN CONSOLE SERVICE ALSO SUPPORTS THE GENERAL RULE THAT ONE
BUSY TERMINAL MUST NOT MONOPOLIZE A SHARED OUTPUT DEVICE.

## 12. IDLE SHOULD BE AN EXPLICIT STATE

ITS HAS A NULL JOB AND EXPLICIT IDLE ACCOUNTING. THIS IS SMALL BUT IMPORTANT.
WHEN NO ORDINARY PROCESS CAN RUN, THE SYSTEM SHOULD ENTER ONE KNOWN IDLE PATH
RATHER THAN SPIN THROUGH USER-SCHEDULER POLICY AS THOUGH USEFUL WORK EXISTS.

DAIMOS SHOULD KEEP ITS IDLE PATH SIMPLE:

- NO PERIODIC POLLING WHICH CAN INSTEAD BE DRIVEN BY INTERRUPTS;
- NO FAKE USER PROCESS MERELY TO OCCUPY THE CPU;
- WAKE IMMEDIATELY FOR DEVICE OR CLOCK WORK;
- MAKE IDLE TIME EASY TO MEASURE IN INSTRUMENTED BUILDS.

THIS HELPS BOTH INTERACTIVE LATENCY AND PERFORMANCE ANALYSIS.

## 13. LINEAR SCANS ARE OFTEN CORRECT FOR DAIMOS

ITS FREQUENTLY SCANS SMALL USER OR DEVICE TABLES. ON A SYSTEM WITH A SMALL
NUMBER OF USERS THIS CAN BE BETTER THAN MAINTAINING MORE ELABORATE QUEUES,
TREES, OR HASH STRUCTURES.

DAIMOS'S EXPECTED WORKLOAD MAKES THE SAME TRADEOFF ATTRACTIVE. WITH A
24-SLOT MINIMUM PROCESS TABLE AND ONLY A FEW NORMALLY ACTIVE USERS:

- A SHORT LINEAR PROCESS SCAN MAY COST LESS RAM AND CODE THAN A SECOND INDEX;
- A LINEAR SWAP-VICTIM SEARCH IS ACCEPTABLE;
- A LINEAR SESSION/PGRP VALIDATION SCAN IS ACCEPTABLE;
- RARE ADMINISTRATIVE OPERATIONS MAY BE O(PROCESS COUNT).

OPTIMIZE THE HOT EVENT/WAKEUP AND RUN-SELECTION PATHS, BUT DO NOT ADD
PERMANENT INDEX STRUCTURES TO MAKE RARE SMALL-N OPERATIONS THEORETICALLY
FASTER.

## 14. INTERACTIVE DEVELOPMENT WORKLOAD

THE ITS COMPARISON SUGGESTS A SECOND WORKSTATION ACCEPTANCE PROFILE IN
ADDITION TO THE LATENCY PROFILE IN 'JOSS-LESSONS.md'.

THE PROFILE SHOULD EXERCISE PROCESS CONTROL:

    LOGIN -> DSH
        ->
    START FOREGROUND CHILD
        ->
    CHILD USES RAW OR COOKED TTY DIRECTLY
        ->
    CTRL-Z / STOP
        ->
    DSH REGAINS TTY
        ->
    BG OR FG
        ->
    CHILD CONTINUES
        ->
    CTRL-C OR NORMAL EXIT
        ->
    DSH RECEIVES STATUS AND PROMPT RETURNS

ALSO TEST:

    DSH
        ->
    PIPELINE WITH MULTIPLE CHILDREN IN ONE PGRP
        ->
    FOREGROUND TTY HANDOFF
        ->
    STOP/CONTINUE
        ->
    GROUP WAIT

AND, AFTER A DEBUGGER EXISTS:

    DSH -> DEBUGGER -> DEBUGGEE

THE DEBUGGER TEST SHOULD PROVE THAT THE KERNEL NEEDS ONLY GENERAL PROCESS
CONTROL AND THE SMALLEST NECESSARY DEBUG ACCESS; IT SHOULD NOT REQUIRE A
DEBUGGER-SPECIFIC SCHEDULER OR TTY PATH.

## 15. MEASUREMENT

THE ITS-DERIVED TESTS SHOULD MEASURE:

- INPUT/EVENT ARRIVAL TO TARGET PROCESS RUNNABLE;
- TARGET RUNNABLE TO FIRST USER INSTRUCTION;
- FOREGROUND TTY HANDOFF TIME;
- STOP TO SHELL PROMPT;
- FG/CONTINUE TO FIRST CHILD INSTRUCTION;
- NUMBER OF SCHEDULER KICKS CAUSED BY SHORT I/O;
- CONTEXT SWITCHES DURING HIGH-RATE I/O;
- RECLAIMED CACHE/BUFFER WORDS BEFORE PROCESS SWAP;
- PROCESS SWAPS DURING INTERACTIVE DEVELOPMENT WORK;
- IDLE TICKS WHEN NO USER WORK IS RUNNABLE.

AS WITH THE JOSS METRICS, PREFER TESTKIT/SIMULATOR TRACING OR A SPECIAL
INSTRUMENTED BUILD. DO NOT ADD A LARGE PERMANENT ACCOUNTING SUBSYSTEM TO THE
PRODUCTION KERNEL.

## 16. IMPLEMENTATION ORDER

THIS DOCUMENT DOES NOT OVERRIDE CURRENT RELEASE GATES.

AFTER THE CURRENT SIZE/CORRECTNESS GATE:

1. COMPLETE DSH JOB CONTROL AGAINST THE EXISTING PROCESS-GROUP, SESSION,
   EVENT, AND TTY PRIMITIVES.
2. ADD THE PROCESS-CONTROL WORKSTATION ACCEPTANCE PROFILE ABOVE.
3. IMPLEMENT THE JOSS-DERIVED LONG-BLOCK WAKEUP EXPERIMENT ONLY AFTER
   BASELINE LATENCY IS MEASURED.
4. VERIFY THAT HIGH-RATE SHORT I/O DOES NOT CREATE EXCESSIVE SCHEDULER KICKS.
5. EXERCISE MEMORY PRESSURE WHILE INTERACTIVE JOB CONTROL IS ACTIVE AND
   CONFIRM THAT RECLAIMABLE CACHE/BUFFER STORAGE IS SACRIFICED BEFORE ACTIVE
   USER WORKING SETS.
6. KEEP THE CURRENT TTY HANDOFF DESIGN; DO NOT ADD AN ITS-LIKE TTY OWNERSHIP
   CHAIN UNLESS THE SESSION/PGRP MODEL PROVES INSUFFICIENT.
7. WHEN A REAL DEBUGGER IS PORTED OR WRITTEN, IDENTIFY THE MINIMUM MISSING
   PROCESS-INSPECTION OPERATIONS AND ADD ONLY THOSE.
8. REVISIT DISPLAY COMMAND-REGION PRIORITY ONLY IF TYPE-340 TIMING SHOWS A
   USER-VISIBLE REFRESH-LATENCY PROBLEM.

## 17. ACCEPTANCE CRITERIA

THE ITS-DERIVED DESIGN IS SUCCESSFUL IF:

- FOREGROUND JOBS ACCESS THEIR TTY DIRECTLY;
- DSH CAN STOP, CONTINUE, BACKGROUND, FOREGROUND, AND WAIT FOR MULTI-PROCESS
  JOBS WITHOUT PROXYING THEIR I/O;
- PROCESS EVENTS REMAIN A SMALL GENERAL FACILITY;
- A FUTURE DEBUGGER CAN BE BUILT BY EXTENDING GENERAL PROCESS CONTROL RATHER
  THAN ADDING A DEBUGGER SUBSYSTEM TO KCORE;
- I/O COMPLETION MAKES PROCESSES RUNNABLE PROMPTLY WITHOUT CAUSING A
  HIGH-RATE RESCHEDULE STORM;
- RECLAIMABLE I/O/CACHE STORAGE IS PREFERRED OVER PROCESS SWAP UNDER PRESSURE;
- IN-FLIGHT I/O PINS ONLY THE MEMORY IT ACTUALLY REQUIRES;
- TERMINAL AND DEVICE BUFFERING REMAINS BOUNDED;
- RARE SMALL-N OPERATIONS REMAIN SIMPLE EVEN WHEN LINEAR;
- THE 32K PDP-6 LOGIN/DSH PATH REMAINS PRACTICAL;
- THE FULL PERMANENT IMAGE REMAINS BELOW THE PROJECT'S HARD RESIDENT LIMIT.

## 18. DESIGN SUMMARY

ITS-138 SHOWS THAT A SMALL INTERACTIVE OPERATING SYSTEM BECOMES POWERFUL WHEN
USER PROGRAMS CAN SUPERVISE OTHER USER PROGRAMS WITH CHEAP GENERAL MECHANISMS.
ITS EXPRESSES THAT THROUGH SUPERIOR/INFERIOR PROCEDURES, USER INTERRUPTS, TTY
TRANSFER, I/O-WAIT SCHEDULING, AND MOVABLE DYNAMIC I/O STORAGE.

DAIMOS SHOULD EXPRESS THE SAME IDEAS THROUGH ITS OWN CLEANER GENERAL MODEL:

    PROCESS + PARENT
    PGRP + SESSION + DOMAIN
    COMPACT EVENTS
    FOREGROUND TTY OWNERSHIP
    BOUNDED DYNAMIC BUFFERS
    RECLAIM BEFORE SWAP
    PROMPT LATENCY-SENSITIVE WAKEUP

THE MOST IMPORTANT RESULT OF THE COMPARISON IS THAT DAIMOS DOES NOT NEED AN
ITS-LIKE MONITOR ARCHITECTURE TO GAIN THE INTERACTIVE BENEFITS. MOST OF THE
REQUIRED MECHANISMS ALREADY EXIST. THE WORK IS TO KEEP THEM SMALL, TEST THEIR
COMPOSITION UNDER REAL WORKSTATION LOAD, AND ADD NEW KERNEL MECHANISM ONLY
WHEN A CONCRETE USERSPACE TOOL PROVES IT NECESSARY.
