# DEC PDP-6 TIMESHARING SYSTEM 1.4 LESSONS FOR DAIMOS

STATUS: DESIGN DIRECTION; NOT YET AN IMPLEMENTATION REQUIREMENT

## 1. PURPOSE

THE DEC PDP-6 TIMESHARING SYSTEM 1.4 (HEREAFTER TS 1.4) IS AN IMPORTANT
REFERENCE FOR DAIMOS BECAUSE IT TARGETS THE SAME BASIC PDP-6 CORE,
RELOCATION/PROTECTION, PRIORITY-INTERRUPT, DATA-CONTROL, DECTAPE, AND TERMINAL
ECONOMICS.

TS 1.4 IS NEITHER A SPECIALIZED SERVICE LIKE JOSS NOR AN INTERACTIVE
PROGRAMMING ENVIRONMENT LIKE ITS. IT IS A SMALL GENERAL TIMESHARING EXECUTIVE.
THAT MAKES ITS MECHANISMS PARTICULARLY RELEVANT TO DAIMOS'S TARGET:

- A MULTIUSER SYSTEM;
- NORMALLY ONLY A FEW CONCURRENT USERS;
- INTERACTIVE SHELL/EDITOR/DEBUGGER WORK;
- BACKGROUND COMPILATION, ASSEMBLY, LINKING, AND TESTING;
- VERY LIMITED CORE;
- VERY SLOW MECHANICAL I/O;
- A PDP-6 BASELINE WHICH MUST REMAIN PRACTICAL AT 32K WORDS.

THE CENTRAL TS 1.4 LESSON IS:

> KEEP THE NORMAL CPU-SCHEDULING QUANTUM LARGE ENOUGH TO BE CHEAP, BUT DO NOT
> MAKE INTERACTIVE OR I/O RESPONSE WAIT FOR THAT QUANTUM TO EXPIRE.

THIS COMPLEMENTS THE OTHER HISTORICAL LESSONS:

- 'JOSS-LESSONS.md' EMPHASIZES HUMAN-VISIBLE RESPONSE-TIME POLICY.
- 'ITS-LESSONS.md' EMPHASIZES COMPOSABLE PROCESS CONTROL AND INTERACTIVE
  USERSPACE TOOLS.
- TS 1.4 EMPHASIZES SMALL GENERAL MECHANISMS, I/O LATENCY, HARDWARE
  UTILIZATION, AND MINIMAL RESIDENT STATE.

THE SOURCE BASIS FOR THIS DOCUMENT IS THE TS-1.4 EXECUTIVE TREE, ESPECIALLY:

- 'EXEC/CLKCSS.MAC' AND 'EXEC/CLOCK.MAC';
- 'EXEC/RUNCSS.MAC';
- 'EXEC/CORE.MAC';
- 'EXEC/SCNSER.MAC';
- 'EXEC/IOCONT.MAC' AND 'EXEC/IOCSS.MAC';
- 'EXEC/DTSER2.MAC';
- 'EXEC/MTPSER.MAC';
- 'EXEC/IOINI1.MAC' AND 'EXEC/IOINI2.MAC';
- 'EXEC/SYSINI.MAC' AND 'EXEC/ONCE.MAC';
- 'EXEC/COMCON.MAC';
- 'EXEC/SAVGET.MAC';
- 'EXEC/ERRCON.MAC'.

## 2. OVERALL TS 1.4 MODEL

TS 1.4 IS FUNDAMENTALLY A SMALL DEVICE-ORIENTED TIMESHARING EXECUTIVE.

ITS BASIC MODEL IS:

    JOB
     |
     +-- CONTIGUOUS CORE ALLOCATION
     |
     +-- ATTACHED TERMINAL
     |
     +-- LOGICAL I/O CHANNELS
           |
           +-- EXPLICITLY ASSIGNED PHYSICAL DEVICES
           +-- USER-OWNED RING BUFFERS
           +-- DEVICE-SPECIFIC SERVICE ROUTINE

IT DOES NOT PROVIDE DAIMOS-LIKE:

- PROCESS GROUPS, SESSIONS, OR DOMAINS;
- A GENERAL VFS;
- PIPES;
- TRANSPARENT PROCESS COMPACTION/SWAPPING;
- RECLAIMABLE FILESYSTEM CACHE CLASSES;
- A GENERAL MULTIUSER CREDENTIAL/PERMISSION MODEL;
- RUNTIME LOADABLE MODULES.

THIS SIMPLICITY IS A LARGE PART OF ITS SMALL SIZE. DAIMOS SHOULD LEARN FROM
THE REPRESENTATION AND CONTROL-FLOW TECHNIQUES WITHOUT DISCARDING THE
GENERAL-PURPOSE FACILITIES WHICH MAKE DAIMOS A BETTER WORKSTATION SYSTEM.

## 3. SEPARATE COMPUTE QUANTUM FROM RESPONSE LATENCY

'NXTJOB' IN 'CLKCSS.MAC' IS EXPLICITLY DESIGNED TO KEEP I/O DEVICES BUSY.
BEFORE ORDINARY COMPUTATION, IT CHECKS WHETHER A SCARCE I/O RESOURCE HAS
BECOME AVAILABLE OR WHETHER ORDINARY I/O WAIT HAS COMPLETED.

THE QUEUE QUANTA IN THE SUPPLIED SOURCE ARE:

    MAGTAPE WAIT                4 TICKS
    DATA-CONTROL WAIT           4 TICKS
    DECTAPE WAIT                4 TICKS
    COMPLETED ORDINARY I/O      6 TICKS
    STRAIGHT COMPUTATION       15 TICKS

AT THE 60-HZ LINE CLOCK THESE CORRESPOND TO APPROXIMATELY:

    4 TICKS   66.7 MS
    6 TICKS  100.0 MS
   15 TICKS  250.0 MS

THE IMPORTANT POINT IS THAT A 250-MS COMPUTE QUANTUM DOES NOT IMPLY 250-MS
I/O RESPONSE. 'CLOCK.MAC' CALLS THE SCHEDULER ON EVERY 60-HZ TICK. IF NO
HIGHER-VALUE EVENT HAS OCCURRED AND THE CURRENT COMPUTE QUANTUM IS NOT
EXHAUSTED, THE CURRENT JOB CONTINUES. IF I/O HAS BECOME SERVICEABLE, THE
SCHEDULER CAN SELECT THAT WORK EARLY.

THE EFFECTIVE POLICY IS:

    CLOCK TICK
        |
        +-- NOTHING IMPORTANT CHANGED
        |       -> KEEP CURRENT COMPUTE JOB
        |
        +-- I/O RESOURCE BECAME USEFUL
        |       -> RUN A RELEVANT WAITER
        |
        '-- COMPUTE QUANTUM EXPIRED
                -> NORMAL ROUND-ROBIN SELECTION

THIS IS A STRONG DESIGN FOR A SMALL MACHINE: CONTEXT SWITCHES NEED NOT OCCUR
EVERY TICK, BUT I/O LATENCY NEED NOT WAIT FOR A LONG COMPUTE QUANTUM.

## 4. DAIMOS SHOULD ACHIEVE THE SAME GOAL EVENT-DRIVEN

DAIMOS ALREADY HAS A DIFFERENT AND CLEANER MECHANISM:

- EVENT-DRIVEN WAKEUP;
- AN INTRUSIVE RUN QUEUE;
- NICE + RECENT-CPU NORMAL SELECTION;
- A SOFTWARE PI6 RESCHEDULE PATH;
- A SHORT NORMAL QUANTUM;
- A FAST 60-HZ PATH BETWEEN QUANTUM BOUNDARIES.

THEREFORE DAIMOS SHOULD NOT COPY TS 1.4'S PER-TICK DEVICE-WAIT SCANS OR ITS
SEPARATE MAGTAPE/DATA-CONTROL/DECTAPE SCHEDULER QUEUES.

THE DAIMOS EQUIVALENT SHOULD BE:

    MEANINGFULLY BLOCKED PROCESS WAKES
        ->
    MAKE IT RUNNABLE
        ->
    REQUEST SOFTWARE PI6 RESCHEDULE
        ->
    RUN THE ORDINARY NICE + RECENT-CPU SELECTOR

AS DESCRIBED IN 'JOSS-LESSONS.md', LONG BLOCKING TIME IS THE PREFERRED FIRST
PROXY FOR A HUMAN-INTERACTIVE WAKEUP. TS 1.4 PROVIDES INDEPENDENT EVIDENCE
THAT IMPORTANT I/O COMPLETION SHOULD BE ABLE TO CAUSE CPU-OWNERSHIP
RECONSIDERATION BEFORE AN UNRELATED COMPUTE QUANTUM EXPIRES.

THE RULE SHOULD REMAIN GENERAL:

- DO NOT CREATE A "TTY PROCESS" CLASS;
- DO NOT CREATE A DECTAPE SCHEDULER CLASS;
- DO NOT KICK PI6 FOR EVERY HIGH-RATE SHORT I/O;
- DO GIVE A LONG-BLOCKED PROCESS A CHANCE TO RUN PROMPTLY;
- KEEP REAL-TIME OWNERSHIP AUTHORITATIVE;
- KEEP NICE AUTHORITATIVE.

## 5. THE NORMAL QUANTUM MAY THEN BE TUNED FOR THROUGHPUT

THIS SEPARATION HAS AN IMPORTANT CONSEQUENCE.

IF INTERACTIVE RESPONSE REQUIRES EVERY COMPUTE JOB TO USE A VERY SHORT
QUANTUM, DAIMOS PAYS MORE:

- CONTEXT SAVES/RESTORES;
- RUN-QUEUE SELECTION;
- CACHE/WORKING-SET DISTURBANCE;
- PI/SCHEDULER OVERHEAD.

IF MEANINGFUL WAKEUPS CAN REQUEST A CHEAP EARLY RESCHEDULE, THE NORMAL
COMPUTE QUANTUM MAY BE CHOSEN PRIMARILY FOR THROUGHPUT AND FAIRNESS.

NO QUANTUM CHANGE SHOULD BE MADE NOW MERELY BECAUSE TS 1.4 USED 15 TICKS.
THE CURRENT DAIMOS QUANTUM SHOULD FIRST BE MEASURED WITH THE JOSS/ITS/TS
WORKSTATION TESTS. ONLY THEN SHOULD LONGER OR SHORTER QUANTA BE COMPARED.

THE TARGET IS:

    LOW HUMAN-VISIBLE WAKEUP LATENCY
    +
    LOW SCHEDULER OVERHEAD

NOT A HISTORICALLY MATCHING QUANTUM VALUE.

## 6. SCHEDULE WORK WHICH CAN START THE NEXT USEFUL I/O

TS 1.4'S SCHEDULER COMMENT SAYS:

    KEEP IO DEVICES BUSY

THIS IS NOT ONLY AN INTERACTIVE-LATENCY RULE. ON DECTAPE, MAGTAPE, OR ANOTHER
SLOW SERIAL DEVICE, THE MACHINE MAY LOSE A LARGE AMOUNT OF WALL-CLOCK TIME IF
THE PROCESS WHICH CAN ISSUE THE NEXT OPERATION SITS BEHIND UNRELATED CPU WORK.

DAIMOS SHOULD THEREFORE MEASURE:

    DEVICE COMPLETION
        ->
    WAITER BECOMES RUNNABLE
        ->
    WAITER GETS CPU
        ->
    NEXT USEFUL DEVICE OPERATION IS ISSUED

THE LAST INTERVAL IS A REAL PERFORMANCE METRIC FOR DECTAPE AND TAPE.

THE FIRST IMPLEMENTATION SHOULD STILL BE THE GENERAL LONG-BLOCK WAKEUP RULE.
ONLY IF MEASUREMENT SHOWS LARGE REMAINING DEVICE-IDLE GAPS SHOULD DAIMOS
CONSIDER A MORE DEVICE-AWARE POLICY.

## 7. SLEEP FOR SCARCE HARDWARE; DO NOT BUSY-WAIT

TS 1.4 EXPLICITLY SERIALIZES SCARCE HARDWARE SUCH AS:

    MAGTAPE CONTROL
    DATA CONTROL
    DECTAPE CONTROL

AND RECORDS WAITERS RATHER THAN LETTING USER JOBS SPIN UNTIL THE RESOURCE
BECOMES FREE.

DAIMOS HAS BETTER GENERAL WAIT/EVENT MECHANISMS, SO THE TRANSFERABLE RULE IS
SIMPLE:

> A PROCESS WAITING FOR SLOW SHARED HARDWARE SHOULD SLEEP. ANOTHER USER
> SHOULD RUN.

BUSY WAITING IS ACCEPTABLE ONLY FOR A VERY SHORT HARDWARE TRANSITION WHERE
SLEEP/WAKEUP WOULD COST MORE THAN THE EXPECTED WAIT AND WHERE THE LOOP CANNOT
STARVE OTHER USERS.

## 8. TWO BUFFERS ARE THE DEFAULT ASYNCHRONOUS PIPELINE

THE TS GENERIC I/O LAYER SUPPORTS USER RING BUFFERS. IF THE USER HAS NOT
EXPLICITLY BUILT A RING, GENERIC INPUT/OUTPUT CAN SET UP TWO BUFFERS.

THIS IS A VERY GOOD SMALL-MACHINE DEFAULT:

    BUFFER A   DEVICE OWNS / FILLS / DRAINS
    BUFFER B   PROCESS OWNS / CONSUMES / PRODUCES

THEN THE ROLES SWAP.

THE FIRST EXTRA BUFFER OFTEN REMOVES MOST OF THE CPU/DEVICE SERIALIZATION.
THE THIRD, FOURTH, OR EIGHTH BUFFER OFTEN COSTS RAM FOR MUCH LESS ADDITIONAL
BENEFIT.

FOR DAIMOS:

- START WITH TWO BUFFERS WHEN A SLOW SEQUENTIAL DEVICE CAN ACTUALLY OVERLAP
  DEVICE TRANSFER AND USER/FILESYSTEM WORK;
- ADD MORE ONLY AFTER MEASUREMENT;
- KEEP HARD UPPER BOUNDS;
- DO NOT ALLOCATE MAXIMUM BUFFERS PER DEVICE INSTANCE BY DEFAULT.

THIS RULE IS PARTICULARLY RELEVANT TO DECTAPE, MAGTAPE, PAPER MEDIA, AND
FUTURE NETWORKING.

## 9. BULK I/O STORAGE SHOULD NOT BECOME PERMANENT KERNEL RAM

TS 1.4 GENERIC I/O PLACES THE RING BUFFERS IN THE USER JOB AREA. THE MONITOR
KEEPS THE SMALL STATE NEEDED TO DRIVE THEM.

DAIMOS SHOULD NOT EXPOSE TS-STYLE DEVICE RING HEADERS AS ITS NORMAL VFS ABI.
THAT WOULD LEAK DEVICE DETAILS INTO APPLICATIONS.

THE MEMORY LESSON IS STILL STRONG:

> IF BULK STORAGE CAN SAFELY BE OWNED BY THE CALLER OR ALLOCATED ONLY FOR THE
> ACTIVE TRANSFER, DO NOT TURN IT INTO PERMANENT KCORE/MRES BSS.

FOR FUTURE HIGH-THROUGHPUT INTERFACES, CONSIDER A BOUNDED CALLER-SUPPLIED OR
DYNAMIC BUFFER BEFORE ADDING A LARGE PER-OPEN OR PER-DEVICE RESIDENT BUFFER.

## 10. DEFER SLOW WORK OUT OF CLOCK/INTERRUPT CONTEXT

'COMCON.MAC' EXPLICITLY REQUIRES CONSOLE COMMAND SETUP ROUTINES, WHICH ARE
CALLED FROM CLOCK CONTEXT, TO FINISH QUICKLY. IF A COMMAND REQUIRES SLOW WORK,
THE COMMAND PATH ARRANGES A RUNNABLE MONITOR JOB AND RETURNS.

THE GENERAL RULE IS:

    PI / CLOCK / OTHER CRITICAL CONTEXT
        ->
    MINIMAL VALIDATION AND STATE PUBLICATION
        ->
    SLEEPABLE/SCHEDULABLE CONTEXT PERFORMS THE SLOW WORK

DAIMOS SHOULD KEEP THIS AS A HARD DESIGN RULE FOR:

- FILESYSTEM WORK;
- MEDIA SEARCH/MOTION;
- LARGE COPIES OR DECOMPRESSION;
- DISPLAY CONTROL WHICH CAN BLOCK;
- FUTURE NETWORK PROTOCOL WORK;
- DEBUGGER/TRACE OPERATIONS;
- ADMINISTRATIVE CONTROL OPERATIONS.

DO NOT CREATE A GENERAL KERNEL-WORKER SUBSYSTEM MERELY TO FOLLOW TS. USE THE
REQUESTING PROCESS'S EXISTING SLEEPABLE EXECUTIVE CONTEXT WHERE IT SUFFICES.

## 11. REUSE THE EXISTING SCHEDULABLE ENTITY

TS 1.4'S 'MONJOB' MECHANISM REUSES A JOB CONTEXT TO EXECUTE SLOW EXECUTIVE
SUBROUTINES SUCH AS SAVE/GET RATHER THAN INTRODUCING A SECOND GENERAL TASK
ABSTRACTION.

THE DAIMOS EQUIVALENT IS:

> PREFER THE REQUESTING PROCESS'S SLEEPABLE SYSCALL CONTEXT OVER A NEW
> KERNEL-THREAD OR WORK-QUEUE ABSTRACTION.

ADD A NEW SCHEDULABLE KERNEL ENTITY ONLY WHEN THERE IS A CONCRETE OPERATION
WHICH CANNOT BE OWNED BY A USER PROCESS OR AN EXISTING KERNEL CONTEXT.

## 12. CORE ALLOCATION: COPY THE ECONOMY, NOT THE ABI

TS 1.4 TRACKS CORE WITH ONE BIT PER 1K-WORD BLOCK AND ALLOCATES ONE CONTIGUOUS
EXTENT TO A JOB. THE USER EXPLICITLY REQUESTS THE NUMBER OF 1K BLOCKS WITH
'CORE'.

THIS IS EXTREMELY SMALL:

- ONE BIT PER 1024 WORDS;
- A FREE-BLOCK COUNT;
- A SIMPLE HOLE SEARCH;
- PDP-6 RELOCATION/PROTECTION FOR THE RESULT.

BUT DAIMOS SHOULD NOT COPY THE INTERFACE OR GRANULARITY:

- USER PROGRAMS SHOULD NOT HAVE TO CHOOSE THEIR PHYSICAL CORE SIZE;
- 1K GRANULARITY CAUSES UNACCEPTABLE INTERNAL FRAGMENTATION FOR DAIMOS'S
  GENERAL WORKLOAD;
- DAIMOS NEEDS COMPACTION, RECLAIM, AND PROCESS SWAP.

THE TRANSFERABLE RULES ARE:

- KEEP ALLOCATION METADATA SMALL;
- PREFER LINEAR EXTENT/BITMAP SCANS FOR TINY TABLES;
- COMPUTE MULTIPLE USEFUL FACTS DURING ONE NECESSARY SCAN;
- DO NOT ADD INDEX STRUCTURES UNLESS THEY SAVE MORE RAM/TIME THAN THEY COST.

## 13. SAVE/GET IS NOT PROCESS SWAPPING

TS 'SAVE' AND 'GET' STORE AND RESTORE A PROGRAM IMAGE ON RETRIEVABLE STORAGE.
'SAVGET.MAC' EXPLICITLY DOES NOT SAVE ALL DEVICE STATE, ACS, OR THE CURRENT
PC AS A TRANSPARENT RUNNING CONTEXT.

THEREFORE TS 1.4 DOES NOT PROVIDE A MODEL FOR DAIMOS PROCESS SWAPPING.

DAIMOS SHOULD KEEP ITS CURRENT GENERAL MODEL:

    CHEAP RECLAIM
        ->
    BACKED FILESYSTEM RECLAIM
        ->
    COMPACTION WHERE USEFUL
        ->
    PROCESS SWAP

AND CONTINUE THE CURRENT WORK TO AVOID WRITING CLEAN EXECUTABLE-BACKED TEXT
TO BACKSTORE.

## 14. TTY ATTACHMENT IS A RESOURCE RELATIONSHIP

TS 1.4 SUPPORTS 'ATTACH' AND 'DETACH'. A TERMINAL DEVICE DATA BLOCK CAN BE
ASSOCIATED WITH A JOB, DETACHED, AND LATER REATTACHED.

THIS REINFORCES THE ITS RESULT:

> THE TERMINAL IS A RESOURCE CONTROLLED BY A JOB/SESSION; IT IS NOT THE
> IDENTITY OF THE PROCESS.

DAIMOS'S SESSION + CONTROLLING-TTY + FOREGROUND-PGRP MODEL IS THE BETTER
GENERALIZATION. DSH SHOULD USE IT DIRECTLY RATHER THAN PROXYING CHILD I/O.

## 15. USER INTERRUPT KEYS MUST REMAIN RESPONSIVE

TS CONTROL-C STOPS THE ATTACHED JOB AND FORCES RESCHEDULING WHEN NECESSARY.
THE PATH DOES NOT REQUIRE THE USER PROGRAM TO COOPERATE.

FOR DAIMOS, FOREGROUND INT/TSTP DELIVERY SHOULD HAVE THE SAME PROPERTY:

- SHORT TTY INPUT PATH;
- NO DEPENDENCE ON TARGET USER CODE;
- PROMPT STOP/INTERRUPT EVENT;
- PROMPT RETURN OF TERMINAL CONTROL TO DSH WHEN THE JOB STOPS.

THE WORKSTATION ACCEPTANCE SUITE SHOULD MEASURE:

    CTRL-C -> TARGET INTERRUPTED
    CTRL-Z -> TARGET STOPPED -> DSH PROMPT

UNDER A COMPETING CPU-BOUND WORKLOAD.

## 16. OUTPUT CANCELLATION IS A REAL INTERACTIVE REQUIREMENT

TS CONTROL-O CAN DISCARD OR SUPPRESS OUTPUT. THIS ADDRESSES A REAL PROBLEM ON
A SLOW TERMINAL: ACCIDENTALLY PRODUCING A LARGE OUTPUT STREAM CAN MAKE THE
MACHINE FEEL UNUSABLE EVEN IF THE CPU SCHEDULER IS RESPONSIVE.

DAIMOS SHOULD NOT ADD CONTROL-O MERELY FOR HISTORICAL COMPATIBILITY.

INSTEAD TEST THE REQUIREMENT:

> CAN A USER ABORT A RUNAWAY FOREGROUND OUTPUT PRODUCER AND REGAIN A USABLE
> TERMINAL QUICKLY?

BOUNDED OUTPUT QUEUES PLUS PROMPT FOREGROUND INT MAY ALREADY SATISFY IT. IF
NOT, ADD THE SMALLEST GENERAL OUTPUT-CANCELLATION MECHANISM RATHER THAN A
TS-SPECIFIC CONTROL CHARACTER.

## 17. DEBUGGING IS A FIRST-CLASS WORKSTATION WORKLOAD

TS HAS SMALL, DIRECT DDT HOOKS AND A DDT TTY MODE. THIS DOES NOT ARGUE FOR
PUTTING A DEBUGGER INTO KCORE.

IT DOES ARGUE THAT DAIMOS'S WORKSTATION ACCEPTANCE MODEL SHOULD INCLUDE:

    DSH -> DEBUGGER -> TARGET PROGRAM

THE FUTURE KERNEL DEBUG INTERFACE SHOULD PROVIDE ONLY THE MINIMUM GENERAL
PRIMITIVES PROVEN NECESSARY BY A REAL DEBUGGER:

- STOP;
- INSPECT/MODIFY MEMORY;
- INSPECT/MODIFY REGISTERS;
- SINGLE-STEP OR EQUIVALENT CONTROL WHERE FEASIBLE;
- CONTINUE;
- REPORT FAULT/STOP STATUS.

## 18. COMPILE/BOOT-TIME SPECIALIZATION IS A MAJOR SIZE TOOL

TS 1.4'S 'SYSTEM'/'ASSOC' MACROS BUILD ONLY THE CONFIGURED DEVICE AND PI
STRUCTURES. 'LINKSR' LINKS DEVICE INTERRUPT SERVICE ROUTINES DURING
INITIALIZATION.

DAIMOS'S KINIT/MINIT/MRES ARCHITECTURE IS A MORE FLEXIBLE VERSION OF THE SAME
PRINCIPLE:

    DISCOVER/CONFIGURE ONCE
        ->
    PATCH OR INSTALL THE MINIMUM RUNTIME PATH
        ->
    DISCARD INITIALIZATION MACHINERY

HARDWARE OR POLICY WHICH IS FIXED AFTER BOOT SHOULD NOT REQUIRE A LARGE
RUNTIME INTERPRETER OR CONFIGURATION TABLE.

THIS ALSO MEANS FUTURE LOADABLE-MODULE SUPPORT MUST NOT FORCE A GENERAL
RUNTIME LOADER/DISPATCH COST INTO SYSTEMS WHICH DO NOT NEED IT.

## 19. ONCE-ONLY CODE VALIDATES KINIT

'ONCE.MAC' DELIBERATELY PLACES ONCE-ONLY INITIALIZATION CODE SO ITS STORAGE
CAN BECOME USER CORE AFTER INITIALIZATION.

DAIMOS KINIT IS THE MORE GENERAL FORM.

KEEP THE RULE:

> IF CODE OR DATA EXISTS ONLY TO ESTABLISH A BOOT-TIME INVARIANT, IT SHOULD
> NOT REMAIN PERMANENT AFTER THAT INVARIANT IS ESTABLISHED.

AUDIT KINIT/MINIT HANDOFFS FOR ACCIDENTAL SURVIVORS RATHER THAN ADDING ANOTHER
SPECIAL DISCARD REGION.

## 20. PI STATE SHOULD MATCH THE ACTUAL CONFIGURATION

TS'S BUILD GENERATES PI SAVE/RESTORE SUPPORT FROM THE DEVICE CONFIGURATION AND
CAN SIZE SAVE AREAS ACCORDING TO THE REQUIREMENTS OF DEVICES ON A LEVEL.

DAIMOS HAS ALREADY APPLIED PART OF THIS PRINCIPLE BY REDUCING ITS PDP-6 PI
STATE AND SPECIALIZING INSTALLED PATHS.

THE GENERAL RULE IS:

- SAVE ONLY STATE PROVEN NECESSARY ON A PI PATH;
- DO NOT RESERVE TABLE SLOTS FOR IMPOSSIBLE SIMULTANEOUS HANDLERS;
- PATCH KNOWN SINGLE-HANDLER PATHS DIRECTLY;
- FOR MULTI-HANDLER LEVELS, PREFER INITIALIZATION-LINKED DIRECT CHAINS OVER A
  PERMANENT GENERIC LIST INTERPRETER IF THE LINKED RESULT IS SMALLER.

THIS LAST ITEM WAS IDENTIFIED IN THE HISTORICAL SIZE WORK AND REMAINS A VALID
REPRESENTATION TECHNIQUE EVEN IF A PARTICULAR OLD MEASUREMENT IS NOW STALE.

## 21. CONTIGUOUS MACHINE CONTEXT SHOULD USE BLT WHERE LEGAL

TS 1.4 LAYS OUT CONTEXT SO CONTIGUOUS REGISTERS CAN BE COPIED WITH BLT.
ITS AND TENEX INDEPENDENTLY USE THE SAME PDP-6/10 TECHNIQUE.

GENERAL RULE:

> IF A SAVE/RESTORE PATH COPIES A CONTIGUOUS RANGE BETWEEN NON-OVERLAPPING
> FIXED AREAS, PREFER ONE PROVEN BLT OVER A LONG MOVE/MOVEM SEQUENCE.

THIS IS BOTH A TEXT-SIZE AND EXECUTION-SPEED OPTIMIZATION.

THE EXACT DAIMOS CONTEXT LAYOUT MUST ALWAYS BE CHECKED BEFORE APPLYING IT:
PI-SAVED ACS, AC17, OVERLAP, AND MACHINE RETURN SEMANTICS MUST REMAIN
CORRECT.

THE TECHNIQUE SHOULD ALSO BE AVAILABLE TO P10SUPER/DAS ANALYSIS FOR
HANDWRITTEN OR GENERATED CODE.

## 22. SMALL TABLES AND DEVICE CHAINS SHOULD STAY LINEAR

TS 1.4 USES LINEAR SCANS FOR:

- JOBS;
- DEVICES;
- LOGICAL/PHYSICAL DEVICE NAMES;
- TTY DEVICE BLOCKS;
- DECTAPE DIRECTORY ENTRIES.

FOR THE EXPECTED DAIMOS WORKSTATION LOAD, THIS IS USUALLY THE RIGHT
RAM/SPEED TRADE:

- 24 PROCESS SLOTS DO NOT REQUIRE A GENERAL SEARCH TREE;
- A FEW MOUNT SLOTS DO NOT REQUIRE HASHING;
- A TWO-BLOCK CACHE DOES NOT REQUIRE LRU INFRASTRUCTURE;
- RARE DEVICE/ADMINISTRATION LOOKUPS MAY BE O(N).

OPTIMIZE THE HOT RUN/WAKEUP/PI PATHS. KEEP RARE SMALL-N OPERATIONS SIMPLE.

## 23. ERROR REPORTING SHOULD PRESERVE CHEAP CONTEXT

TS 1.4 REPORTS ERRORS WITH JOB, DEVICE, OR ADDRESS CONTEXT WHEN THAT
INFORMATION IS ALREADY AVAILABLE:

    ERROR IN JOB ...
    ADDRESS CHECK FOR ...
    ILL DT BLOCK NO. ...
    ILL DEVICE DATA MODE FOR ...
    IO TO UNASSIGNED CHANNEL

DAIMOS SHOULD FOLLOW THE SAME RULE:

> DO NOT THROW AWAY DIAGNOSTIC CONTEXT WHICH IS ALREADY PRESENT AND CHEAP TO
> REPORT.

LARGE MESSAGE CATALOGS OR FORMATTING ENGINES DO NOT BELONG IN KCORE. DETAILED
USER-FACING EXPLANATION BELONGS IN USERSPACE.

## 24. DEVICE RETRY BELONGS NEAR THE DEVICE

TS MAGTAPE AND DECTAPE SERVICE PERFORM BOUNDED DEVICE-SPECIFIC RETRIES BEFORE
REPORTING A FINAL ERROR.

DAIMOS SHOULD KEEP LOW-LEVEL RETRY IN THE DRIVER WHEN:

- THE HARDWARE HAS A WELL-DEFINED RETRY PROCEDURE;
- RETRY IS CHEAP COMPARED WITH FAILING THE HIGHER-LEVEL OPERATION;
- THE RETRY COUNT IS BOUNDED;
- FILESYSTEMS DO NOT NEED TO UNDERSTAND THE MECHANICAL RECOVERY SEQUENCE.

DO NOT CREATE A GENERIC RETRY FRAMEWORK FOR DEVICES WHOSE RECOVERY SEMANTICS
ARE DIFFERENT.

## 25. TS 1.4 DECTAPE FORMAT LESSONS

THE TS 1.4 DECTAPE FORMAT IS DIRECTLY RELEVANT TO THE PLANNED DTFS
PERSONALITY.

'DTSER2.MAC' SHOWS:

- DIRECTORY DATA IN DECTAPE BLOCK 1;
- FOUR-WORD DIRECTORY ENTRIES;
- A PER-UNIT IN-CORE DIRECTORY COPY IN THE MULTIPLE-DIRECTORY BUILD;
- LINKED FILE DATA BLOCKS;
- A SIMPLE NEXT-FREE-BLOCK VALUE ('UFREE');
- 'LOOKUP', 'ENTER', 'GETF', 'SETI', 'SETO', INPUT/OUTPUT, AND DUMP PATHS.

THE CURRENT COMPATIBILITY PLAN SHOULD REMAIN READ-ONLY FIRST:

    DTC
      ->
    BCACHE
      ->
    DTFS PERSONALITY 030
      ->
    READ TS DIRECTORY
      ->
    FOLLOW LINKED FILE BLOCKS
      ->
    VFS READ-ONLY FILE

DO NOT EMULATE THE TS EXECUTIVE'S WHOLE I/O ABI.

A WRITABLE PERSONALITY WOULD REQUIRE A SEPARATE DESIGN REVIEW OF:

- DIRECTORY UPDATE ORDER;
- 'UFREE';
- FILE BLOCK LINKS;
- BLOCK-1 WRITEBACK;
- CLOSE/RELEASE SEMANTICS;
- INTERRUPTED UPDATE BEHAVIOR;
- ERROR/RETRY SEMANTICS.

READ-ONLY SUPPORT IS MUCH SMALLER AND SAFER.

## 26. DECTAPE DIRECTORY CACHING IS CORRECT

TS CACHES THE DIRECTORY IN CORE BECAUSE RE-READING BLOCK 1 FROM A MECHANICAL
TAPE FOR EVERY LOOKUP WOULD BE EXPENSIVE.

DAIMOS SHOULD PRESERVE THE BEHAVIOR BUT USE ITS OWN GENERAL CACHE DESIGN:

- BCACHE FOR CLEAN BLOCKS;
- DRUM-BACKED CACHE WHERE AVAILABLE;
- NO LARGE PER-UNIT PERMANENT DIRECTORY AREA MERELY BECAUSE A UNIT EXISTS.

THIS IS AN EXAMPLE OF A GENERAL RULE:

> CACHE THE SMALL HIGH-REUSE METADATA WHICH AVOIDS MECHANICAL I/O, BUT MAKE
> THE CACHE RECLAIMABLE.

## 27. HISTORICAL SIZEOPT LESSONS: WHY THEY BELONG HERE

OLDER REVISIONS OF DAIMOS 'SIZEOPT.MD' CONTAINED COMPARISONS WITH FUZIX,
JOSS, ITS, TS 1.4, LATER ITS, AND TENEX. THAT FILE WAS LATER PRUNED SO IT
CONTAINS ONLY LIVE SIZE-OPTIMIZATION WORK.

THE OLD COMPARISONS CONTAINED USEFUL ARCHITECTURAL RULES WHICH SHOULD NOT BE
LOST. THEY BELONG IN DESIGN DOCUMENTATION, NOT IN A LIVE WORKLIST.

THE FOLLOWING SECTIONS PRESERVE THOSE DURABLE CROSS-SYSTEM LESSONS WITHOUT
RESTORING STALE MEASUREMENTS OR ALREADY-COMPLETED IMPLEMENTATION TASKS.

## 28. CROSS-SYSTEM RULE: KEEP ONLY LIVE RUNTIME STATE

FUZIX, TS 1.4, ITS, AND TENEX ALL REINFORCE THE SAME QUESTION:

    IS THIS WORD STILL NEEDED AFTER INITIALIZATION OR MOUNT?

IF THE ANSWER IS NO, IT SHOULD NOT REMAIN IN PERMANENT RUNTIME STATE.

APPLY THIS TO:

- KINIT/MINIT HANDOFF OBJECTS;
- FILESYSTEM MOUNT STATE;
- DEVICE INITIALIZATION STATE;
- ROOT-DISCOVERY STATE;
- VALIDATION-ONLY SUPERBLOCK FIELDS;
- BOOT-ONLY TABLES;
- DIAGNOSTIC/PROBE SCRATCH.

PREFER REPURPOSING A WORD AFTER ITS FIRST LIFETIME ENDS WHEN THE TWO USES
CANNOT OVERLAP.

DO NOT CREATE A SECOND "COMPACT RUNTIME COPY" IF THE COPY CODE AND DUPLICATE
STRUCTURE COST MORE THAN SIMPLY LAYING OUT THE ORIGINAL HANDOFF STATE FOR
LIFETIME REUSE.

## 29. CROSS-SYSTEM RULE: USE LIFETIME OVERLAYS

FUZIX REUSES PER-PROCESS UDATA SCRATCH. JOSS SHARES SCRATCH UNDER LIMITED
REENTRANCY. TS 1.4 USES SMALL CURRENT-EXECUTIVE STATE INSTEAD OF LARGE
ARBITRARILY DEEP PER-JOB EXECUTIVE STACKS. ITS USES PACKED RESTART STATE.

THE COMMON DESIGN RULE IS:

> TWO LARGE OBJECTS WHICH PROVABLY CANNOT BE LIVE AT THE SAME TIME SHOULD NOT
> AUTOMATICALLY REQUIRE TWO PHYSICAL STORAGE AREAS.

FOR DAIMOS, CLASSIFY SCRATCH AS:

1. STATE WHICH MUST SURVIVE A PROCESS SWITCH/SLEEP;
2. TRANSIENT NON-SLEEPING EXECUTIVE SCRATCH;
3. STATE WHICH SURVIVES A SLEEP ONLY BECAUSE THE CURRENT IMPLEMENTATION
   PRESERVES A DEEP CONTINUATION.

CLASS 1 MUST REMAIN PROCESS-PRIVATE OR OTHERWISE STABLE.

CLASS 2 SHOULD PREFER ACS, A SHORT STACK FRAME, OR AN ALREADY-SERIALIZED
SHARED WORKSPACE.

CLASS 3 IS A POSSIBLE FUTURE RAM-SAVING TARGET, BUT ONLY IF SERIALIZATION OR A
RESTARTABLE OPERATION CAN REPLACE THE PER-PROCESS STORAGE WITHOUT DAMAGING
CONCURRENCY OR SIMPLICITY.

## 30. CROSS-SYSTEM RULE: DO NOT PAY FOR FULL REENTRANCY WITHOUT NEED

JOSS AND TS 1.4 MAKE LIMITED REENTRANCY AN EXPLICIT SIZE ADVANTAGE.

IN DAIMOS, ORDINARY EXECUTIVE CODE IS NOT ARBITRARILY PROCESS-PREEMPTED. A
PROCESS SWITCH OCCURS AT DEFINED SCHEDULER/SLEEP POINTS.

THEREFORE A NON-SLEEPING DEVICE OR KERNEL PATH DOES NOT NEED:

- A PER-PROCESS COPY OF ALL TRANSIENT SCRATCH;
- A SOFTWARE OWNERSHIP WORD SOLELY TO PREVENT ANOTHER PROCESS ENTERING;
- A GENERAL REENTRANT OBJECT MODEL;
- LOCKING WHICH PROTECTS ONLY AGAINST A SCHEDULER SWITCH WHICH CANNOT OCCUR.

PI REENTRY, RECURSIVE KERNEL CALLS, AND EXPLICIT RESCHEDULING MUST STILL BE
PROVEN ABSENT BEFORE REMOVING SUCH STATE.

## 31. CROSS-SYSTEM RULE: ONE SCAN SHOULD RETURN ALL CHEAP RELATED FACTS

FUZIX AND TENEX BOTH DEMONSTRATE THIS WELL.

IF A SMALL TABLE OR EXTENT ARRAY MUST ALREADY BE WALKED, RETURN ALL RELATED
FACTS WHICH ARE ESSENTIALLY FREE DURING THAT WALK.

EXAMPLES:

- FIT FOUND;
- TOTAL FREE STORAGE;
- LARGEST HOLE;
- FRAGMENTED VS EXHAUSTED;
- BEST OR FIRST SUITABLE ENTRY;
- PRESENCE/COUNT INFORMATION.

DO NOT ADD PERSISTENT INDEXES TO AVOID A SECOND SCAN UNLESS THE INDEX ITSELF
HAS A CLEAR RAM/SPEED WIN.

## 32. CROSS-SYSTEM RULE: LAYOUT DATA FOR PDP-6 INSTRUCTIONS

FUZIX, ITS, AND TENEX ALL REINFORCE PACKING ACCORDING TO MACHINE OPERATIONS,
NOT SOURCE-LANGUAGE AESTHETICS.

FOR EVERY RESIDENT STRUCTURE ASK:

- CAN TWO 18-BIT VALUES SHARE A WORD?
- CAN FLAGS OCCUPY OTHERWISE UNUSED BITS BESIDE AN 18-BIT ADDRESS?
- CAN STATE-DEPENDENT VALUES REUSE ONE WORD?
- CAN A FIELD MOVE DELETE A SHIFT/MASK FROM A HOT PATH?
- CAN TWO HANDLER ADDRESSES SHARE A WORD?
- CAN A POINTER HALF ALSO CARRY A SMALL MODE OR CAPABILITY FIELD?

HOWEVER, A MORE DENSE LAYOUT IS NOT AUTOMATICALLY BETTER. IF EVERY ACCESS
NEEDS EXTRA SHIFTS/MASKS, THE TEXT AND CPU COST MAY EXCEED THE DATA SAVING.

HLRZ/HRRZ, DPB/LDB, AND NATURAL HALFWORD OPERATIONS SHOULD DRIVE THE LAYOUT.

## 33. CROSS-SYSTEM RULE: KEEP THE PROCESS DESCRIPTOR TINY

FUZIX SEPARATES SMALL SCHEDULER-VISIBLE PROCESS STATE FROM LARGER UDATA. ITS
USES A COMPACT FIXED USER BLOCK. TENEX PACKS QUEUE LINKS, QUANTUM, JOB
IDENTITY, AND POINTERS AGGRESSIVELY.

DAIMOS'S THREE-WORD PROCESS DESCRIPTOR IS ALREADY THE CORRECT RESPONSE.

DO NOT GROW IT FOR CONVENIENCE.

FUTURE PROCESS RAM SAVINGS SHOULD PREFER:

- U-AREA REDUCTION;
- STACK HIGH-WATER REDUCTION;
- LIFETIME OVERLAYS;
- SHARED SCRATCH WHERE SAFE;
- STATE-DEPENDENT FIELD REUSE.

DO NOT CHANGE THE PROCESS TABLE TO A POWER-OF-TWO STRIDE MERELY TO SAVE A FEW
ADDRESS-CALCULATION INSTRUCTIONS.

## 34. CROSS-SYSTEM RULE: RESTARTABLE BLOCKING IS THE LARGE FUTURE RAM LEVER

TS 1.4 AND ITS BOTH SHOW THE ARCHITECTURAL ALTERNATIVE TO SAVING A DEEP
KERNEL CONTINUATION FOR EVERY BLOCKED PROCESS.

THE CURRENT DAIMOS MODEL IS:

    ENTER EXECUTIVE
        ->
    BUILD STACK FRAMES
        ->
    PROC_WAIT_EVENT
        ->
    PRESERVE THE PROCESS-PRIVATE EXECUTIVE CONTINUATION
        ->
    RESUME AT THE SAME POINT

THE RESTARTABLE MODEL IS:

    ENTER OPERATION
        ->
    RESOURCE NOT READY
        ->
    SAVE A SMALL EXPLICIT RESTART/WAIT RECORD
        ->
    RETURN TO SCHEDULER
        ->
    WAKE
        ->
    REENTER/RECHECK OPERATION

ITS'S EXECUTABLE WAIT WORDS AND TENEX'S PACKED WAIT-PREDICATE STATE SHOW HOW
COMPACT THIS CAN BECOME.

THIS COULD EVENTUALLY REMOVE A LARGE AMOUNT OF PER-PROCESS KERNEL-STACK RAM.
IT IS ALSO A LARGE ARCHITECTURAL CHANGE.

THEREFORE:

- DO NOT USE IT AS A 0.9 SIZE WORKAROUND;
- FIRST EXHAUST LOCAL STACK-FRAME, SHARED-SCRATCH, AND LIFETIME OVERLAYS;
- IF POST-0.9 WORKING-SET MEASUREMENTS STILL SHOW U-AREA RAM AS A DOMINANT
  COST, REVISIT RESTARTABLE BLOCKING AS A DELIBERATE ARCHITECTURE PROJECT.

## 35. CROSS-SYSTEM RULE: INITIALIZATION-TIME PATCHING BEFORE RUNTIME DISPATCH

JOSS, TS 1.4, ITS, AND TENEX ALL USE MACHINE CODE, TABLES, OR CONTROL PATHS
WHICH ARE SPECIALIZED AFTER CONFIGURATION.

DAIMOS ALREADY USES THIS STYLE.

PREFERENCE ORDER:

1. EXACT STATIC SHARING/FOLDING WITH ZERO RUNTIME COST;
2. SOURCE CANONICALIZATION WHICH MAKES THE BODIES SHAREABLE;
3. KINIT/MINIT-TIME PATCHING OF BOOT-CONSTANT DIFFERENCES;
4. PER-INSTANCE PATCH WORD + XCT OR A TINY VENEER;
5. RUNTIME SELF-MODIFICATION ONLY WHEN EXISTING EXCLUSION MAKES IT SAFE AND
   THE MEASURED SAVING IS MATERIAL.

BOOT-CONSTANT EXAMPLES INCLUDE:

- DEVICE SERVICE ADDRESS;
- NEXT PI HANDLER;
- INSTALLED STORAGE BACKEND;
- FIXED CONTROLLER/UNIT CHOICE;
- READ/WRITE VECTOR;
- OPTIONAL FEATURE PRESENCE.

DO NOT KEEP A GENERAL RESIDENT DISPATCH TABLE FOR A CHOICE WHICH NEVER CHANGES
AFTER INITIALIZATION IF A PATCHED DIRECT PATH IS SMALLER.

## 36. CROSS-SYSTEM RULE: PATCH-TO-FOLD NEAR-CLONES

WHEN TWO COLD ROUTINES DIFFER IN ONLY ONE OR TWO WORDS, ASK WHETHER THOSE
DIFFERENCES CAN BECOME BOOT/MOUNT-CONSTANT PATCH PARAMETERS SO THE LARGE BODY
BECOMES IDENTICAL.

THE USEFUL FORMS INCLUDE:

- PATCHED JRST/PUSHJ TARGET;
- XCT OF A PER-INSTANCE INSTRUCTION;
- PATCHED IMMEDIATE OR EFFECTIVE-ADDRESS FIELD;
- TINY INSTANCE-SPECIFIC PREFIX/SUFFIX AROUND ONE COMMON BODY.

THIS SHOULD REMAIN A P10FOLD/P10SUPER ANALYSIS CATEGORY.

COUNT THE COST OF:

- PATCH CELLS;
- VENEERS;
- XCT/JRST EXECUTION;
- ANY SERIALIZATION;
- ANY KCORE ANCHOR WHICH OPTIONAL MRES PACKAGES WOULD OTHERWISE AVOID.

DO NOT PARAMETERIZE A FOUR-WORD ROUTINE TO SAVE TWO WORDS. THE TECHNIQUE IS
USEFUL WHEN A VERY SMALL PATCH UNLOCKS A MATERIAL COMMON BODY.

## 37. CROSS-SYSTEM RULE: PACK COLD CONTROL DISPATCH MORE AGGRESSIVELY

LATER ITS REPLACED SOME PARALLEL FULL-INSTRUCTION CONTROL TABLES WITH PACKED
METHOD DESCRIPTORS INTERPRETED BY A COMMON COLD PATH. TENEX PACKS FLAGS WITH
HANDLER ADDRESSES.

THIS SUGGESTS A GENERAL DAIMOS RULE:

> FOR COLD CONTROL-PLANE OPERATIONS, A SMALL METHOD DESCRIPTOR + ONE SHARED
> INTERPRETER MAY BE SMALLER THAN MANY TINY NEAR-IDENTICAL HANDLERS.

DO NOT APPLY THIS TO HOT DATA TRANSFER OR SCHEDULER PATHS.

THE FIRST REPRESENTATION TO TRY SHOULD ALWAYS BE THE SIMPLEST:

- TWO 18-BIT HANDLER ADDRESSES PER WORD;
- ADDRESS + FLAGS IN THE OTHER HALF;
- SMALL DIRECT METHOD CODES ONLY IF THEY REMOVE ENOUGH LEAF CODE TO WIN.

## 38. CROSS-SYSTEM RULE: COMMON LITERALS ONLY AFTER LINKER MEASUREMENT

TENEX EXPLICITLY REUSES GLOBAL CONSTANT WORDS AND SOMETIMES ALIASES A CONSTANT
TO A VALUE ALREADY PRESENT IN AN IMMUTABLE TABLE.

DAIMOS SHOULD FIRST DETERMINE WHAT DAS/DLINK ALREADY COALESCE.

IF IDENTICAL LITERALS SURVIVE DUPLICATED IN THE FINAL IMAGE:

1. PREFER AN ALIAS OF AN ALREADY-REQUIRED IMMUTABLE WORD;
2. THEN CONSIDER ONE SHARED COMMON CONSTANT;
3. OTHERWISE KEEP THE LOCAL LITERAL.

DO NOT CREATE OBSCURE CROSS-SUBSYSTEM DEPENDENCIES TO SAVE A SINGLE WORD.

## 39. CROSS-SYSTEM RULE: RESIDENT/COLD CODE BOUNDARY

TENEX'S RESIDENT/SWAPPABLE MONITOR SPLIT IS A USEFUL FUTURE MODEL EVEN THOUGH
THE PDP-6 CANNOT PAGE MONITOR CODE.

IF DAIMOS LATER IMPLEMENTS KERNEL OVERLAYS, KEEP PERMANENT:

- PI-SAFE ENTRY/COMPLETION;
- SCHEDULER/LOCK/RESOURCE TESTS;
- TINY TRAMPOLINES;
- STATE REQUIRED WHILE THE COLD BODY IS ABSENT.

MOVE ONLY WHOLE COLD OPERATIONS SUCH AS:

- RARE ADMINISTRATION;
- LARGE REPORTING/FORMATTING;
- INFREQUENT VALIDATION;
- COLD CONTROL FUNCTIONS.

DO NOT SPLIT HOT DEVICE OR SCHEDULER LOOPS INTO OVERLAYS.

THE OVERLAY WORK REMAINS POST-MEASUREMENT AND POST-0.9 AS ALREADY PLANNED.

## 40. CROSS-SYSTEM RULE: SHARED BUFFER POOLS ONLY WHEN THEY REPLACE MORE RAM

JOSS SHARES BUFFER STORAGE ACROSS MULTIPLE DEVICES. ITS HAS A CENTRAL DYNAMIC
I/O BUFFER POOL. TS 1.4 USES USER-OWNED RINGS. EACH IS A DIFFERENT RESPONSE TO
THE SAME PROBLEM: DO NOT RESERVE MAXIMUM BUFFERING FOR EVERY DEVICE/USER.

DAIMOS ALREADY DOES BETTER FOR MANY DEVICES BY USING:

- CALLER-OWNED BUFFERS;
- CLEAN RECLAIMABLE BCACHE;
- SHARED FILESYSTEM WORKSPACE;
- NO DATA BUFFER AT ALL FOR SIMPLE POLLED DEVICES.

THE FUTURE RULE IS:

> IF MULTIPLE ASYNCHRONOUS DEVICES REALLY REQUIRE KERNEL-OWNED QUEUED
> BUFFERS, COMPARE ONE BOUNDED SHARED POOL AGAINST PER-DEVICE POOLS.

DO NOT ADD A COMMON BUFFER POOL MERELY BECAUSE HISTORICAL SYSTEMS HAD ONE.

## 41. CROSS-SYSTEM RULE: SIMPLE SPECIALIZED DEVICE PATHS BEAT LARGE GENERIC OBJECT LAYERS

FUZIX DEVICE SWITCHES, TS DDBS, ITS DEVICE TABLES, AND TENEX DEVICE TABLES
WERE APPROPRIATE TO THEIR ABIS. THEY DO NOT IMPLY THAT DAIMOS NEEDS A LARGE
GENERAL DEVICE OBJECT.

DAIMOS SHOULD KEEP:

- OPTIONAL MRES PACKAGES;
- SMALL OPERATION-SPECIFIC VECTORS;
- PATCHED DIRECT ENTRIES;
- DEVICE-SPECIFIC MECHANICAL SCHEDULERS;
- COMMON HELPERS ONLY WHERE SEMANTICS ARE TRULY COMMON.

DO NOT UNIFY:

- DSK, DRM, AND TAPE MECHANICAL SCHEDULERS;
- FILESYSTEM DIRECTORY SCANNERS WITH DIFFERENT ON-MEDIA SEMANTICS;
- DISTINCT ALLOCATION MAPS MERELY BECAUSE THEY ALL USE BITS;
- EVERY BUSY/LOCK STATE INTO A GENERIC MUTEX LAYER.

GENERALIZATION MUST PRODUCE A MEASURED SIZE/SPEED WIN, NOT MERELY CLEANER
SOURCE.

## 42. CROSS-SYSTEM RULE: FINAL SIZE AUTHORITY IS THE LINKED IMAGE

TENEX POST-LOAD COMPACTION AND THE DAIMOS SIZE WORK BOTH REINFORCE THIS:

> SOURCE SIZE AND OBJECT SIZE ARE NOT THE PERMANENT-RAM RESULT.

AFTER SOURCE-LEVEL SHRINKING AND P10FOLD/P10SUPER:

- INSPECT THE FINAL KCORE/MRES MAP;
- FIND UNREFERENCED DATA WHICH SURVIVED LINKING;
- FIND DUPLICATED IMMUTABLE METADATA;
- FIND OPTIONAL TABLE HOLES;
- FIND DUPLICATED LITERALS/POINT WORDS;
- VERIFY THAT FUTURE/DEVELOPMENT METADATA IS NOT LINKED;
- MEASURE THE ACTUAL PERMANENT LAST ADDRESS.

KEEP 'SIZEOPT.MD' AS THE LIVE WORKLIST. KEEP THESE HISTORICAL DESIGN RULES
HERE SO THE WORKLIST CAN BE PRUNED WITHOUT LOSING THE REASONING.

## 43. WORKSTATION ACCEPTANCE PROFILE

THE TS 1.4 COMPARISON ADDS I/O-UTILIZATION MEASUREMENTS TO THE JOSS/ITS
WORKSTATION TESTS.

TEST AT LEAST:

    SESSION 1     DSH/EDITOR, HUMAN-LIKE BLOCK/WAKE
    SESSION 2     SECOND INTERACTIVE OR MOSTLY-IDLE LOGIN
    BACKGROUND    CPU-BOUND BUILD/TEST LOOP
    STORAGE       DECTAPE OR OTHER SLOW I/O
    MEMORY        ONE RUN WITH ENOUGH PRESSURE TO EXERCISE RECLAIM/SWAP

MEASURE:

- LONG-BLOCK WAKEUP -> FIRST USER INSTRUCTION;
- INPUT EVENT -> FOREGROUND PROCESS RUNNABLE;
- CTRL-C -> INTERRUPT/STOP EFFECT;
- CTRL-Z -> STOP -> SHELL REGAINS TTY -> PROMPT;
- DEVICE COMPLETION -> NEXT USEFUL DEVICE COMMAND;
- CPU CONTEXT SWITCHES PER SECOND;
- SCHEDULER KICKS CAUSED BY SHORT I/O;
- BACKGROUND CPU PROGRESS;
- RECLAIM BEFORE PROCESS SWAP;
- PROCESS SWAP-IN -> FIRST USER INSTRUCTION;
- TERMINAL OUTPUT ABORT -> USABLE PROMPT.

THE ACCEPTANCE GOAL IS NOT TO MAXIMIZE A SINGLE BENCHMARK. IT IS TO KEEP THE
MACHINE RESPONSIVE WHILE USEFUL BACKGROUND WORK AND SLOW DEVICE I/O CONTINUE
TO MAKE PROGRESS.

## 44. IMPLEMENTATION ORDER

THIS DOCUMENT DOES NOT OVERRIDE THE CURRENT PERMANENT-SIZE/CORRECTNESS GATE.

AFTER THAT GATE:

1. ADD THE JOSS/ITS/TS WORKSTATION LATENCY TESTS BEFORE CHANGING SCHEDULER
   POLICY.
2. MEASURE LONG-BLOCK WAKEUP DELAY WITH A COMPETING CPU-BOUND PROCESS.
3. IF THE NORMAL QUANTUM IS VISIBLE, TEST THE MINIMAL LONG-BLOCK SOFTWARE-PI6
   RESCHEDULE RULE USING EXISTING PACKED SCHEDULER STATE.
4. MEASURE DEVICE-COMPLETION -> NEXT-OPERATION LATENCY ON DECTAPE.
5. KEEP TWO-BUFFERING AS THE DEFAULT FIRST EXPERIMENT FOR DEVICES WHICH CAN
   OVERLAP TRANSFER AND CONSUMPTION/PRODUCTION.
6. COMPLETE DSH JOB CONTROL USING EXISTING PGRP/SESSION/EVENT/TTY PRIMITIVES.
7. ADD READ-ONLY TS-1.4 DTFS PERSONALITY 030 THROUGH DTC/BCACHE/VFS WHEN THAT
   POST-0.9 ITEM IS REACHED.
8. CONTINUE SIZE WORK THROUGH THE LIVE 'SIZEOPT.MD'; USE SECTIONS 27-42 HERE
   AS DESIGN RULES, NOT AS AN AUTOMATIC TODO LIST.
9. REVISIT RESTARTABLE BLOCKING OR KERNEL OVERLAYS ONLY AFTER CHEAPER
   MEASURED RAM/TEXT SAVINGS ARE EXHAUSTED.

## 45. ACCEPTANCE CRITERIA

THE TS-DERIVED WORK IS SUCCESSFUL IF:

- HUMAN-INTERACTIVE WAKEUPS CAN RECEIVE PROMPT CPU SERVICE WITHOUT REQUIRING
  AN ARTIFICIALLY TINY COMPUTE QUANTUM;
- SHORT HIGH-RATE I/O DOES NOT CAUSE A RESCHEDULE STORM;
- CPU-BOUND BACKGROUND WORK STILL MAKES FAIR PROGRESS;
- SLOW SERIAL DEVICES DO NOT SIT IDLE FOR A LARGE FRACTION OF A QUANTUM AFTER
  THEIR WAITER CAN PROCEED;
- NORMAL DEVICE PIPELINING USES THE SMALLEST BUFFER COUNT WHICH ACHIEVES THE
  REQUIRED OVERLAP;
- LARGE BULK BUFFERS DO NOT BECOME UNCONDITIONAL PERMANENT KERNEL RAM;
- PI/CLOCK PATHS REMAIN SHORT;
- TTY INTERRUPT/JOB-CONTROL PATHS REMAIN PROMPT;
- TS-1.4 DECTAPE COMPATIBILITY DOES NOT IMPORT THE HISTORICAL EXECUTIVE I/O
  ABI INTO VFS;
- BOOT/MOUNT-ONLY STATE IS RECLAIMED OR REPURPOSED;
- THE THREE-WORD PROCESS DESCRIPTOR DOES NOT GROW FOR CONVENIENCE;
- THE FULL PERMANENT IMAGE REMAINS BELOW THE PROJECT HARD LIMIT;
- THE 32K PDP-6 BUILD STILL REACHES NORMAL LOGIN/DSH.

## 46. DESIGN SUMMARY

TS 1.4 SHOWS THAT A VERY SMALL GENERAL TIMESHARING EXECUTIVE CAN REMAIN
RESPONSIVE WITHOUT MAKING EVERY CPU QUANTUM TINY. IT DOES THIS BY ALLOWING
IMPORTANT I/O READINESS TO AFFECT CPU SELECTION EARLY, BY SLEEPING ON SCARCE
HARDWARE, BY OVERLAPPING DEVICE WORK WITH SMALL BUFFER RINGS, AND BY KEEPING
THE PERMANENT MONITOR AGGRESSIVELY SPECIALIZED.

DAIMOS SHOULD IMPLEMENT THE SAME GOALS USING ITS OWN MORE GENERAL MECHANISMS:

    EVENT-DRIVEN WAKEUPS
    + SOFTWARE PI6 RESCHEDULE
    + NICE/RECENT-CPU FAIRNESS
    + BOUNDED TWO-BUFFER-FIRST I/O
    + CALLER/DYNAMIC BULK STORAGE
    + KINIT/MINIT SPECIALIZATION
    + SMALL MRES PACKAGES
    + RECLAIM/COMPACTION/SWAP

THE BROADER HISTORICAL SIZE COMPARISON ADDS ONE CONSISTENT MESSAGE:

> STORE ONLY WHAT MUST BE LIVE, SHARE ONLY WHAT IS TRULY COMMON, SPECIALIZE
> WHAT BECOMES CONSTANT, AND LET THE FINAL LINKED PDP-6 IMAGE -- NOT SOURCE
> AESTHETICS -- DECIDE WHETHER AN ABSTRACTION IS WORTH ITS COST.
