# SESSION-SHARED USER TEXT ON PDP-6

STATUS: DESIGN NOTE, NOT IMPLEMENTED
DATE: 2026-07-08

THIS NOTE RECORDS A PDP-6 MEMORY-SAVING DESIGN FOR DAIMOS V0.5/V1: SHARE
PURE USER-MODE TEXT BETWEEN PROCESSES THAT BELONG TO THE SAME LOGIN SESSION,
WHILE KEEPING THE KERNEL AND OTHER SESSIONS PROTECTED BY THE PDP-6
RELOCATION/PROTECTION HARDWARE.

THE DESIGN IS INTENTIONALLY NOT A MODERN SHARED-LIBRARY DESIGN.  PDP-6 HAS NO
PAGE TABLE, NO READ-ONLY USER TEXT PAGES, NO PER-PAGE PERMISSIONS, AND NO
COPY-ON-WRITE.  SHARING IS THEREFORE A MEMORY-SAVING MECHANISM INSIDE ONE
TRUSTED SESSION, NOT A SECURITY BOUNDARY BETWEEN SAME-SESSION PROCESSES.

## 1. GOAL

INTERACTIVE USE MAY HAVE FEW CONCURRENT LOGINS, BUT EACH LOGIN CAN RUN SEVERAL
RELATED PROCESSES:

'''TEXT
LOGIN SESSION
    TMUX-LITE
    SHELL
    SHELL
    EDITOR
    EDITOR
    SMALL COMMANDS
'''

STATIC LINKING EVERY IMAGE GIVES THE BEST ISOLATION, BUT REPEATS THE SAME
LIBRARY AND COMMAND TEXT MANY TIMES.  A SESSION ARENA ALLOWS THOSE PROCESSES TO
SHARE ONE COPY OF SELECTED PURE TEXT OBJECTS:

'''TEXT
PHYSICAL MEMORY

+--------------------------+
! KERNEL / EXECUTIVE       !
+--------------------------+
! SESSION ARENA A          !
!   SHARED LIBC TEXT       !
!   SHARED SHELL TEXT      !
!   SHARED EDITOR TEXT     !
!   PROCESS 1 DATA/STACK   !
!   PROCESS 2 DATA/STACK   !
!   PROCESS 3 DATA/STACK   !
+--------------------------+
! SESSION ARENA B          !
+--------------------------+
'''

THE HARDWARE BOUNDARY IS STILL ONLY AROUND THE WHOLE ARENA:

'''TEXT
KERNEL PROTECTED FROM USER:         YES
OTHER SESSIONS/USERS PROTECTED:     YES
SAME-SESSION PROCESSES SEPARATED:   NO
SHARED TEXT READ-ONLY IN HARDWARE:  NO
'''

## 2. BASIC MODEL

A LOGIN CREATES A SESSION ARENA.  CHILD PROCESSES IN THAT LOGIN SESSION INHERIT
THAT ARENA.  THE SCHEDULER LOADS THE SAME RELOCATION/PROTECTION REGISTERS FOR
ALL PROCESSES IN THE ARENA, AND PROCESS SWITCHING INSIDE THE ARENA CHANGES ONLY
CPU/PROCESS STATE, NOT THE MEMORY PROTECTION BOUNDARY.

EACH PROCESS STILL HAS PRIVATE STATE:

'''TEXT
PROCESS SLOT
    REGISTERS
    STACK
    BSS
    DATA
    HEAP
    FILE TABLE OR FILE TABLE POINTER
    CURRENT DIRECTORY
    EVENT/PLEDGE STATE
    ERRNO
    STDIO STATE
    ALLOCATOR STATE
'''

SHARED OBJECTS ARE TEXT-ONLY BY CONVENTION:

'''TEXT
SHARED TEXT OBJECT
    INSTRUCTIONS
    CONSTANTS
    JUMP TABLES
    SYSCALL STUBS
    REENTRANT LIBRARY CODE
'''

FORBIDDEN IN SHARED TEXT:

'''TEXT
WRITABLE GLOBALS
STATIC BUFFERS
ALLOCATOR STATE
STDIO STATE
CURRENT FILE STATE
TERMINAL STATE
SELF-MODIFYING CODE
'''

BECAUSE THE HARDWARE CANNOT ENFORCE READ-ONLY TEXT, THIS RULE IS ENFORCED BY
FORMAT, LOADER POLICY, CHECKSUMS, TESTS, AND CONVENTION.  IT IS NOT A HARD
SECURITY PROPERTY AGAINST MALICIOUS OR BADLY CORRUPTED SAME-SESSION CODE.

## 3. SECURITY PROPERTY

THE INTENDED SECURITY PROPERTY IS:

'''TEXT
A PROCESS CAN DAMAGE ITSELF AND POSSIBLY OTHER PROCESSES IN ITS OWN LOGIN
SESSION, BUT CANNOT DIRECTLY OVERWRITE THE KERNEL OR ANOTHER SESSION'S ARENA.
'''

THIS IS SIMILAR TO TREATING A LOGIN SESSION AS THE UNIT OF MEMORY ISOLATION.
THAT IS ACCEPTABLE ONLY IF IT IS DOCUMENTED AS A DESIGN TRADEOFF.

THE DESIGN SHOULD BE COMBINED WITH A CHEAP PLEDGE-LIKE SYSCALL MASK:

'''TEXT
MEMORY PROTECTION CONTAINS WRITES
PLEDGE CONTAINS AUTHORITY
'''

A CORRUPTED SAME-SESSION PROCESS MAY CORRUPT SHARED TEXT OR ANOTHER STACK, BUT
ITS SYSTEM CALLS CAN STILL BE LIMITED SO IT CANNOT MOUNT DEVICES, OPEN ARBITRARY
FILES, WRITE CONFIGDB, OR EXEC NEW TOOLS AFTER IT HAS DROPPED THOSE RIGHTS.

## 4. LOADER MODEL

THE LOADER MAINTAINS A SESSION-LOCAL TEXT-OBJECT TABLE:

'''TEXT
TEXT OBJECT
    NAME
    ABI VERSION
    MACHINE MINIMUM
    BASE WORD
    LENGTH WORDS
    ENTRY TABLE OFFSET
    RELOCATION/CHECKSUM STATE
    REFERENCE COUNT
    FLAGS
'''

USEFUL FLAGS:

'''TEXT
PURE_TEXT       NO WRITABLE STATE IN TEXT OBJECT
REENTRANT       ALL PER-PROCESS STATE IS EXTERNAL
SESSION_SHARED  MAY BE LOADED INTO THE SESSION TEXT POOL
OVERLAY_OK      MAY BE USED AS AN OVERLAY OBJECT
PINNED          DO NOT DISCARD WHILE ANY PROCESS MAY CALL IT
'''

AT EXEC TIME:

'''TEXT
1. VALIDATE THE EXECUTABLE HEADER
2. ALLOCATE PRIVATE PROCESS DATA/STACK/HEAP INSIDE THE SESSION ARENA
3. RESOLVE REQUIRED SHARED TEXT OBJECTS FROM THE SESSION TABLE
4. LOAD MISSING SHARED TEXT OBJECTS ONCE INTO THE SESSION TEXT POOL
5. BOUNDS-CHECK ENTRY POINTS AND RELOCATIONS
6. START THE PROCESS WITH A PROCESS-PRIVATE STATE POINTER
'''

PROGRAMS MUST NOT CALL ARBITRARY ADDRESSES IN THE TEXT POOL.  THEY CALL LOADER
EXPORTED ENTRY POINTS OR NORMAL LINKED ENTRY STUBS.

## 5. ABI CONSEQUENCE

SHARED CODE NEEDS A RELIABLE WAY TO FIND PER-PROCESS STATE.  POSSIBLE CHOICES:

'''TEXT
RESERVED AC HOLDS PROCESS POINTER
FIXED WORD IN THE PROCESS SLOT HOLDS SELF POINTER
KERNEL SUPPLIES CURRENT PROCESS POINTER ON SYSCALL RETURN
'''

THE PREFERRED ABI SHOULD BE SMALL AND FAST.  IF RESERVING ONE AC IS TOO COSTLY,
USE A FIXED PROCESS-SLOT BASE KNOWN TO THE LOADER AND SHARED-LIBRARY STUBS.

ALL SHARED CODE MUST ACCESS MUTABLE STATE THROUGH THE PROCESS POINTER:

'''TEXT
ERRNO           -> PROC + P_ERRNO
STDIO TABLE     -> PROC + P_STDIO
MALLOC STATE    -> PROC + P_MALLOC
TERMINAL STATE  -> PROC + P_TTY
'''

THIS IS THE MAIN SOURCE-LEVEL DISCIPLINE NEEDED TO MAKE SESSION-SHARED TEXT
WORK.

## 6. FRAGMENTATION CONSEQUENCES

SESSION ARENAS CREATE A DIFFERENT FRAGMENTATION PROBLEM FROM ORDINARY
PER-PROCESS ALLOCATION.

THE DANGEROUS MIX IS:

'''TEXT
LONG-LIVED SHARED TEXT
SHORT-LIVED PROCESS DATA AND STACKS
MEDIUM-LIVED OVERLAYS
VARIABLE-SIZED HEAPS
'''

IF ALL OF THESE ARE PLACED IN ONE GENERAL FREE LIST, HOLES ACCUMULATE QUICKLY:

'''TEXT
ARENA START
+------------------+
! SHARED LIBC TEXT ! LONG-LIVED
+------------------+
! PROCESS A DATA   ! SHORT-LIVED
+------------------+
! OVERLAY X        ! MEDIUM-LIVED
+------------------+
! PROCESS B STACK  ! SHORT-LIVED
+------------------+
! FREE HOLE        !
+------------------+
! SHARED VI TEXT   ! LONG-LIVED
+------------------+
! FREE HOLE        !
+------------------+
ARENA END
'''

CONSEQUENCES:

'''TEXT
FREE MEMORY MAY EXIST BUT NOT AS ONE USABLE RUN
LARGE EXEC OR OVERLAY LOADS CAN FAIL EARLY
SESSION LIFETIME MAKES TEXT-POOL HOLES PERSIST
LONG INTERACTIVE SESSIONS GET WORSE OVER TIME
TMUX-LITE INCREASES THE PRESSURE BY KEEPING MANY PROCESS SLOTS ALIVE
'''

THE FIX IS TO AVOID ONE MIXED ALLOCATOR.  SPLIT THE ARENA INTO REGIONS WITH
SEPARATE ALLOCATION POLICIES:

'''TEXT
+--------------------------+
! SESSION CONTROL BLOCK    !
+--------------------------+
! SHARED TEXT POOL         ! GROWS UPWARD, LONG-LIVED
+--------------------------+
! OVERLAY CACHE POOL       ! DISCARDABLE, MOVABLE BY RELOAD
+--------------------------+
! PROCESS SLOTS/DATA       ! FIXED OR SIZE-CLASSED
+--------------------------+
! STACKS                   ! FIXED-SIZE OR BOUNDED SLOTS
+--------------------------+
! HEAP/SCRATCH POOL        ! SHORT-LIVED
+--------------------------+
'''

RECOMMENDED V0.5/V1 POLICY:

'''TEXT
SHARED TEXT POOL:
    APPEND-ONLY WITHIN A SESSION
    REFCOUNTED
    NOT COMPACTED WHILE PROCESSES RUN
    FREED ONLY WHEN REFCOUNT REACHES ZERO OR SESSION ENDS

OVERLAY POOL:
    DISCARDABLE CACHE
    CAN BE EVICTED AND RELOADED FROM DISK
    NEVER CONTAINS THE ONLY COPY OF PERSISTENT STATE

PROCESS STATE:
    USE FIXED-SIZE OR SMALL SIZE-CLASS SLOTS WHERE POSSIBLE
    AVOID ARBITRARY PER-PROCESS ALLOCATIONS IN THE SHARED TEXT POOL

STACKS:
    FIXED OR A FEW FIXED CLASSES
    NO AUTOMATIC GROWTH AT FIRST

LARGE TEMPORARY BUFFERS:
    ALLOCATE FROM A SCRATCH REGION
    RELEASE AT SYSCALL/TOOL PHASE BOUNDARIES
'''

THIS SACRIFICES SOME THEORETICAL MEMORY EFFICIENCY TO PREVENT FATAL EXTERNAL
FRAGMENTATION.

### FRAGMENTATION FAILURE MODES

FAILURE MODES SHOULD BE EXPLICIT:

'''TEXT
TEXT_NOMEM       NO ROOM FOR A REQUIRED SHARED TEXT OBJECT
PROC_NOMEM       NO ROOM FOR PROCESS PRIVATE STATE
STACK_NOMEM      NO ROOM FOR REQUESTED STACK CLASS
OVL_NOMEM        OVERLAY CACHE CANNOT FIT OBJECT AFTER EVICTION
ARENA_FULL       NO REGION CAN SATISFY THE SESSION REQUEST
'''

ON 'OVL_NOMEM', THE LOADER MAY EVICT OTHER OVERLAYS AND RETRY.  ON
'TEXT_NOMEM', THE SESSION MAY NEED TO START THE PROCESS WITH PRIVATE TEXT, DENY
THE EXEC, OR ASK THE USER TO CLOSE PROCESSES.  THAT POLICY IS STILL OPEN.

## 7. WILL OVERLAYS HELP MORE?

YES.  OVERLAYS HELP IN A DIFFERENT WAY AND SHOULD PROBABLY BE IMPLEMENTED
BEFORE FULL SESSION-SHARED LIBRARIES.

SESSION-SHARED TEXT SAVES MEMORY ACROSS SEVERAL PROCESSES:

'''TEXT
THREE EDITORS SHARE ONE EDITOR COMMAND-TEXT OBJECT
'''

OVERLAYS SAVE MEMORY INSIDE ONE LARGE PROGRAM BY LOADING ONLY THE CURRENTLY
NEEDED PHASE:

'''TEXT
RESIDENT EDITOR CORE
    OVERLAY: SEARCH
    OVERLAY: SUBSTITUTE
    OVERLAY: FILE WRITE
    OVERLAY: HELP
'''

THE TWO MECHANISMS COMBINE WELL:

'''TEXT
SESSION ARENA
    SHARED RESIDENT EDITOR CORE
    SHARED LIBC TEXT
    OVERLAY CACHE
        EDITOR OVERLAY: SUBSTITUTE
        SHELL OVERLAY: PARSER EXTENSION
    PROCESS-PRIVATE EDITOR BUFFERS
'''

GOOD OVERLAY CANDIDATES:

'''TEXT
VI HELP AND RARELY USED COMMANDS
REGEX ENGINE, IF LARGE
CONFIG VALIDATION PASSES
COMPILER PHASES
LINKER/ARCHIVE OPERATIONS
FILESYSTEM REPAIR TOOLS
TERMINAL DESCRIPTION EXPANSION
'''

BAD OVERLAY CANDIDATES:

'''TEXT
HOT SYSCALL STUBS
BASIC RECORD I/O
SCHEDULER-FACING RUNTIME GLUE
INNER EDITOR CURSOR MOTION
SMALL STRING ROUTINES
'''

OVERLAYS REDUCE RESIDENT PRESSURE, BUT ADD LATENCY AND COMPLEXITY:

'''TEXT
OVERLAY LOOKUP ON CALL PATH
DISK READS WHEN EVICTED
ENTRY-POINT VALIDATION
STATE HANDOFF DISCIPLINE
MORE LOADER CODE
MORE FAILURE CASES
'''

THE SAFE DESIGN RULE IS:

'''TEXT
AN OVERLAY MAY CONTAIN CODE AND CONSTANTS.  PERSISTENT MUTABLE STATE BELONGS IN
PROCESS-PRIVATE DATA OR AN EXPLICIT SESSION SERVICE OBJECT, NOT IN THE OVERLAY.
'''

## 8. DOES SWAPPING HELP WITH OVERLAYS?

YES, BUT SWAPPING AND OVERLAYS SOLVE DIFFERENT PROBLEMS.

OVERLAYS REDUCE HOW MUCH OF A PROGRAM MUST BE MEMORY-RESIDENT AT ONE TIME.
SWAPPING REMOVES WHOLE INACTIVE PROCESSES OR INACTIVE SESSION REGIONS FROM CORE.
TOGETHER THEY HELP MORE THAN EITHER ALONE:

'''TEXT
WITHOUT OVERLAYS:
    SWAP HAS TO WRITE/READ LARGE COMPLETE PROCESS IMAGES

WITH OVERLAYS:
    INACTIVE CODE CAN SIMPLY BE DISCARDED
    ONLY PRIVATE DATA, STACKS, AND DIRTY STATE NEED SWAPPING
'''

BEST POLICY:

'''TEXT
SHARED TEXT:
    CLEAN COPY EXISTS ON DISK
    DO NOT SWAP IF RELOADABLE
    DISCARD AND RELOAD INSTEAD

OVERLAYS:
    CLEAN COPY EXISTS ON DISK
    NEVER SWAP CLEAN OVERLAYS
    EVICT AND RELOAD

PROCESS DATA/STACK/HEAP:
    DIRTY AND PRIVATE
    SWAP WHEN PROCESS SLEEPS OR SESSION PRESSURE IS HIGH

SESSION CONTROL TABLES:
    SMALL
    KEEP RESIDENT IF POSSIBLE
'''

THIS MEANS SWAPPING HELPS MOST WHEN IT IS DATA-FOCUSED:

'''TEXT
SWAP OUT INACTIVE PROCESS PRIVATE STATE
KEEP OR RELOAD SHARED TEXT FROM FILESYSTEM
THROW AWAY CLEAN OVERLAYS INSTEAD OF WRITING THEM TO SWAP
'''

FOR TMUX-LITE, AN IDLE SHELL/EDITOR PANE IS A GOOD SWAP CANDIDATE:

'''TEXT
ACTIVE PANE:
    RESIDENT PROCESS STATE
    NEEDED TEXT/OVERLAY OBJECTS

IDLE PANE:
    PRIVATE DATA/STACK SWAPPED
    CLEAN OVERLAYS DISCARDED
    SHARED TEXT KEPT ONLY IF STILL REFERENCED BY ACTIVE PANES
'''

THIS KEEPS SWAP I/O SMALLER AND REDUCES ARENA FRAGMENTATION, BECAUSE DISCARDABLE
OVERLAY SPACE CAN BE RECLAIMED WITHOUT PRESERVING CONTENTS.

## 9. RECOMMENDED IMPLEMENTATION ORDER

'''TEXT
1. KEEP STATIC LINKING AS THE DEFAULT BASELINE.
2. ADD EXECUTABLE FLAGS FOR PURE/REENTRANT/SESSION-SHAREABLE TEXT.
3. ADD PROCESS-PRIVATE STATE DISCIPLINE TO LIBC/RUNTIME CODE.
4. ADD A SIMPLE SESSION ARENA WITH REGION ALLOCATORS.
5. ADD SESSION-SHARED SYSCALL STUBS AND SMALL LIBC TEXT FIRST.
6. ADD OVERLAYS FOR LARGE TOOLS BEFORE BROAD SHARED LIBRARIES.
7. ADD DISCARDABLE OVERLAY CACHE.
8. ADD DATA-FOCUSED SWAPPING FOR IDLE PROCESSES.
9. ADD OPTIONAL SESSION-SHARED EDITOR/SHELL TEXT AFTER TESTS PROVE REENTRANCY.
'''

DO NOT START BY SHARING COMPLICATED CODE.  START WITH THE CODE LEAST LIKELY TO
KEEP HIDDEN MUTABLE STATE.

## 10. REQUIRED DESIGN DECISIONS

THESE DECISIONS MUST BE SETTLED BEFORE IMPLEMENTATION.

### ISOLATION UNIT

'''TEXT
A. SHARE BY UID
B. SHARE BY LOGIN SESSION
C. SHARE BY EXPLICIT PROCESS GROUP
D. NO SHARING IN V0.5
'''

RECOMMENDED: B.  IT SAVES MEMORY FOR TMUX-LITE AND MULTIPLE SHELLS/EDITORS WHILE
NOT COUPLING UNRELATED LOGINS OR BATCH JOBS UNDER THE SAME UID.

### SAME-SESSION TRUST MODEL

'''TEXT
A. SAME-SESSION PROCESSES ARE MUTUALLY TRUSTED
B. ONLY SAME EXECUTABLE FAMILY MAY SHARE TEXT
C. ONLY SIGNED/BASE-SYSTEM IMAGES MAY SHARE TEXT
D. SHARING IS DISABLED FOR SETUID/PRIVILEGED IMAGES
'''

RECOMMENDED: A PLUS D FOR V0.5/V1; CONSIDER C LATER.

### ARENA LAYOUT

'''TEXT
A. ONE GENERAL FREE LIST
B. SPLIT REGIONS FOR TEXT, OVERLAYS, PROCESS SLOTS, STACKS, SCRATCH
C. FIXED ARENA TEMPLATE PER SESSION CLASS
'''

RECOMMENDED: B.  A IS TOO FRAGILE UNDER LONG SESSIONS.

### SHARED TEXT LIFETIME

'''TEXT
A. APPEND-ONLY UNTIL LOGOUT
B. REFCOUNT AND FREE ON LAST CLOSE
C. DISCARD LRU TEXT OBJECTS UNDER PRESSURE
D. COMPACT TEXT POOL WHILE SESSION RUNS
'''

RECOMMENDED: B FOR NORMAL TEXT, C ONLY FOR EXPLICITLY RELOADABLE OVERLAYS, NOT
D IN V0.5/V1.

### FRAGMENTATION POLICY

'''TEXT
A. FAIL EXEC WHEN REGION CANNOT FIT
B. FALL BACK TO PRIVATE TEXT
C. EVICT OVERLAYS AND RETRY
D. COMPACT OR REBUILD SESSION ARENA
'''

RECOMMENDED: C FOR OVERLAYS, A OR B FOR TEXT.  D IS TOO COMPLEX INITIALLY.

### TEXT PURITY CONTRACT

'''TEXT
A. DOCUMENTED CONVENTION ONLY
B. LOADER CHECKS SECTION LAYOUT AND REJECTS WRITABLE STATE IN SHARED TEXT
C. ASSEMBLER/COMPILER EMITS PURITY METADATA
D. HOST-SIDE VERIFIER REQUIRED FOR BASE-SYSTEM SHARED IMAGES
'''

RECOMMENDED: B INITIALLY, D FOR RELEASE IMAGES, C LATER.

### PER-PROCESS STATE POINTER ABI

'''TEXT
A. RESERVE ONE AC
B. FIXED PROCESS-SLOT ADDRESS
C. PASS STATE POINTER TO EVERY SHARED ENTRY POINT
D. USE KERNEL-PROVIDED CURRENT PROCESS WORD
'''

RECOMMENDED: DECIDE AFTER MEASURING CODE COST.  A IS FAST BUT CONSUMES AN AC;
B IS SIMPLER FOR EARLY CODE.

### OVERLAY SCOPE

'''TEXT
A. PRIVATE PER PROCESS
B. SHARED WITHIN SESSION
C. GLOBAL KERNEL-MANAGED CLEAN CACHE
D. NO OVERLAYS UNTIL AFTER SWAPPING
'''

RECOMMENDED: A FIRST, THEN B.  AVOID C ON PDP-6 UNTIL THE LOADER AND CACHE ARE
PROVEN SMALL.

### OVERLAY STATE RULE

'''TEXT
A. OVERLAYS MAY OWN MUTABLE STATE
B. OVERLAYS MAY ONLY USE PROCESS-PRIVATE STATE
C. OVERLAYS MAY USE SESSION SERVICE STATE
'''

RECOMMENDED: B FOR V0.5/V1.

### SWAPPING UNIT

'''TEXT
A. SWAP WHOLE PROCESS IMAGE INCLUDING TEXT
B. SWAP ONLY PRIVATE DATA/STACK/HEAP
C. SWAP WHOLE SESSION ARENA
D. SWAP PER-REGION
'''

RECOMMENDED: B FIRST.  CLEAN SHARED TEXT AND OVERLAYS SHOULD BE RELOADED, NOT
WRITTEN TO SWAP.

### PLEDGE INTERACTION

'''TEXT
A. NO PLEDGE INTERACTION
B. PLEDGE MASK IS PER PROCESS
C. PLEDGE MASK IS PER SESSION
D. SHARED TEXT MAY REQUEST PRIVILEGES
'''

RECOMMENDED: B.  SHARED TEXT NEVER GRANTS AUTHORITY.

### SETUID AND PRIVILEGED PROGRAMS

'''TEXT
A. NEVER USE SESSION-SHARED TEXT
B. MAY SHARE ONLY ROOT-OWNED VERIFIED TEXT
C. GET A PRIVATE ARENA
D. UNSUPPORTED IN V0.5
'''

RECOMMENDED: A OR C.  NEVER LET AN UNPRIVILEGED SESSION TEXT OBJECT RUN INSIDE A
PRIVILEGED IMAGE.

## 12. SUMMARY

SESSION-SHARED USER TEXT IS A GOOD PDP-6 COMPROMISE:

'''TEXT
WHAT IT SAVES:
    REPEATED LIBC/SHELL/EDITOR TEXT INSIDE ONE INTERACTIVE LOGIN

WHAT IT PROTECTS:
    KERNEL AND OTHER SESSIONS FROM USER WRITES

WHAT IT DOES NOT PROTECT:
    PROCESSES WITHIN THE SAME SESSION FROM EACH OTHER
'''

OVERLAYS SHOULD STILL BE USED.  THEY REDUCE THE LIVE CODE FOOTPRINT OF LARGE
PROGRAMS AND COMBINE WELL WITH DATA-FOCUSED SWAPPING.  THE MOST ROBUST PDP-6
PLAN IS THEREFORE:

'''TEXT
SESSION-SHARED PURE TEXT FOR COMMON RESIDENT CODE
OVERLAYS FOR LARGE RARELY USED CODE
DATA-FOCUSED SWAPPING FOR IDLE PROCESS STATE
PLEDGE-LIKE SYSCALL MASKS FOR AUTHORITY REDUCTION
'''

## 13. FEASIBILITY REVIEW AND HARDWARE INVARIANTS

THE DESIGN IS FEASIBLE, BUT ONLY IF THE PDP-6 PROTECTION DOMAIN AND THE
SHARED-TEXT ABI ARE EXPLICIT ARCHITECTURAL INVARIANTS.

### PDP-6 PROTECTION DOMAIN

THE PDP-6 RELOCATION/PROTECTION HARDWARE NATURALLY MAKES ONE CONTIGUOUS LOGIN
ARENA THE USER MEMORY PROTECTION UNIT.  PROCESSES INSIDE THAT ARENA ARE
MUTUALLY UNPROTECTED.  THE KERNEL AND OTHER ARENAS REMAIN OUTSIDE THE ALLOWED
USER RANGE.

'''TEXT
KERNEL                         STRONGLY ISOLATED
OTHER LOGIN SESSION            STRONGLY ISOLATED
SAME-SESSION PROCESS           MUTUALLY TRUSTED
'''

THE MACHINE BACKEND, NOT THE GENERIC MEMORY LAYER, DEFINES THE REQUIRED ARENA
ALIGNMENT, RELOCATION GRANULARITY, AND PROTECTION-LIMIT ROUNDING.

ALL PROCESSES SHARING ONE UNPROTECTED ARENA MUST BELONG TO THE SAME SECURITY
AND PRIVILEGE DOMAIN:

'''TEXT
ONE NO-MMU SHARED ARENA == ONE TRUST DOMAIN
'''

SETUID OR OTHERWISE PRIVILEGED EXECUTION MUST NOT REUSE AN ORDINARY
UNPRIVILEGED SESSION ARENA OR UNVERIFIED SESSION-SHARED TEXT.

### PRIVATE DATA IS AN ABI REQUIREMENT

SHARING TEXT DOES NOT BY ITSELF MAKE DATA/BSS PRIVATE.  AN ORDINARY ABSOLUTE
REFERENCE TO A WRITABLE SYMBOL RESOLVES TO THE SAME LOGICAL ADDRESS FOR EVERY
PROCESS USING THE SHARED TEXT.  PDP-6 RELOCATION MOVES THE WHOLE ARENA; IT DOES
NOT PROVIDE A DIFFERENT DATA MAPPING FOR EACH PROCESS.

THEREFORE FULL PROGRAM TEXT SHARING REQUIRES A REAL DAIMOS SHARED-TEXT ABI.
ALL MUTABLE STATE USED BY SHARED TEXT MUST BE REACHED THROUGH PROCESS-PRIVATE
STATE.

CANDIDATE MECHANISMS ARE:

'''TEXT
RESERVED AC HOLDS PROCESS/DATA POINTER
FIXED PROCESS-SLOT BASE
EXPLICIT STATE POINTER AT SHARED ENTRY POINTS
SCHEDULER-MAINTAINED CURRENT-PROCESS POINTER WORD
'''

THE CURRENT-PROCESS WORD IS WORTH MEASURING: A SINGLE-CPU PDP-6 HAS ONLY ONE
RUNNING USER PROCESS, SO THE SCHEDULER CAN CHANGE ONE KNOWN WORD AT CONTEXT
SWITCH WITHOUT PERMANENTLY CONSUMING AN AC.

THE FINAL ABI MUST BE CHOSEN FROM MEASURED GCC/KCC CODE SIZE, EXECUTION COST,
AC PRESSURE, HAND-WRITTEN ASSEMBLER COST, AND LOADER COMPLEXITY.

### SHAREABILITY CLASSES

PURE REENTRANT RUNTIME TEXT IS THE FIRST TARGET:

'''TEXT
SYSCALL VENEERS
MEMORY/STRING PRIMITIVES WITHOUT WRITABLE GLOBAL STATE
INTEGER/RECORD HELPERS
OTHER PURE LEAF RUNTIME ROUTINES
'''

WHOLE SHELLS, EDITORS, STDIO, ALLOCATORS, AND CODE WITH STATIC OR GLOBAL
WRITABLE STATE MUST WAIT UNTIL THE PRIVATE-STATE ABI IS IMPLEMENTED AND
VERIFIED.

## 14. GENERIC DAIMOS MEMORY MODEL

SESSION ARENAS ARE ONE NO-MMU REALIZATION OF A BROADER DAIMOS MEMORY MODEL.
THE GENERIC MODEL MUST ALSO SUPPORT KA-BBN, KA-ITS, KI, KS, KL, AND OTHER MMU
IMPLEMENTATIONS WITHOUT FORCING PDP-6 MECHANISMS ONTO THEM.

'''TEXT
KERNEL SUBSYSTEMS
        |
        V
MEMORY OBJECTS + ADDRESS SPACES
        |
        V
MACHINE VM BACKEND
        |
        +-- PDP-6 / NO-MMU
        +-- KA-BBN
        +-- KA-ITS
        +-- KI
        +-- KS
        +-- KL
'''

THE GENERIC LAYER DESCRIBES STORAGE IDENTITY, OWNERSHIP, SHARING, PROTECTION
INTENT, AND EXECUTABLE LAYOUT.  EACH MACHINE BACKEND REALIZES THOSE SEMANTICS
USING ITS OWN HARDWARE.

### MEMORY OBJECTS AND CENTRAL DESCRIPTOR TABLE

A MEMORY OBJECT IS THE STABLE KERNEL IDENTITY OF A COARSE BODY OF STORAGE.  ITS
IDENTITY DOES NOT DEPEND ON ITS CURRENT PHYSICAL PLACEMENT.

'''TEXT
MEMORY OBJECT
    HANDLE / OBJECT ID
    SIZE
    TYPE / TRAITS
    OWNER
    REFERENCE COUNT
    BACKEND STATE
'''

LIKELY COARSE OBJECTS INCLUDE EXECUTABLE TEXT, PRIVATE DATA, STACKS, OVERLAY
MEMBERS, LARGE BUFFERS, DISCARDABLE CACHES, AND NO-MMU SESSION ARENAS.

THE CENTRAL TABLE DESCRIBES MEMORY OBJECTS, NOT ARBITRARY C POINTERS:

'''TEXT
HANDLE -> DESCRIPTOR -> CURRENT BACKING / PLACEMENT
'''

IT THEREFORE LIMITS THE NUMBER OF SIMULTANEOUS MEMORY OBJECTS, NOT THE NUMBER
OF POINTERS IN USER PROGRAMS OR THE KERNEL.  SMALL KERNEL OBJECTS SHOULD USE
FIXED-SIZE POOLS RATHER THAN CONSUMING ONE CENTRAL DESCRIPTOR EACH.  IF HANDLE
SLOTS ARE RECYCLED, A GENERATION FIELD SHOULD BE CONSIDERED TO DETECT STALE
HANDLES.

### ADDRESS SPACES

STORAGE IDENTITY AND ADDRESS-SPACE PLACEMENT ARE SEPARATE:

'''TEXT
MEMORY OBJECT = STORAGE / CONTENT
ADDRESS SPACE = MAPPING / LAYOUT
'''

THIS IS MOSTLY BOOKKEEPING ON PDP-6 BUT FUNDAMENTAL ON MMU MACHINES.  ONE TEXT
OBJECT MAY BE MAPPED INTO SEVERAL MMU ADDRESS SPACES WITHOUT BECOMING SEVERAL
STORAGE OBJECTS.

THE GENERIC API SHOULD EXPRESS OPERATIONS SUCH AS ALLOCATE, FREE, RESIZE, PIN,
UNPIN, MAP, AND UNMAP WITHOUT EXPOSING A PARTICULAR MACHINE'S PAGE-TABLE
FORMAT.  PAGES MUST NOT BE THE UNIVERSAL GENERIC ALLOCATION UNIT; NO-MMU
MACHINES NATURALLY ALLOCATE EXTENTS WHILE MMU BACKENDS MAY PAGE OBJECTS
INTERNALLY.

### PINNING

MOVABLE STORAGE BECOMES TEMPORARILY NON-MOVABLE WHEN CODE OR HARDWARE REQUIRES
A STABLE ADDRESS:

'''TEXT
MEM_PIN(OBJECT)       OBTAIN A STABLE USABLE ADDRESS/MAPPING
MEM_UNPIN(OBJECT)     ALLOW RELOCATION/RECLAIM AGAIN
'''

ON NO-MMU MACHINES THIS PRIMARILY PREVENTS PHYSICAL RELOCATION.  ON MMU
MACHINES IT MAY ALSO PREVENT BACKING PAGES FROM BEING RECLAIMED OR REMAPPED.

## 15. NO-MMU EXTENT ALLOCATION AND COMPACTION

THE NO-MMU BACKEND SHOULD USE COALESCING PHYSICAL EXTENTS FOR LARGE OBJECTS,
FIXED-SIZE OR SIZE-CLASS POOLS FOR FREQUENT SMALL KERNEL OBJECTS, AND
MARK/RELEASE SCRATCH ARENAS FOR PHASE-LIFETIME TEMPORARIES.

RECLAMATION SHOULD NORMALLY BE PRESSURE DRIVEN:

'''TEXT
ALLOCATE
    TRY FREE EXTENT
    COALESCE ADJACENT FREE EXTENTS
    RECLAIM DISCARDABLE OBJECTS
    COMPACT MOVABLE OBJECTS
    RETRY
'''

A LOW-PRIORITY KERNEL MAINTENANCE PROCESS MAY COMPACT OPPORTUNISTICALLY, BUT
PERIODIC MOVEMENT IS POLICY, NOT AN ARCHITECTURAL REQUIREMENT.

### WHOLE-SESSION RELOCATION

A PDP-6 SESSION ARENA IS AN ESPECIALLY USEFUL TOP-LEVEL MOVABLE OBJECT.  IF
EVERY INTERNAL ADDRESS REMAINS AT THE SAME OFFSET FROM THE ARENA BASE, MOVING
THE COMPLETE ARENA DOES NOT REQUIRE REWRITING INTERNAL USER POINTERS.

'''TEXT
1. STOP ALL PROCESSES IN THE ARENA
2. VERIFY THAT THE ARENA IS NOT PINNED
3. COPY THE COMPLETE ARENA TO A SUITABLE FREE PHYSICAL EXTENT
4. UPDATE THE CENTRAL MEMORY-OBJECT DESCRIPTOR
5. USE THE NEW RELOCATION BASE WHEN A PROCESS RESUMES
'''

LOGICAL ADDRESSES INSIDE THE SESSION DO NOT CHANGE.

'''TEXT
BEFORE:
KERNEL | SESSION A | FREE | SESSION B | FREE | SESSION C

AFTER:
KERNEL | SESSION A | SESSION B | SESSION C | FREE........
'''

FOR PDP-6 THE SESSION ARENA IS THEREFORE BOTH:

'''TEXT
A HARDWARE PROTECTION/TRUST DOMAIN
A TOP-LEVEL MOVABLE PHYSICAL MEMORY OBJECT
'''

THE ORIGINAL SPLIT-REGION SESSION ALLOCATOR REMAINS USEFUL INTERNALLY, BUT THE
ARENA ITSELF MUST NOT BE ASSUMED TO BE PERMANENTLY FIXED IN PHYSICAL MEMORY.
THE INITIAL IMPLEMENTATION SHOULD NOT ATTEMPT ARBITRARY LIVE COMPACTION INSIDE
A SESSION.

## 16. MMU BACKENDS

MMU-CAPABLE PDP-10 SYSTEMS RETAIN THE SAME GENERIC MEMORY OBJECTS AND ADDRESS
SPACE MODEL, BUT USE HARDWARE MAPPINGS INSTEAD OF THE PDP-6 ARENA MECHANISM.

'''TEXT
GENERIC MEMORY OBJECT
        |
        +-- NO-MMU: CONTIGUOUS PHYSICAL EXTENT / ARENA
        |
        +-- MMU: VIRTUAL MAPPING -> PHYSICAL BACKING
'''

KA-BBN, KA-ITS, KI, KS, AND KL REQUIRE SEPARATE MACHINE BACKENDS WHERE THEIR
HARDWARE MODELS DIFFER.  THE GENERIC INTERFACE MUST NOT PRETEND THAT THEY SHARE
ONE PAGE-TABLE FORMAT.

PHYSICAL COMPACTION IS NORMALLY UNNECESSARY ON AN MMU MACHINE WHEN CONTIGUOUS
LOGICAL STORAGE CAN USE NON-CONTIGUOUS PHYSICAL BACKING.  THE LOGICAL LOGIN
SESSION MAY STILL EXIST, BUT IT NEED NOT REMAIN THE MEMORY PROTECTION OR
PHYSICAL ALLOCATION UNIT.

## 17. SHARED EXECUTABLE TEXT ACROSS BACKENDS

SHARED EXECUTABLE TEXT IS GENERIC; THE PDP-6 SESSION ARENA IS NOT.

'''TEXT
ONE IMMUTABLE/SHAREABLE TEXT OBJECT
        |
        +-- EXECUTION CONTEXT A
        +-- EXECUTION CONTEXT B
        +-- EXECUTION CONTEXT C
'''

NO-MMU PDP-6 REALIZATION:

'''TEXT
TEXT EXISTS ONCE INSIDE ONE TRUSTED SESSION ARENA
SAME-SESSION PROCESSES MAY EXECUTE IT
PRIVATE WRITABLE STATE REQUIRES THE SHARED-TEXT ABI
READ-ONLY TEXT CANNOT BE ENFORCED BY THE PDP-6 MMU
'''

MMU REALIZATION:

'''TEXT
THE SAME TEXT BACKING MAY BE MAPPED INTO MULTIPLE ADDRESS SPACES
PRIVATE DATA AND STACK MAPPINGS DIFFER PER PROCESS
READ/EXECUTE PROTECTION IS USED WHERE THE MACHINE SUPPORTS IT
'''

THUS:

'''TEXT
SHARED EXECUTABLE TEXT       GENERIC CONCEPT
SESSION-SHARED ARENA TEXT    PDP-6/NO-MMU MECHANISM
'''

## 18. OVERLAY MODEL ACROSS BACKENDS

OVERLAYS ARE A GENERIC EXECUTABLE/ADDRESS-SPACE CONCEPT, NOT A PDP-6-SPECIFIC
ALLOCATOR FEATURE.

'''TEXT
OVERLAY GROUP
    LOGICAL REGION
    MEMBERS A, B, C
    ACTIVE MEMBER
'''

NO-MMU REALIZATION LOADS OR COPIES THE REQUIRED MEMBER INTO THE OVERLAY REGION
AND DISCARDS CLEAN INACTIVE MEMBERS.  AN MMU BACKEND MAY INSTEAD UNMAP THE OLD
MEMBER AND MAP THE NEW MEMBER AT THE SAME LOGICAL REGION.

OVERLAYS MAY REMAIN USEFUL ON MMU MACHINES WHEN LOGICAL ADDRESS SPACE, RATHER
THAN PHYSICAL RAM, IS THE LIMITING RESOURCE.

PERSISTENT MUTABLE STATE MUST REMAIN OUTSIDE CLEAN OVERLAY CODE IN
PROCESS-PRIVATE OR EXPLICITLY MANAGED STATE.

## 19. OBJECT TRAITS AND POLICY

GENERIC OBJECT TRAITS SHOULD RECORD SEMANTICS WITHOUT ASSUMING EVERY BACKEND
CAN ENFORCE THEM IN HARDWARE.  THE REPRESENTATION MUST REMAIN SMALL.

'''TEXT
TEXT      | SHARED | READ | EXEC
DATA      | PRIVATE | READ | WRITE
STACK     | PRIVATE | READ | WRITE
OVERLAY   | READ | EXEC
CACHE     | DISCARDABLE
SESSION   | MOVABLE
'''

BACKEND-SPECIFIC MECHANISMS INCLUDE:

'''TEXT
NO-MMU:
    PHYSICAL EXTENTS
    SESSION RELOCATION/PROTECTION
    WHOLE-ARENA COMPACTION
    PHYSICAL OVERLAY LOAD/COPY

MMU:
    MACHINE-SPECIFIC MAPPINGS
    HARDWARE PROTECTION
    NON-CONTIGUOUS PHYSICAL BACKING WHERE SUPPORTED
    MAPPING-BASED OVERLAY SWITCHING
    OPTIONAL PAGING/SWAPPING POLICY
'''

## 20. DOBJ/DLINK AND EXECUTABLE BOUNDARY

DOBJ1/DARC1/DLINK SHOULD PRESERVE EXECUTABLE SEMANTICS NEEDED BY THIS MODEL BUT
MUST NOT ENCODE DAIMOS RUNTIME SESSION OR MACHINE POLICY.

THE IMPORTANT SEMANTIC DISTINCTION IS:

'''TEXT
TEXT    IMMUTABLE/SHAREABLE PROGRAM TEXT
DATA    INITIALIZED WRITABLE PRIVATE STATE
BSS     ZERO-FILLED WRITABLE PRIVATE STATE
'''

RUNTIME CONCEPTS SUCH AS SESSION IDENTITY, SESSION-SHARING POLICY, PLEDGE
PROFILE, OVERLAY CACHE POLICY, OR MACHINE-SPECIFIC ARENA PLACEMENT BELONG TO
THE DAIMOS LOADER/KERNEL POLICY.

THE SHARED-TEXT ABI MAY EVENTUALLY REQUIRE SMALL COMPILER/LINKER/EXECUTABLE
METADATA.  IF SO, IT MUST BE SPECIFIED AS A MACHINE-INDEPENDENT ABI FEATURE,
NOT INTRODUCED ACCIDENTALLY AS PDP-6 SESSION POLICY.

## 21. FAILURE, RECOVERY, AND CONSISTENCY RULES

MOVEMENT AND RECLAMATION MUST HAVE EXPLICIT FAILURE SEMANTICS.  A COMPACTION OR
RELOCATION OPERATION MUST EITHER LEAVE THE OLD OBJECT VALID OR COMPLETE THE
MOVE AND PUBLISH THE NEW DESCRIPTOR; HALF-PUBLISHED PLACEMENT IS NOT ALLOWED.

A SAFE INITIAL MOVE SEQUENCE IS COPY-THEN-PUBLISH:

'''TEXT
RESERVE DESTINATION
COPY SOURCE TO DESTINATION
VERIFY REQUIRED INVARIANTS
ATOMically PUBLISH NEW BASE/DESCRIPTOR STATE
RELEASE OLD EXTENT
'''

ON A SINGLE CPU, INTERRUPTS OR SCHEDULING MUST NOT OBSERVE A DESCRIPTOR BETWEEN
OLD AND NEW PLACEMENT.  KERNEL/DMA USERS OF A MOVABLE OBJECT MUST PIN IT.

CLEAN TEXT AND CLEAN OVERLAYS SHOULD BE DISCARDED AND RELOADED RATHER THAN
WRITTEN TO SWAP.  DIRTY PRIVATE STATE IS THE PRIMARY SWAP CANDIDATE.

OWNERSHIP TRANSITIONS ACROSS TRUST DOMAINS MUST NOT LEAK OLD CONTENTS.  MEMORY
RETURNED FROM ONE SESSION/UID DOMAIN AND ALLOCATED TO ANOTHER MUST BE CLEARED
BEFORE USER ACCESS.  INTERNAL REUSE WITHIN THE SAME TRUST DOMAIN MAY USE A
CHEAPER POLICY WHEN THE CALLING ABI GUARANTEES INITIALIZATION.

OBJECT LIFETIME MUST ALSO BE EXPLICIT.  A DESCRIPTOR MAY NOT BE RECYCLED WHILE
REFERENCES, PINS, ACTIVE MAPPINGS, I/O, OR AN IN-PROGRESS MOVE STILL EXIST.
REFERENCE COUNTS EXPRESS LOGICAL OWNERSHIP; PIN COUNTS EXPRESS TEMPORARY
PHYSICAL-STABILITY REQUIREMENTS.  THEY ARE DIFFERENT CONDITIONS.

DEVICE I/O THAT USES CORE ADDRESSES MUST PIN THE TARGET OBJECT FOR THE COMPLETE
I/O LIFETIME.  THE INITIAL IMPLEMENTATION SHOULD SIMPLY REFUSE TO MOVE AN
OBJECT WITH A NONZERO PIN COUNT RATHER THAN ATTEMPTING DEVICE-SPECIFIC LIVE
RELOCATION.

MEMORY PRESSURE SHOULD BE HANDLED IN THIS ORDER UNLESS MEASUREMENTS SHOW A
BETTER POLICY:

'''TEXT
COALESCE FREE EXTENTS
DROP CLEAN/DISCARDABLE OVERLAYS AND CACHES
RELOCATE/COMPACT STOPPED MOVABLE ARENAS
SWAP INACTIVE PRIVATE STATE, IF SWAPPING EXISTS
FAIL THE REQUEST WITH A PRECISE RESOURCE ERROR
'''

## 22. BOOTSTRAP AND DEGRADED MODE

THE MEMORY MANAGER MUST BOOT WITHOUT REQUIRING THE FULL DYNAMIC OBJECT SYSTEM
TO ALREADY EXIST.  EARLY KERNEL MEMORY, INTERRUPT/DEVICE STATE, AND THE INITIAL
ALLOCATOR METADATA MUST COME FROM A SMALL FIXED BOOTSTRAP REGION OR MONOTONIC
BOOT ALLOCATOR.

AFTER THE NORMAL MEMORY MANAGER IS INITIALIZED, UNUSED BOOTSTRAP SPACE MAY BE
RETURNED ONLY IF NO PERMANENT POINTERS REFER TO IT.

THE SYSTEM MUST ALSO HAVE A VALID DEGRADED MODE IN WHICH SHARED TEXT,
COMPACTION, OVERLAY CACHING, OR SWAPPING ARE DISABLED.  PRIVATE STATIC IMAGES
AND NON-MOVABLE EXTENTS REMAIN THE CORRECTNESS BASELINE.

THIS IS IMPORTANT FOR BRING-UP ON NEW PDP-10 MEMORY BACKENDS.

## 23. ACCOUNTING AND OBSERVABILITY

MEMORY SAVING FEATURES MUST BE MEASURABLE.  THE KERNEL SHOULD MAINTAIN SMALL
COUNTERS SUFFICIENT TO ANSWER:

'''TEXT
TOTAL/FREE PHYSICAL WORDS
LARGEST FREE EXTENT
NUMBER OF MEMORY OBJECTS
WORDS IN SHARED TEXT
WORDS IN PRIVATE PROCESS STATE
WORDS IN DISCARDABLE OVERLAYS/CACHES
COMPACTION COUNT AND WORDS MOVED
RECLAIM/EVICTION COUNT
SWAP WORDS READ/WRITTEN, IF ENABLED
ALLOCATION FAILURES BY CLASS
'''

THESE COUNTERS ARE PART OF THE DESIGN, NOT OPTIONAL DEBUG BLOAT: WITHOUT THEM
THE MEMORY COST OF SHARING, OVERLAYS, COMPACTION, AND MMU BACKENDS CANNOT BE
COMPARED RATIONALLY.

## 24. REVISED IMPLEMENTATION ORDER

'''TEXT
1. KEEP STATIC LINKING AND PRIVATE PROCESS IMAGES AS THE BASELINE.
2. ADD THE GENERIC CENTRAL MEMORY-OBJECT DESCRIPTOR MODEL.
3. ADD THE PDP-6 COALESCING PHYSICAL-EXTENT BACKEND.
4. REPRESENT A LOGIN ARENA AS A TOP-LEVEL MOVABLE MEMORY OBJECT.
5. ADD STOPPED WHOLE-ARENA RELOCATION/COMPACTION.
6. RETAIN SIMPLE SESSION-LOCAL REGION/SIZE-CLASS/SCRATCH ALLOCATORS.
7. DEFINE AND MEASURE THE SHARED-TEXT PRIVATE-STATE ABI.
8. SHARE ONLY DEMONSTRABLY PURE RUNTIME/LIBC TEXT FIRST.
9. ADD OVERLAYS FOR LARGE OR RARELY USED CODE.
10. ADD DISCARDABLE OVERLAY CACHING.
11. ADD DATA-FOCUSED SWAPPING ONLY IF REQUIRED.
12. SHARE SHELL/EDITOR TEXT ONLY AFTER GCC, KCC, LOADER, AND RUNTIME TESTS
    PROVE CORRECT PRIVATE-STATE ACCESS.
13. ADD KA-BBN, KA-ITS, KI, KS, AND KL BACKENDS BEHIND THE SAME GENERIC
    MEMORY-OBJECT/ADDRESS-SPACE INTERFACE.
'''

'''TEXT
                    DAIMOS GENERIC MEMORY MODEL

                 MEMORY OBJECTS + ADDRESS SPACES
                            |
             +--------------+--------------+
             |                             |
         NO-MMU PDP-6                  MMU PDP-10
             |                             |
      PHYSICAL EXTENTS                VM MAPPINGS
      SESSION ARENAS                  PROCESS ADDRESS SPACES
      ARENA PROTECTION                HARDWARE PROTECTION
      WHOLE-ARENA COMPACTION          PHYSICAL BACKING ALLOCATION
             |                             |
             +--------------+--------------+
                            |
                  SHARED EXECUTABLE TEXT
                         OVERLAYS
'''

FOR PDP-6:

'''TEXT
LOGIN SESSION
    = MEMORY PROTECTION DOMAIN
    = TRUST DOMAIN
    = TOP-LEVEL MOVABLE PHYSICAL MEMORY OBJECT

WITHIN THE SESSION:
    PURE TEXT MAY BE SHARED
    PRIVATE WRITABLE STATE IS PROVIDED BY AN EXPLICIT ABI
    SAME-SESSION PROCESSES ARE NOT MEMORY-ISOLATED
    OVERLAYS ARE CLEAN/DISCARDABLE WHERE POSSIBLE
'''

FOR MMU SYSTEMS:

'''TEXT
PROCESS ADDRESS SPACES BECOME THE NORMAL PROTECTION UNIT
SHARED TEXT IS REALIZED BY SHARED MAPPINGS
PRIVATE DATA/STACKS USE PRIVATE MAPPINGS
OVERLAYS MAY SWITCH MAPPINGS RATHER THAN COPY CODE
THE PDP-6 SESSION-ARENA MEMORY MECHANISM IS NOT REQUIRED
'''

THE STRONGEST NEW PROPERTY OF THE COMBINED DESIGN IS WHOLE-SESSION PHYSICAL
RELOCATION: PDP-6 RELOCATION ALLOWS A STOPPED SESSION ARENA TO MOVE WITHOUT
REWRITING ITS INTERNAL LOGICAL POINTERS.  THIS MAKES COARSE COMPACTION BOTH
CHEAP IN METADATA AND ROBUST AGAINST EXTERNAL FRAGMENTATION.

THE MAIN REMAINING RISK IS FULL-PROGRAM SHARED TEXT.  PURE RUNTIME TEXT IS
STRAIGHTFORWARD; SHELL/EDITOR SHARING REQUIRES A DELIBERATELY SPECIFIED
PRIVATE-STATE ABI AND CORRESPONDING COMPILER, LINKER, LOADER, AND RUNTIME
SUPPORT.
