# DECtape filesystems: DTFS and TSFS

**Documentation consolidation: 2026-11-09.** This is the single
filesystem-specific design reference for DAIMOS DECtape. It preserves the
implemented V1 contract, proposed TSFS V1.2 architecture and dated evidence;
it does **not** claim that the V1.2 redesign is implemented.

## Reading guide and authority

- **Implemented:** the existing native DTFS engine and TSFS V1.1 media,
  subject to current DAIMOS source and `PROJECT-STATE.MD`.
- **Proposed:** TSFS V1.2 metadata sharding, offline placement and independent
  tape prepositioning; retain V1.1 compatibility until verified otherwise.
- **Deferred:** parity/striping, trace optimizer and optional TENEX/ITS DTFS
  personalities; no claim of activation.
- **Hardware:** `../HARDWARE/dectape.md` remains the hardware/emulator timing
  reference and is not folded into this filesystem specification.
- **Boot integration:** `../BOOT/BOOTINFO.MD` and KINIT documentation own
  generic boot contracts; this page owns tape format and tape-specific policy.
- **Tests:** individual historical measurements are dated observations, not
  substitutes for a present-day test run.

The material below is relocated with its original text intact so the first
redesign step is documentation consolidation, not a silent format change.
Original source headings and dates are retained for auditability. Some older
plans explicitly record their historical implementation status; read those
alongside the current-state summary above.

# DECTAPE FILESYSTEMS V1

FILESYSTEMS: NATIVE DTFS PLUS TSFS; TENEX/ITS COMPATIBILITY DISABLED

THIS DOCUMENT COLLECTS THE CURRENT IMPLEMENTED DAIMOS DECTAPE FILESYSTEM
CONTRACT AND EXPLICITLY DEFERRED OPTIMIZATION/FORMAT WORK. IT REPLACES
SEPARATE TAPE-FILESYSTEM NOTES. IN V1, "TAPE FILESYSTEM" MEANS DECTAPE
FILESYSTEM. MTC516 MAGTAPE MAY
CARRY A RAW DAIMOS BOOT BLOCK/BOOT STREAM, INSTALL MEDIA, BACKUPS, DOCUMENT
TRANSFER, AND TAR-LIKE SEQUENTIAL ARCHIVE STRUCTURES, BUT IT DOES NOT GET AN
ORDINARY MOUNTED FILESYSTEM.

SCHEDULE (2026-11-01 V903): TSFS V1.2 SHARDED METADATA AND FORMAT
DEVELOPMENT ARE POST-KCORE, PRE-0.9 TASKS. THEY ARE NOT PART OF THE
ACTIVE KCORE BACKLOG OR ITS FUNCTIONAL FREEZE. KCORE WORK MUST STILL
PRESERVE EXISTING TSFS BOOT COMPATIBILITY.

## TYPE-136 TAPE DATA COMPLETION (2026-11-03 V1089)

DAIMOS'S OPTIONAL TAPE MRES SERVES BOTH TYPE-551 DECTAPE AND TYPE-516
MAGTAPE THROUGH THE SHARED TYPE-136 DATA CHANNEL. THE EXISTING DECTAPE
BLOCK-SEARCH AND MAGTAPE MOTION/CONTROL TIMERS ARE DISTINCT FROM THE
NOW-BOUNDED DATA TRANSFER: NEGATIVE `STORAGE_STATE` IDENTIFIES DTC OR
MTC READ/WRITE, WHILE THE POSITIVE `STORAGE_COUNT` MUST REMAIN THE DMA
WORD COUNT. THEREFORE THE SEARCH-RETRY WORD IS REUSED AS A 60-HZ DATA
TIMEOUT ONCE THE SEARCH HAS FOUND ITS BLOCK, AND ALSO FOR MTC DATA I/O.

DECTAPE DATA TRANSFER TIMEOUT IS 300 APR TICKS (5 SECONDS AT 60 HZ).
MAGTAPE DATA TRANSFER TIMEOUT IS 5400 TICKS (90 SECONDS AT 60 HZ).
KINIT PATCHES THE OPTIONAL `STORAGE_CLOCK_TAPE_JUMP` TO THE MRES
`TAPE_WATCHDOG_TICK_V1089`; THE ABSENT-PROVIDER DEFAULT IS A NO-OP.
EXPIRY STOPS THE CONTROLLER, SETS THE NORMAL ERROR STATE 7, INCREMENTS
THE CORRESPONDING DEVICE ERROR COUNT, INVALIDATES DECTAPE MOTION, AND
WAKES THE ORIGINAL TAPE WAITER. THAT PROCESS RETURNS AN I/O ERROR AND
RELEASES ITS OWN FS PROVIDER LEASE THROUGH THE ORDINARY RETURN PATH.
NO TIMER HANDLER MAY STEAL A FS LOCK OR DISCARD THE PROCESS STACK.

NATIVE PDP-6 SOURCE-LINKED TIMEOUT/NEGATIVE-CONTROL TESTS, ONLINE TYPE-516
RECORD READ/WRITE/CONTROL AND TYPE-551 STREAM/REVERSE TESTS PASS. FULL
256K KCC IMAGE BUILDS AND BOOTS THROUGH DTC/MTC MINIT TO INIT/LOGIN.
THE ADDED KCORE CLOCK CALL COSTS ONE CODE WORD, WITH NO NEW PERSISTENT
TIMER WORD. THE TAPE MRES GROWS FROM 375 TO 405 RESIDENT WORDS (+30),
WITH ITS 15 BSS WORDS UNCHANGED: COMBINED KCORE/TAPE RESIDENCY +31 WORDS.
THIS REQUIRES A WORKING APR CLOCK AND DOES NOT PROVIDE
GENERAL CANCELLATION FOR SOFTWARE-STALLED FILESYSTEM PROVIDERS.

## 1. PURPOSE

DAIMOS HAS TWO DECTAPE FILESYSTEM ENGINES:

'''TEXT
DTFS    SINGLE-DECTAPE READ/WRITE ENGINE FOR DAIMOS-NATIVE MEDIA
TSFS    NATIVE READ-ONLY MULTI-DECTAPE TAPESET FILESYSTEM
'''

DTFS IS THE NORMAL SINGLE-DECTAPE VFS PROVIDER.  THE SUPPORTED PDP-6 BUILD
MOUNTS DAIMOS-NATIVE DTFS MEDIA ONLY.  TENEX/ITS compatibility source is kept
as dormant reference code but is compiled out of the production MRES.

THE 2026-10-16 V21 MOUNT-CAPACITY AUDIT REMOVED THE OPTIONAL FOREIGN
PERSONALITY BRANCH'S FOUR-WORD SELF-MODIFYING XCT TABLE. WHEN TEST-ENABLED,
TENEX/ITS PERSONALITY LOOKUP NOW READS THE EXISTING MM-BACKED PER-MOUNT
MEDIA WORD AFTER VALIDATING ITS ZERO-BASED SLOT AGAINST THE PUBLISHED
VFS MOUNT LIMIT. THERE IS NO SECOND PERSONALITY TABLE OR RAM INCREASE.
THE NORMAL DTFS SPACE SERVICE ALSO USES THAT BOOT-SIZED LIMIT INSTEAD OF A
FIXED FOUR-SLOT CHECK. NATIVE PDP-6 TESTS COVER SLOTS 10/26, INVALID 27,
AND FOREIGN PERSONALITY FLAGS. TENEX/ITS REMAIN **DISABLED** IN THE
SUPPORTED BUILD; THIS IS COMPATIBILITY CODE REPAIR, NOT ITS ENABLEMENT.
IN V22, KINIT SELECTS CAPACITY FROM SUCCESSFULLY PROBED CONTROLLERS AND
VALIDATED TSFS PHYSICAL MEMBER UNITS. AN EIGHT-UNIT DTC CONTROLLER WITH A
ONE-MEMBER TSFS ROOT AND MEMFS REQUIRES NINE SLOTS; AN EIGHT-MEMBER ROOT
LEAVES TWO (ROOT PLUS MEMFS). THE TSFS-ROOT PROFILE DOES NOT INSTALL
D6FS, SO DSK/DRM DEVICES NEVER CONSUME PHANTOM MOUNT SLOTS. THE VFS LIMIT
IS PUBLISHED AFTER ALL SIX MM-BACKED TABLE BASE POINTERS.

TSFS IS THE DAIMOS TAPESET FORMAT: IT SPANS 1 TO 8 DECTAPES AND PRESENTS ONE
READ-ONLY FILESYSTEM FOR RESCUE, INSTALL, OR COMPACT DISTRIBUTION SETS.

'''

TSFS V1.1 IS:

'''TEXT
READ-ONLY

MEMBER COUNT CHOSEN BY THE MANIFEST/IMAGE, NOT BY A DEFAULT
NATIVE DECTAPE BLOCKS AS FILESYSTEM BLOCKS

'''

THE FIRST IMPLEMENTATION DOES NOT NEED 'TSPACK'. IT NEEDS ONLY A SIMPLE IMAGE

DTFS PERSONALITY SUPPORT IN V1 IS READ/WRITE:

'''TEXT
PROBE NATIVE / TENEX / ITS FORMAT
MOUNT THROUGH THE SAME DTFS VFS PROVIDER
LIST/OPEN/READ/STAT
CREATE/WRITE/TRUNCATE/RENAME/UNLINK WHERE THE MEDIA FORMAT SUPPORTS IT
PRESERVE NATIVE DIRECTORY, ALLOCATION, AND DATA-BLOCK RULES
NO CONVERSION-ON-MOUNT
NO PER-PERSONALITY FULL-BLOCK BUFFER
'''

FORMAT-SPECIFIC NAME/METADATA TRANSLATION MUST STAY SMALL AND PACKED.  DO NOT
STORE LARGE HUMAN-READABLE TRANSLATION TABLES IN KRES.

### VFS OWNERSHIP AND MODE POLICY

DAIMOS USES NINE-BIT UID AND GID VALUES (0..0777).  DTFS DOES NOT WRITE UNIX
OWNERSHIP INTO NATIVE, TENEX, OR ITS MEDIA.  INSTEAD EACH DTFS MOUNT IS OWNED
BY THE PROCESS THAT MOUNTED IT; THE COMPACT UID9,GID9 OWNER IS KEPT ONLY IN
RUNTIME MOUNT STATE AND IS RETURNED BY STAT FOR THE MOUNT ROOT AND EVERY FILE.
A ROOT BOOT/SYSTEM MOUNT THEREFORE NATURALLY APPEARS AS 0:0.  FILE-LEVEL CHOWN
IS NOT REPRESENTABLE ON DTFS MEDIA AND REMAINS UNSUPPORTED.

NATIVE DTFS RETAINS ITS ONE EXECUTABLE PROPERTY: THE VFS MODE IS 0666 PLUS
0111 WHEN THE NATIVE EXECUTE BIT IS SET, AND CHMOD COLLAPSES THE REQUEST TO
THAT EXECUTE PROPERTY.  FOREIGN TENEX/ITS MODES ARE SYNTHETIC (0444 WHEN
READ-ONLY, 0666 WHEN WRITABLE).  NONE OF THESE POLICIES ALTER FOREIGN MEDIA.

DTFS HAS NO MEANINGFUL PER-FILE MTIME IN THE SUPPORTED MEDIA PERSONALITIES,
SO VFS STAT RETURNS MTIME 0.

## 4. BOOT AND SYSTEM ROLE

DECTAPE FILESYSTEMS ARE NOT DAIMOS BOOT MEDIA. DTFS AND TSFS
MUST NOT RESERVE OR INTERPRET A DAIMOS BOOT BLOCK OR BOOTSTREAM. THE KERNEL
NORMALLY COMES FROM DISK, PAPER TAPE CHAIN, OR RAW MAGTAPE BOOT BLOCK/BOOT
STREAM. MAGTAPE CAN ALSO CARRY INSTALL MEDIA, BACKUPS, DOCUMENT-TRANSFER
RECORDS, AND TAR-LIKE SEQUENTIAL ARCHIVES; THOSE ARE STREAM/ARCHIVE FORMATS,
NOT ORDINARY MOUNTED FILESYSTEMS.

DECTAPE FILESYSTEMS CAN STILL BE DAIMOS ROOT FILESYSTEMS. A TSFS TAPESET IS A
VALID READ-ONLY ROOT FILESYSTEM AFTER THE KERNEL AND DTC551 DRIVER ARE RESIDENT.
IN THAT MODE, BOOT LOADS KRES/KINIT FROM NON-DECTAPE MEDIA, THEN ROOT SELECTION
MOUNTS THE TSFS SET.

DESCRIPTOR REPLICAS ARE NOT A BOOT AREA. THEY ARE ONLY MOUNT RELIABILITY DATA.

## 5. CAPACITY AND TAPE COUNT

THERE IS NO TSFS DEFAULT TAPE COUNT.

THE MANIFEST/PROFILE DETERMINES THE NUMBER OF MEMBERS NEEDED, FROM 1 TO 8.
A 6-MEMBER IMAGE MAY BE A COMMON GENERATED PROFILE, BUT IT IS NOT A FILESYSTEM
RULE.

A MISSING MEMBER IS FATAL IN V1 BECAUSE THERE IS NO PARITY/RECONSTRUCTION.

## 6. DECTAPE MODEL

USE THIS MENTAL MODEL:

'''TEXT
DECTAPE = BLOCK-ADDRESSABLE SEQUENTIAL MEDIUM WITH VERY HIGH SEEK COST
'''

DO NOT TREAT IT LIKE A NORMAL DISK FOR LAYOUT. RANDOM ACCESS IS LEGAL, BUT
TSFS IMAGES SHOULD BE PLACED SO COMMON READS ARE MOSTLY SEQUENTIAL OR NEAR EACH
OTHER.

## 7. CONTROLLER PARALLELISM ASSUMPTION

FOR V1, BE CONSERVATIVE:

'''TEXT
SEVERAL DECTAPE UNITS MAY EXIST AND MAY HAVE INDEPENDENT MOTION STATE, BUT THE
CONTROLLER/DATA PATH SHOULD BE TREATED AS ONE ACTIVE TRANSFER STREAM PER
CONTROLLER.
'''

THEREFORE TSFS V1 MUST NOT DEPEND ON TRUE SIMULTANEOUS MULTI-DRIVE DATA READS.
IT MAY STILL BENEFIT FROM SPREADING HOT FILES ACROSS MEMBERS AND FROM LATER
PREPOSITIONING/READ-AHEAD POLICIES.

## 8. PLACEMENT POLICY FOR V1

DO NOT USE MANDATORY BLOCK-LEVEL ROUND-ROBIN STRIPING.

V1 PLACEMENT IS COARSE:

'''TEXT
SMALL FILE          CONTIGUOUS ON ONE MEMBER
NORMAL FILE         ONE OR MORE NORMAL EXTENTS, EACH ON ONE MEMBER
LARGE FILE          MAY HAVE SEVERAL LARGE EXTENTS ON DIFFERENT MEMBERS
METADATA            COMPACT AND EASY TO FIND
'''

ROUND-ROBIN BLOCK PLACEMENT IS DEFERRED. FUTURE LARGE-FILE STRIPING SHOULD BE
PREPARED IN THE EXTENT FORMAT BUT REJECTED BY THE V1 KERNEL.

## 9. FUTURE STRIPING PREPARATION

EXTENT RECORDS MUST INCLUDE AN EXTENT TYPE FIELD.

V1 SUPPORTS ONLY:

'''TEXT
EXT_NORMAL
'''

RESERVE:

'''TEXT
EXT_STRIPED
'''

IF A V1 KERNEL SEES 'EXT_STRIPED', IT MUST REJECT THE FILESYSTEM OR REJECT THE
FILE AS AN UNSUPPORTED TSFS FORMAT. V1 IMAGE BUILDERS MUST EMIT ONLY
'EXT_NORMAL'.

THIS LETS FUTURE 'TSPACK' SPLIT LARGE SEQUENTIAL FILES ACROSS MEMBERS WITHOUT
CHANGING THE BASIC PATHNAME/FILE LAYOUT.

## 10. MEMBER DISCOVERY

TSFS MEMBER PLACEMENT MUST BE DRIVE-INDEPENDENT. OPERATORS SHOULD NOT HAVE TO
INSERT MEMBER 0 INTO A FIXED DRIVE.

MINIT SHOULD SCAN AVAILABLE DECTAPE DRIVES:

'''TEXT
FOR EACH DECTAPE DRIVE:
    READ DESCRIPTOR REPLICAS
    VALIDATE TSFS MAGIC/CHECKSUM/VERSION
    COLLECT TAPESET_ID, GENERATION, MEMBER_COUNT, MEMBER_INDEX

CHOOSE A COMPLETE MATCHING SET:
    SAME TAPESET_ID
    SAME GENERATION
    SAME MEMBER_COUNT
    EXACTLY ONE MEMBER_INDEX IN 0..MEMBER_COUNT-1
'''

MOUNT FAILS ON:

'''TEXT
MISSING MEMBER
DUPLICATE MEMBER_INDEX
WRONG GENERATION
BAD DESCRIPTOR CHECKSUM
UNSUPPORTED FORMAT FLAGS
'''

EXTRA UNRELATED TAPES ARE IGNORED UNLESS THE OPERATOR EXPLICITLY SELECTS THEM.

THE MOUNTED INSTANCE RECORDS:

'''TEXT
TSFS MEMBER INDEX -> PHYSICAL DECTAPE DRIVE
'''

## 11. ON-TAPE STRING AND PATH RULES

USE SIXBIT PATHS AND NAMES, LIKE THE DISK FILESYSTEM.

RULES:

'''TEXT
UPPERCASE ONLY
COUNTED SIXBIT WORDS
NO C STRINGS
NO NUL TERMINATORS
NO VARIABLE IN-CORE POINTER VALUES ON TAPE
'''

EXAMPLE PATHS:

'''TEXT
/SYSTEM/EXEC/SH
/OPTION/BASE/EXEC/LS
/SYSTEM/INIT
/SYSTEM/LIB/RUNTIME
'''

THE SLASH CHARACTER IS STORED AS ITS SIXBIT CODE. PATH VALUES ARE COMPARED AS
PACKED SIXBIT WORD SEQUENCES.

## 12. PATH LOOKUP STRUCTURE

DO NOT USE LINKED LISTS FOR TSFS PATH LOOKUP. TSFS IS READ-ONLY; INSERTION COST
IS IRRELEVANT AND LINKED LISTS WASTE SEEKS.

DO NOT START WITH AN ON-TAPE TREE. IT ADDS CODE AND RECOVERY COMPLEXITY THAT
V1 DOES NOT NEED.

USE:

'''TEXT
SORTED FULL-PATH INDEX
OPTIONAL DIRECTORY RANGE TABLE
'''

LOOKUP:

'''TEXT
BINARY SEARCH COUNTED SIXBIT FULL PATH
'''

DIRECTORY LISTING:

'''TEXT
FIND DIRECTORY RANGE
SCAN IMMEDIATE CHILDREN IN SORTED INDEX
'''

THE DIRECTORY RANGE TABLE IS AN OPTIMIZATION AND SHOULD BE SMALL. IF THE FIRST
IMPLEMENTATION WANTS TO BE EVEN SMALLER, IT CAN DERIVE DIRECTORY LISTINGS BY
PREFIX SCAN AND ADD THE RANGE TABLE LATER.

## 13. MINIMAL FILE FLAGS

TSFS HAS NO BOOT AREA AND NO NORMAL MULTIUSER HIDDEN/SYSTEM VIEW. KEEP FLAGS
MINIMAL.

V1 COMPATIBLE FLAGS:

'''TEXT
TSF_DIR   SYNTHETIC DIRECTORY ENTRY, IF EXPLICIT DIRECTORIES ARE STORED
TSF_EXEC  FILE MAY BE OFFERED TO THE EXEC LOADER
'''

RESERVED OR UNSUPPORTED IN V1:

'''TEXT
TSF_COMPRESSED
TSF_BOOT
TSF_STRIPED_FILE
TSF_SPECIAL
'''

THE OLD 'SYSTEM' AND 'HIDDEN' IDEAS ARE NOT NEEDED FOR V1. THEY CAN REMAIN
RESERVED IF THE FIELD HAS SPARE BITS, BUT THE V1 CODE SHOULD NOT IMPLEMENT
POLICY AROUND THEM.

EXEC RULE:

'''TEXT
TSF_EXEC PERMITS AN EXEC-LOADER ATTEMPT.
THE LOADER MUST STILL VALIDATE THE ACTUAL EXECUTABLE FORMAT.
'''

## 14. DESCRIPTOR CONCEPT

USE A MINIMAL MEMBER DESCRIPTOR, SIMILAR IN SPIRIT TO BLOCKSET/MEDIA
DESCRIPTORS, BUT MUCH SMALLER THAN THE DISK BOOT DESCRIPTOR. IT ONLY IDENTIFIES
THE TAPESET AND POINTS TO THE TABLE DIRECTORY.

DESCRIPTOR REPLICAS SHOULD LIVE AT FIXED BLOCKS ON EVERY MEMBER, FOR EXAMPLE:

'''TEXT
BLOCK 0      PRIMARY DESCRIPTOR
BLOCK 1      BACKUP DESCRIPTOR
LAST BLOCK   OPTIONAL FINAL BACKUP DESCRIPTOR
'''

EXACT REPLICA POSITIONS CAN BE FINALIZED IN THE HEADER, BUT V1 SHOULD USE AT
LEAST TWO DESCRIPTOR COPIES PER MEMBER.

## 15. MEMBER DESCRIPTOR FIELDS

THE IMPLEMENTED PACKED WORD LAYOUT IS DEFINED IN `SYSTEM/KERNEL/FS/TSFS.H`.
ITS DESCRIPTOR CARRIES THESE FIELDS:

'''TEXT
MAGIC
FORMAT_MAJOR
FORMAT_MINOR
FLAGS
TAPESET_ID_HI
TAPESET_ID_LO
GENERATION
MEMBER_COUNT
MEMBER_INDEX
BLOCK_COUNT
TDIR_MEMBER
TDIR_BLOCK
TDIR_BLOCKS

NOTES:

'''TEXT

MEMBER_COUNT        1..8
MEMBER_INDEX        0..MEMBER_COUNT-1

DESCRIPTOR_CHECKSUM CHECKSUM OF DESCRIPTOR WORDS WITH CHECKSUM FIELD ZEROED
'''

DO NOT CALL THESE 'ROOT BLOCKS'; THEY ARE A TABLE DIRECTORY POINTER, NOT A UNIX
ROOT DIRECTORY.

## 16. TABLE DIRECTORY

THE TABLE DIRECTORY IS THE METADATA ROOT. IT TELLS THE KERNEL WHERE ALL OTHER
STATIC TABLES LIVE.

THE TABLE DIRECTORY SHOULD CONTAIN RECORDS FOR:

'''TEXT
NAME INDEX
SIXBIT PATH POOL
FILE TABLE
EXTENT TABLE
DIRECTORY RANGE TABLE, OPTIONAL
CHECKSUM TABLE OR EXTENT CHECKSUMS
RESERVED FUTURE TABLES
'''

A TABLE DIRECTORY ENTRY SHOULD INCLUDE AT LEAST:

'''TEXT
TABLE_ID
FLAGS
MEMBER_INDEX
START_BLOCK
BLOCK_COUNT
RECORD_WORDS
RECORD_COUNT
CHECKSUM
'''

V1 CAN KEEP ALL MANDATORY METADATA TABLES UNCOMPRESSED AND UNSTRIPED.

## 17. FILE TABLE

TSFS V1.1 KEEPS THE IMPLEMENTED EIGHT-WORD FILE RECORD.  THIS IS DELIBERATE:
EIGHT WORDS GIVE EXACTLY 16 RECORDS PER 0200-WORD DECTAPE BLOCK, SO THE PDP-6
RUNTIME CAN INDEX RECORDS WITH SHIFTS/MASKS INSTEAD OF DIVISION.

THE LOW HALF OF PARENT_FLAGS CARRIES TYPE PLUS MODE: TYPE USES THE LOW TWO
BITS, BITS 2..5 ARE RESERVED ZERO, AND MODE12 OCCUPIES BITS 6..17.  OWNERSHIP
IS ONE COMPACT UID9,GID9 HALFWORD.  DIRECTORY SIZE IS OTHERWISE UNUSED, SO A
DIRECTORY STORES OWNER THERE; REGULAR-FILE AUX IS OTHERWISE UNUSED, SO A
REGULAR FILE STORES OWNER THERE.  DIRECTORY AUX RETAINS FIRST_CHILD,CHILD_COUNT.
THUS PER-FILE MODE/OWNER COSTS NO NINTH RECORD WORD.

MKTSFS MANIFEST ENTRIES MAY SUPPLY THESE IMMUTABLE ATTRIBUTES:

'''TEXT
D /PATH [MODE UID GID]
F /PATH HOST-SOURCE [MODE UID GID]
'''

MODE IS OCTAL; UID/GID ARE DECIMAL 0..511.  OMITTED ATTRIBUTES DEFAULT TO
0555 0 0 FOR DIRECTORIES AND 0444 0 0 FOR REGULAR FILES.  TSFS DOES NOT STORE
PER-FILE MTIME; STAT RETURNS MTIME 0.

'PATH_INDEX' REFERS TO THE SORTED PATH/NAME INDEX ENTRY. THE ACTUAL PATHNAME IS
STORED IN THE SIXBIT PATH POOL.

IF DIRECTORIES ARE EXPLICIT, DIRECTORY RECORDS USE 'TSF_DIR' AND HAVE ZERO
SIZE AND ZERO EXTENTS.

## 18. EXTENT TABLE

A NORMAL V1 EXTENT SHOULD BE ONE CONTIGUOUS RANGE ON ONE MEMBER.

SUGGESTED LOGICAL FIELDS:

'''TEXT
EXTENT_TYPE
FLAGS
FILE_BLOCK_START
FILE_BLOCK_COUNT
MEMBER_INDEX
PHYSICAL_BLOCK
PHYSICAL_COUNT
EXTENT_CHECKSUM
RESERVED
'''

V1 RULES:

'''TEXT
EXTENT_TYPE MUST BE EXT_NORMAL
MEMBER_INDEX MUST BE VALID
PHYSICAL_COUNT MUST MATCH OR COVER FILE_BLOCK_COUNT
RESERVED STRIPING FIELDS MUST BE ZERO
'''

FUTURE STRIPING CAN ADD STRIPE GROUP, CHUNK SIZE, MEMBER MASK, OR AN INDIRECT
STRIPE DESCRIPTOR THROUGH RESERVED FIELDS OR A NEW TABLE TYPE.

## 19. CHECKSUMS

CHECKSUMS ARE MANDATORY FOR TSFS BECAUSE TAPE MEDIA AND DESCRIPTOR MISMATCH
ERRORS MUST BE CAUGHT EARLY.

V1 MUST CHECKSUM:

'''TEXT
MEMBER DESCRIPTORS
TABLE DIRECTORY
METADATA TABLE PAGES
FILE/EXTENT DATA AS DESCRIBED BY EXTENT CHECKSUMS
'''

THE CHECKSUM IS FOR CORRUPTION DETECTION, NOT SECURITY.

RECOMMENDED ALGORITHM FOR FIRST IMPLEMENTATION:

'''TEXT
36-BIT ROTATING ADD/XOR CHECKSUM OVER 36-BIT WORDS
'''

THE EXACT FUNCTION IS SHARED BY THE IMAGE TOOLS AND TRANSIENT METADATA
VALIDATOR.  MEMBER DESCRIPTORS, TABLE DIRECTORY, AND METADATA TABLE PAGES ARE
CHECKED BEFORE THE KERNEL ACCEPTS THE MOUNT HANDOFF.  EXTENT-DATA CHECKSUMS ARE
AUTHORITATIVE OFFLINE-INTEGRITY DATA AND `TSFSCHECK` VALIDATES THEM OVER THE
FULL PHYSICAL EXTENT.  V1 DOES NOT FORCE THE RESIDENT READER TO REREAD AN
ENTIRE TWO-BLOCK STORED RESTART FOR EVERY PARTIAL READ JUST TO RECOMPUTE THAT
WHOLE-EXTENT CHECKSUM; D6LZ STREAM STRUCTURE/LENGTH IS STILL CHECKED during
DECODE.  A FUTURE PER-BLOCK RUNTIME DATA CHECKSUM FORMAT REQUIRES A FORMAT
REVISION RATHER THAN ADDING HIDDEN READ AMPLIFICATION TO V1.

THE CHECKSUM FUNCTION MUST REMAIN SMALL, DETERMINISTIC, AND ENDIAN-INDEPENDENT
AT THE IMAGE LEVEL.

A PRACTICAL RULE:

'''TEXT
CHECKSUM FIELD IS TREATED AS ZERO WHILE CALCULATING ITS CONTAINING OBJECT
'''

XOR/PARITY IS DEFERRED. RESERVE AN INCOMPATIBLE FEATURE FLAG:

'''TEXT
TSFS_F_PARITY
'''

IF SET, V1 REFUSES TO MOUNT.

## 20. COMPRESSION

TSFS REGULAR-FILE PAYLOAD DATA IS COMPRESSED WITH D6LZ36 BY DEFAULT IN NEW
IMAGES.  THIS IS A FILE/EXTENT REPRESENTATION, NOT A TRANSPARENT COMPRESSED
DECTAPE BLOCK DEVICE.

KEEP MEMBER DESCRIPTORS, TABLE DIRECTORY, FILE TABLE, EXTENT TABLE, AND OTHER
MOUNT/PATH METADATA DIRECT AND UNCOMPRESSED.  THIS LETS MEMBER DISCOVERY,
CHECKSUM VALIDATION, LOOKUP, READDIR, AND STAT OPERATE WITHOUT FIRST DECODING A
STREAM AND KEEPS CORRUPTION LOCALITY SIMPLE.

MKTSFS AND TSPACK COMPRESS REGULAR-FILE PAYLOADS OFFLINE.  TSFSCHECK MUST
VALIDATE BOTH STORED EXTENT BOUNDS AND THE D6LZ36 STREAM/EXPECTED LOGICAL WORD
COUNT.  THE FORMAT MUST RECORD ENOUGH PER-FILE/PER-EXTENT INFORMATION TO MAP
LOGICAL FILE OFFSETS TO COMPRESSED EXTENTS WITHOUT SCANNING UNRELATED FILES.

THE KERNEL READ PATH REUSES THE RESIDENT D6LZ36 DECODER.  DECOMPRESSION IS
BOUNDED AND STREAMING: NO WHOLE-FILE INFLATION, NO PER-MOUNT HISTORY COPY, AND
NO SECOND RESIDENT D6LZ IMPLEMENTATION.  RANDOM SEEK MAY RESTART AT A COMPRESSED
EXTENT BOUNDARY; TSPACK SHOULD KEEP RESTARTABLE EXTENTS SMALL ENOUGH FOR
ACCEPTABLE DECTAPE LATENCY WHILE STILL OBTAINING USEFUL COMPRESSION.
MULTI-EXTENT AND CROSS-MEMBER FILES MOVE TO THE NEXT VALIDATED COMPRESSED EXTENT
AND RESTART THE DECODER THERE.

EVERY REGULAR-FILE EXTENT IS EXPLICITLY ENCODED.  `D6LZ` IS USED WHEN IT
REDUCES PHYSICAL DECTAPE BLOCK OCCUPANCY; `STORED` IS THE INCOMPRESSIBLE ESCAPE
REPRESENTATION AND IS NOT A SECOND RAW-FILE ARCHITECTURE.  V1 USES FIXED
0400-WORD RESTART EXTENTS (THE FINAL EXTENT MAY BE SHORTER).  THIS MAKES RANDOM
ACCESS DIRECT: THE RESTART INDEX IS `FILE_WORD_OFFSET / 0400`.

DO NOT IMPLEMENT A TRANSPARENT COMPRESSED DECTAPE BLOCK LAYER FOR TSFS.

## 21. BUFFER AND CACHE POLICY

THE 32K-WORD PDP-6 BASELINE IS AUTHORITATIVE.  THE CURRENT IMPLEMENTATION USES
ONE SHARED 128-WORD FULL-BLOCK WORKSPACE FOR DTFS, D6FS, AND OTHER SERIALIZED
BLOCK-FILESYSTEM OPERATIONS.  THE PLANNED BSTORE/BCACHE CONSOLIDATION IN
`KERNEL/BSTORE.MD` ADDS ONE COMMON CLEAN TWO-BLOCK RAM L1 FOR D6FS AND
DTFS/TSFS WITHOUT A PER-MOUNT PRIVATE DATA CACHE.  DTFS MUST USE THE SMALLEST

## Part 2: Proposed TSFS V1.2 sharded-metadata design

*Relocated from `KERNEL/TSFS.MD` (original text follows).*

# TSFS

## 1. Scope

TSFS is the read-only native DECtape filesystem.  V1.1 remains the current
compatible on-media format.  A set may contain one through eight members,
using the complete three-bit DTC unit namespace.  Mount and boot discovery
validate set identity, generation, member descriptors, table checksums and
extent structure transiently; the resident provider keeps only compact,
validated state.

TSFS V1.2 is a locality and latency optimization for immutable media.  It does
not change filesystem semantics.  The design deliberately spends host CPU,
host RAM and a small amount of tape capacity during image construction to
minimize PDP-6/KA10 runtime RAM, kernel code and mechanical DECtape latency.

The central observation is that a multi-member DECtape set is not merely extra
capacity.  Each physical transport is an independent positioning resource.
Several tapes may move toward useful locations concurrently even though the
shared Type-136 data channel can transfer only one block at a time.

V1.2 therefore treats metadata as a set of one-block physical shards placed
across members and along each tape.  A logical metadata station may require
one or more shards, but every individual shard is exactly one DECtape block.
The number of distinct shard classes depends on the metadata size and the
number of members in the set.  Surplus members and surplus longitudinal
positions are used for staggered replicas.

## 2. Existing V1.1 representation

V1.1 uses 128-word DECtape blocks.  Each member contains redundant member
descriptors.  Canonical metadata consists of a table directory plus fixed-size
file and extent records.  Regular file data uses fixed `0400`-word restart
extents; each extent is STORED or D6LZ36 only when compression saves whole
DECtape blocks.

V1.1 metadata is intentionally direct and simple, but repeated metadata access
can force long seeks back toward the canonical tables.  This is inexpensive in
fast simulators and expensive on mechanically faithful DECtape timing.

V1.2 keeps the V1.1 canonical metadata as the authoritative recovery and
compatibility representation.  The optimized shards are additional derived
metadata and may always be regenerated from the canonical form.

## 3. Design goals

V1.2 shall satisfy the following goals:

- every physical optimized metadata shard is exactly one 128-word block;
- metadata size is structurally bounded and never depends on a probabilistic
  compressor meeting a target ratio;
- the layout adapts to sets containing one through eight members;
- independent tape motion is exploited when several members are present;
- the Type-136 data channel remains globally serialized for actual transfers;
- normal metadata access minimizes mechanical seek distance and reversals;
- common operations should need as few shard transfers as possible;
- the image builder, not the resident kernel, performs expensive optimization;
- permanent kernel RAM growth must be negligible;
- the existing mount syscall size and VFS interface should remain unchanged;
- V1.1 media must continue to mount normally;
- damaged optimized metadata must fall back to another replica or to canonical
  V1.1 metadata without modifying the read-only media.

## 4. Terminology

**Member** is one logical tape in a TSFS set.  A set contains 1..8 members.

**Shard** is one 128-word optimized metadata block.  No shard spans multiple
physical blocks.

**Shard class** is the logical role of a shard, for example A, B or C.  All
replicas of one class encode equivalent logical information.

**Metadata station** is a complete set of one replica from every shard class
required to describe the filesystem.  A station is logical, not necessarily a
contiguous physical object and not necessarily resident on one tape.

**Replica** is another physical copy of a shard class.

**Anchor** is the physical block position associated with a shard replica.
Local physical locations may be encoded as unsigned distances from an anchor.

## 5. Adaptive shard width

Let `M` be the number of members and let `W` be the number of distinct shard
classes needed by the compact metadata.  `W` must satisfy:

    1 <= W <= M <= 8

`mktsfs` constructs the compact logical metadata and chooses the smallest `W`
for which the required information fits in `W * 128` words under the V1.2
structural encoding and policy constraints.

Examples:

    one-member set, metadata <= 128 words:      W=1
    two-member set, metadata <= 128 words:      W=1, second member is replica capacity
    two-member set, metadata <= 256 words:      W=2
    four-member set, metadata <= 256 words:     W=2, two members are replica capacity
    eight-member set, metadata <= 384 words:    W=3, five members are replica capacity

If the compact metadata requires more shard classes than the set has members,
the requested optimized profile cannot be represented.  `mktsfs` must either
choose a less aggressive profile explicitly permitted by the caller or fail
the build.  It must not silently create a multi-block physical shard.

This gives the format a hard physical bound: one optimized metadata read from
one member never exceeds one block.

## 6. Split by function, not by byte range

The compact metadata must not be divided mechanically as words 0..127,
128..255, and so on.  Shard classes are semantic so common operations can
avoid unnecessary transfers.

The preferred ordering is:

### 6.1 Class A: namespace and routing

Class A contains enough information to perform pathname traversal and decide
which additional shard, if any, is needed.  It should include:

- compact directory topology;
- component names in packed variable-length SIXBIT storage;
- file type and immutable mode/owner information where it fits efficiently;
- file size or compact size class information;
- home member/home region or equivalent routing information;
- direct location information for simple files when that avoids an indirect
  metadata access;
- indexes needed to locate exceptional/multi-extent metadata in later classes.

LOOKUP, READDIR, PARENT and many STAT operations should normally need only A.

### 6.2 Class B: data mapping

Class B contains normal extent/data mapping information that does not fit
profitably in A.  Common extent records use implicit information aggressively:

- logical start is implied by the extent ordinal and fixed `0400`-word restart
  size;
- the local member is implicit where possible;
- the physical location is encoded relative to a nearby shard anchor;
- STORED/D6LZ is one bit;
- block count uses only the bits required by the bounded shape;
- the existing 36-bit integrity checksum is retained unless an equivalent
  hierarchical integrity design is separately proven.

The common extent target is two words: one packed location/shape word and one
checksum word.  A one-word extent is permitted only if integrity information
has been preserved elsewhere with equivalent detection guarantees.

### 6.3 Classes C..H: overflow and uncommon structure

Additional classes exist only when metadata cannot fit in A+B.  They contain
overflow names, unusual extent shapes, cross-member exceptions, additional
integrity information, or other infrequent data.  A must indicate whether a
later class is needed so the kernel does not transfer it speculatively unless
the placement/timing model says doing so is beneficial.

`mktsfs` should strongly prefer layouts in which boot-critical and commonly
used files resolve with A alone or A+B.

## 7. Relative physical location encoding

Absolute DECtape block numbers waste bits and ignore the placement guarantee.
V1.2 should encode local data positions as:

    direction bit + unsigned distance from the shard anchor

The magnitude is unsigned.  Forward/backward direction is explicit.  This is
simple on PDP-6 and avoids signed-distance corner cases.

The required magnitude width is determined by the maximum service radius of
the placement class.  For a 578-block DECtape, evenly partitioned regions give
approximately:

    2 stations/member: maximum local radius about 145 blocks -> 8 magnitude bits
    3 stations/member: maximum local radius about  97 blocks -> 7 magnitude bits
    4 stations/member: maximum local radius about  73 blocks -> 7 magnitude bits
    5 stations/member: maximum local radius about  58 blocks -> 6 magnitude bits
    6 stations/member: maximum local radius about  48 blocks -> 6 magnitude bits
    8 stations/member: maximum local radius about  36 blocks -> 6 magnitude bits

More replicas can therefore reduce both mechanical latency and metadata bit
cost.  This positive feedback must be included in the host-side optimizer.

The common local form omits the member number entirely.  Cross-member or
out-of-radius extents use a bounded escape representation containing an
explicit member and wider/absolute position.  The optimizer assigns a strong
cost to escape records so they remain uncommon.

## 8. Placement on one member

For one shard class on one tape, identical replicas that minimize worst-case
distance follow the one-dimensional minimax placement rule: divide the usable
tape into equal service regions and center a replica in each region, adjusted
for reserved blocks and the actual one-block shard extent.

Positions should be derived from a compact placement class rather than stored
as a resident list.  The descriptor/handoff needs only enough information to
reconstruct the chosen geometry, such as replica count and placement class.

## 9. Placement across several members

When `M > W`, surplus member capacity is used for replicas.  Replicas of the
same shard class must be staggered longitudinally rather than aligned at the
same block numbers.  Staggering produces a denser virtual set of service
points when the runtime may choose among transports.

Example for `M=4`, `W=2`:

    member 0: A replicas at phase 0
    member 1: B replicas at phase 0
    member 2: A replicas at phase 1/2
    member 3: B replicas at phase 1/2

A metadata operation may choose the nearest A from member 0 or 2 and the
nearest B from member 1 or 3 independently.  It is not bound to a fixed A/B
pair.

For `M=8`, `W=2`, an image may use four effective A carriers and four effective
B carriers, or a different weighted split when A is accessed substantially
more often than B.  Replica counts are therefore an optimization result, not a
fixed `M/W` rule.

## 10. Parallel seek model

DECtape transports can be useful in parallel even though the shared Type-136
data path cannot transfer from two units simultaneously.

For metadata requiring A+B, the desired operation is:

    choose nearest A replica
    choose nearest B replica
    start both transports positioning concurrently
    wait for both positions
    transfer A through Type-136
    transfer B through Type-136 only if A says B is required

Mechanical latency is therefore approximated by:

    max(seek_A, seek_B, ...)
      + transfer_A
      + transfer_B_if_needed
      + controller/switch overhead

not by the sum of all seek distances.

This is the principal reason the optimal layout depends on member count.

## 11. Current DTC limitation and required driver extension

The current DAIMOS DTC path serializes search and transfer with the global
`storage_state`.  `dtc_read_block()` refuses a new operation while another is
active, so V1.2 cannot yet overlap positioning requests even though per-unit
`dtc_motion[8]` state already exists.

V1.2 should not replace the Type-136 transfer serialization.  Instead the DTC
driver gains a small positioning interface separating mechanical motion from
data-channel ownership.  Conceptually:

    dtc_position(unit, target_block)
        start/continue search or prepositioning for one transport
        do not claim Type-136 for a block transfer

    dtc_position_status(unit)
        report reached/in-progress/error and update dtc_motion[unit]

    dtc_read_positioned(unit, block, dst)
        acquire the shared Type-136 transfer path
        transfer one block once the unit is positioned

The exact assembly ABI may differ, but the architecture must preserve:

- one small per-unit motion/position state;
- one global Type-136 transfer owner;
- ability for several Type-551 transports to be moving toward targets;
- no large per-request buffers;
- correct timeout/error accounting per unit;
- no global stop that unnecessarily destroys useful motion state on unrelated
  units except where the real controller semantics require it.

This DTC work is useful beyond TSFS because it removes the current assumption
that one tape's mechanical search makes every DECtape transport unavailable.

## 12. Speculative positioning

Class A is intentionally authoritative for deciding which later classes are
needed.  Nevertheless the runtime may preposition likely B/C replicas while A
is being sought or transferred.

For a common A+B operation:

1. choose A and probable B using current `dtc_motion` estimates;
2. start both seeks;
3. read A;
4. if A requires B, read the already positioned B;
5. otherwise leave B positioned for possible future use and avoid its block
   transfer.

Rare class C requests should not normally incur transfer cost, but the host
profile may justify speculative positioning when a known boot transition makes
C highly probable.

## 13. Host-side optimization problem

`mktsfs` owns all expensive layout choices.  The optimizer considers at least:

- member count `M`;
- candidate shard width `W`;
- compact metadata word counts per semantic class;
- replica count per class;
- longitudinal replica positions and phase offsets;
- file/data placement around metadata anchors;
- relative-distance bit width and escape-record count;
- tape-distance cost;
- reversal/turnaround cost;
- member-switch/controller cost;
- parallel seek cost using the maximum seek among concurrently positioned
  shards rather than the sum;
- expected transfer count per operation;
- boot/runtime transition weights from an external profile;
- capacity consumed by metadata replicas.

The optimizer should minimize a weighted objective combining runtime latency
and metadata size while obeying hard correctness and capacity constraints.
Because the filesystem is immutable, expensive dynamic programming,
branch-and-bound or other host-only search methods are acceptable.  Runtime
must not reproduce the optimizer.

For small images the builder should seek an exact optimum or prove a tight
bound where practical.  For larger images a deterministic bounded heuristic
may be used, but `mktsfs` must report the resulting measurable properties:

- chosen `W`;
- words used in every shard class;
- replicas per class;
- worst-case nearest-replica distance;
- expected weighted seek cost under the supplied profile;
- escape-record count;
- metadata capacity overhead per member.

## 14. Transition profiles

Workload knowledge must not be hard-coded into `mktsfs`.  The image build may
provide a separate transition/profile input.  A DAIMOS root profile can weight
the normal sequence, for example:

    INIT -> MOUNTALL -> FSTAB -> INITTAB -> LOGIN -> PASSWD -> DSH

The profile may also express access frequencies or probabilities for pathname
components and executable/data transitions.  `mktsfs` uses the profile to
choose file regions, shard replica weights and speculative positioning value.

Without a profile, `mktsfs` uses a deterministic generic objective emphasizing
worst-case metadata seek distance, low escape count and compact placement.

## 15. Integrity and recovery

Every optimized shard carries enough identity to reject a stale or unrelated
replica and has its own checksum.  Set ID, generation, class and replica/layout
identity must be validated before use.

On failure, the runtime tries another replica of the same required class,
preferably the next-lowest predicted latency.  If the optimized representation
cannot provide a complete valid metadata answer, the implementation falls back
to the canonical V1.1 metadata.

TSFS is read-only.  No in-place repair, replica synchronization or mutable
nearest-copy state is required.

## 16. Mount and boot handoff

The current mount ABI already reserves four TSFS-specific words in the 20-word
handoff, including one currently reserved word.  V1.2 should preserve the
syscall size and repack these words to describe:

- the logical-member to physical-DTC-unit map;
- V1.1/V1.2 runtime format selector;
- shard width `W`;
- compact placement/replica class parameters;
- canonical recovery locator as needed.

Exact bit allocation should be chosen only after the compact V1.2 encoder is
prototyped.  The design must prefer derived placement over resident location
arrays.

KINIT performs equivalent transient validation for a TSFS boot root and emits
the same compact runtime description.  KINIT code may grow modestly because it
is transient; permanent KCORE/MRES growth remains the stricter constraint.

## 17. Resident TSFS changes

The resident provider should remain mechanically simple.  Its new work is:

- decode the compact handoff;
- determine which shard class a metadata operation needs;
- choose the lowest-cost replica using `dtc_motion` and the derived placement;
- request prepositioning of multiple units when useful;
- transfer the required one-block shards through the shared Type-136 path;
- decode compact namespace/extent records into existing scratch workspace;
- fall back to another replica or canonical metadata on error.

LOOKUP, READDIR, STAT, PARENT, file reads, VFS semantics and D6LZ payload
decoding should otherwise remain structurally unchanged.

No permanent 256/384-word metadata buffer should be introduced.  Decoding must
operate from the existing block workspace or similarly bounded transient
storage.

## 18. Tool and component responsibilities

### `DAIMOS/tools/host/mktsfs`

Major changes:

- V1.2 compact semantic encoder;
- adaptive shard-width selection;
- relative-location and escape encoding;
- replica-count optimizer;
- staggered one-dimensional placement;
- multi-member parallel-seek cost model;
- data-region layout optimizer;
- optional external transition profile;
- V1.1 canonical metadata generation retained.

### `DAIMOS/tools/host/tsfscheck`

Major changes:

- validate every shard identity/checksum;
- decode V1.2 and compare it logically with canonical V1.1 metadata;
- verify derived placement and non-overlap;
- verify all local relative distances are representable;
- verify escape records and cross-member mappings;
- verify every required shard class has sufficient valid replica coverage;
- report chosen layout/cost properties.

### Userspace `MOUNT.TSFS` / scanner

Moderate changes:

- recognize V1.2 descriptors;
- validate the optimized metadata structure transiently;
- discover all eight possible members;
- construct the compact runtime handoff without retaining metadata tables.

### KINIT TSFS boot scanner

Moderate transient changes equivalent to the userspace scanner.

### DTC driver

Small but important architectural change: separate concurrent mechanical
prepositioning from serialized Type-136 block transfer.

### Resident TSFS provider

Small change relative to host tooling: shard selection, bounded decoding and
fallback.

### VFS and syscall surface

No semantic change and no mount-syscall size increase expected.

## 19. Recommended implementation order

Implementation should proceed in this order so the on-media format is derived
from measured packing rather than guesswork:

1. Add a host-only prototype compact encoder for the current root metadata.
2. Measure exact class A/B/C word counts and prove the minimum feasible `W`
   for 1..8 members.
3. Implement the one-block shard format and decoder in DAIMOS `tools/host` only.
4. Extend `tsfscheck` and require logical equivalence with V1.1 metadata.
5. Implement relative-distance encoding and the escape format.
6. Implement single-member longitudinal replica placement and measure seek
   bounds.
7. Implement multi-member staggered replica optimization using the parallel
   seek `max()` cost model.
8. Add transition-profile support and data placement optimization.
9. Extend userspace `MOUNT.TSFS` validation/handoff.
10. Extend KINIT boot-root validation/handoff.
11. Add DTC preposition/search-only support with per-unit state while retaining
    one global Type-136 transfer owner.
12. Add resident nearest-shard selection and compact decoding.
13. Test 1-, 2-, 3-, 4- and 8-member sets under SIMH and AAP, including damaged
    replicas, reversals, simultaneous positioning and canonical fallback.
14. Measure AAP boot/login latency against V1.1 before making V1.2 the default
    root-image format.

## 20. Acceptance criteria

V1.2 is complete when all of the following hold:

- one through eight members are supported;
- every optimized metadata shard is exactly one physical DECtape block;
- the builder selects `W` from actual packed metadata and available members;
- surplus members are used as staggered replica capacity where beneficial;
- multi-shard positioning can proceed concurrently on independent transports;
- actual Type-136 transfers remain correctly serialized;
- common pathname operations avoid unnecessary B/C shard transfers;
- current-root optimized metadata fits the measured shard plan produced by the
  prototype, with no undocumented size assumption;
- corrupted optimized shards fall back to replicas/canonical metadata;
- V1.1 media remains readable;
- no large permanent metadata buffer is added to the kernel;
- `mktsfs` and `tsfscheck` report enough layout metrics to compare optimizer
  changes objectively;
- SIMH and AAP boot-root regression tests pass;
- AAP demonstrates a material reduction in boot/login seek latency versus V1.1.


## 21. TSFS-root resident module profile (2026-10-12)

It never installs D6FS, even if Type-270 disk or Type-236 drum hardware is

### Relocated from `DAIMOS/design/tsfs-value-record-lease-cost-20261026-v429.md`

# Proposal B v429: value-returning TSFS record lease cost gate

Status: read-only source and testkit analysis PASS; no kernel change or
memory saving accepted.

`tsfs_file_record` returns a pointer into the shared 128-word transfer
workspace, using 16 eight-word records/block. `tsfs_extent_record`
returns a four-word record, 32/block. `tsfs_parent_common` passes the
file record pointer to the parent-name consumer. `tsfs_readdir` reads
a parent record and then fetches a child record, so the first pointer
cannot be assumed valid after the second read. The compressed-word
path also consumes data from `fs_block_workspace` in its decoder.

The proposed value-returning API therefore needs at least eight
additional words of per-call storage per copied file record, or four
per copied extent record, beyond saved registers and call linkage.
Copying only a projected subset may cost fewer words, but requires
per-operation ABI analysis and cannot simply replace the existing
record pointer with an unowned address. Meanwhile sleeping physical
I/O still needs buffer ownership until completion, independent of how
later metadata is represented. A blanket value-copy transformation
does not itself remove the global provider lock and is NOT accepted
without an end-to-end total-RAM reduction.

New `daimos-testkit` guard
`tests/validation/daimos-tsfs-record-lease-v429.py` PASS: verifies
record widths, workspace pointer lifetime, parent/readdir consumers,
and D6LZ input dependence. This is a source-level contract guard,
not a real multi-process race test.

Next action: find an operation-specific projection that is already
copied to a caller-owned result (e.g., stat/name), calculate its full
resident and stack impact, and benchmark a reversible implementation
*with* ownership shortening. Reject code growth without a proven
runtime benefit. Global provider locking remains mandatory.

Reference full linked image: KCORE 8995, KCORE+MRES 15543,
PERMANENT_LAST 15590. Strict 32K acceptance is deferred.
