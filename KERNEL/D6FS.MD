# DAIMOS D6FS V2 TECHNICAL SPECIFICATION

*COMPACT STRIPED-DISKSET FILESYSTEM FOR PDP-6 THROUGH KL10-CLASS DAIMOS*

## DOCUMENT METADATA

- STATUS: DESIGN FREEZE
- DATE: 2026-08-29
- SCOPE: D6FS CORE FORMAT AND SEMANTICS
- ENCODING: PLAIN ASCII; ALL ON-DISK WORDS ARE 36-BIT PDP-10 WORDS

## 1. PURPOSE

D6FS IS THE NATIVE DAIMOS DISK FILESYSTEM.  V2 DELIBERATELY REMOVES STORAGE
POLICY THAT DOES NOT BELONG IN THE FILESYSTEM WHILE RETAINING THE FEATURES THAT
ARE USEFUL ON PDP-6/KA10 SYSTEMS AND DO NOT MAKE THE FORMAT FRAGILE.

D6FS IS:

- HIERARCHICAL;
- EXTENT BASED;
- UNIX-PERMISSIONED;
- DESIGNED OVER A STRIPED DAIMOS DISKSET;
- RECOVERED BY FSCK AFTER AN UNCLEAN SHUTDOWN;
- SMALL ENOUGH FOR A 64KW PDP-6 KERNEL;
- LARGE ENOUGH IN FORMAT FOR PRACTICAL KL10 DISKSETS.

D6FS IS NOT A RAID IMPLEMENTATION, JOURNALED FILESYSTEM, SNAPSHOT SYSTEM,
OVERLAY FILESYSTEM, OR GENERAL STORAGE-POLICY ENGINE.

## 2. FROZEN SIMPLIFICATIONS

THE FOLLOWING OLD D6FS/P6SYS FEATURES ARE REMOVED FROM D6FS V2:

- CONFIGFS / CFGSTORE INTEGRATION;
- HOT/COLD/SYSREAD/WORK ARENAS;
- HEAT TRACKING AND HEAT PROMOTION;
- SPILL POLICY;
- FSUNDO / METADATA INTENT LOG;
- METADATA CHECKSUMS;
- CONTINUATION FCBS;
- SEALED IMAGES;
- OVERLAYS, COPY-UP, WHITEOUTS, AND OPAQUE DIRECTORIES;
- D6FS VIEW COMPOSITION;
- ONLINE PACK LEVELS AND PACK_NEEDED STATE;
- D6FS-OWNED SWAP, BOOTSTREAM, OR LOGSTORE ALLOCATION.

CONFIGURATION IS A HIGHER-LEVEL OR SYNTHETIC-NAMESPACE CONCERN.

BOOTSTREAM, SWAP, AND LOGSTORE ARE RESERVED DISKSET REGIONS.  THEY ARE NOT
D6FS ALLOCATION ARENAS OR D6FS SYSTEM OBJECTS.

## 3. WORD AND BLOCK CONVENTIONS

ALL D6FS WORDS ARE 36 BITS.

BIT NUMBERING:

    BIT 0   MOST SIGNIFICANT
    BIT 35  LEAST SIGNIFICANT
    LH      BITS 0..17
    RH      BITS 18..35

ONE D6FS BLOCK IS 128 36-BIT WORDS.

D6FS ADDRESSES BLOCKS IN ONE LINEAR LOGICAL DISKSET ADDRESS SPACE.  PHYSICAL
MEMBER NUMBER, CYLINDER, TRACK, AND SECTOR ARE NOT STORED IN FCBS OR EXTENTS.
THE DISKSET/DRIVER LAYER MAPS LOGICAL BLOCKS TO PHYSICAL MEMBERS.

## 4. DISKSETS

### 4.1 MEMBER COUNT

A DAIMOS D6FS DISKSET CONTAINS 1 THROUGH 8 MEMBERS.

THE LIMIT OF EIGHT IS INTENTIONAL:

- PURE STRIPING MEANS ANY MISSING MEMBER BREAKS THE FILESYSTEM;
- LARGE MEMBER COUNTS THEREFORE REDUCE PRACTICAL RELIABILITY;
- EIGHT IS LARGE ENOUGH FOR SERIOUS KL10-CLASS MASSBUS CONFIGURATIONS;
- THE CURRENT BOOT DESCRIPTOR ALREADY HAS SUFFICIENT MEMBER MASK/COUNT SPACE.

THE FORMAT MUST NOT RESERVE RAM FOR EIGHT MEMBERS WHEN FEWER ARE PRESENT.

### 4.2 LAYOUT

THE ONLY D6FS DISKSET DATA LAYOUT IS STRIPING.

THERE IS NO CONCATENATED, MIRRORED, PARITY, OR ALTERNATE RAID-LIKE LAYOUT.

THE NORMAL STRIPE UNIT IS ONE 128-WORD D6FS BLOCK UNLESS A DEVICE-SPECIFIC
BOOT REGION DEFINES A DIFFERENT PRE-D6FS UNIT.

### 4.3 UNEQUAL MEMBER SIZES

DISKS MAY HAVE UNEQUAL USABLE SIZES.

CAPACITY IS NOT TRUNCATED TO THE SHORTEST MEMBER.  THE DISKSET LAYER USES
SHRINKING-WIDTH STRIPE ZONES DERIVED FROM MEMBER SIZES.

EXAMPLE FOR MEMBERS WITH 1000, 1500, AND 2000 USABLE BLOCKS:

    ZONE 0  MEMBER DEPTH    0..999     WIDTH 3: A B C
    ZONE 1  MEMBER DEPTH 1000..1499    WIDTH 2:   B C
    ZONE 2  MEMBER DEPTH 1500..1999    WIDTH 1:     C

TOTAL LOGICAL CAPACITY IS THE SUM OF USABLE MEMBER CAPACITIES.

FOR N MEMBERS THERE ARE AT MOST N STRIPE ZONES.  THE ZONE TABLE IS DERIVED AT
DISKSET ASSEMBLY TIME AND NEED NOT BE STORED IN EACH D6FS METADATA OBJECT.

### 4.4 FAILURE SEMANTICS

IF ANY REQUIRED MEMBER IS MISSING, HAS THE WRONG DISKSET IDENTITY, OR DOES NOT
MATCH THE ACCEPTED DISKSET GENERATION/MEMBERSHIP DESCRIPTION, THE DISKSET IS
BROKEN.

NORMAL D6FS MOUNT MUST FAIL.  THERE IS NO DEGRADED MODE.

OFFLINE RECOVERY TOOLS MAY OPEN MEMBERS INDIVIDUALLY.

### 4.5 BOOT KNOWLEDGE

THE EXISTING DAIMOS BOOT MODEL IS PRESERVED: STAGE1 ALREADY KNOWS AND VALIDATES
THE COMPLETE DISKSET BEFORE LOADING THE STRIPED BOOTSTREAM.  D6FS DOES NOT
INTRODUCE A SECOND DISKSET-DISCOVERY MECHANISM.

## 5. LOGICAL ADDRESS AND SIZE LIMIT

D6FS V2 USES A 24-BIT LOGICAL BLOCK ADDRESS.

MAXIMUM LOGICAL D6FS ADDRESS SPACE:

    2^24 BLOCKS
    2^31 36-BIT WORDS

THIS IS APPROXIMATELY 9.66 GB WHEN A 36-BIT WORD IS COUNTED AS 4.5 BYTES.

THIS LIMIT IS INTENDED TO COVER LARGE PRACTICAL KL10-CLASS DISKSETS WITHOUT
MAKING EVERY EXTENT OR METADATA POINTER MULTIWORD.

## 6. OBJECT TYPES

D6FS V2 HAS THREE ORDINARY OBJECT TYPES:

    REGULAR FILE
    DIRECTORY
    SYMBOLIC LINK

THERE ARE NO HARD LINKS.

THERE ARE NO DEVICE NODES IN ORDINARY D6FS.

SYMLINK CONTENT IS STORED THROUGH THE SAME EXTENT-BACKED DATA PATH AS REGULAR
FILE CONTENT.  V2 HAS NO INLINE/FAST SYMLINK REPRESENTATION.

## 7. NAMES

D6FS V2 NAMES ARE SIXBIT AND AT MOST 24 CHARACTERS.

A DIRECTORY ENTRY STORES THE COMPLETE NAME, A COMPACT HASH, THE CHILD FCB, AND
A CACHED OBJECT TYPE.  THE HASH AND CACHED TYPE ARE ACCELERATORS ONLY.  THE
FCB AND FULL NAME ARE AUTHORITATIVE.

HASH MATCH MUST ALWAYS BE FOLLOWED BY FULL NAME COMPARISON.

## 8. UNIX OWNERSHIP AND PERMISSIONS

D6FS USES SIMPLE UNIX-LIKE OWNERSHIP AND MODE SEMANTICS:

    UID
    GID
    RWX MODE BITS

D6FS V2 DOES NOT IMPLEMENT ACLS, PROJECT PROTECTION WORDS, CAPABILITIES, OR
SEPARATE DELETE/CONTROL PROTECTION CLASSES.

## 9. PERSISTENT FILE FLAGS

THE V2 FLAG SET IS:

    APPEND      CONTENT MAY ONLY BE EXTENDED AT EOF
    NOUNLINK    ORDINARY UNLINK/RENAME-AWAY IS FORBIDDEN
    NODUMP      BACKUP/DUMP TOOLS SHOULD OMIT THE OBJECT
    ARCHIVE     OBJECT IS MARKED FOR ARCHIVAL POLICY/TOOLS
    IMMUTABLE   CONTENT AND METADATA ARE FROZEN
    HIDDEN      OMIT FROM NORMAL NON-ALL DIRECTORY LISTINGS
    SYSTEM      RESERVED FOR SYSTEM-MANAGED OBJECT POLICY

UNUSED FLAG BITS MUST BE ZERO ON CREATION AND PRESERVED/IGNORED WHEN READING A
NEWER COMPATIBLE FORMAT.

APPEND IS A PERSISTENT ATTRIBUTE AND IS DISTINCT FROM PER-OPEN O_APPEND.
APPEND RESTRICTS CONTENT UPDATES, NOT NAMESPACE OPERATIONS.  NOUNLINK OR
IMMUTABLE PROVIDE NAMESPACE PROTECTION.

IMMUTABLE FORBIDS ORDINARY WRITE, TRUNCATE, CHMOD/CHOWN, RENAME, AND UNLINK.
CLEARING IMMUTABLE OR NOUNLINK REQUIRES AN EXPLICIT PRIVILEGED OPERATION.

ARCHIVE IS A POLICY MARKER.  D6FS ITSELF DOES NOT AUTOMATICALLY REWRITE IT ON
EVERY FILE WRITE.

## 10. TIMESTAMPS

D6FS V2 STORES MTIME ONLY.

THERE IS NO ATIME AND NO CTIME.

## 11. FCB IDENTITY

AN FCB NUMBER IS THE ON-DISK OBJECT ID WITHIN ONE MOUNTED D6FS.

D6FS V2 HAS NO FCB GENERATION NUMBER.

STALE RUNTIME REFERENCES ARE INVALIDATED BY MOUNT/VNODE LIFETIME RULES.  THEY
ARE NOT MADE PERSISTENT IN THE ON-DISK FORMAT.

EACH NON-ROOT OBJECT HAS EXACTLY ONE PARENT DIRECTORY BECAUSE HARD LINKS DO NOT
EXIST.  THE FCB STORES ITS PARENT FCB NUMBER.

## 12. EXTENTS

### 12.1 FIXED INLINE EXTENTS

EACH FCB HAS EXACTLY SEVEN INLINE EXTENT SLOTS.

THERE ARE NO CONTINUATION FCBS AND NO INDIRECT EXTENT BLOCKS.

AN UNUSED EXTENT SLOT IS ZERO AND MUST FOLLOW ALL USED SLOTS.

### 12.2 EXTENT WORD

EACH OF THE SEVEN EXTENT WORDS IS:

    BITS  0..23   START24
    BITS 24..35   LENLOW12

START24 IS THE LOGICAL D6FS START BLOCK.

LENGTH IS STORED AS COUNT-1.

### 12.3 SHARED EXTENT LENGTH-HIGH WORD

ONE ADDITIONAL FCB WORD STORES FIVE HIGH LENGTH BITS FOR EACH EXTENT:

    BITS  0..4    EXTENT 0 LENHIGH5
    BITS  5..9    EXTENT 1 LENHIGH5
    BITS 10..14   EXTENT 2 LENHIGH5
    BITS 15..19   EXTENT 3 LENHIGH5
    BITS 20..24   EXTENT 4 LENHIGH5
    BITS 25..29   EXTENT 5 LENHIGH5
    BITS 30..34   EXTENT 6 LENHIGH5
    BIT      35   RESERVED, ZERO IN V2

FOR A USED EXTENT:

    COUNT_MINUS_1 = (LENHIGH5 << 12) | LENLOW12
    LENGTH_BLOCKS = COUNT_MINUS_1 + 1

MAXIMUM EXTENT LENGTH IS 131072 BLOCKS = 16 MEGAWORDS.

SEVEN MAXIMUM EXTENTS DESCRIBE UP TO 112 MEGAWORDS OF FILE DATA.

A ZERO EXTENT SLOT IS IDENTIFIED BY THE FCB'S EXTENT COUNT/ORDER, NOT BY
INTERPRETING START=0/LEN=0 AS AN ALLOCATED ONE-BLOCK EXTENT.

### 12.4 EXTENT ALLOCATION RULE

ON GROWTH:

1. EXTEND THE LAST EXTENT CONTIGUOUSLY WHEN POSSIBLE.
2. OTHERWISE ALLOCATE A NEW CONTIGUOUS EXTENT.
3. IF ALL SEVEN EXTENTS ARE IN USE AND CONTIGUOUS EXTENSION IS IMPOSSIBLE,
   RETURN ENOSPC EVEN IF FRAGMENTED FREE SPACE EXISTS.
4. OFFLINE PACKFS MAY DEFRAGMENT/RELOCATE THE FILE.

THIS DELIBERATELY TRADES A RARE FRAGMENTATION LIMIT FOR A MUCH SMALLER KERNEL
AND FORMAT.

## 13. FCB FORMAT

D6FS V2 USES A FIXED 16-WORD FCB.  THE FORMAT IS DESIGNED TO FIT ALL CORE
METADATA AND SEVEN LARGE INLINE EXTENTS WITHOUT CONTINUATIONS.

    WORD 00  TYPE3 | FLAGS9 | MODE12 | TAIL4 | EXTENT_COUNT4 | RESERVED4
    WORD 01  UID18 | GID18
    WORD 02  SIZE_WORDS36
    WORD 03  MTIME36
    WORD 04  PARENT_FCB18 | RESERVED18
    WORD 05  EXTENT_LENGTH_HIGH WORD
    WORD 06  EXTENT 0
    WORD 07  EXTENT 1
    WORD 10  EXTENT 2
    WORD 11  EXTENT 3
    WORD 12  EXTENT 4
    WORD 13  EXTENT 5
    WORD 14  EXTENT 6
    WORD 15  RESERVED36
    WORD 16  RESERVED36
    WORD 17  RESERVED36

WORD NUMBERS ABOVE ARE OCTAL.

TYPE3 VALUES ARE RESERVED FOR REGULAR, DIRECTORY, AND SYMLINK PLUS FUTURE
COMPATIBLE TYPES.

TAIL4 RECORDS THE NUMBER OF VALID 9-BIT BYTES IN THE FINAL 36-BIT WORD FOR
BYTE-STREAM INTERPRETATION.  ZERO MEANS THE FILE ENDS ON A WORD BOUNDARY OR IS
EMPTY; THE BYTE-STREAM LAYER DEFINES THE PRECISE ZERO/FOUR-BYTE RULE FROM
SIZE_WORDS.

THE THREE RESERVED WORDS ARE INTENTIONAL FORMAT HEADROOM.  THEY MUST BE ZERO
WHEN CREATING A V2 FCB AND IGNORED/PRESERVED WHERE REQUIRED FOR COMPATIBLE
FUTURE EXTENSIONS.

THERE IS NO FCB CHECKSUM, GENERATION, CTIME, HEAT, ARENA, SPILL, ROLE, OR
CONTINUATION POINTER.

## 14. DIRECTORY ENTRY FORMAT

D6FS V2 USES A FIXED SIX-WORD DIRECTORY ENTRY:

    WORD 0  NAME SIXBIT CHARACTERS 1..6
    WORD 1  NAME SIXBIT CHARACTERS 7..12
    WORD 2  NAME SIXBIT CHARACTERS 13..18
    WORD 3  NAME SIXBIT CHARACTERS 19..24
    WORD 4  HASH24 | TYPE3 | FLAGS9
    WORD 5  CHILD_FCB18 | RESERVED18

DIRECTORY-ENTRY FLAGS ARE ENTRY-LOCAL FORMAT FLAGS ONLY; THEY ARE NOT A SECOND
COPY OF THE FCB'S PERSISTENT FILE FLAGS.

AN EMPTY ENTRY HAS CHILD_FCB ZERO AND ZERO NAME WORDS.

THE PARENT IS IMPLICIT IN THE DIRECTORY CONTAINING THE ENTRY; THE CHILD FCB
STORES ITS PARENT EXPLICITLY FOR '..', FSCK, AND RENAME VALIDATION.

DIRECTORY ENTRIES HAVE NO GENERATION NUMBER.

## 15. FREE SPACE MAP

### 15.1 AUTHORITATIVE BITMAP

THE AUTHORITATIVE FREE MAP IS ONE BIT PER LOGICAL D6FS BLOCK.

    0 = ALLOCATED/RESERVED
    1 = FREE

FSCK MAY REBUILD IT FROM THE RESERVED METADATA RANGES AND ALL VALID FCB
EXTENTS.

### 15.2 COMPACT SUMMARY

D6FS V2 ADDS A VERY COMPACT SUMMARY:

    ONE SUMMARY BIT PER 128-WORD FREE-MAP BLOCK

A SUMMARY BIT MEANS:

    1 = THE CORRESPONDING BITMAP BLOCK CONTAINS AT LEAST ONE FREE BLOCK
    0 = THE CORRESPONDING BITMAP BLOCK IS FULLY ALLOCATED

ONE FREE-MAP BLOCK CONTAINS 4608 ALLOCATION BITS, SO ONE SUMMARY BIT COVERS
4608 D6FS BLOCKS.

AT THE 2^24-BLOCK MAXIMUM FILESYSTEM SIZE THE ENTIRE SUMMARY IS ABOUT 3641
BITS, OR ABOUT 102 36-BIT WORDS.

THE SUMMARY IS AN ACCELERATOR, NOT THE AUTHORITY.  FSCK MAY REBUILD IT FROM
THE FREE MAP.

### 15.3 BOUNDED ALLOCATION LOOKAHEAD

THE KERNEL DOES NOT NEED TO KEEP THE WHOLE FREE MAP RESIDENT.

MOUNT STATE KEEPS:

- AN ALLOCATION CURSOR;
- THE CURRENT SUMMARY WINDOW/BLOCK;
- THE CURRENT FREE-MAP WINDOW/BLOCK.

ALLOCATION PROCEDURE:

1. TRY TO EXTEND THE FILE'S LAST EXTENT.
2. START NEAR THE FILE/ALLOCATION CURSOR.
3. USE SUMMARY BITS TO SKIP FULL FREE-MAP BLOCKS.
4. LOAD A CANDIDATE BITMAP BLOCK.
5. FIND THE LONGEST USEFUL CONTIGUOUS FREE RUN.
6. ALLOCATE IT AND ADVANCE THE CURSOR.

THIS BORROWS THE BOUNDED LOOKAHEAD PRINCIPLE FROM SMALL EMBEDDED FILESYSTEMS
WITHOUT COPYING FLASH-SPECIFIC COW/CRC/WEAR-LEVELING MACHINERY.

## 16. SUPERBLOCKS AND DIRTY STATE

D6FS V2 KEEPS TWO SUPERBLOCK COPIES, A AND B.

THERE ARE NO SUPERBLOCK OR METADATA CHECKSUMS.

EACH COPY CONTAINS AT LEAST:

- D6FS MAGIC AND FORMAT VERSION;
- FILESYSTEM UUID;
- DISKSET UUID/IDENTITY BINDING;
- SUPERBLOCK SEQUENCE NUMBER;
- CLEAN/DIRTY STATE;
- LOGICAL FILESYSTEM BLOCK COUNT;
- ROOT FCB;
- FCB TABLE LOCATION/SIZE;
- FREE MAP LOCATION/SIZE;
- FREE-MAP SUMMARY LOCATION/SIZE;
- RESERVED FORMAT FIELDS.

ON MOUNT, BOTH COPIES ARE STRUCTURALLY VALIDATED.  THE HIGHEST-SEQUENCE VALID
COPY IS AUTHORITATIVE.

WRITABLE MOUNT:

1. WRITE/FLUSH A NEW DIRTY SUPERBLOCK GENERATION.
2. BEGIN NORMAL WRITES.

CLEAN UNMOUNT:

1. FLUSH FILE DATA.
2. FLUSH DIRECTORY/FCB/FREE-MAP METADATA.
3. FLUSH DEVICE CACHE/QUEUE AS REQUIRED.
4. WRITE/FLUSH A NEW CLEAN SUPERBLOCK GENERATION.

AFTER AN UNCLEAN SHUTDOWN A STRUCTURALLY SANE FILESYSTEM MAY BE MOUNTED
READ-ONLY.  WRITABLE MOUNT REQUIRES FSCK.

THERE IS NO FSUNDO OR INTENT LOG.

## 17. ORDERED METADATA WRITES

THE ABSENCE OF A JOURNAL DOES NOT MEAN RANDOM WRITE ORDER.

MUTATIONS MUST BE ORDERED SO A CRASH PREFERABLY CREATES A RECOVERABLE LEAK
RATHER THAN A LIVE REFERENCE TO UNINITIALIZED OR FREE STORAGE.

FOR EXAMPLE, WHEN ADDING A NEW EXTENT:

1. ALLOCATE THE FREE-MAP BITS IN MEMORY.
2. WRITE THE COMPLETE NEW DATA BLOCKS.
3. PERSIST THE ALLOCATION STATE.
4. PERSIST THE FCB EXTENT/SIZE UPDATE.

CREATE/RENAME/UNLINK MUST USE SIMILAR RECOVERABLE ORDERING AND FSCK MUST KNOW
THE POSSIBLE INTERMEDIATE STATES.

## 18. CACHES

### 18.1 BLOCK CACHE

D6FS RETAINS A WRITEBACK BLOCK CACHE.

SUPPORTED CONFIGURATIONS SHOULD INCLUDE 2, 4, 8, AND 16 128-WORD BLOCKS.
THE PDP-6 DEFAULT MUST BE SELECTED BY BENCHMARKING; 4 OR 8 IS THE EXPECTED
USEFUL RANGE.

USE A COMPACT CLOCK/SECOND-CHANCE OR EQUIVALENT APPROXIMATE-LRU REPLACEMENT
POLICY.  DO NOT SPEND RAM ON LARGE TIMESTAMPS OR ELABORATE LRU LISTS.

### 18.2 LOOKUP CACHE

D6FS/VFS RETAINS A SMALL PATH COMPONENT LOOKUP CACHE.

INITIAL TARGET: 16 ENTRIES, APPROXIMATELY TWO WORDS EACH:

    WORD 0  PARENT_FCB18 | CHILD_FCB18
    WORD 1  HASH24 | STATE/AGE12

FULL NAME VALIDATION IS STILL REQUIRED WHEN NEEDED TO AVOID HASH ALIASING.

### 18.3 NO EXTENT CACHE

THERE IS NO SEPARATE EXTENT CACHE.  THE SEVEN EXTENTS ARE ALREADY PART OF THE
FCB/VNODE METADATA.

## 19. STATISTICS

D6FS RETAINS SMALL GLOBAL MONOTONIC COUNTERS BECAUSE THEY ARE NECESSARY TO
MEASURE WHETHER CACHE AND ALLOCATION OPTIMIZATIONS HELP.

ALWAYS-ON TARGET COUNTERS:

    PHYSICAL_READS
    PHYSICAL_WRITES
    IO_ERRORS
    BLOCK_CACHE_HITS
    BLOCK_CACHE_MISSES
    BLOCK_CACHE_WRITEBACKS
    LOOKUP_CACHE_HITS
    LOOKUP_CACHE_MISSES
    EXTENT_EXTENSIONS
    NEW_EXTENTS
    ALLOCATION_FAILURES

PERFORMANCE/DIAGNOSTIC BUILDS MAY ADD:

    DISK_REQUESTS_QUEUED
    SEEK_WRAPS
    SEEK_DISTANCE
    DIRECTORY_ENTRIES_EXAMINED
    HASH_REJECTS
    FULL_NAME_COMPARES
    FREEMAP_SUMMARY_SKIPS
    FREEMAP_BLOCKS_SCANNED
    CACHE_EVICTIONS

NO PER-FILE COUNTERS, HISTOGRAMS, OR RESIDENT TEXT RENDERING ARE REQUIRED.

## 20. FILE LOCKING

WHOLE-FILE ADVISORY LOCKING IS KEPT.

LOCK TYPES:

    SHARED
    EXCLUSIVE
    UNLOCK

LOCKS ARE RUNTIME VFS/OPEN-FILE STATE.  NOTHING IS STORED ON DISK.

LOCKS BELONG TO THE OPEN-FILE OBJECT; DUPLICATED DESCRIPTORS SHARE THE LOCK,
AND THE LAST CLOSE RELEASES IT.  PROCESS EXIT RELEASES LOCKS THROUGH NORMAL
DESCRIPTOR CLOSURE.

D6FS V2 HAS NO BYTE-RANGE OR MANDATORY LOCKS.

## 21. OPEN-UNLINK AND RENAME

OPEN-UNLINK SEMANTICS ARE IMPLEMENTED BY VFS/VNODE LIFETIME STATE.

BECAUSE THERE ARE NO HARD LINKS, ON-DISK REFERENCE ACCOUNTING IS SIMPLE.
AN UNCLEAN SHUTDOWN MAY LEAVE AN ORPHAN FCB/EXTENTS; FSCK RECLAIMS THEM.

RENAME MUST PRESERVE THE SINGLE-PARENT INVARIANT AND UPDATE THE CHILD FCB'S
PARENT FIELD WHEN MOVING ACROSS DIRECTORIES.

## 22. RESERVED DISKSET REGIONS

BOOTSTREAM, SWAP, AND LOGSTORE ARE DISKSET REGIONS OUTSIDE D6FS ALLOCATION.
THEY ARE STRIPED USING THE SAME DISKSET MEMBER MAPPING.

### 22.1 BOOTSTREAM

BOOTSTREAM IS PLACED LOW IN THE DISKSET, AFTER THE REQUIRED BOOT/DISKSET
DESCRIPTOR AREA.

THE BOOT LOADER ALREADY KNOWS THE COMPLETE DISKSET AND ITS MEMBER-LOCAL
BOOTSTREAM CONTRIBUTIONS.  THIS BEHAVIOR IS PRESERVED.

D6FS EXPOSES BOOTSTREAM AS A HIDDEN READ-ONLY FILE USING THE ORDINARY READ
PATH.  ITS FCB IS SYSTEM-MANAGED, HIDDEN, IMMUTABLE, AND PINNED TO THE
BOOTSTREAM RESERVED EXTENT DESCRIBED BY THE DISKSET/BOOT METADATA.  NORMAL D6FS
WRITE/TRUNCATE/UNLINK/RENAME MUST NOT MODIFY IT.  RAW DEVICE ACCESS, DD, OR
SPECIAL INSTALL/BOOT TOOLS MAY REPLACE ITS CONTENTS.

THE BOOTSTREAM EXTENT IS RESERVED BEFORE D6FS ALLOCATION AND IS NEVER RETURNED
AS FREE SPACE.  APART FROM THAT PINNING RULE, BOOTSTREAM READS USE THE ORDINARY
D6FS FILE/EXTENT PATH.

### 22.2 SWAP

SWAP IS PLACED HIGH IN THE DISKSET AND IS STRIPED.

DEFAULT/UPPER V1 TARGET SIZE:

    512 KILOWORDS = 4096 D6FS BLOCKS

MKSWAP/MKFS TOOLS MUST ALLOW A SMALLER SIZE, INCLUDING ZERO WHEN NO SWAP IS
WANTED.  THE EXACT COMMAND SPELLING IS A TOOL INTERFACE DECISION; THE FORMAT
RECORDS THE RESERVED RANGE.

SWAP IS NOT A D6FS FILE OR FCB.

### 22.3 LOGSTORE

LOGSTORE IS THE HIGHEST-PLACED RESERVED DISKSET REGION AND IS STRIPED.

DEFAULT SIZE:

    32 KILOWORDS = 256 D6FS BLOCKS

THE SIZE IS FORMATTER/MAINTENANCE-TOOL CONFIGURABLE AND MAY BE RESIZED OFFLINE.

LOGSTORE IS A SMALL INDEPENDENT CIRCULAR BINARY EVENT STORE.  D6FS DOES NOT
ALLOCATE, JOURNAL, CHECKSUM, OR INTERPRET IT.

THE DETAILED LOGSTORE RECORD FORMAT IS A SEPARATE SPECIFICATION.

### 22.4 HIGH-END ORDER

THE DEFAULT HIGH-END ORDER IS:

    ... D6FS ... | SWAP | LOGSTORE | END OF DISKSET

RESIZING SWAP OR LOGSTORE IS AN OFFLINE LAYOUT OPERATION.  IF D6FS OCCUPIES
BLOCKS NEEDED BY A NEW BOUNDARY, PACKFS/RESIZE TOOLS MUST MOVE THEM FIRST.

## 23. PACKFS

PACKFS IS NO LONGER A HEAT/ARENA/ONLINE POLICY ENGINE.

IT IS AN OFFLINE DEFRAGMENTER AND COMPACTOR.

PACKFS SHOULD:

1. MOVE EACH MOVABLE FILE TOWARD FEWER/LARGER CONTIGUOUS EXTENTS;
2. PREFER ONE EXTENT WHEN PRACTICAL;
3. COMPACT DIRECTORY STORAGE WHERE USEFUL;
4. COALESCE FREE SPACE;
5. REBUILD/VERIFY THE FREE-MAP SUMMARY;
6. LEAVE BOOTSTREAM, SWAP, LOGSTORE, BAD/RESERVED BLOCKS, AND OTHER PINNED
   DISKSET REGIONS UNTOUCHED;
7. FINISH WITH FILESYSTEM VALIDATION.

PACKFS RUNS ON AN UNMOUNTED OR MAINTENANCE-READ-ONLY FILESYSTEM.  D6FS V2 HAS
NO ONLINE PACKER.

HOST/OFFLINE PACKFS IMPLEMENTATION BELONGS IN PDP10-TOOLS.  A TARGET
MAINTENANCE FRONT END MAY REUSE THE SAME FORMAT RULES.

## 24. BAD BLOCKS

BAD PHYSICAL MEDIA IS A DISKSET/DEVICE-LAYER CONCERN.

D6FS SEES ONLY LOGICAL BLOCKS THAT THE DISKSET LAYER MAKES AVAILABLE OR MARKS
RESERVED/UNUSABLE.

THE D6FS FREE MAP MUST NEVER ALLOCATE LOGICAL BLOCKS RESERVED FOR KNOWN BAD
MEDIA OR DISKSET METADATA.

THERE IS NO TRANSPARENT RAID-LIKE REMAPPING OR DEGRADED MEMBER OPERATION IN
D6FS.

## 25. DISK REQUEST SCHEDULING

SEEK SCHEDULING BELONGS IN THE PHYSICAL DISK DRIVER, BELOW DISKSET STRIPING.

FOR SEEK-BASED DEVICES THE DRIVER SHOULD USE THE TENEX-STYLE ONE-WAY ELEVATOR
POLICY:

1. SERVICE THE NEAREST QUEUED REQUEST AT OR ABOVE THE CURRENT CYLINDER/TRACK.
2. CONTINUE IN THE SAME DIRECTION.
3. WHEN NO REQUEST REMAINS ABOVE, WRAP TO THE LOWEST QUEUED REQUEST.
4. KEEP QUEUES SMALL AND FIXED/BOUNDED FOR PDP-6 RAM COST.

EACH PHYSICAL MEMBER HAS ITS OWN SEEK POSITION/QUEUE STATE.

DO NOT COPY UNNEEDED TENEX PRIORITY-CLASS COMPLEXITY INTO THE DRIVER.

## 26. EMBEDDED-FILESYSTEM TECHNIQUES ADOPTED

D6FS V2 ADOPTS ONLY SMALL, GENERAL TECHNIQUES THAT FIT PDP-6 CONSTRAINTS:

- BOUNDED FREE-MAP LOOKAHEAD WINDOW;
- ALLOCATION CURSOR INSTEAD OF A FULL RESIDENT ALLOCATION TREE;
- SMALL FIXED CACHE BUDGETS;
- DUAL SUPERBLOCKS WITH SEQUENCE/STATE;
- RECOVERABLE ORDERED WRITES;
- COMPACT FREE-MAP SUMMARY;
- NO REQUIREMENT TO KEEP THE WHOLE FREE MAP IN RAM.

D6FS V2 EXPLICITLY DOES NOT ADOPT:

- INLINE FILE DATA;
- FLASH WEAR LEVELING;
- CRC/CHECKSUM TREES;
- COPY-ON-WRITE METADATA TREES;
- METADATA PAIRS FOR EVERY DIRECTORY/FCB;
- LARGE DYNAMIC INDEX TREES.

## 27. FSCK

D6FSCK MUST VALIDATE AT LEAST:

- BOTH SUPERBLOCKS AND SEQUENCE/STATE;
- DISKSET/FILESYSTEM SIZE BOUNDS;
- FCB TYPE/MODE/FLAG VALIDITY;
- SINGLE-PARENT DIRECTORY INVARIANT;
- DIRECTORY CHILD REFERENCES;
- FULL NAME/HASH CONSISTENCY;
- EXTENT COUNT, ORDER, RANGE, AND OVERLAP;
- MAXIMUM SEVEN EXTENTS;
- FILE SIZE VERSUS EXTENT CAPACITY;
- RESERVED/BAD BLOCK REFERENCES;
- CROSS-LINKED EXTENTS;
- ORPHAN FCBS;
- FREE MAP VERSUS ALL LIVE EXTENTS;
- FREE-MAP SUMMARY VERSUS FREE MAP.

FSCK MAY REBUILD THE FREE MAP AND SUMMARY FROM STRUCTURAL METADATA.

A DIRTY FILESYSTEM REQUIRES FSCK BEFORE WRITABLE MOUNT.

## 28. EXPLICIT NON-FEATURES

D6FS V2 HAS NO:

- HARD LINKS;
- SPARSE FILES;
