## 1. SCOPE AND NON-SCOPE

### 1.1 SCOPE

THIS DOCUMENT SPECIFIES D6FS V1, THE DAIMOS V1 FILESYSTEM FORMAT AND
SEMANTICS USED BY:

  - P6SYS FSREGION: THE ORDINARY FILESYSTEM REGION INSIDE THE LOCKED SYSTEM
    DISK-SET LAYOUT.
  - P6VOL: A MOUNTABLE DATA/IMAGE/PROJECT VOLUME, NORMALLY ON ONE DSK270-LIKE
    DISK PACK.

THE DOCUMENT SPECIFIES:

  - NATIVE FILESYSTEM OBJECT MODEL;
  - EXACT CORE WORD LAYOUTS FOR THE SUPERBLOCK, RUNS, FCBS, AND DIRECTORY
    ENTRIES;
  - ALLOCATION, FREE-SPACE, AND RESERVED/BAD-MEDIA OBJECT MODEL;
  - METADATA INTENT-LOG RECOVERY MODEL;
  - UNIX-LIKE V1 BEHAVIOR WHERE DAIMOS INTENTIONALLY FOLLOWS UNIX SEMANTICS;
  - IMAGE/OVERLAY BEHAVIOR AS SUPPORTED BY P6SYS/P6VOL V1.

### 1.2 NON-SCOPE

THE FOLLOWING ARE EXPLICITLY OUTSIDE THIS DOCUMENT:

  - DTFS DESIGN.  DECTAPE/MICROTAPE STORAGE HAS DIFFERENT OPTIMIZATION GOALS
    AND IS A SEPARATE FILESYSTEM DESIGN.
  - P6ARC DESIGN.  MAGTAPE ARCHIVE/BACKUP STREAMS ARE NOT MOUNTED FILESYSTEMS.
  - UTF-9 FILENAME FILESYSTEMS FOR LATER LARGER PDP-10 SYSTEMS.
  - FULL POSIX ACLS, CAPABILITIES, HARD LINKS, SPARSE FILES, BYTE-RANGE LOCKS,
    MANDATORY LOCKS, QUOTA/ACCOUNTING COUNTERS, DEVICE NODES IN ORDINARY
    FILESYSTEMS, FULL DATA JOURNALING, AND COW METADATA TREES.

P6ARC MAY LATER RECORD PREFERRED RESTORE REGION/ARENA HINTS FOR FILES, BUT THAT
BELONGS TO THE ARCHIVE/RESTORE DESIGN, NOT THIS FILESYSTEM SPECIFICATION.

## 2. DESIGN GOALS

D6FS V1 IS DESIGNED FOR PDP-6/KA10-CLASS DAIMOS, WITH THE FOLLOWING GOALS:

  - USE 36-BIT PDP-10-NATIVE DATA STRUCTURES.
  - REMAIN UNIX-LIKE WHERE IT MATERIALLY REDUCES COMPATIBILITY COMPLEXITY.
  - KEEP THE UNIX LAYER THIN; AVOID A SECOND OPERATING SYSTEM IN TRANSLATION.
  - AVOID OVER-ENGINEERING FOR MACHINES ABOVE THE DAIMOS V1 CEILING.
  - FAVOR FIXED-SIZE METADATA, SIMPLE FSCK, SIMPLE RESCUE TOOLS, AND COMPACT
    ON-DISK STRUCTURES.
  - AVOID ATIME CHURN, SPARSE-FILE COMPLEXITY, ARBITRARY HARD LINKS, DEVICE
    NODES IN ORDINARY FILESYSTEMS, AND FULL DATA JOURNALING.
  - SUPPORT SEALED IMAGES, WRITABLE OVERLAYS, CONTROLLED SPILL, AND LATER
    CONTAINER-LIKE ROOT VIEWS WITHOUT BLOCK-LEVEL SNAPSHOTS.
  - SUPPORT AUTOMATIC MAINTENANCE WHERE CHEAP, BUT NEVER DEPEND ON IT FOR
    CORRECTNESS.

## 3. TERMINOLOGY

#### D6FS

  THE FILESYSTEM FORMAT SPECIFIED BY THIS DOCUMENT.

#### P6SYS

  LOCKED DAIMOS SYSTEM DISK-SET PROFILE.  P6SYS MAY CONSIST OF 2, 3, OR 4 FIXED
  DSK270-LIKE MEMBERS.  P6SYS CONTAINS REGIONS/STORES PLUS AN ORDINARY D6FS
  FILESYSTEM REGION.

#### P6VOL

  MOUNTABLE DAIMOS DATA/IMAGE/PROJECT VOLUME PROFILE, NORMALLY A SINGLE
  DSK270-LIKE DISK.  P6VOL IS NOT INHERENTLY SINGLE-USER.  IT CAN BE PRIVATE,
  SHARED, PROJECT, ARCHIVE, IMAGE, BUILD, OR CONTAINER-BASE STORAGE.

#### P6PACK

  INFORMAL PHYSICAL TERM FOR A REMOVABLE/OPERATOR DISK PACK.  IT IS NOT THE
  FILESYSTEM PROFILE NAME.

REGION
  A NAMED PHYSICAL OR LOGICAL AREA WITHIN A DISK-SET LAYOUT.  P6SYS REGIONS
  INCLUDE BOOTSAFE, KERNEL, SWAPFAST, CFGSTORE, LOGSTORE, AND FSREGION.

STORE
  A TYPED NON-FILE STORE, SUCH AS CFGSTORE OR LOGSTORE.  STORES ARE NOT
  ORDINARY DIRECTORY TREES.

ARENA
  ALLOCATION CLASS INSIDE A D6FS FILESYSTEM.  ARENAS SEPARATE LIFETIMES AND
  PLACEMENT GOALS, FOR EXAMPLE SYSREAD, WORK, NORMAL, AND COLD.

VIEW
  A NAMESPACE COMPOSITION.  A VIEW MAY COMBINE A SEALED BASE IMAGE, WRITABLE
  OVERLAY, SYNTHETIC NAMESPACES, AND SELECTED MOUNTS.

HEAD FCB
  THE VISIBLE FILE CONTROL BLOCK REFERENCED BY A DIRECTORY ENTRY.

CONTINUATION FCB
  INTERNAL FCB USED TO EXTEND A RUN LIST.  IT IS NOT A FILESYSTEM OBJECT TYPE
  AND IS NEVER REFERENCED DIRECTLY FROM A DIRECTORY.

## 4. MACHINE WORD, BLOCK, BYTE, AND POINTER CONVENTIONS

### 4.1 WORD

ALL ON-DISK WORDS ARE 36-BIT PDP-6/PDP-10 WORDS.

BIT NUMBERING IN THIS DOCUMENT:

  BIT 0      = MOST SIGNIFICANT BIT OF A 36-BIT WORD
  BIT 35     = LEAST SIGNIFICANT BIT
  LH         = BITS 0..17
  RH         = BITS 18..35

A PACKED POINTER WORD WRITTEN AS:

  A ! B

MEANS:

  BITS 0..17   = A
  BITS 18..35  = B

### 4.2 BLOCK

THE FUNDAMENTAL D6FS STORAGE UNIT IS:

  1 FILESYSTEM BLOCK = 128 WORDS

THIS IS THE UNIT FOR ALLOCATION BITMAPS, FREE MAPS, AND RUN
LENGTHS.  LARGER TRANSFER UNITS MAY BE USED BY DRIVERS, BUFFER CACHE, OR SWAP,
BUT THE FILESYSTEM BLOCK REMAINS 128 WORDS.

### 4.3 9-BIT BYTE STREAMS

REGULAR BYTE/TEXT STREAMS USE FOUR 9-BIT BYTES PER 36-BIT WORD:

  BYTE 0 = BITS 0..8
  BYTE 1 = BITS 9..17
  BYTE 2 = BITS 18..26
  BYTE 3 = BITS 27..35

THE UNIX-VISIBLE BYTE COUNT IS DERIVED FROM THE NATIVE SIZE_WORDS AND
 TAIL_9BYTES FIELDS.  SEE SECTION 10.

### 4.4 SIXBIT NAMES

ALL V1 FILENAMES, DIRECTORY NAMES, SYSTEM OBJECT NAMES, AND SYMLINK TARGETS ARE
STRICT SIXBIT.  UTF-9 FILENAMES ARE NOT PART OF D6FS V1.

FIXED SIXBIT SYMBOL FIELDS:

  DSYM6   = 1 WORD  = 6 SIXBIT CHARACTERS
  DSYM12  = 2 WORDS = 12 SIXBIT CHARACTERS
  DSYM18  = 3 WORDS = 18 SIXBIT CHARACTERS
  DSYM24  = 4 WORDS = 24 SIXBIT CHARACTERS

RULES:

  - UPPERCASE ONLY;
  - TRAILING-SPACE PADDED;
  - NO NUL TERMINATOR;
  - UNSUPPORTED CHARACTERS ARE REJECTED;
  - IDENTIFIERS ARE NAMES, NOT FREE TEXT.

### 4.5 POINTERS

V1 ROOT POINTERS STORED IN THE SUPERBLOCK ARE 18-BIT BLOCK NUMBERS RELATIVE TO
THE START OF THE D6FS FILESYSTEM REGION OR P6VOL VOLUME.  ZERO MEANS ABSENT
UNLESS THE FIELD IS REQUIRED.

BECAUSE ROOT POINTERS ARE 18-BIT, ALL ROOT METADATA TABLES MUST BE PLACED IN
THE V1 METADATA ROOT ADDRESSABLE RANGE.  ARENA TABLES MAY DESCRIBE DATA ARENAS
OUTSIDE THE SMALL ROOT METADATA AREA IF THE PROFILE SUPPORTS IT.

## 5. PROFILES: P6SYS, P6VOL, P6PACK

### 5.1 P6SYS

P6SYS IS THE SYSTEM DISK-SET PROFILE.

FROZEN P6SYS BEHAVIOR:

  - SUPPORTS 2, 3, OR 4 FIXED LOCKED DSK270-LIKE MEMBERS;
  - DEFAULT MACHINE LAYOUT MAY BE 3 FIXED SYSTEM DISKS PLUS 1 MOUNTABLE PACK,
    BUT THE P6SYS LAYOUT MUST BE GENERATED BY FORMATTER METADATA, NOT HARDCODED;
  - CONTAINS TYPED REGIONS AND STORES OUTSIDE ORDINARY FILESYSTEM ALLOCATION;
  - HAS AN ORDINARY D6FS FSREGION;
  - SYSTEM REGIONS AND STORES NEVER SPILL INTO OR OUT OF FSREGION.

P6SYS FIXED REGIONS:

  BOOTSAFE  BOOT LOADER / BOOT-VISIBLE DATA; READ AT BOOT, NOT RUNTIME-HOT
  KERNEL    KERNEL IMAGE REGION; READ AT BOOT, NOT ORDINARY FS
  SWAPFAST  FIXED SWAP REGION OUTSIDE FS; RUNTIME-HOT
  CFGSTORE  TYPED MACHINE/CONFIG STORES OUTSIDE ORDINARY FS
  LOGSTORE  TYPED BINARY EVENT RINGS OUTSIDE ORDINARY FS
  FSREGION  ORDINARY D6FS FILESYSTEM REGION

### 5.2 P6VOL

P6VOL IS A MOUNTABLE DATA/IMAGE/PROJECT VOLUME PROFILE.

FROZEN P6VOL BEHAVIOR:

  - NORMALLY ONE PHYSICAL DISK PACK;
  - MOUNTABLE AND DISMOUNTABLE;
  - NO BOOT/KERNEL/SWAP REGIONS BY DEFAULT;
  - SUPPORTS ORDINARY FILES;
  - SUPPORTS SEALED IMAGES;
  - SUPPORTS WRITABLE OVERLAYS;
  - SUPPORTS TYPED VOLUME/USER/PROJECT CONFIG STORE IF PRESENT;
  - SUPPORTS OPTIONAL VOLUME-LOCAL BINARY LOGS IF PRESENT;
  - SUPPORTS AUTOMATIC MAINTENANCE USING THE SAME FRAMEWORK AS P6SYS;
  - USES THE SAME FCB/RUN/DIRECTORY PRIMITIVES AS P6SYS.

P6VOL IS NOT SINGLE-USER.  IT MAY HOLD SHARED PROJECTS, PRIVATE HOMES, SOURCE
BASELINES, SEALED IMAGES, WRITABLE EXPERIMENTS, ARCHIVES, AND LATER CONTAINER
ROOTS.

### 5.3 P6PACK

P6PACK IS ONLY THE INFORMAL PHYSICAL TERM FOR A REMOVABLE DISK PACK.  IT IS NOT
THE FILESYSTEM FORMAT NAME.

## 6. REGIONS, STORES, ARENAS, AND VIEWS

### 6.1 OWNERSHIP RULE

REGIONS MAY OVERLAP ONLY AS VIEWS, ALIASES, OR DIAGNOSTIC DESCRIPTIONS OF THE
SAME PHYSICAL SPAN.  OVERLAP NEVER IMPLIES TWO WRITABLE OWNERS.

HARD RULE:

  EVERY WRITABLE BLOCK HAS EXACTLY ONE OWNING ALLOCATOR/STORE.

SYNTHETIC NAMESPACES MAY OVERLAP VIEWS BECAUSE THEY DO NOT ALLOCATE BLOCKS.

### 6.2 P6SYS NON-FS REGIONS

THE FOLLOWING NEVER SPILL AND NEVER ACCEPT SPILL:

  BOOTSAFE
  KERNEL
  SWAPFAST
  CFGSTORE
  LOGSTORE

### 6.3 D6FS ARENAS

INSIDE FSREGION/P6VOL, D6FS V1 USES ALLOCATION ARENAS.

STANDARD ARENAS:

  SYSREAD  STABLE READ-MOSTLY FILES: /BIN, /LIB, /SBIN, TOOLS, KCC BINARIES
  WORK     /TMP, COMPILER SCRATCH, BUILD OUTPUT, UNPACKING AREA
  NORMAL   ORDINARY MUTABLE FILES, SOURCES, USER/SYSTEM DATA
  COLD     DOCS, OLD SOURCE DROPS, ARCHIVES, RARELY USED DATA

P6VOL MAY USE FEWER ARENAS, BUT THE ON-DISK FORMAT SUPPORTS THE SAME ARENA
CONCEPT.

### 6.4 SPILL POLICY

CONTROLLED AUTOMATIC SPILL IS ALLOWED:

  WORK   -> TEMPORARY OVERFLOW OR NORMAL
  NORMAL -> COLD
  SYSREAD -> NORMAL ONLY DURING INSTALL/UPDATE

SPILL MARKS THE FILESYSTEM DEGRADED OR PACK_NEEDED.  PACKER/MAINTENANCE REPAIRS
SPILL LATER.

### 6.5 VIEW MODEL

A VIEW MAY COMPOSE:

  - ONE SEALED BASE IMAGE;
  - ONE WRITABLE OVERLAY;
  - SYNTHETIC /DEV, /ETC, /VAR/LOG, AND OTHER VIEWS;
  - SELECTED MOUNTS.

FILE LOOKUP IN AN IMAGE/OVERLAY VIEW:

  1. CHECK OVERLAY DIRECTORY;
  2. OVERLAY WHITEOUT HIDES BASE ENTRY;
  3. OVERLAY ENTRY WINS;
  4. OTHERWISE USE BASE ENTRY.

## 7. FILENAME, PATHNAME, AND TEXT CONVENTIONS

### 7.1 FILENAME MODEL

D6FS V1 FILENAMES ARE STRICT SIXBIT DSYM24 PATH COMPONENTS.

FROZEN RULES:

  - FILENAMES ARE STRICT SIXBIT ONLY;
  - DIRECTORY NAMES ARE STRICT SIXBIT ONLY;
  - MAX COMPONENT LENGTH IS DSYM24 = 24 SIXBIT CHARS = 4 WORDS;
  - NO TOPS-LIKE NAME.EXT SPLIT;
  - '.' IS AN ORDINARY LEGAL FILENAME CHARACTER;
  - EXTENSION SEMANTICS ARE CONVENTIONS ONLY;
  - '/' IS THE PATH SEPARATOR;
  - PATH TRAVERSAL IS UNIX-LIKE.

EXAMPLES OF ORDINARY NAMES:

  KCC
  KCC.EXE
  README
  README.1
  MAKEFILE
  LIBC.A

### 7.2 FULL PATH LIMIT

D6FS V1 MAXIMUM FULL PATH LENGTH:

  256 SIXBIT CHARACTERS, INCLUDING SEPARATORS

### 7.3 DOT AND DOT-DOT

D6FS PROVIDES UNIX-LIKE '.' AND '..' SEMANTICS.

RULES:

  - '.' REFERS TO CURRENT DIRECTORY;
  - '..' REFERS TO PARENT DIRECTORY;
  - ROOT HAS '..' EQUAL TO '.';
  - IMPLEMENTATION MAY SYNTHESIZE '.' AND '..' RATHER THAN STORE THEM AS REAL
    DIRECTORY RECORDS;
  - EXTERNALLY VISIBLE BEHAVIOR IS UNIX-LIKE.

BECAUSE ARBITRARY HARD LINKS ARE NOT SUPPORTED, '.' AND '..' MUST NOT CREATE A
PERSISTENT HARD-LINK MODEL.

### 7.4 TEXT LINE ENDINGS

DAIMOS V1 TEXT FILES USE LF ONLY.

  '\N' = LINE SEPARATOR

NO NATIVE CRLF FORMAT, NO NATIVE CR-ONLY FORMAT, AND NO RECORD-ORIENTED TEXT
FILE FORMAT EXIST IN D6FS V1.  TERMINAL DRIVERS MAY TRANSLATE LF TO CR/LF FOR
DISPLAY WHERE NECESSARY, BUT FILESYSTEMS DO NOT PERFORM LINE-ENDING TRANSLATION.

## 8. NATIVE FILE OBJECT MODEL

### 8.1 OBJECT TYPES

D6FS V1 FCB OBJECT TYPES:

  REG      REGULAR FILE
  DIR      DIRECTORY
  SYMLINK  SYMBOLIC LINK

NO OTHER FILESYSTEM OBJECT TYPES EXIST IN V1.

EXECUTABLE/OBJECT/ARCHIVE/KERNEL/SCRIPT DISTINCTIONS ARE CONTENT FORMATS OR
LOADER POLICY, NOT FILESYSTEM OBJECT TYPES.

EXAMPLES:

  FOO.O      REG, CONTENT MAY BE DOBJ FORMAT
  LIBC.A     REG, CONTENT MAY BE DARC ARCHIVE FORMAT
  /BIN/KCC   REG, CONTENT MAY BE DEXE EXECUTABLE FORMAT
  SCRIPT.SH  REG, CONTENT MAY BEGIN WITH #!

### 8.2 NO DEVICE NODES

/DEV IS SYNTHETIC.  ORDINARY D6FS FILESYSTEMS DO NOT STORE REAL DEVICE NODES.

### 8.3 NO HARD LINKS

D6FS V1 HAS NO ARBITRARY USER-CREATED HARD LINKS.  DIRECTORY ENTRIES NORMALLY
REFERENCE ONE OWNING HEAD FCB.  IMAGE SHARING IS IMAGE/VIEW-LEVEL, NOT HARD-LINK
LEVEL.

### 8.4 CONTINUATION FCBS

CONTINUATION/CHAINED-RUN FCBS ARE INTERNAL ALLOCATION RECORDS.  THEY DO NOT
CREATE A FILESYSTEM OBJECT TYPE.  DIRECTORY ENTRIES MAY REFERENCE ONLY HEAD
FCBS.

## 9. PROTECTION MODEL

### 9.1 NATIVE OWNERSHIP

D6FS V1 USES PROJECT/USER OWNERSHIP NATIVELY:

  OWNER_PROJECT
  OWNER_USER
  PROTECTION_WORD

UNIX UID/GID/MODE ARE COMPATIBILITY VIEWS ONLY:

  UID -= OWNER_USER
  GID -= OWNER_PROJECT
  MODE -= PROTECTION_WORD MAPPING

THE MODEL MUST REMAIN UNIX-MAPPABLE AND MUST NOT REQUIRE A COMPLEX UNIX
COMPATIBILITY ENGINE.

### 9.2 ACCESS CLASSES

NATIVE ACCESS CLASSES:

  OWNER
  SAME PROJECT/GROUP
  OTHER
  SYSTEM/OPERATOR

### 9.3 OPERATIONS

REQUIRED PROTECTION OPERATIONS:

  READ
  WRITE
  EXECUTE/SEARCH
  APPEND/UPDATE
  DELETE/CONTROL

### 9.4 DIRECTORY PERMISSIONS

DIRECTORY PERMISSION SEMANTICS ARE UNIX-LIKE:

  DIRECTORY READ    = LIST ENTRIES
  DIRECTORY WRITE   = CREATE, UNLINK, RENAME ENTRIES
  DIRECTORY EXECUTE = SEARCH/TRAVERSE

DELETE/RENAME PERMISSION IS CHECKED PRIMARILY ON THE CONTAINING DIRECTORY, AS
IN UNIX.

### 9.5 UNSUPPORTED V1 SECURITY FEATURES

THE FOLLOWING ARE RESERVED BUT NOT PART OF V1 FILESYSTEM SEMANTICS:

  - FULL ACLS;
  - CAPABILITIES;
  - PER-VIEW PERMISSION REWRITING;
  - RICH DENY/ALLOW POLICY OBJECTS;
  - COMPLEX MANDATORY LOCKING OR MANDATORY ACCESS POLICY.

## 10. FILE SIZE, BYTE STREAMS, AND LINE ENDINGS

### 10.1 NATIVE FILE SIZE

D6FS V1 STORES FILE SIZE PRIMARILY AS 36-BIT WORDS PLUS A FINAL PARTIAL 9-BIT
BYTE COUNT.

NATIVE FIELDS:

  SIZE_WORDS
    NUMBER OF LOGICAL 36-BIT WORDS USED BY THE FILE

  TAIL_9BYTES
    0 = FINAL WORD IS COMPLETE / WORD-ALIGNED
    1 = ONE VALID 9-BIT BYTE IN FINAL PARTIAL WORD
    2 = TWO VALID 9-BIT BYTES IN FINAL PARTIAL WORD
    3 = THREE VALID 9-BIT BYTES IN FINAL PARTIAL WORD

NO FULL BYTE-COUNT FIELD IS STORED NATIVELY.

### 10.2 UNIX BYTE COUNT DERIVATION

UNIX-VISIBLE ST_SIZE IS DERIVED CHEAPLY:

  IF TAIL_9BYTES == 0:
      ST_SIZE = SIZE_WORDS << 2
  ELSE:
      ST_SIZE = ((SIZE_WORDS - 1) << 2) + TAIL_9BYTES

THUS WORD-ALIGNED FILES USE:

  ST_SIZE = SIZE_WORDS * 4 = SIZE_WORDS << 2

### 10.3 FILE CONTENT PACKING

REGULAR BYTE/TEXT STREAMS ARE PACKED AS FOUR 9-BIT BYTES PER 36-BIT WORD.  LF IS
THE LINE SEPARATOR.  WORD-NATIVE BINARY FILES NORMALLY HAVE TAIL_9BYTES = 0.

### 10.4 SPARSE FILES

SPARSE FILES ARE NOT IMPLEMENTED IN V1.

RULES:

  - REG FILES HAVE NO HOLES;
  - DIR FILES HAVE NO HOLES;
  - WRITES PAST EOF ALLOCATE AND ZERO-FILL INTERVENING STORAGE;
  - F_SPARSE_RESERVED MUST BE ZERO IN V1;
  - FSCK REJECTS OR MARKS UNSUPPORTED FILES WITH SPARSE FLAGS SET.

## 11. TIMESTAMPS AND HEAT TRACKING

### 11.1 STORED TIMESTAMPS

D6FS V1 STORES:

  MTIME  CONTENT MODIFICATION TIME
  CTIME  METADATA/STATUS CHANGE TIME

D6FS V1 DOES NOT STORE EXACT POSIX ATIME AS A CORRECTNESS REQUIREMENT.

UNIX COMPATIBILITY:

  - STAT().ST_ATIME IS SYNTHESIZED BY DEFAULT;
  - DEFAULT ATIME SYNTHESIS MAY USE MTIME OR A MOUNT POLICY;
  - READS DO NOT DIRTY FCBS SOLELY TO UPDATE EXACT ATIME.

### 11.2 OPTIONAL HEAT TRACKING

D6FS V1 SUPPORTS OPTIONAL LAZY ACCESS HEAT TRACKING FOR MAINTENANCE AND ARENA
PROMOTION.

FIELDS IN THE FCB MAY INCLUDE:

  LAST_ACCESS_EPOCH
  ACCESS_COUNT_SATURATING
  HEAT_CLASS

POLICY:

  - OPTIONAL PER MOUNT/VIEW/ARENA;
  - DISABLED BY DEFAULT ON SLOW/REMOVABLE MEDIA;
  - ENABLED BY MOUNT OPTION OR FORMATTER POLICY;
  - NOT EXACT POSIX ATIME;
  - NEVER REQUIRED FOR CORRECTNESS;
  - MAY BE UPDATED IN MEMORY AND FLUSHED LAZILY;
  - ACCESS COUNTER IS SATURATING, NOT EXACT;
  - PACKER MAY USE HEAT TO PROMOTE CLOSED FILES TO HOTTER ARENAS.

## 12. SUPERBLOCK: EXACT 16-WORD FORMAT

### 12.1 OVERVIEW

EVERY D6FS FILESYSTEM HAS A COMPACT 16-WORD SUPERBLOCK.

NO HUMAN-READABLE VOLUME LABEL IS STORED IN THE BASE FILESYSTEM SUPERBLOCK.
VOLUME IDENTITY IS A 3-WORD, 108-BIT FILESYSTEM UUID.

D6FS_SUPER_V1, EXACTLY 16 WORDS:

  WORD 00  MAGIC/PROFILE/VERSION
  WORD 01  FLAGS/STATE/LAYOUT_GENERATION_SMALL
  WORD 02  FS_UUID[0]
  WORD 03  FS_UUID[1]
  WORD 04  FS_UUID[2]
  WORD 05  ROOT_DIR_FCB ! FCB_TABLE_PTR
  WORD 06  ARENA_TABLE_PTR ! FREE_MAP_PTR
  WORD 07  INTENT_LOG_PTR ! BAD_BLOCK_TABLE_PTR
  WORD 08  IMAGE_TABLE_PTR ! OVERLAY_TABLE_PTR
  WORD 09  CFG_STORE_PTR ! LOG_STORE_PTR
  WORD 10  TOTAL_BLOCKS
  WORD 11  REGION_COUNT/PROFILE_DATA ! RESERVED
  WORD 12  LAYOUT_GENERATION
  WORD 13  CLEAN_GENERATION_OR_LAST_CLEAN_TIME_COARSE
  WORD 14  CHECKSUM
  WORD 15  ALTERNATE_SUPER_PTR ! RESERVED

### 12.2 WORD 00: MAGIC/PROFILE/VERSION

  BITS 0..17    MAGIC18     SIXBIT "D6F" OR ASSIGNED D6FS MAGIC
  BITS 18..23   PROFILE6    1=P6SYS-FSREGION, 2=P6VOL, OTHERS RESERVED
  BITS 24..29   MAJOR6      V1 = 1
  BITS 30..35   MINOR6      V1 INITIAL = 0

### 12.3 WORD 01: FLAGS/STATE/LAYOUT_GENERATION_SMALL

  BITS 0..5     STATE6
  BITS 6..17    FLAGS12
  BITS 18..35   LAYOUT_GENERATION_SMALL18

STATE6 VALUES:

  0  UNKNOWN/INVALID
  1  CLEAN
  2  DIRTY
  3  DEGRADED
  4  PACK_NEEDED
  5  FSCK_NEEDED
  6..63 RESERVED

FLAGS12 VALUES ARE PROFILE-DEFINED.  REQUIRED FLAGS:

  BIT FLAG WITHIN FLAGS12:
    0  READONLY_COMPAT
    1  HAS_IMAGES
    2  HAS_OVERLAYS
    3  HAS_CFG_STORE
    4  HAS_LOG_STORE
    5  HEAT_TRACKING_ALLOWED
    6  SPARSE_RESERVED_MUST_BE_ZERO
    7..11 RESERVED

### 12.4 WORDS 02..04: FS_UUID

  FS_UUID[0..2] = 108-BIT DAIMOS FILESYSTEM IDENTITY

THIS IS NOT A MODERN 128-BIT UUID, BUT IS SUFFICIENT FOR DAIMOS V1 VOLUME AND
MEMBER IDENTITY.

### 12.5 WORDS 05..09: ROOT POINTERS

EACH WORD PACKS TWO 18-BIT BLOCK POINTERS:

  BITS 0..17   LEFT POINTER
  BITS 18..35  RIGHT POINTER

POINTERS ARE BLOCK NUMBERS RELATIVE TO THIS D6FS FILESYSTEM.  ZERO MEANS ABSENT
UNLESS THE FIELD IS MANDATORY.

  WORD 05 LH ROOT_DIR_FCB       REQUIRED FCB ID OR FCB TABLE INDEX
          RH FCB_TABLE_PTR      REQUIRED METADATA BLOCK POINTER

  WORD 06 LH ARENA_TABLE_PTR    REQUIRED METADATA BLOCK POINTER
          RH FREE_MAP_PTR       REQUIRED METADATA BLOCK POINTER

  WORD 07 LH INTENT_LOG_PTR     REQUIRED UNLESS CLEAN READ-ONLY IMAGE PROFILE
          RH BAD_BLOCK_TABLE_PTR OPTIONAL, ZERO IF ABSENT

  WORD 08 LH IMAGE_TABLE_PTR    OPTIONAL, ZERO IF ABSENT
          RH OVERLAY_TABLE_PTR  OPTIONAL, ZERO IF ABSENT

  WORD 09 LH CFG_STORE_PTR      OPTIONAL, ZERO IF ABSENT
          RH LOG_STORE_PTR      OPTIONAL, ZERO IF ABSENT

### 12.6 WORD 10: TOTAL_BLOCKS

  BITS 0..35 TOTAL NUMBER OF 128-WORD BLOCKS IN THIS D6FS FILESYSTEM.

### 12.7 WORD 11: REGION/PROFILE DATA

  BITS 0..17    REGION_COUNT_OR_PROFILE_DATA18
  BITS 18..35   RESERVED18, MUST BE ZERO IN V1 UNLESS PROFILE DEFINES IT

P6VOL MAY SET REGION_COUNT_OR_PROFILE_DATA18 TO ZERO OR A SMALL REGION COUNT.
P6SYS FSREGION USUALLY RELIES ON THE OUTER P6SYS DISK-SET REGION TABLE.

### 12.8 WORD 12: LAYOUT_GENERATION

  BITS 0..35 FULL LAYOUT GENERATION COUNTER

INCREMENTED ON STRUCTURAL LAYOUT UPDATES SUCH AS TABLE RELOCATION, IMAGE TABLE
ROOT CHANGES, OR FORMATTER-LEVEL LAYOUT CHANGES.

### 12.9 WORD 13: CLEAN_GENERATION_OR_LAST_CLEAN_TIME_COARSE

  BITS 0..35 PROFILE-DEFINED CLEAN GENERATION OR COARSE CLEAN TIMESTAMP.

THIS FIELD IS USED TO VALIDATE CLEAN STATE AND AID RECOVERY DIAGNOSTICS.

### 12.10 WORD 14: CHECKSUM

CHECKSUM OVER WORDS 00..15 WITH WORD 14 TREATED AS ZERO.

V1 CHECKSUM ALGORITHM:

  - 36-BIT END-AROUND SUM OF ALL 36-BIT WORDS WITH CHECKSUM FIELD ZEROED,
    THEN ONES-COMPLEMENT THE RESULT.

A STRONGER CHECKSUM MAY BE USED IN A LATER PROFILE.  V1 TOOLS MUST AT LEAST
SUPPORT THE END-AROUND CHECKSUM.

### 12.11 WORD 15: ALTERNATE SUPERBLOCK POINTER

  BITS 0..17    ALTERNATE_SUPER_PTR
  BITS 18..35   RESERVED18, MUST BE ZERO IN V1

THE ALTERNATE SUPERBLOCK IS A BACKUP COPY LOCATED AT A FORMATTER-CHOSEN SAFE
METADATA LOCATION.

### 12.12 SUPERBLOCK PLACEMENT

RECOMMENDED PLACEMENT:

  - PRIMARY SUPERBLOCK AT FIXED FIRST D6FS BLOCK OF THE FILESYSTEM REGION;
  - ALTERNATE SUPERBLOCK AT FIXED LAST SAFE METADATA BLOCK OR FORMATTER-CHOSEN
    BACKUP LOCATION.

FOR P6SYS:

  P6SYS DISK-SET LABEL/REGION TABLE -> POINTS TO FSREGION
  FSREGION SUPERBLOCK               -> THIS 16-WORD D6FS SUPERBLOCK

## 13. RUN WORD FORMAT

### 13.1 FORMAT

ONE RUN WORD DESCRIBES ONE CONTIGUOUS RANGE OF 128-WORD FILESYSTEM BLOCKS.

  BITS 0..5     ARENA_ID6
  BITS 6..21    START_BLOCK16
  BITS 22..33   COUNT_MINUS_1_12
  BITS 34..35   RUN_KIND2

FIELDS:

  ARENA_ID6
    ALLOCATION ARENA ID, 0..63

  START_BLOCK16
    BLOCK OFFSET INSIDE THE ARENA

  COUNT_MINUS_1_12
    ENCODED COUNT MINUS ONE

  RUN_KIND2
    0 = RUN_UNUSED
    1 = RUN_OWNED
    2 = RUN_OWNED_NOMOVE / PINNED
    3 = RESERVED

### 13.2 COUNT

FOR RUN_KIND != RUN_UNUSED:

  BLOCK_COUNT = COUNT_MINUS_1_12 + 1

MAXIMUM RUN LENGTH:

  4096 BLOCKS = 4096 * 128 WORDS = 512 KW

### 13.3 UNUSED RUN

RUN_UNUSED MUST HAVE ALL OTHER FIELDS ZERO:

  ARENA_ID = 0
  START_BLOCK = 0
  COUNT_MINUS_1 = 0
  RUN_KIND = 0

### 13.4 RUN OWNERSHIP

EVERY BLOCK DESCRIBED BY A LIVE RUN HAS EXACTLY ONE OWNER.  FSCK MUST DETECT AND
REPAIR/REPORT DOUBLE ALLOCATION.

## 14. FCB FORMAT: HEAD AND CONTINUATION RECORDS

### 14.1 RECORD SIZE

ALL FCB RECORDS ARE FIXED-SIZE 16-WORD RECORDS.  HEAD AND CONTINUATION FCBS USE
THE SAME RECORD SIZE.  CONTINUATION RECORDS LEAVE UNUSED FIELDS ZERO.

### 14.2 WORD 00: FCB HEADER WORD

  BITS 0..17    MAGIC18       SIXBIT "FCB"
  BITS 18..23   OBJECT_TYPE6  1=REG, 2=DIR, 3=SYMLINK
  BITS 24..25   ROLE2         1=HEAD, 2=CONTINUATION
  BITS 26..27   TAIL_9BYTES2  VALID ONLY FOR HEAD REG/SYMLINK
  BITS 28..35   FCB_FLAGS8

OBJECT_TYPE6 VALUES:

  0 INVALID/RESERVED
  1 REG
  2 DIR
  3 SYMLINK
  4..63 RESERVED

ROLE2 VALUES:

  0 INVALID
  1 HEAD
  2 CONTINUATION
  3 RESERVED

FCB_FLAGS8 REQUIRED BITS:

  BIT 0  F_READONLY_IMAGE_MEMBER
  BIT 1  F_WHITEOUT_TARGET_RESERVED
  BIT 2  F_SPARSE_RESERVED, MUST BE ZERO IN V1
  BIT 3  F_HEAT_VALID
  BIT 4  F_PACK_NEEDED_HINT
  BIT 5  F_NOMOVE
  BIT 6  RESERVED
  BIT 7  RESERVED

### 14.3 HEAD FCB LAYOUT

D6FS_HEAD_FCB_V1, 16 WORDS:

  WORD 00  FCB HEADER WORD
  WORD 01  FCB_ID ! FCB_GENERATION
  WORD 02  OWNER_PROJECT ! OWNER_USER
  WORD 03  PROTECTION_WORD
  WORD 04  SIZE_WORDS
  WORD 05  MTIME
  WORD 06  CTIME
  WORD 07  PARENT_FCB ! NEXT_FCB
  WORD 08  DIRECT_RUN[0]
  WORD 09  DIRECT_RUN[1]
  WORD 10  DIRECT_RUN[2]
  WORD 11  DIRECT_RUN[3]
  WORD 12  LAST_ACCESS_EPOCH ! ACCESS_COUNT ! HEAT_CLASS
  WORD 13  PREFERRED_ARENA ! SPILL_POLICY ! HEAT_POLICY ! RESERVED
  WORD 14  RESERVED
  WORD 15  CHECKSUM

### 14.4 HEAD FCB FIELD DETAILS

WORD 01:

  BITS 0..17    FCB_ID18
  BITS 18..35   FCB_GENERATION18

WORD 02:

  BITS 0..17    OWNER_PROJECT18
  BITS 18..35   OWNER_USER18

WORD 03:

  BITS 0..35    PROTECTION_WORD36

THE EXACT PROTECTION BIT ASSIGNMENT IS KERNEL-DEFINED BUT MUST MAP SIMPLY TO
UNIX OWNER/GROUP/OTHER READ/WRITE/EXECUTE SEMANTICS PLUS NATIVE CONTROL BITS.

WORD 04:

  BITS 0..35    SIZE_WORDS36

WORD 05:

  BITS 0..35    MTIME36

WORD 06:

  BITS 0..35    CTIME36

WORD 07:

  BITS 0..17    PARENT_FCB18
  BITS 18..35   NEXT_FCB18

PARENT_FCB RULES:

  - MEANINGFUL FOR DIR;
  - ROOT DIRECTORY PARENT_FCB POINTS TO ITSELF;
  - FOR REG/SYMLINK MAY BE ZERO OR CREATOR DIRECTORY HINT; NOT AUTHORITATIVE
    FOR REACHABILITY.

NEXT_FCB RULES:

  - ZERO MEANS NO CONTINUATION FCB;
  - NONZERO POINTS TO FIRST CONTINUATION FCB.

WORDS 08..11:

  DIRECT_RUN[0..3] USING THE RUN WORD FORMAT IN SECTION 13.

WORD 12:

  BITS 0..17    LAST_ACCESS_EPOCH18
  BITS 18..29   ACCESS_COUNT_SATURATING12
  BITS 30..35   HEAT_CLASS6

THESE FIELDS ARE ONLY VALID IF F_HEAT_VALID IS SET.  THEY ARE OPTIONAL LAZY HEAT
TRACKING HINTS, NOT EXACT POSIX ATIME.

WORD 13:

  BITS 0..5     PREFERRED_ARENA6
  BITS 6..11    SPILL_POLICY6
  BITS 12..17   HEAT_POLICY6
  BITS 18..35   RESERVED18, MUST BE ZERO IN V1

WORD 14:

  RESERVED36, MUST BE ZERO IN V1

WORD 15:

  CHECKSUM OVER WORDS 00..15 WITH WORD 15 TREATED AS ZERO.

### 14.5 CONTINUATION FCB LAYOUT

D6FS_CONT_FCB_V1, 16 WORDS:

  WORD 00  FCB HEADER WORD, ROLE=CONTINUATION
  WORD 01  FCB_ID ! FCB_GENERATION
  WORD 02  HEAD_FCB_ID ! SEQUENCE_NUMBER
  WORD 03  RESERVED ! NEXT_FCB
  WORD 04  DIRECT_RUN[0]
  WORD 05  DIRECT_RUN[1]
  WORD 06  DIRECT_RUN[2]
  WORD 07  DIRECT_RUN[3]
  WORD 08  RESERVED
  WORD 09  RESERVED
  WORD 10  RESERVED
  WORD 11  RESERVED
  WORD 12  RESERVED
  WORD 13  RESERVED
  WORD 14  RESERVED
  WORD 15  CHECKSUM

WORD 02:

  BITS 0..17    HEAD_FCB_ID18
  BITS 18..35   SEQUENCE_NUMBER18

WORD 03:

  BITS 0..17    RESERVED18, MUST BE ZERO IN V1
  BITS 18..35   NEXT_FCB18

CONTINUATION RULES:

  - DIRECTORY ENTRIES MAY NOT REFERENCE CONTINUATION FCBS;
  - CONTINUATION FCBS POINT BACK TO THEIR HEAD FCB;
  - SEQUENCE NUMBERS START AT 1 AND INCREASE MONOTONICALLY;
  - FSCK REJECTS LOOPS AND MISMATCHED HEAD REFERENCES;
  - CONTINUATION FCBS ARE USED ONLY FOR GENUINELY LARGE FILES OR UNAVOIDABLE
    LARGE DIRECTORIES, NOT ORDINARY FRAGMENTATION.

### 14.6 DIRECT CAPACITY

A HEAD FCB HAS FOUR DIRECT RUNS.

MAXIMUM DIRECT FILE SPAN IF ALL FOUR RUNS ARE MAXIMUM LENGTH:

  4 * 4096 BLOCKS = 16384 BLOCKS = 2 MW

LARGER FILES USE CONTINUATION FCBS.

## 15. DIRECTORY FORMAT

### 15.1 DIRECTORY OBJECT

A DIRECTORY IS AN FCB WITH OBJECT_TYPE DIR.  DIRECTORY DATA BLOCKS CONTAIN
FIXED-SIZE DIRECTORY RECORDS.  DIRECTORIES ARE ALLOCATED THROUGH NORMAL RUNS.
DIRECTORIES ARE READABLE THROUGH READDIR/GETDENTS-STYLE CALLS BUT ARE NOT
WRITABLE AS ORDINARY FILE BYTE STREAMS.

### 15.2 DIRECTORY ENTRY SIZE

D6FS_DIRREC_V1 IS 6 WORDS.

  WORD 00  NAME_DSYM24[0]
  WORD 01  NAME_DSYM24[1]
  WORD 02  NAME_DSYM24[2]
  WORD 03  NAME_DSYM24[3]
  WORD 04  FCB_ID ! ENTRY_GENERATION
  WORD 05  ENTRY_STATE ! CACHED_TYPE ! NAME_HASH

### 15.3 WORD 04

  BITS 0..17    FCB_ID18
  BITS 18..35   ENTRY_GENERATION18

FCB_ID MUST REFERENCE A HEAD FCB FOR LIVE ENTRIES.

### 15.4 WORD 05

  BITS 0..5     ENTRY_STATE6
  BITS 6..11    CACHED_TYPE6
  BITS 12..35   NAME_HASH24

ENTRY_STATE6 VALUES:

  0 FREE
  1 LIVE
  2 DELETED
  3 WHITEOUT
  4 MOUNT_HINT_RESERVED
  5..63 RESERVED

CACHED_TYPE6 VALUES:

  0 UNKNOWN/UNUSED
  1 REG
  2 DIR
  3 SYMLINK
  4..63 RESERVED

NAME_HASH24 IS A NON-AUTHORITATIVE LOOKUP ACCELERATOR.  NAME COMPARISON USES
THE DSYM24 NAME, NOT THE HASH.

### 15.5 WHITEOUTS

OVERLAY WHITEOUT ENTRY:

  ENTRY_STATE = WHITEOUT
  FCB_ID = 0
  NAME = HIDDEN BASE NAME

### 15.6 DOT AND DOT-DOT

'.' AND '..' MAY BE SYNTHESIZED.  IF PHYSICALLY PRESENT, FSCK MUST VALIDATE
THAT THEY MATCH UNIX-LIKE SEMANTICS.  IMPLEMENTATIONS SHOULD PREFER SYNTHESIS TO
AVOID INTRODUCING HARD-LINK SEMANTICS.

### 15.7 DIRECTORY MUTATION

DIRECTORY MUTATION OCCURS ONLY THROUGH KERNEL FILESYSTEM OPERATIONS:

  CREATE
  UNLINK
  RENAME
  MKDIR
  RMDIR
  SYMLINK

## 16. ARENA TABLE AND ALLOCATION POLICY

### 16.1 ARENA TABLE ENTRY

D6FS_ARENA_ENTRY_V1 IS 4 WORDS.

  WORD 00  ARENA_ID ! ARENA_CLASS ! FLAGS ! SPEED_RANK ! ACCESS_RANK
  WORD 01  ARENA_START_BLOCK
  WORD 02  ARENA_BLOCK_COUNT
  WORD 03  FREE_HINT ! GENERATION ! CHECKSUM_SMALL

WORD 00:

  BITS 0..5     ARENA_ID6
  BITS 6..11    ARENA_CLASS6
  BITS 12..23   FLAGS12
  BITS 24..29   SPEED_RANK6
  BITS 30..35   ACCESS_RANK6

ARENA_CLASS6 STANDARD VALUES:

  0 INVALID
  1 SYSREAD
  2 WORK
  3 NORMAL
  4 COLD
  5 SPILL_RESERVED
  6..63 PROFILE-DEFINED

WORD 01:

  BITS 0..35 ARENA_START_BLOCK36, ABSOLUTE WITHIN D6FS FILESYSTEM

WORD 02:

  BITS 0..35 ARENA_BLOCK_COUNT36

WORD 03:

  BITS 0..17 FREE_HINT18
  BITS 18..29 GENERATION12
  BITS 30..35 CHECKSUM_SMALL6

THE ARENA TABLE AS A WHOLE IS PROTECTED BY ITS METADATA BLOCK CHECKSUM.  THE
SMALL CHECKSUM IS ONLY A QUICK DIAGNOSTIC HINT.

### 16.2 PLACEMENT POLICY

NEW FILE PLACEMENT IS SELECTED BY:

  1. EXPLICIT MOUNT/VIEW POLICY;
  2. PARENT DIRECTORY POLICY;
  3. CREATION HINT;
  4. FALLBACK ARENA.

DEFAULT POLICY:

  /BIN, /LIB, /SBIN     -> SYSREAD DURING INSTALL/UPDATE ONLY
  /TMP, /VAR/TMP, BUILD -> WORK
  ORDINARY FILES        -> NORMAL
  ARCHIVE/DOCS          -> COLD ONLY BY EXPLICIT TOOL/POLICY

THE KERNEL MUST NOT HARDCODE SPECIFIC PATHNAMES FOR POLICY.  POLICY COMES FROM
CONFIG/VIEW/MOUNT METADATA.

### 16.3 ALLOCATION PREFERENCE

ALLOCATOR SHOULD PREFER:

  - CONTIGUOUS RUNS;
  - SAME ARENA AS POLICY TARGET;
  - NO SPILL UNLESS POLICY PERMITS;
  - NO USE OF BAD OR SUSPECT BLOCKS;
  - LOCALITY COMPATIBLE WITH ARENA/ACCESS HINTS.

## 17. FREE-SPACE MAP

### 17.1 FORMAT

D6FS V1 USES PER-ARENA FREE-SPACE BITMAPS PLUS SUMMARIES.

UNIT:

  1 BIT = ONE 128-WORD FILESYSTEM BLOCK

### 17.2 BITMAP MEANING

REQUIRED CONVENTION:

  BIT 0 = ALLOCATED/UNAVAILABLE
  BIT 1 = FREE

BAD BLOCKS ARE NEVER REPRESENTED AS FREE.

### 17.3 FREE-MAP HEADER

D6FS_FREEMAP_HEADER_V1 IS 4 WORDS.

  WORD 00  MAGIC/VERSION/ARENA_ID
  WORD 01  BITMAP_START_BLOCK ! SUMMARY_START_BLOCK
  WORD 02  ARENA_BLOCK_COUNT
  WORD 03  FREE_COUNT_OR_HINT ! GENERATION ! CHECKSUM_SMALL

WORD 00:

  BITS 0..17    MAGIC18 = SIXBIT "FRM"
  BITS 18..23   VERSION6 = 1
  BITS 24..29   ARENA_ID6
  BITS 30..35   FLAGS6

WORD 01:

  BITS 0..17    BITMAP_START_BLOCK18
  BITS 18..35   SUMMARY_START_BLOCK18

WORD 02:

  BITS 0..35    ARENA_BLOCK_COUNT36

WORD 03:

  BITS 0..17    FREE_COUNT_HINT18
  BITS 18..29   GENERATION12
  BITS 30..35   CHECKSUM_SMALL6

### 17.4 AUTHORITY

DURING NORMAL OPERATION THE FREE MAP IS AUTHORITATIVE.  DURING FSCK THE FREE
MAP CAN BE RECONSTRUCTED FROM ALL LIVE HEAD AND CONTINUATION FCB RUNS.

## 18. BAD MEDIA AND RESERVED SYSTEM OBJECTS

### 18.1 POLICY

D6FS DOES NOT CARRY A MANDATORY SEPARATE BAD-MEDIA TABLE IN THE LIVE V1 FORMAT.
BAD PHYSICAL MEDIA, SWAP AREAS, LOG AREAS, AND OTHER RESERVED PHYSICAL RANGES
ARE REPRESENTED AS HIDDEN PINNED SYSTEM FCBS WHEN THE DEVICE/PROFILE REQUIRES
THEM.

THE ALLOCATOR ONLY NEEDS ONE RULE:

'''TEXT
ALLOCATED PINNED FCB RUNS ARE NOT FREE
'''

IT DOES NOT NEED TO KNOW WHETHER A PINNED HIDDEN OBJECT REPRESENTS BAD MEDIA,
SWAP, LOGS, BOOTSTREAM RESERVATION, OR ANOTHER MAINTENANCE-ONLY RANGE.

BAD-MEDIA SOURCES:

  - FORMATTER;
  - RUNTIME I/O ERROR;
  - FSCK VERIFICATION;
  - OPERATOR DIAGNOSTICS.

### 18.2 SYSTEM FCB REPRESENTATION

RESERVED MEDIA OBJECTS USE NORMAL FCB RUN OWNERSHIP WITH THESE FLAGS:

'''TEXT
SYSTEM
PINNED
UNLINKED
'''

'SYSTEM' MARKS THE OBJECT AS KERNEL/MAINTENANCE-OWNED. 'PINNED' PREVENTS PACK
OR PLACEMENT TOOLS FROM MOVING IT. 'UNLINKED' KEEPS IT OUT OF ORDINARY
DIRECTORY ENUMERATION. MAINTENANCE TOOLS CAN STILL FIND AND LABEL THE OBJECT
THROUGH SUPERBLOCK SYSTEM-OBJECT POINTERS OR PRIVILEGED SCANS.

THE CURRENT SUPERBLOCK RESERVES SYSTEM-OBJECT WORDS FOR:

'''TEXT
WORD 7: BOOTSTREAM_FCB18 ! SWAPFAST_FCB18
WORD 8: LOGSTORE_FCB18   ! RESERVED18
'''

BAD-MEDIA FCBS ARE INTENTIONALLY NOT A FIXED SUPERBLOCK ROLE. REAL-MEDIA
PROFILES MAY CREATE THEM DURING FORMATTING OR FSCK; CLEAN EMULATOR PROFILES CAN
COMPILE OUT EVEN THE BAD-MEDIA IMPORT STUBS.

### 18.3 HANDLING

RULES:

  - ALLOCATOR NEVER USES BLOCKS OWNED BY HIDDEN PINNED SYSTEM FCBS AS FREE;
  - PACKER MAY EVACUATE SUSPECT BLOCKS IF READABLE;
  - FSCK REPORTS FILES WITH UNREADABLE OWNED BLOCKS;
  - V1 DOES NOT REQUIRE HEROIC LOW-LEVEL SECTOR REMAPPING.

## 19. METADATA INTENT LOG

### 19.1 SCOPE

D6FS V1 USES A SMALL METADATA INTENT LOG.  IT JOURNALS METADATA INTENT RECORDS
ONLY.  IT DOES NOT JOURNAL FILE DATA.

INTENT LOG COVERS:

  - CREATE;
  - UNLINK;
  - RENAME;
  - MKDIR/RMDIR;
  - SYMLINK;
  - FCB ALLOCATION/FREE;
  - FCB METADATA UPDATE;
  - RUN ALLOCATION/FREE;
  - FREE-MAP UPDATE;
  - DIRECTORY ENTRY INSERT/REMOVE/UPDATE;
  - IMAGE/OVERLAY METADATA UPDATE;
  - ARENA SPILL/PACK STATE CHANGES.

### 19.2 TRANSACTION MODEL

EACH METADATA TRANSACTION HAS:

  TRANSACTION_ID
  OPERATION TYPE
  TARGET FS_UUID AND LAYOUT GENERATION
  AFFECTED FCB IDS
  AFFECTED DIRECTORY FCB IDS
  AFFECTED RUN/FREE-MAP RANGES
  BEFORE/AFTER DATA SUFFICIENT TO REPLAY OR ROLL BACK
  COMMIT MARKER
  CHECKSUM

### 19.3 INTENT-LOG RECORD HEADER

D6FS_LOGREC_HEADER_V1 IS 4 WORDS, FOLLOWED BY OPERATION-SPECIFIC PAYLOAD.

  WORD 00  MAGIC/VERSION/OPCODE/STATE

  WORD 03  PAYLOAD_WORDS ! CHECKSUM_PART

WORD 00:

  BITS 0..17    MAGIC18 = SIXBIT "LOG"
  BITS 18..23   VERSION6 = 1
  BITS 24..29   OPCODE6
  BITS 30..35   TX_STATE6

OPCODE6 STANDARD VALUES:

  0 INVALID
  1 CREATE
  2 UNLINK
  3 RENAME
  4 MKDIR
  5 RMDIR
  6 SYMLINK
  7 FCB_ALLOC

  9 FCB_UPDATE

 11 RUN_FREE
 12 FREEMAP_UPDATE
 13 DIR_UPDATE
 14 IMAGE_OVERLAY_UPDATE

 16..63 RESERVED

TX_STATE6 VALUES:

  0 INVALID
  1 INTENT
  2 PREPARED
  3 COMMITTED
  4 APPLIED
  5 CANCELLED
  6..63 RESERVED

WORD 01:

  BITS 0..35 TRANSACTION_ID36

WORD 02:

  BITS 0..17 TARGET_FCB18
  BITS 18..35 TARGET_DIR_FCB18

WORD 03:

  BITS 0..17 PAYLOAD_WORDS18
  BITS 18..35 CHECKSUM_PART18

### 19.4 RECOVERY

ON MOUNT AFTER DIRTY STATE:

  1. VALIDATE SUPERBLOCK AND LOG HEADER;
  2. SCAN INTENT LOG;
  3. IGNORE INCOMPLETE/UNCOMMITTED TRANSACTIONS;
  4. REPLAY COMMITTED TRANSACTIONS NOT FULLY APPLIED;
  5. MARK APPLIED WHERE NEEDED;
  6. RUN QUICK CONSISTENCY CHECKS;
  7. MOUNT NORMALLY OR REQUIRE FSCK IF INCONSISTENT.

FILE DATA IS NOT JOURNALED.  DATA DURABILITY DEPENDS ON WRITE/FSYNC ORDERING.

## 20. MOUNT, DISMOUNT, DIRTY-STATE, AND RECOVERY RULES

### 20.1 FILESYSTEM STATES

STATE VALUES ARE STORED IN THE SUPERBLOCK STATE FIELD:

  CLEAN
  DIRTY
  DEGRADED
  PACK_NEEDED
  FSCK_NEEDED

### 20.2 MOUNT RULES

CLEAN:

  MOUNT NORMALLY.

DIRTY:

  REPLAY INTENT LOG, RUN QUICK CHECKS, THEN MOUNT OR REQUIRE REPAIR.

DEGRADED:

  MOUNT ALLOWED, MAINTENANCE NOTIFIED.

PACK_NEEDED:

  MOUNT ALLOWED, PACKER SCHEDULED.

FSCK_NEEDED:

  READ-ONLY OR RESCUE MOUNT UNTIL FSCK SUCCEEDS.

### 20.3 DISMOUNT RULES

CLEAN DISMOUNT MUST:

  - FLUSH DIRTY FILE DATA;
  - FLUSH METADATA;
  - FLUSH INTENT-LOG COMPLETION STATE;
  - FLUSH CONFIG/LOG STORES IF PRESENT;
  - WRITE CLEAN GENERATION/STATE;
  - UPDATE CHECKSUM.

### 20.4 P6SYS

P6SYS CANNOT BE FULLY DISMOUNTED WHILE RUNNING.  CLEAN SHUTDOWN WRITES CLEAN.
UNCLEAN RESTART REPLAYS THE INTENT LOG BEFORE NORMAL BOOT.

### 20.5 P6VOL

P6VOL IS EXPLICITLY MOUNTED/DISMOUNTED.  DIRTY REMOVAL REQUIRES REPLAY/FSCK ON
NEXT MOUNT.

## 21. CACHE AND WRITEBACK POLICY

### 21.1 CACHE UNIT

D6FS V1 USES A SMALL UNIFIED BLOCK BUFFER CACHE.

  CACHE UNIT = 128-WORD FILESYSTEM BLOCK

### 21.2 PRIORITY

PRIORITY ORDER:

  HIGHEST:
    INTENT LOG
    FCB BLOCKS
    FREE MAPS
    DIRECTORY BLOCKS

  MEDIUM:
    RECENTLY USED FILE DATA

  LOW:
    SEQUENTIAL SCAN DATA
    WORK/TEMP DATA

### 21.3 WRITE POLICY

RULES:

  - WRITE-BACK FOR NORMAL FILES;
  - WRITE-THROUGH OR FORCED ORDERING FOR INTENT-LOG COMMIT RECORDS;
  - READ-AHEAD FOR SEQUENTIAL RUNS;
  - DELAYED WRITE ALLOWED EXCEPT FSYNC/SYNC/DISMOUNT;
  - DIRTY METADATA MUST BE FLUSHED BEFORE CLEAN STATE IS WRITTEN.

NO VM/PAGE-CACHE SOPHISTICATION IS REQUIRED IN V1.

## 22. CORE FILESYSTEM OPERATIONS

### 22.1 CREATE

CREATE:

  - CHECKS PARENT DIRECTORY WRITE/SEARCH PERMISSION;
  - ALLOCATES A HEAD FCB;
  - ALLOCATES INITIAL DATA ONLY IF NEEDED;
  - INSERTS A LIVE DIRECTORY ENTRY;
  - RECORDS METADATA INTENT TRANSACTION.

### 22.2 UNLINK

UNLINK:

  - CHECKS CONTAINING DIRECTORY PERMISSIONS;
  - REMOVES THE DIRECTORY ENTRY ATOMICALLY;
  - IF FILE IS NOT OPEN, FREES FCB/RUNS;
  - IF FILE IS OPEN, MARKS FCB RUNTIME-UNLINKED AND FREES AFTER LAST CLOSE.

### 22.3 MKDIR/RMDIR

MKDIR CREATES A DIR OBJECT AND INITIALIZES PARENT_FCB.

RMDIR REQUIRES THE DIRECTORY TO BE EMPTY EXCLUDING SYNTHESIZED '.' AND '..' AND
WHITEOUT RULES AS APPLICABLE.

### 22.4 READ/WRITE

READ MAPS LOGICAL WORD/BYTE OFFSETS THROUGH RUN LISTS.  WRITE ALLOCATES REAL
STORAGE WHEN EXTENDING.  NO SPARSE HOLES ARE CREATED.

### 22.5 CHMOD/CHOWN MAPPING

CHMOD UPDATES PROTECTION_WORD.  CHOWN UPDATES OWNER_USER/OWNER_PROJECT.  UNIX
UID/GID/MODE MAPPINGS MUST REMAIN THIN AND DETERMINISTIC.

## 23. RENAME, FSYNC, AND DURABILITY PATTERNS

### 23.1 RENAME SEMANTICS

D6FS V1 SUPPORTS UNIX-LIKE ATOMIC RENAME WITHIN ONE MOUNTED FILESYSTEM/VIEW.

RULES:

  - FILE RENAME IS ATOMIC;
  - DIRECTORY RENAME IS ATOMIC WITH LOOP/ANCESTOR CHECKS;
  - REPLACEMENT OF EXISTING TARGET FOLLOWS UNIX-LIKE RULES;
  - CROSS-FILESYSTEM RENAME FAILS;
  - AFTER CRASH/RECOVERY EITHER OLD NAME OR NEW NAME MUST BE VALID, NOT A
    HALF-CREATED NAMESPACE STATE.

### 23.2 FSYNC AND SYNC

D6FS V1 SUPPORTS:

  FSYNC(FD)
  SYNC()
  CLEAN DISMOUNT VOLUME/STORE SYNC

NO FULL SYNCHRONOUS MOUNT MODE IS REQUIRED IN V1.

FSYNC(FD) FLUSHES:

  - DIRTY DATA BLOCKS FOR THE FILE;
  - FILE SIZE;
  - RUN/FCB ALLOCATION METADATA NEEDED TO FIND FILE DATA;
  - MTIME/CTIME CHANGES;
  - ENOUGH METADATA THAT THE FILE REMAINS VALID AFTER CRASH/FSCK.

### 23.3 DIRECTORY FSYNC

FOR V1, FSYNC(PARENT DIRECTORY) MEANS:

  FLUSH DIRECTORY METADATA AND RENAME/LINK/UNLINK RECORDS NEEDED TO MAKE THE
  NAMESPACE UPDATE DURABLE.

### 23.4 SAFE UPDATE PATTERN

REQUIRED SUPPORTED PATTERN:

  WRITE TEMP
  FSYNC(TEMP)
  RENAME TEMP FINAL
  FSYNC(PARENT DIRECTORY)

## 24. OPEN-UNLINK, TRUNCATE, APPEND, AND LOCKS

### 24.1 OPEN-UNLINK

D6FS V1 FOLLOWS UNIX-LIKE OPEN-UNLINK BEHAVIOR:

  - UNLINK REMOVES THE DIRECTORY ENTRY;
  - IF FILE IS OPEN, FCB/DATA REMAIN ALIVE UNTIL LAST CLOSE;
  - NO NEW PATH LOOKUP CAN FIND IT;
  - STORAGE IS FREED AFTER LAST RUNTIME REFERENCE DISAPPEARS.

OPEN-REFERENCE COUNTS ARE RUNTIME KERNEL STATE, NOT PERSISTENT METADATA.

### 24.2 TRUNCATE/FTRUNCATE

TRUNCATE/FTRUNCATE ARE SUPPORTED FOR REG FILES.

RULES:

  - SHRINK FREES NOW-UNUSED RUNS;
  - EXTEND ALLOCATES AND ZERO-FILLS REAL STORAGE;
  - NO SPARSE HOLES IN V1;
  - TAIL_9BYTES IS UPDATED CONSISTENTLY;
  - DIR AND SYMLINK ARE NOT USER-TRUNCATED.

### 24.3 O_APPEND

D6FS V1 SUPPORTS O_APPEND.

RULES:

  - APPEND IS ATOMIC PER WRITE CALL;
  - KERNEL CHOOSES EOF AT WRITE TIME;
  - USERLAND SEEK POSITION IS IGNORED FOR APPEND WRITES;
  - FILE SIZE UPDATE IS PART OF THE SAME FILESYSTEM OPERATION;
  - NO PERSISTENT APPEND-ONLY ATTRIBUTE IN V1.

### 24.4 FILE LOCKS

D6FS V1 SUPPORTS WHOLE-FILE ADVISORY LOCKS.

RULES:

  - LOCKS ARE RUNTIME KERNEL STATE;
  - LOCKS ARE NOT STORED IN FILESYSTEM METADATA;
  - LOCKS VANISH ON CLOSE, PROCESS EXIT, OR REBOOT;
  - NO BYTE-RANGE LOCKS IN V1;
  - NO MANDATORY LOCKS IN V1.

UNIX MAPPING:

  - FLOCK-STYLE WHOLE-FILE LOCKING IS SUPPORTED;
  - FCNTL BYTE-RANGE LOCKING IS UNSUPPORTED OR REDUCED TO WHOLE-FILE ADVISORY
    SEMANTICS;
  - MANDATORY LOCKING IS UNSUPPORTED.

## 25. SYMLINKS AND SHEBANG EXECUTION

### 25.1 SYMLINK OBJECT

A SYMLINK IS AN FCB OBJECT OF TYPE SYMLINK.

PAYLOAD:

  - SIXBIT PATH STRING;
  - MAXIMUM SYMLINK TARGET LENGTH = 256 SIXBIT CHARS;
  - TARGET MAY BE ABSOLUTE OR RELATIVE;
  - NO UTF-9 SYMLINK TARGETS IN V1.

RECOMMENDED SYMLINK EXPANSION DEPTH:

  MAX_SYMLINK_DEPTH = 8

### 25.2 SHEBANG EXECUTION

SCRIPTS ARE REG FILES.  THERE IS NO SCRIPT FCB TYPE.

KERNEL EXEC LOADER RECOGNIZES #! AT THE START OF EXECUTABLE REG FILES.

RULES:

  - EXECUTABLE SCRIPT REQUIRES EXECUTE PERMISSION;
  - INTERPRETER PATH IS STRICT SIXBIT PATH;
  - NO PATH SEARCH INSIDE KERNEL;
  - ONE OPTIONAL INTERPRETER ARGUMENT AT MOST;
  - RECURSION DEPTH LIMIT, RECOMMENDED MAX_SHEBANG_RECURSION = 4;
  - OTHERWISE EXEC RETURNS ENOEXEC.

EXECUTABILITY RULE:

  A FILE IS RUNNABLE ONLY IF:
    - FCB TYPE IS REG;
    - EXECUTE PERMISSION IS SET;
    - FILE CONTENTS ARE RECOGNIZED BY EXEC LOADER AS DEXE OR #! SCRIPT OR
      ANOTHER SUPPORTED EXECUTABLE FORMAT.

FILENAME SUFFIXES SUCH AS .EXE ARE CONVENTIONS ONLY.

## 26. IMAGES, OVERLAYS, COPY-UP, AND WHITEOUTS

### 26.1 BASE IMAGES

A SEALED IMAGE IS A READ-ONLY FILESYSTEM TREE.

RULES:

  - MOUNTED READ-ONLY;
  - WRITES GO TO OVERLAY BY COPY-UP;
  - DIRECT WRITE TO SEALED IMAGE FAILS;
  - FSCK MAY VERIFY SEALED IMAGE CHECKSUMS/GENERATION;
  - PACKER MAY OPTIMIZE SEALED IMAGE ONLY DURING EXPLICIT IMAGE BUILD/COMMIT;
  - BASE IMAGES MAY CONTAIN READ-ONLY CONFIG DEFAULTS;
  - BASE IMAGES NEVER CONTAIN LIVE LOGS.

### 26.2 WRITABLE OVERLAYS

A WRITABLE OVERLAY CONTAINS MODIFICATIONS TO A BASE IMAGE:

  - LOCAL FILES/DIRECTORIES;
  - COPY-UP FILES;
  - WHITEOUT DIRECTORY ENTRIES;
  - PER-OVERLAY CONFIG OVERRIDES;
  - PER-OVERLAY INSTANCE LOGS IF CONFIGURED.

### 26.3 COPY-UP

WRITE TO BASE-ONLY FILE:

  1. COPY FILE METADATA/DATA INTO OVERLAY;
  2. MODIFY OVERLAY COPY;
  3. BASE REMAINS UNCHANGED.

DELETE BASE-ONLY FILE:

  1. CREATE OVERLAY WHITEOUT;
  2. BASE REMAINS UNCHANGED.

### 26.4 RENAME IN OVERLAYS/VIEWS

RULES:

  - RENAME INSIDE WRITABLE OVERLAY IS ATOMIC;
  - RENAME OF BASE-ONLY OBJECT CAUSES COPY-UP INTO OVERLAY, THEN RENAME;
  - RENAME OVER BASE-ONLY TARGET CREATES OVERLAY REPLACEMENT PLUS WHITEOUT OF
    BASE TARGET;
  - CROSS-VIEW/CROSS-FILESYSTEM RENAME FAILS.

### 26.5 COMMIT/REPACK

A COMMIT/REPACK OPERATION MAY MERGE BASE + LIVE OVERLAY INTO A NEW SEALED BASE
AND CLEAR THE LIVE OVERLAY.  THIS IS AN EXPLICIT MAINTENANCE/INSTALL OPERATION,
NOT BLOCK-LEVEL SNAPSHOTTING.

## 27. SYNTHETIC NAMESPACES AND /DEVICE

### 27.1 /DEVICE AND POSIX /DEV

/DEVICE IS THE DAIMOS NATIVE SYNTHETIC DEVICE NAMESPACE.  THE POSIX PERSONALITY
MAY EXPOSE /DEV AS A COMPATIBILITY VIEW OVER THE SAME KERNEL INVENTORY.

RULES:

  - GENERATED FROM LIVE DRIVER INVENTORY AND MACHINE CONFIG;
  - ORDINARY FILESYSTEMS DO NOT STORE REAL DEVICE NODES;
  - D6FS VOLUMES REMAIN PORTABLE AND DO NOT CONTAIN STALE HARDWARE NODES;
  - MKNOD() IS NOT A NORMAL FILESYSTEM OPERATION IN V1;
  - UNIX COMPATIBILITY MAPS /DEV ACCESS ONTO THE SYNTHETIC /DEVICE NAMESPACE.

EXAMPLES OF NATIVE SYNTHETIC NAMES:

  /DEVICE/CTY0
  /DEVICE/TTY0
  /DEVICE/DSK0
  /DEVICE/DSK1
  /DEVICE/DTC0
  /DEVICE/MTC0

### 27.2 /CONFIG AND POSIX /ETC OR /VAR/LOG

NATIVE CONFIG/LOG STATE IS TYPED STORE DATA, NOT ORDINARY AUTHORITATIVE TEXT
FILES.  /CONFIG IS THE DAIMOS NATIVE SYNTHETIC CONFIGURATION VIEW WHEN THAT
STORE EXISTS.

SYNTHETIC POSIX VIEWS MAY EXPOSE:

  /ETC
  /VAR/LOG

UNIX PERSONALITY MAY RENDER TEXT FILES FROM TYPED STORES, BUT THE TYPED STORES
ARE AUTHORITATIVE.

## 28. /HOME AND MOUNT POLICY

/HOME PLACEMENT IS POLICY-DRIVEN.

RULES:

  - /HOME IS NOT HARDCODED TO P6SYS OR P6VOL;
  - USER HOME ROOTS MAY LIVE ON P6SYS, P6VOL, DTFS, OR LATER REMOTE/NETWORK
    FILESYSTEMS;
  - KERNEL FILESYSTEM PROFILES DO NOT HARDCODE /HOME PLACEMENT;
  - COMPILER SCRATCH AND TEMPORARY FILES SHOULD DEFAULT TO P6SYS WORK OR ANOTHER
    CONFIGURED WORK ARENA, NOT NECESSARILY THE USER'S HOME MEDIUM.

DTFS MAY LATER PROVIDE SMALL USER HOMES, BUT DTFS ITSELF IS OUTSIDE THIS D6FS
DOCUMENT.

## 29. MAINTENANCE, PACKING, SPILL, AND HEAT PROMOTION

### 29.1 HEALTH STATES

D6FS HEALTH STATES:

  OK/CLEAN
  DIRTY
  DEGRADED
  PACK_NEEDED
  FSCK_NEEDED

### 29.2 PACKER LEVELS

LEVEL 0 ONLINE CLEANUP:

  - DELETE STALE TEMP;
  - TRIM/ROTATE RINGS;
  - REBUILD SUMMARIES;
  - CLEAR DEAD SPILL;
  - CAN RUN ONLINE.

LEVEL 1 IDLE ONLINE REPAIR:

  - REPAIR TEMP SPILL;
  - MOVE CLOSED/NONCRITICAL FILES;
  - RESTORE ARENA LOCALITY;
  - REDUCE ORDINARY FRAGMENTATION;
  - LOW I/O ONLY.

LEVEL 2 ONLINE FULL PACK, BEST EFFORT:

  - COMPACT NORMAL/COLD/WORK;
  - REPAIR SURVIVING SPILL;
  - REDUCE FILES TO FEWER RUNS;
  - SKIP OPEN/UNSAFE OBJECTS;
  - ALLOWED BUT NOT REQUIRED/RELIABLE IN V1.

LEVEL 3 BOOT/SINGLE-USER/RESCUE/QUIESCENT PACK:

  - MOVE CRITICAL OBJECTS;
  - REBUILD SYSREAD PERFECTLY;
  - RESIZE/REBUILD ARENAS;
  - REPAIR METADATA PLACEMENT;
  - GUARANTEED COMPLETE REPAIR PATH.

### 29.3 V1 REQUIREMENTS

D6FS V1 REQUIRES:

  - CONTROLLED AUTOMATIC SPILL;
  - DEGRADED/PACK_NEEDED HEALTH STATES;
  - MAINTENANCE TRIGGER/EVENT SUPPORT;
  - LEVEL 0 CLEANUP ONLINE;
  - LEVEL 1 SAFE ONLINE REPAIR OF CLOSED/NONCRITICAL FILES;
  - BOOT/QUIESCENT PACK IF PACK_NEEDED REMAINS SET;
  - OPERATOR COMMAND TO FORCE PACK AT NEXT BOOT.

### 29.4 HEAT PROMOTION

IF HEAT TRACKING IS ENABLED, MAINTENANCE MAY PROMOTE FREQUENTLY ACCESSED CLOSED
FILES FROM NORMAL/COLD INTO HOTTER ARENAS.

RULES:

  - NEVER SYNCHRONOUS WITH READ;
  - NEVER REQUIRED FOR CORRECTNESS;
  - NEVER CHANGES FILE IDENTITY;
  - SKIPPED FOR OPEN/UNSAFE FILES;
  - CONTROLLED BY MOUNT/ARENA POLICY.

## 30. P6SYS LAYOUT RELATIONSHIP

P6SYS DISK-SET LAYOUT IS OUTSIDE THE ORDINARY D6FS SUPERBLOCK.

P6SYS STRUCTURE:

  P6SYS DISK-SET LABEL / REGION TABLE
    -> BOOTSAFE
    -> KERNEL
    -> SWAPFAST
    -> CFGSTORE
    -> LOGSTORE
    -> FSREGION

FSREGION CONTAINS A D6FS SUPERBLOCK AND ORDINARY FILESYSTEM METADATA.

P6SYS REGION DESCRIPTORS SHOULD INCLUDE:

  REGION_ID
  CLASS
  MEMBER/MAPPING
  START/COUNT OR MAPPING TABLE
  OWNER_SUBSYSTEM
  ACCESS_MODE
  OVERLAP_GROUP
  PRIORITY
  FLAGS

USEFUL FLAGS:

  EXCLUSIVE_ALLOC
  VIEW_ONLY
  SYNTHETIC
  RAW_DEBUG
  BOOT_VISIBLE
  MIRROR
  NOFS

P6SYS BOOT/KERNEL/SWAP/CONFIG/LOG REGIONS ARE OUTSIDE ORDINARY FILE ALLOCATION.

## 31. P6VOL LAYOUT RELATIONSHIP

P6VOL IS A MOUNTABLE D6FS VOLUME, NORMALLY ONE DISK.

P6VOL CONTAINS:

  - D6FS SUPERBLOCK;
  - FCB TABLE;
  - ARENA TABLE;
  - FREE MAPS;
  - OPTIONAL IMAGE TABLE;
  - OPTIONAL OVERLAY TABLE;
  - OPTIONAL CONFIG STORE POINTER;
  - OPTIONAL LOG STORE POINTER;
  - HIDDEN PINNED SYSTEM FCBS FOR RESERVED RANGES IF NEEDED;
  - ORDINARY DATA ARENAS.

P6VOL DOES NOT CONTAIN BY DEFAULT:

  - BOOTSAFE;
  - KERNEL;
  - SWAPFAST;
  - MACHINE IDENTITY;
  - GLOBAL SYSTEM LOGS.

P6VOL MAY STILL CONTAIN SEALED IMAGES AND OVERLAYS.

## 32. VALIDATION AND FSCK RULES

### 32.1 BASIC VALIDATION

FSCK MUST VALIDATE:

  - SUPERBLOCK MAGIC/VERSION/CHECKSUM;
  - FS_UUID CONSISTENCY BETWEEN PRIMARY/ALTERNATE SUPERBLOCK;
  - STATE AND GENERATION FIELDS;
  - TABLE POINTERS WITHIN VALID METADATA AREA;
  - ARENA TABLE SANITY;
  - FREE-MAP SANITY;
  - FCB CHECKSUMS;
  - DIRECTORY RECORDS;
  - INTENT-LOG REPLAY STATE;
  - HIDDEN PINNED RESERVED/BAD-MEDIA OBJECT EXCLUSION.

### 32.2 FCB VALIDATION

FOR EVERY HEAD FCB:

  - OBJECT_TYPE IS REG/DIR/SYMLINK;
  - ROLE IS HEAD;
  - TAIL_9BYTES IS 0..3;
  - SPARSE FLAG IS ZERO;
  - DIRECT RUNS ARE VALID OR UNUSED;
  - CONTINUATION CHAIN HAS NO LOOPS;
  - CONTINUATION SEQUENCE NUMBERS ARE MONOTONIC;
  - CONTINUATION RECORDS POINT BACK TO THE HEAD;
  - ALLOCATED BLOCKS ARE NOT DOUBLE-OWNED.

### 32.3 DIRECTORY VALIDATION

FOR EVERY DIRECTORY:

  - DIRECTORY FCB TYPE IS DIR;
  - RECORDS ARE 6-WORD ALIGNED;
  - LIVE ENTRIES REFERENCE HEAD FCBS ONLY;
  - WHITEOUT ENTRIES HAVE FCB_ID = 0;
  - DSYM24 NAMES ARE VALID SIXBIT;
  - NO INVALID OBJECT TYPE CACHE VALUES;
  - PARENT_FCB SEMANTICS ARE VALID FOR ROOT AND NORMAL DIRECTORIES;
  - NO DIRECTORY LOOPS EXCEPT ROOT SELF-PARENT RULE.

### 32.4 FREE-MAP VALIDATION

FSCK MAY REBUILD FREE MAPS FROM FCB RUNS.

RULES:

  - ALLOCATED BLOCKS OWNED BY EXACTLY ONE RUN;
  - FREE BLOCKS NOT REFERENCED BY ANY RUN;
  - BAD/SUSPECT/RETIRED BLOCKS NOT FREE;
  - METADATA BLOCKS PROTECTED FROM ALLOCATION.

### 32.5 INTENT-LOG VALIDATION

ON DIRTY MOUNT OR FSCK:

  - INCOMPLETE/UNCOMMITTED TRANSACTIONS IGNORED;
  - COMMITTED BUT UNAPPLIED TRANSACTIONS REPLAYED;
  - APPLIED TRANSACTIONS MAY BE CHECKPOINTED/CLEARED;
  - INVALID CHECKSUM OR IMPOSSIBLE TRANSACTION FORCES FSCK_NEEDED.

## 33. RESERVED FEATURES AND EXPLICIT EXCLUSIONS

RESERVED BUT NOT IMPLEMENTED IN D6FS V1:

  - UTF-9 FILENAMES;
  - FULL ACLS/CAPABILITIES;
  - ARBITRARY HARD LINKS;
  - SPARSE FILES;
  - BYTE-RANGE LOCKS;
  - MANDATORY LOCKS;
  - ENFORCED QUOTAS;
  - FILESYSTEM ACCOUNTING COUNTERS;
  - FULL METADATA JOURNAL;
  - DATA JOURNAL;
  - COW METADATA TREE;
  - DEVICE NODES IN ORDINARY FILESYSTEMS;
  - FULL ONLINE ACTIVE-FILE PACKER;
  - ONLINE SYSREAD PERFECT REPACK WHILE MULTI-USER ACTIVE;
  - ONLINE ARENA RESIZING;
  - DTFS FORMAT;
  - P6ARC FORMAT.

UNSUPPORTED FLAGS MUST BE ZERO UNLESS A LATER COMPATIBLE PROFILE EXPLICITLY
DEFINES THEM.
