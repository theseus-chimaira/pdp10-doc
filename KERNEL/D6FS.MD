# DAIMOS D6FS V2 TECHNICAL SPECIFICATION

*COMPACT NATIVE DISK FILESYSTEM FOR PDP-6 THROUGH KL10-CLASS DAIMOS*

## DOCUMENT METADATA

- STATUS: DESIGN FREEZE; CONSERVATIVE CRASH-RECOVERY CONTRACT IMPLEMENTED
- DATE: 2026-09-22
- SCOPE: D6FS CORE FORMAT, SEMANTICS, AND LOGICAL-BLOCK CONTRACT
- ENCODING: PLAIN ASCII; ALL ON-DISK WORDS ARE 36-BIT PDP-10 WORDS

## 1. PURPOSE

D6FS IS THE NATIVE DAIMOS DISK FILESYSTEM.  V2 DELIBERATELY KEEPS STORAGE
POLICY OUT OF THE FILESYSTEM AND RETAINS ONLY THE FORMAT AND RUNTIME SEMANTICS
NEEDED TO STORE FILES EFFICIENTLY ON PDP-6/KA10 THROUGH KL10-CLASS SYSTEMS.

D6FS IS:

- HIERARCHICAL;
- EXTENT BASED;
- UNIX-PERMISSIONED;
- MOUNTED ON ONE LINEAR LOGICAL BLOCK REGION EXPORTED BY A LOWER BLOCK LAYER;
- DETECTS UNCLEAN SHUTDOWN; CURRENT BASELINE RECOVERY IS FSCK WHILE THE
  REQUIRED BOUNDED MOUNT-TIME RECOVERY PROTOCOL IS REOPENED;
- SMALL ENOUGH FOR THE 32K-WORD PDP-6 SYSTEM BASELINE;
- LARGE ENOUGH IN FORMAT FOR PRACTICAL KL10-CLASS VOLUMES.

D6FS IS NOT A BLOCKSET IMPLEMENTATION, RAID IMPLEMENTATION, PHYSICAL-MEDIA
MAPPER, JOURNALED FILESYSTEM, SNAPSHOT SYSTEM, OVERLAY FILESYSTEM, OR GENERAL
STORAGE-POLICY ENGINE.

## 2. FROZEN SIMPLIFICATIONS

THE FOLLOWING OLD D6FS/P6SYS FEATURES ARE REMOVED FROM D6FS V2:

- CONFIGFS / CFGSTORE INTEGRATION;
- HOT/COLD/SYSREAD/WORK ARENAS;
- HEAT TRACKING AND HEAT PROMOTION;
- SPILL POLICY;
- THE DAIMOSV1 FSUNDO IMPLEMENTATION AS-IS; D6FS V2 INSTEAD USES THE FROZEN
  CONSERVATIVE DIRTY-MEDIA/FSCK RECOVERY CONTRACT DESCRIBED BELOW;
- METADATA CHECKSUMS;
- CONTINUATION FCBS;
- SEALED IMAGES;
- OVERLAYS, COPY-UP, WHITEOUTS, AND OPAQUE DIRECTORIES;
- D6FS VIEW COMPOSITION;
- ONLINE PACK LEVELS AND PACK_NEEDED STATE;
- BLOCKSET ASSEMBLY OR STRIPING;
- BAD-PHYSICAL-SECTOR REPRESENTATION;
- PHYSICAL SEEK SCHEDULING;
- D6FS-OWNED BOOTSTREAM ALLOCATION.

CONFIGURATION IS A HIGHER-LEVEL OR SYNTHETIC-NAMESPACE CONCERN.  BLOCKSET
ASSEMBLY AND PHYSICAL-MEDIA POLICY ARE SPECIFIED IN 'KERNEL/BLOCKSET.MD' AND
THE DEVICE/BOOT DOCUMENTS.  D6FS DOES OWN THE LOGICAL BLOCK RESERVATIONS FOR
OPTIONAL SWAP AND LOGSTORE AREAS, BUT DOES NOT GIVE THEM FILE/FCB SEMANTICS.

## 3. WORD AND BLOCK CONVENTIONS

ALL D6FS WORDS ARE 36 BITS.

BIT NUMBERING:

    BIT 0   MOST SIGNIFICANT
    BIT 35  LEAST SIGNIFICANT
    LH      BITS 0..17
    RH      BITS 18..35

ONE D6FS BLOCK IS 128 36-BIT WORDS.

D6FS ADDRESSES BLOCKS IN ONE LINEAR FILESYSTEM-REGION ADDRESS SPACE.  BLOCK 0
IS THE FIRST BLOCK OF THE D6FS REGION, NOT BLOCK 0 OF A PHYSICAL DISK OR OF THE
WHOLE BLOCKSET.  PHYSICAL MEMBER NUMBER, CYLINDER, TRACK, SECTOR, BAD-MEDIA
REMAPS, STRIPE ZONES, SWAP, LOGSTORE, AND BOOT REGIONS ARE NOT STORED IN FCBS
OR EXTENTS.

## 4. STORAGE BOUNDARY

D6FS CONSUMES ONE LINEAR LOGICAL BLOCK SPACE EXPORTED BY THE LOWER BLOCK/
BLOCKSET LAYER.  PHYSICAL MEMBER SELECTION, STRIPING, SEEK/ROTATION SCHEDULING,
AND BAD-MEDIA MAPPING REMAIN BELOW D6FS.

D6FS V2 MAY PERSIST AT MOST ONE SWAP RESERVATION AND AT MOST ONE LOGSTORE
RESERVATION.  EITHER MAY BE ABSENT/ZERO-SIZED.  THESE ARE SUPERBLOCK METADATA,
NOT BLOCKSET SEMANTICS.  WORD 005 ENCODES SWAP START24|LENLOW12, WORD 006
ENCODES LOGSTORE START24|LENLOW12, AND WORD 017 CARRIES SWAP LENHIGH12 AT
NUMERIC SHIFT 24 AND LOGSTORE LENHIGH12 AT NUMERIC SHIFT 12; ITS LOW 12 BITS
REMAIN RESERVED ZERO.  FORMATTERS AND MAINTENANCE TOOLS MUST PRESERVE THIS
ENCODING.

LOGSTORE IS A RESERVED RANGE INSIDE D6FS TOTAL_BLOCKS AND IS EXCLUDED FROM THE
AUTHORITATIVE FREE MAP.  CURRENT DSK SWAP IS DIFFERENT: ITS LOGICAL START MUST
EQUAL D6FS TOTAL_BLOCKS AND ITS LENGTH EXTENDS INTO THE RAW TRAILING CAPACITY
EXPORTED BY THE LOWER STORAGE LAYOUT.  DBOOT CONTINUES TO DESCRIBE THAT PHYSICAL
CAPACITY, BUT THE D6FS SUPERBLOCK IS THE AUTHORITATIVE ACTIVE SWAP RESERVATION
ON NEW MEDIA.  LEGACY V2 MEDIA WITH ZEROED SWAP FIELDS AND A NONZERO DBOOT
TAIL MUST BE UPGRADED OFFLINE WITH `D6SWAP --MIGRATE-RESERVATION`.  THE KERNEL
NO LONGER USES THE DBOOT TAIL AS A SEMANTIC SWAP FALLBACK.

THE GENERAL CONTRACT IS FOR ACTIVE STORAGE SERVICES TO BE OWNED BY A SPECIFIC
VFS MOUNT.  VFS PACKS DISTINCT SWAP AND LOGSTORE OWNERSHIP BITS INTO ITS
EXISTING MOUNT-FLAG WORD, SO NO PER-MOUNT DATA WORD IS ADDED.  AT MOST ONE
MOUNT MAY OWN SWAP AND AT MOST ONE MAY OWN LOGSTORE.  `VFS_UNMOUNT` REJECTS A
MOUNT BEFORE SYNC OR PROVIDER TEARDOWN WHILE EITHER TYPE REMAINS ACTIVE.
`VFS_STORAGE_RELEASE` RELEASES ONLY THE REQUESTED OWNED TYPE; RELEASING SWAP
DOES NOT DROP A LOGSTORE PIN, AND VICE VERSA.

THE CURRENT ROOT BOOT PATH STILL VALIDATES THE SELECTED D6FS SUPERBLOCK
DIRECTLY, CACHES THE SWAP RANGE IN THE FIXED PDP-6 FAST PATH, AND ACTIVATES
LOGSTORE FROM THE SAME SELECTED SUPERBLOCK.  FILESYSTEM-INDEPENDENT LOGICAL
BACKING IS IMPLEMENTED AS A THREE-WORD RUNTIME DESCRIPTOR:

    WORD 0   READ-CALLBACK,,WRITE-CALLBACK
    WORD 1   BACKING-SPECIFIC OPAQUE WORD
    WORD 2   LOGICAL BLOCK CAPACITY

THE CALLBACK ABI RECEIVES THE OPAQUE WORD, LOGICAL BLOCK NUMBER, AND BLOCK
BUFFER.  D6FS EMBEDS THIS DESCRIPTOR IN EACH READER AND ALL FILE-BLOCK I/O
ENTERS THE GENERIC BACKING DISPATCHER.  DIRECT UNIT/BASE TRANSLATION AND THE
CURRENT ROOT-BLOCKSET BRIDGE ARE STORAGE-LAYER ADAPTERS; D6FS DOES NOT ENCODE
DSK270 OR BLOCKSET ROUTING POLICY.  A FUTURE PER-MOUNT STORAGE-SET CALLBACK MAY
USE THE OPAQUE WORD AS AN EXPLICIT REENTRANT BLOCKSET-DESCRIPTOR POINTER.

THE FIXED ROOT READER SINGLETON HAS BEEN REMOVED.  EACH MOUNTED D6FS INSTANCE
OWNS A 17-WORD READER FROM MANAGED CORE.  TWO WORDS SEPARATE THE FILESYSTEM UUID
FROM THE PHYSICAL A/B SUPERBLOCK LOCATIONS, SO RUNTIME MOUNT IDENTITY DOES NOT
OVERWRITE MEDIA IDENTITY.  FIXED KCORE HOLDS ONE ACTIVE-READER POINTER AND A
FOUR-WORD O(1) MOUNT-ID SLOT VECTOR; IT DOES NOT PREALLOCATE ANY READERS.
PROVIDER DISPATCH SELECTS THE READER FROM THE VNODE MOUNT ID BEFORE ENTERING
FILESYSTEM OPERATIONS.

THE RUNTIME `SYS_EXT_D6FS_MOUNT` PATH ACCEPTS A TRANSIENTLY VALIDATED 17-WORD
HANDOFF FOR A DIRECT DSK BACKING AND CURRENTLY CREATES READ-ONLY SECONDARY D6FS
MOUNTS.  THE PROVIDER ALLOCATES A NEW READER, CALLS VFS MOUNT, INSTALLS THE
READER ONLY AFTER VFS CHOOSES THE MOUNT SLOT, THEN REPLACES THE HANDOFF MARKER
WITH TRUSTED STORAGE-LAYER CALLBACKS.  ROOT AND SECONDARY INSTANCES THEREFORE
KEEP INDEPENDENT READER, BACKING, UUID, SUPERBLOCK, CACHE, AND READ-ONLY/WRITABLE
STATE.  PDP-6 target regressions execute the production selector, mount body,
and cache lookup and verify separation.  Full two-media SIMH acceptance is not
yet claimed because the available simulator configuration halts at the unrelated
SLV probe before userspace.  Typed per-mount reservation activation/lifetime is
implemented and PDP-6 target-validated through the production VFS
mount/release/unmount path.

D6FS CLEAN UNMOUNT AND RO<->RW REMOUNT ARE IMPLEMENTED WITH ONE SHARED A/B
SUPERBLOCK TRANSITION.  RW->RO WRITES THE OPPOSITE SUPERBLOCK COPY WITH AN
INCREMENTED SEQUENCE AND CLEAN STATE; ONLY AFTER THAT WRITE SUCCEEDS ARE THE
RUNTIME WRITABLE BIT AND VFS READ-ONLY POLICY CHANGED.  RO->RW WRITES DIRTY
FIRST AND ENABLES WRITES ONLY AFTER SUCCESS.  A FAILED SUPERBLOCK PUBLICATION
LEAVES THE SEQUENCE, SELECTED COPY, D6FS WRITABLE STATE, AND VFS POLICY
UNCHANGED.  WRITABLE UNMOUNT REUSES THE SAME CLEAN PUBLICATION BEFORE RECLAIMING
THE CLEAN-ONLY CACHE AND RELEASING THE MOUNT-OWNED READER.  D6FS DATA/METADATA
WRITES ARE SYNCHRONOUS AND THE DYNAMIC CACHE STORES CLEAN BLOCKS ONLY, SO THERE
IS NO SEPARATE DIRTY-BUFFER FLUSH QUEUE IN THIS TRANSITION.

THE ON-DISK CRASH-RECOVERY CONTRACT ALSO COVERS ALLOCATION/FREE-MAP/SUMMARY,
FCB/DIRECTORY, AND RESERVATION UPDATES.  THE SELECTED DIRTY GENERATION IS THE
RECOVERY BOUNDARY; D6FSCK MAY REPAIR ONLY STRUCTURALLY UNAMBIGUOUS OWNERSHIP.

ACTIVE SWAP/LOGSTORE I/O BYPASSES D6FS FILE I/O AND USES THE LOWER STORAGE PATH.

CONTIGUITY MEANS CONTIGUITY IN THE LOGICAL ADDRESS SPACE EXPORTED BY THE
STORAGE-SET LAYER.  KNOWN PHYSICAL BAD MEDIA ARE STABLY REMAPPED TO RESERVED
SPARES BELOW THIS LAYER; D6FS, SWAP, AND LOGSTORE MUST NOT MAINTAIN PARALLEL
BAD-BLOCK TABLES.

ON MOVING-HEAD DISK MEDIA, FORMATTER/MAINTENANCE POLICY PLACES SWAP AT THE
FAST OUTER EDGE AND LOGSTORE AT THE INNER EDGE DIRECTLY AFTER THE BOOT AREA.
SIZES/BOUNDARIES MUST USE DEVICE-EFFICIENT TRACK/CYLINDER GEOMETRY RATHER THAN
A RAM-SIZE MULTIPLIER.  DRUM MEDIA HAVE NO INNER/OUTER PLACEMENT RULE.  THESE
ARE PLACEMENT POLICIES, NOT FCB SEMANTICS; THE ON-DISK RESERVATION DESCRIPTORS
STORE LOGICAL START/LENGTH.

RESERVATIONS MAY BE CREATED AFTER FILESYSTEM CREATION, GROWN, SHRUNK, MOVED,
OR DELETED WHILE THE CORRESPONDING SERVICE IS INACTIVE.  `D6SWAP
--MIGRATE-RESERVATION` IS THE ONE-TIME V2 UPGRADE FOR MEDIA WHOSE DBOOT RAW
TAIL PREDATES AUTHORITATIVE D6FS SWAP METADATA.  MOVEMENT PRESERVES
CONTENTS.  AN ACTIVE SWAP OR LOGSTORE REGISTRATION PINS THE CONTAINING MOUNT
AGAINST UNMOUNT UNTIL THE SERVICE IS DEACTIVATED.

## 5. LOGICAL ADDRESS AND SIZE LIMIT

D6FS V2 USES A 24-BIT LOGICAL BLOCK ADDRESS.

MAXIMUM LOGICAL D6FS ADDRESS SPACE:

    2^24 BLOCKS
    2^31 36-BIT WORDS

THIS IS APPROXIMATELY 9.66 GB WHEN A 36-BIT WORD IS COUNTED AS 4.5 BYTES.

THIS LIMIT IS INTENDED TO COVER LARGE PRACTICAL KL10-CLASS VOLUMES WITHOUT
MAKING EVERY EXTENT OR METADATA POINTER MULTIWORD.

## 6. OBJECT TYPES

D6FS V2 HAS THREE ORDINARY OBJECT TYPES:

    REGULAR FILE
    DIRECTORY
    SYMBOLIC LINK

THERE ARE NO HARD LINKS.

THERE ARE NO DEVICE NODES IN ORDINARY D6FS.

SYMLINK CONTENT IS STORED THROUGH THE SAME EXTENT-BACKED DATA PATH AS REGULAR
FILE CONTENT.  V2 HAS NO INLINE/FAST SYMLINK REPRESENTATION.

## 7. NAMES

D6FS V2 NAMES ARE SIXBIT AND AT MOST 24 CHARACTERS.

A DIRECTORY ENTRY STORES THE COMPLETE NAME, A COMPACT HASH, THE CHILD FCB, AND
A CACHED OBJECT TYPE.  THE HASH AND CACHED TYPE ARE ACCELERATORS ONLY.  THE
FCB AND FULL NAME ARE AUTHORITATIVE.

HASH MATCH MUST ALWAYS BE FOLLOWED BY FULL NAME COMPARISON.

## 8. UNIX OWNERSHIP AND PERMISSIONS

D6FS USES SIMPLE UNIX-LIKE OWNERSHIP AND MODE SEMANTICS:

    UID
    GID
    RWX MODE BITS

D6FS V2 DOES NOT IMPLEMENT ACLS, PROJECT PROTECTION WORDS, CAPABILITIES, OR
SEPARATE DELETE/CONTROL PROTECTION CLASSES.

## 9. PERSISTENT FILE FLAGS

THE V2 FLAG SET IS:

    APPEND      CONTENT MAY ONLY BE EXTENDED AT EOF
    NOUNLINK    ORDINARY UNLINK/RENAME-AWAY IS FORBIDDEN
    NODUMP      BACKUP/DUMP TOOLS SHOULD OMIT THE OBJECT
    ARCHIVE     OBJECT IS MARKED FOR ARCHIVAL POLICY/TOOLS
    IMMUTABLE   CONTENT AND METADATA ARE FROZEN
    HIDDEN      OMIT FROM NORMAL NON-ALL DIRECTORY LISTINGS
    SYSTEM      RESERVED FOR SYSTEM-MANAGED OBJECT POLICY

UNUSED FLAG BITS MUST BE ZERO ON CREATION AND PRESERVED/IGNORED WHEN READING A
NEWER COMPATIBLE FORMAT.

APPEND IS A PERSISTENT ATTRIBUTE AND IS DISTINCT FROM PER-OPEN O_APPEND.
APPEND RESTRICTS CONTENT UPDATES, NOT NAMESPACE OPERATIONS.  NOUNLINK OR
IMMUTABLE PROVIDE NAMESPACE PROTECTION.

IMMUTABLE FORBIDS ORDINARY WRITE, TRUNCATE, CHMOD/CHOWN, RENAME, AND UNLINK.
CLEARING IMMUTABLE OR NOUNLINK REQUIRES AN EXPLICIT PRIVILEGED OPERATION.

ARCHIVE IS A POLICY MARKER.  D6FS ITSELF DOES NOT AUTOMATICALLY REWRITE IT ON
EVERY FILE WRITE.

## 10. TIMESTAMPS

D6FS V2 STORES ONE 36-BIT MTIME FIELD ONLY.

MTIME36 USES THE CHRONOLOGICALLY SORTABLE UTC TIME36 FORMAT FROZEN IN
KERNEL/CLOCK.MD.  IT COVERS 2026-01-01 THROUGH 2125-12-31 AND CAN BE COMPARED
DIRECTLY AS AN UNSIGNED 36-BIT VALUE WITHIN THAT RANGE.  VFS/STAT MUST EXPOSE
IT.  D6FS NOW UPDATES IT ON RELEVANT FILE/DIRECTORY MUTATIONS; TOUCH USES
THE SAME GETTIME SOURCE.  NATIVE MAKE IS NOT YET CLAIMED WORKING.

MTIME 0 MEANS UNKNOWN/UNINITIALIZED.  NORMAL SELF-HOSTING MAKE MUST NOT
SILENTLY TRUST UNKNOWN OR OUT-OF-RANGE MTIME VALUES.

THERE IS NO ATIME AND NO CTIME.

## 11. FCB IDENTITY

AN FCB NUMBER IS THE ON-DISK OBJECT ID WITHIN ONE MOUNTED D6FS.

D6FS V2 HAS NO FCB GENERATION NUMBER.

STALE RUNTIME REFERENCES ARE INVALIDATED BY MOUNT/VNODE LIFETIME RULES.  THEY
ARE NOT MADE PERSISTENT IN THE ON-DISK FORMAT.

EACH NON-ROOT OBJECT HAS EXACTLY ONE PARENT DIRECTORY BECAUSE HARD LINKS DO NOT
EXIST.  THE FCB STORES ITS PARENT FCB NUMBER.

## 12. EXTENTS

### 12.1 FIXED INLINE EXTENTS

EACH FCB HAS EXACTLY SEVEN INLINE EXTENT SLOTS.

THERE ARE NO CONTINUATION FCBS AND NO INDIRECT EXTENT BLOCKS.

AN UNUSED EXTENT SLOT IS ZERO AND MUST FOLLOW ALL USED SLOTS.

### 12.2 EXTENT WORD

EACH OF THE SEVEN EXTENT WORDS IS:

    BITS  0..23   START24
    BITS 24..35   LENLOW12

START24 IS THE LOGICAL D6FS START BLOCK.

LENGTH IS STORED AS COUNT-1.

### 12.3 SHARED EXTENT LENGTH-HIGH WORD

ONE ADDITIONAL FCB WORD STORES FIVE HIGH LENGTH BITS FOR EACH EXTENT:

    BITS  0..4    EXTENT 0 LENHIGH5
    BITS  5..9    EXTENT 1 LENHIGH5
    BITS 10..14   EXTENT 2 LENHIGH5
    BITS 15..19   EXTENT 3 LENHIGH5
    BITS 20..24   EXTENT 4 LENHIGH5
    BITS 25..29   EXTENT 5 LENHIGH5
    BITS 30..34   EXTENT 6 LENHIGH5
    BIT      35   RESERVED, ZERO IN V2

FOR A USED EXTENT:

    COUNT_MINUS_1 = (LENHIGH5 << 12) | LENLOW12
    LENGTH_BLOCKS = COUNT_MINUS_1 + 1

MAXIMUM EXTENT LENGTH IS 131072 BLOCKS = 16 MEGAWORDS.

SEVEN MAXIMUM EXTENTS DESCRIBE UP TO 112 MEGAWORDS OF FILE DATA.

A ZERO EXTENT SLOT IS IDENTIFIED BY THE FCB'S EXTENT COUNT/ORDER, NOT BY
INTERPRETING START=0/LEN=0 AS AN ALLOCATED ONE-BLOCK EXTENT.

### 12.4 EXTENT ALLOCATION RULE

ON GROWTH:

1. EXTEND THE LAST EXTENT CONTIGUOUSLY WHEN POSSIBLE.
2. OTHERWISE ALLOCATE A NEW CONTIGUOUS EXTENT.
3. IF ALL SEVEN EXTENTS ARE IN USE AND CONTIGUOUS EXTENSION IS IMPOSSIBLE,
   RETURN ENOSPC EVEN IF FRAGMENTED FREE SPACE EXISTS.
4. OFFLINE PACKFS MAY DEFRAGMENT/RELOCATE THE FILE.

THIS DELIBERATELY TRADES A RARE FRAGMENTATION LIMIT FOR A MUCH SMALLER KERNEL
AND FORMAT.

## 13. FCB FORMAT

D6FS V2 USES A FIXED 16-WORD FCB.  THE FORMAT IS DESIGNED TO FIT ALL CORE
METADATA AND SEVEN LARGE INLINE EXTENTS WITHOUT CONTINUATIONS.

    WORD 00  TYPE3 | FLAGS9 | MODE12 | TAIL4 | EXTENT_COUNT4 | RESERVED4
    WORD 01  UID18 | GID18
    WORD 02  SIZE_WORDS36
    WORD 03  MTIME36
    WORD 04  PARENT_FCB18 | RESERVED18
    WORD 05  EXTENT_LENGTH_HIGH WORD
    WORD 06  EXTENT 0
    WORD 07  EXTENT 1
    WORD 10  EXTENT 2
    WORD 11  EXTENT 3
    WORD 12  EXTENT 4
    WORD 13  EXTENT 5
    WORD 14  EXTENT 6
    WORD 15  RESERVED36
    WORD 16  RESERVED36
    WORD 17  RESERVED36

WORD NUMBERS ABOVE ARE OCTAL.

TYPE3 VALUES ARE RESERVED FOR REGULAR, DIRECTORY, AND SYMLINK PLUS FUTURE
COMPATIBLE TYPES.

TAIL4 RECORDS THE NUMBER OF VALID 9-BIT BYTES IN THE FINAL 36-BIT WORD FOR
BYTE-STREAM INTERPRETATION.  ZERO MEANS THE FILE ENDS ON A WORD BOUNDARY OR IS
EMPTY; THE BYTE-STREAM LAYER DEFINES THE PRECISE ZERO/FOUR-BYTE RULE FROM
SIZE_WORDS.

THE THREE RESERVED WORDS ARE INTENTIONAL FORMAT HEADROOM.  THEY MUST BE ZERO
WHEN CREATING A V2 FCB AND IGNORED/PRESERVED WHERE REQUIRED FOR COMPATIBLE
FUTURE EXTENSIONS.

THERE IS NO FCB CHECKSUM, GENERATION, CTIME, HEAT, ARENA, SPILL, ROLE, OR
CONTINUATION POINTER.

## 14. DIRECTORY ENTRY FORMAT

D6FS V2 USES A FIXED SIX-WORD DIRECTORY ENTRY:

    WORD 0  NAME SIXBIT CHARACTERS 1..6
    WORD 1  NAME SIXBIT CHARACTERS 7..12
    WORD 2  NAME SIXBIT CHARACTERS 13..18
    WORD 3  NAME SIXBIT CHARACTERS 19..24
    WORD 4  HASH24 | TYPE3 | FLAGS9
    WORD 5  CHILD_FCB18 | RESERVED18

DIRECTORY-ENTRY FLAGS ARE ENTRY-LOCAL FORMAT FLAGS ONLY; THEY ARE NOT A SECOND
COPY OF THE FCB'S PERSISTENT FILE FLAGS.

AN EMPTY ENTRY HAS CHILD_FCB ZERO AND ZERO NAME WORDS.

THE PARENT IS IMPLICIT IN THE DIRECTORY CONTAINING THE ENTRY; THE CHILD FCB
STORES ITS PARENT EXPLICITLY FOR '..', FSCK, AND RENAME VALIDATION.

DIRECTORY ENTRIES HAVE NO GENERATION NUMBER.

## 15. FREE SPACE MAP

### 15.1 AUTHORITATIVE BITMAP

THE AUTHORITATIVE FREE MAP IS ONE BIT PER LOGICAL D6FS BLOCK.

    0 = ALLOCATED/RESERVED
    1 = FREE

FSCK MAY REBUILD IT FROM THE RESERVED METADATA RANGES AND ALL VALID FCB
EXTENTS.

### 15.2 COMPACT SUMMARY

D6FS V2 ADDS A VERY COMPACT SUMMARY:

    ONE SUMMARY BIT PER 128-WORD FREE-MAP BLOCK

A SUMMARY BIT MEANS:

    1 = THE CORRESPONDING BITMAP BLOCK CONTAINS AT LEAST ONE FREE BLOCK
    0 = THE CORRESPONDING BITMAP BLOCK IS FULLY ALLOCATED

ONE FREE-MAP BLOCK CONTAINS 4608 ALLOCATION BITS, SO ONE SUMMARY BIT COVERS
4608 D6FS BLOCKS.

AT THE 2^24-BLOCK MAXIMUM FILESYSTEM SIZE THE ENTIRE SUMMARY IS ABOUT 3641
BITS, OR ABOUT 102 36-BIT WORDS.  IT THEREFORE ALWAYS FITS IN EXACTLY ONE
128-WORD D6FS BLOCK.  THE KERNEL VALIDATES THIS V2 INVARIANT.  RUNTIME D6FS
STATE NEEDS ONLY THE 24-BIT SUMMARY START; IT IS PACKED INTO THE UPPER 24 BITS
OF THE EXISTING MOUNT-STATE WORD, LEAVING THE LOW 12 BITS FOR MOUNT FLAGS.
THIS AVOIDS RESTORING THE TWO RESIDENT SUMMARY FIELDS REMOVED BY THE SIZE
SWEEP.

THE CURRENT KERNEL USES A TWO-BLOCK FULLY-ASSOCIATIVE CLEAN CACHE BACKED BY
ONE RECLAIMABLE 0405-WORD DYNAMIC SLAB (261 DECIMAL WORDS).  EARLIER CODE
ALLOWED FOUR SUCH SLABS; THE SINGLE-SLAB POLICY CUTS THE MAXIMUM D6FS CACHE
RAM FROM ABOUT 1044 WORDS TO 261 WORDS, SHRINKS RESIDENT CACHE MANAGEMENT
CODE, AND REMAINS EXPLICITLY RECLAIMABLE UNDER MEMORY PRESSURE.

THE SUMMARY IS AN ACCELERATOR, NOT THE AUTHORITY.  FSCK MAY REBUILD IT FROM
THE FREE MAP.

### 15.3 BOUNDED ALLOCATION LOOKAHEAD

THE KERNEL DOES NOT NEED TO KEEP THE WHOLE FREE MAP RESIDENT.

MOUNT STATE KEEPS:

- AN ALLOCATION CURSOR;
- THE CURRENT SUMMARY WINDOW/BLOCK;
- THE CURRENT FREE-MAP WINDOW/BLOCK.

ALLOCATION PROCEDURE:

1. TRY TO EXTEND THE FILE'S LAST EXTENT.
2. START NEAR THE FILE/ALLOCATION CURSOR.
3. USE SUMMARY BITS TO SKIP FULL FREE-MAP BLOCKS.
4. LOAD A CANDIDATE BITMAP BLOCK.
5. FIND THE LONGEST USEFUL CONTIGUOUS FREE RUN.
6. ALLOCATE IT AND ADVANCE THE CURSOR.

THIS BORROWS THE BOUNDED LOOKAHEAD PRINCIPLE FROM SMALL EMBEDDED FILESYSTEMS
WITHOUT COPYING FLASH-SPECIFIC COW/CRC/WEAR-LEVELING MACHINERY.

## 16. SUPERBLOCKS AND DIRTY STATE

D6FS V2 KEEPS TWO SUPERBLOCK COPIES, A AND B.

THERE ARE NO SUPERBLOCK OR METADATA CHECKSUMS.

EACH COPY CONTAINS AT LEAST:

- D6FS MAGIC AND FORMAT VERSION;
- FILESYSTEM UUID;
- SUPERBLOCK SEQUENCE NUMBER;
- CLEAN/DIRTY STATE;
- LOGICAL FILESYSTEM BLOCK COUNT;
- ROOT FCB;
- FCB TABLE LOCATION/SIZE;
- FREE MAP LOCATION/SIZE;
- FREE-MAP SUMMARY LOCATION/SIZE;
- OPTIONAL SWAP RESERVATION START/SIZE;
- OPTIONAL LOGSTORE RESERVATION START/SIZE;
- RESERVED FORMAT FIELDS.

ON MOUNT, BOTH COPIES ARE STRUCTURALLY VALIDATED.  SEQUENCE ORDER IS MODULO
36 BITS USING THE HALF-RANGE RULE: A POSITIVE MODULO DELTA SMALLER THAN 2^35
IS NEWER.  COPIES EXACTLY HALF THE SEQUENCE SPACE APART ARE AMBIGUOUS AND ARE
REJECTED.  EQUAL-SEQUENCE COPIES MUST BE IDENTICAL.  IF ONE COPY IS INVALID,
THE OTHER MAY BE SELECTED ONLY IF IT IS OTHERWISE VALID.

THE SELECTED GENERATION MUST BE CLEAN.  A SELECTED DIRTY GENERATION IS NEVER
MOUNTABLE, EVEN READ-ONLY, AND THE KERNEL MUST NOT FALL BACK TO AN OLDER CLEAN
COPY.  ONCE A NEWER DIRTY GENERATION EXISTS, SYNCHRONOUS METADATA WRITES MAY
ALREADY HAVE CHANGED THE FILESYSTEM relative to that older copy.

WRITABLE MOUNT / RO->RW:

1. WRITE/FLUSH A NEW DIRTY SUPERBLOCK GENERATION TO THE OPPOSITE COPY.
2. BEGIN NORMAL WRITES ONLY AFTER THAT PUBLICATION SUCCEEDS.

CLEAN UNMOUNT / RW->RO:

1. COMPLETE SYNCHRONOUS FILE/DIRECTORY/FCB/FREE-MAP UPDATES.
2. WRITE/FLUSH A NEW CLEAN SUPERBLOCK GENERATION TO THE OPPOSITE COPY.
3. CHANGE RUNTIME/VFS WRITE POLICY ONLY AFTER THAT PUBLICATION SUCCEEDS.

THE V2 CRASH-RECOVERY CONTRACT IS THEREFORE CONSERVATIVE AND BOUNDED:

- IF THE INITIAL DIRTY PUBLICATION TEARS OR IS STRUCTURALLY INVALID, METADATA
  WRITES HAVE NOT STARTED; THE SURVIVING CLEAN GENERATION IS SAFE TO MOUNT.
- ONCE DIRTY IS DURABLE, ANY CRASH REQUIRES D6FSCK.  AN OLDER CLEAN COPY IS
  NEVER USED AS A ROLLBACK IMAGE.
- IF FINAL CLEAN PUBLICATION TEARS, THE PREVIOUS VALID DIRTY GENERATION REMAINS
  AUTHORITATIVE AND THE KERNEL REFUSES THE FILESYSTEM UNTIL D6FSCK RECOVERS IT.
- ALLOCATION BEFORE FCB PUBLICATION MAY LEAVE LEAKED ALLOCATION BITS; D6FSCK
  MAY FREE THEM WHEN OWNERSHIP IS UNAMBIGUOUS.
- DIRECTORY REMOVAL BEFORE FCB RECLAMATION MAY LEAVE AN ORPHAN FCB; D6FSCK MAY
  RECLAIM IT AND ITS UNIQUE EXTENTS.  CROSS-DIRECTORY RENAME DELIBERATELY
  REMOVES THE OLD NAME FIRST, SO A CRASH MAY LOSE THE RENAME BUT MUST NOT
  CREATE A SECOND HARD-LINK-LIKE REFERENCE.
- CLEARING AN FCB BEFORE ITS EXTENT BITS ARE FREED MAY LEAVE leaked allocation;
  D6FSCK repairs the map from live structural ownership.
- A CRASH BETWEEN FREE-MAP AND SUMMARY WRITES MAY LEAVE ONLY A SUMMARY
  MISMATCH; D6FSCK REBUILDS THE SUMMARY FROM THE FREE MAP.
- CROSS-LINKS, CONFLICTING DIRECTORY OWNERSHIP, SUPERBLOCK IDENTITY CONFLICTS,
  AND OTHER AMBIGUOUS STATES ARE NOT REPAIRED AUTOMATICALLY.

D6FSCK CHECK-ONLY MODE TREATS A SELECTED DIRTY GENERATION AS AN ERROR.
D6FSCK -R FIRST PERFORMS THE FULL STRUCTURAL SCAN.  WHEN REPAIRS ARE
DETERMINISTIC IT PUBLISHES A NEWER DIRTY GENERATION BEFORE THE FIRST REPAIR
WRITE, WRITES DIRECTORY/FCB/ALLOCATION REPAIRS, THEN PUBLISHES AN EVEN NEWER
CLEAN GENERATION.  IF CORRUPTION IS AMBIGUOUS, IT WRITES NOTHING.

D6FS V2 STILL HAS NO SUPERBLOCK OR METADATA CHECKSUMS.  THE RECOVERY CONTRACT
RELIES ON THE LOWER BLOCK PROVIDER REPORTING WHOLE-BLOCK WRITE SUCCESS OR
FAILURE AND ON STRUCTURAL VALIDATION OF A/B COPIES; AN ARBITRARY WORD-TORN
SUPERBLOCK THAT HAPPENS TO REMAIN STRUCTURALLY VALID CANNOT BE DISTINGUISHED
FROM A VALID COPY.  ADDING A GENERAL JOURNAL OR CHECKSUM TREE IS NOT PART OF V2.

## 17. ORDERED METADATA WRITES

THE ABSENCE OF A JOURNAL DOES NOT MEAN RANDOM WRITE ORDER.

MUTATIONS MUST BE ORDERED SO A CRASH PREFERABLY CREATES A RECOVERABLE LEAK
RATHER THAN A LIVE REFERENCE TO UNINITIALIZED OR FREE STORAGE.

FOR EXAMPLE, WHEN ADDING A NEW EXTENT:

1. ALLOCATE THE FREE-MAP BITS IN MEMORY.
2. WRITE THE COMPLETE NEW DATA BLOCKS.
3. PERSIST THE ALLOCATION STATE.
4. PERSIST THE FCB EXTENT/SIZE UPDATE.

CREATE/RENAME/UNLINK MUST USE SIMILAR RECOVERABLE ORDERING AND FSCK MUST KNOW
THE POSSIBLE INTERMEDIATE STATES.

## 18. RUNTIME BUFFERING AND CACHES

BLOCK BUFFERING IS AN IMPLEMENTATION PROPERTY, NOT PART OF THE D6FS FORMAT.
THE RUNTIME DESIGN IS IMPLEMENTED AS A DYNAMIC, RECLAIMABLE BLOCK CACHE
BORROWING OTHERWISE-FREE MANAGED CORE.  D6FS DOES NOT RESERVE A LARGE FIXED
ARRAY OF FULL-BLOCK BUFFERS IN THE PERMANENT KERNEL IMAGE.  THE FIRST
IMPLEMENTATION USES UP TO FOUR 0405-OCTAL-WORD SLABS, EACH HOLDING TWO 128-WORD
BLOCKS PLUS KEYS/METADATA.  CACHE KEYS ARE D6FS READER/MOUNT IDENTITY PLUS
LOGICAL BLOCK NUMBER.

CACHE DATA MEMORY IS ELASTIC:

```TEXT
IDLE/FREE MANAGED CORE
    -> CACHE MAY GROW ON DEMAND

PROCESS/MODULE MEMORY PRESSURE
    -> DROP CLEAN CACHE BLOCKS FIRST
    -> WRITE BACK DIRTY CACHE BLOCKS EARLY ENOUGH TO MAKE THEM RECLAIMABLE
    -> COMPACT IF A CONTIGUOUS EXTENT IS STILL NEEDED
    -> SWAP A PROCESS ONLY AFTER RECLAIMABLE CACHE HAS BEEN SACRIFICED
```

THE CURRENT CACHE IS WRITE-THROUGH: A STORE REACHES THE CACHE ONLY AFTER THE
BACKING D6FS WRITE SUCCEEDS.  EVERY CACHE BLOCK IS THEREFORE CLEAN AND
REGENERABLE, SO RECLAIM NEVER INITIATES FILESYSTEM I/O.  DIRTY-BUFFER WRITEBACK
IS DELIBERATELY DEFERRED UNTIL MEASUREMENTS SHOW THAT ITS COMPLEXITY IS NEEDED.

CACHE GROWTH MUST LEAVE A SMALL MM RESERVE SO AN IDLE MACHINE DOES NOT TURN THE
LAST FREE WORD INTO CACHE.  THE EXACT WATERMARK IS AN IMPLEMENTATION/MEASUREMENT
CHOICE, NOT AN ON-DISK FORMAT PROPERTY.  ON A BUSY 32K PDP-6 THE CACHE MUST BE
ABLE TO CONTRACT TOWARD A VERY SMALL MINIMUM; ON A LARGER OR IDLE MACHINE IT
MAY CONSUME MUCH OF THE OTHERWISE UNUSED MANAGED CORE.

THE ALLOCATOR/RECLAIM PATH MUST NEVER START BLOCKING FILESYSTEM I/O FROM
INTERRUPT CONTEXT.  CLEAN RECLAIM MAY BE IMMEDIATE.  DIRTY WRITEBACK SHOULD BE
STARTED FROM PROCESS/SERVICE CONTEXT BEFORE SEVERE PRESSURE WHEN PRACTICAL; A
SLEEPABLE ALLOCATION PATH MAY FORCE WRITEBACK AND RETRY, BUT AN INTERRUPT PATH
MUST DEFER OR FAIL RATHER THAN SLEEP.

CACHE KEYS MUST INCLUDE AT LEAST THE D6FS MOUNT/INSTANCE AND LOGICAL BLOCK
NUMBER.  TWO MOUNTED D6FS FILESYSTEMS MAY USE THE SAME LOGICAL BLOCK NUMBER AND
MUST NEVER ALIAS.  CACHE INVALIDATION/FLUSH RULES APPLY PER mount, and unmount
OR READ-ONLY TRANSITION MUST FLUSH OR INVALIDATE ALL AFFECTED ENTRIES SAFELY.

FIXED CACHE METADATA MUST BE SMALL.  CACHE ENTRY DESCRIPTORS SHOULD BE PACKED
AND STORED WITH OR ADJACENT TO DYNAMICALLY ALLOCATED BLOCKS WHERE THAT REDUCES
PERMANENT STATE.  A LARGE PREALLOCATED DESCRIPTOR TABLE IS NOT ACCEPTABLE.
LRU/CLOCK POLICY IS AN IMPLEMENTATION CHOICE; THE REPLACEMENT ALGORITHM SHOULD
FAVOR A COMPACT REPRESENTATION OVER EXACT TIMESTAMPING WHEN THE PERFORMANCE
TRADE IS SIMILAR.

THE SHARED PERMANENT 128-WORD `FS_BLOCK_WORKSPACE` REMAINS THE SERIALIZED
TRANSFER BUFFER USED BY THE EXISTING FILESYSTEM/I/O PATH.  CACHE HITS COPY INTO
THAT WORKSPACE; MISSES READ INTO IT AND THEN populate managed-core cache data.
THE CACHE ADDS NO SECOND PERMANENT FULL-BLOCK BUFFER.  REPLACING THE SHARED
WORKSPACE IS NOT REQUIRED FOR THE FIRST CACHE IMPLEMENTATION AND SHOULD BE
REVISITED ONLY IF A SMALLER CORRECT TRANSFER PATH IS FOUND.

CACHE BUFFER CONTENTS BORROW MANAGED CORE AND ARE NOT PART OF THE FIXED
RESIDENT+SCRATCH FOOTPRINT USED FOR THE BELOW-16K KERNEL-IMAGE GATE.  THE CACHE
CODE, PERMANENT BOOKKEEPING, AND ANY IRREDUCIBLE FIXED SCRATCH DO COUNT.  AT
RUNTIME CACHE USE STILL CONSUMES PHYSICAL CORE AND THEREFORE PARTICIPATES IN
NORMAL MEMORY-PRESSURE ACCOUNTING.

A PATHNAME/LOOKUP CACHE MAY BE ADDED AFTER THE BLOCK CACHE ONLY IF NATIVE
SELF-HOSTING MEASUREMENTS SHOW THAT PATHNAME TRAVERSAL REMAINS MATERIAL.  IT
MUST USE THE SAME RECLAIMABLE-MEMORY PRINCIPLE.  THERE IS NO SEPARATE EXTENT
CACHE; THE SEVEN EXTENTS ARE ALREADY PART OF THE FCB/VNODE METADATA.

## 19. STATISTICS POLICY

D6FS V2 REQUIRES NO ALWAYS-ON PERFORMANCE COUNTERS.

COUNTERS USED FOR OPTIMIZATION MAY BE COMPILED INTO DIAGNOSTIC/PERFORMANCE
BUILDS OR EXPOSED BY THE LAYER THAT OWNS THE EVENT.  IN PARTICULAR, PHYSICAL
READ/WRITE, SEEK, QUEUE, AND BAD-MEDIA STATISTICS BELONG TO THE BLOCK/DISK
LAYERS, NOT TO D6FS.

DO NOT SPEND PERMANENT PDP-6 RAM OR HOT-PATH INSTRUCTIONS ON A COUNTER THAT HAS
NO CONSUMER.

## 20. VFS-OWNED RUNTIME SEMANTICS

WHOLE-FILE ADVISORY LOCKS, OPEN-FILE REFERENCE COUNTS, DESCRIPTOR LIFETIME,
AND OPEN-UNLINK LIFETIME ARE VFS/OPEN-FILE STATE.  NOTHING FOR THESE FEATURES
IS STORED IN THE D6FS ON-DISK FORMAT.

BECAUSE D6FS HAS NO HARD LINKS, AN UNCLEAN SHUTDOWN MAY LEAVE AN ORPHAN
FCB/EXTENTS AFTER OPEN-UNLINK; FSCK RECLAIMS THEM.

RENAME MUST PRESERVE THE SINGLE-PARENT INVARIANT AND UPDATE THE CHILD FCB'S
PARENT FIELD WHEN MOVING ACROSS DIRECTORIES.

D6FS V2 HAS NO BYTE-RANGE OR MANDATORY LOCKS.

## 21. PACKFS

PACKFS IS NO LONGER A HEAT/ARENA/ONLINE POLICY ENGINE.

IT IS AN OFFLINE DEFRAGMENTER AND COMPACTOR.

PACKFS SHOULD:

1. MOVE EACH MOVABLE FILE TOWARD FEWER/LARGER CONTIGUOUS EXTENTS;
2. PREFER ONE EXTENT WHEN PRACTICAL;
3. COMPACT DIRECTORY STORAGE WHERE USEFUL;
4. COALESCE FREE SPACE;
5. REBUILD/VERIFY THE FREE-MAP SUMMARY;
6. MOVE ORDINARY FILE EXTENTS AS NEEDED TO PREPARE ALIGNED FREE RUNS FOR
   SWAP/LOGSTORE CREATE, GROW, OR MOVE OPERATIONS;
7. PRESERVE SWAP/LOGSTORE RESERVED RANGES UNLESS AN EXPLICIT OFFLINE
   RESERVATION OPERATION IS BEING PERFORMED;
8. NEVER ADDRESS BLOCKS OUTSIDE THE D6FS LOGICAL REGION;
9. FINISH WITH FILESYSTEM VALIDATION.

PACKFS RUNS ON AN UNMOUNTED OR MAINTENANCE-READ-ONLY FILESYSTEM.  D6FS V2 HAS
NO ONLINE PACKER.

HOST/OFFLINE PACKFS IMPLEMENTATION BELONGS IN PDP10-TOOLS.  A TARGET
MAINTENANCE FRONT END MAY REUSE THE SAME FORMAT RULES.

## 22. EMBEDDED-FILESYSTEM TECHNIQUES ADOPTED

D6FS V2 ADOPTS ONLY SMALL, GENERAL TECHNIQUES THAT FIT PDP-6 CONSTRAINTS:

- BOUNDED FREE-MAP LOOKAHEAD WINDOW;
- ALLOCATION CURSOR INSTEAD OF A FULL RESIDENT ALLOCATION TREE;
- ELASTIC RECLAIMABLE BLOCK CACHE FROM MANAGED CORE;
- DUAL SUPERBLOCKS WITH SEQUENCE/STATE;
- RECOVERABLE ORDERED WRITES;
- COMPACT FREE-MAP SUMMARY;
- NO REQUIREMENT TO KEEP THE WHOLE FREE MAP IN RAM.

D6FS V2 EXPLICITLY DOES NOT ADOPT:

- INLINE FILE DATA;
- FLASH WEAR LEVELING;
- CRC/CHECKSUM TREES;
- COPY-ON-WRITE METADATA TREES;
- METADATA PAIRS FOR EVERY DIRECTORY/FCB;
- LARGE DYNAMIC INDEX TREES.

## 23. FSCK

D6FSCK MUST VALIDATE AT LEAST:

- BOTH SUPERBLOCKS AND SEQUENCE/STATE;
- FILESYSTEM SIZE BOUNDS;
- FCB TYPE/MODE/FLAG VALIDITY;
- SINGLE-PARENT DIRECTORY INVARIANT;
- DIRECTORY CHILD REFERENCES;
- FULL NAME/HASH CONSISTENCY;
- EXTENT COUNT, ORDER, RANGE, AND OVERLAP;
- MAXIMUM SEVEN EXTENTS;
- FILE SIZE VERSUS EXTENT CAPACITY;
- METADATA OR EXTENTS OUTSIDE THE D6FS LOGICAL REGION;
- CROSS-LINKED EXTENTS;
- ORPHAN FCBS;
- SWAP/LOGSTORE RESERVATION BOUNDS, NON-OVERLAP, AND REQUIRED DEVICE ALIGNMENT;
- RESERVED RANGES VERSUS FILESYSTEM METADATA AND LIVE FCB EXTENTS;
- FREE MAP VERSUS ALL LIVE EXTENTS AND SWAP/LOGSTORE RESERVED RANGES;
- FREE-MAP SUMMARY VERSUS FREE MAP.

FSCK MAY REBUILD THE FREE MAP AND SUMMARY FROM STRUCTURAL METADATA.

CURRENT MAINTENANCE TOOLS USE THE SAME RESERVATION CODEC AS THE KERNEL.  LOGSTORE
BLOCKS ARE STRUCTURAL RESERVED OWNERSHIP AND MUST REMAIN ALLOCATED IN THE FREE
MAP.  THE SWAP RESERVATION STARTS AT TOTAL_BLOCKS AND MUST FIT THE VALIDATED RAW
TAIL.  FCB EXTENTS MUST BE ORDERED AND NON-OVERLAPPING EVEN WITHIN ONE FCB.
PACKFS PRESERVES SWAP/LOGSTORE METADATA.  D6SWAP --MIGRATE-RESERVATION UPGRADES
LEGACY ZERO-SWAP SUPERBLOCKS, AND OFFLINE TAIL RESIZE PRESERVES THE OVERLAPPING
LOGICAL SWAP CONTENTS WHILE USING DIRTY->METADATA/GEOMETRY->CLEAN ORDERING.

A SELECTED DIRTY GENERATION REQUIRES FSCK BEFORE ANY MOUNT.  THE KERNEL
MUST NOT FALL BACK TO AN OLDER CLEAN COPY.

- HARD LINKS;
- SPARSE FILES;
- INLINE FILES;
- CONTINUATION FCBS;
- INDIRECT EXTENT BLOCKS;
- DATA OR METADATA JOURNAL;
- METADATA CHECKSUMS;
- ATIME OR CTIME;
- ACLS;
- QUOTAS;
- BYTE-RANGE LOCKS;
- MANDATORY LOCKS;
- DEVICE NODES;
- SEALED IMAGE FORMAT;
- OVERLAY/COPY-UP/WHITEOUT FORMAT;
- VIEW FORMAT;
- HOT/COLD ARENAS;
- HEAT TRACKING;
- ONLINE DEFRAGMENTER;
- RAID/PARITY/MIRRORING;
- BLOCKSET MEMBERSHIP OR STRIPING;
- PHYSICAL BAD-BLOCK MAPS;
- PHYSICAL SEEK SCHEDULING;
- SWAP OR LOGSTORE CONTENT FORMAT;

MKFS.D6FS MUST ACCEPT OPTIONAL INITIAL SWAP AND LOGSTORE SIZE PARAMETERS AND

THEN DISK SPACE, WITH ABSTRACTION ELEGANCE ONLY AFTER THOSE COSTS ARE ACCEPTABLE.
A LAYER MAY THEREFORE USE A SPECIAL RAW RANGE OR A TINY PRIVATE ACCELERATOR
WHEN THAT IS MEASURABLY SMALLER/FASTER THAN A MORE GENERAL MECHANISM.
