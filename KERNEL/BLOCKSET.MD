# CURRENT BLOCKSET IMPLEMENTATION STATE (2026-09-24)

BLOCKSET IS THE COMMON LOGICAL BLOCK-SET ABSTRACTION.  A SINGLE D6FS DSK ROOT
BYPASSES BLOCKSET COMPLETELY.  A MULTI-MEMBER DSK ROOT INSTALLS A COMPACT
41-WORD ROOT MRES USING HOMOGENEOUS EQUAL-SIZE INTERLEAVE.  THE ROOT RUNTIME
DESCRIPTOR IS 10 WORDS FOR THE CURRENT FOUR-DSK PROFILE.  THE REENTRANT GENERIC
MAPPER USES THE PUBLIC 16-WORD/SEVEN-MEMBER DESCRIPTOR FROM BLOCKSET.H AND LIVES
IN A SEPARATE ASSEMBLY OBJECT SO ROOT D6FS DOES NOT PAY FOR CONCAT CODE.

THE GENERIC MAPPER SUPPORTS EQUAL-SIZE INTERLEAVE AND CONCAT.  IT DOES NOT
IMPLEMENT UNEQUAL-MEMBER ZONE STRIPING.  UNEQUAL MEMBER WINDOWS USE CONCAT.
THE CURRENT DSK ROOT DISCOVERY ACCEPTS THE HOMOGENEOUS EQUAL-SIZE INTERLEAVE
PROFILE ONLY.

THE FILESYSTEM, NOT BLOCKSET, OWNS PLACEMENT POLICY.  TSFS CHOOSES TAPE-LOCAL
SEQUENTIAL EXTENTS; BLOCKSET ONLY TRANSLATES A CHOSEN LOGICAL BLOCK TO MEMBER
AND PHYSICAL BLOCK.  DEVICE-SPECIFIC REQUEST SCHEDULING REMAINS IN DSK270,
DRM236, OR THE RELEVANT LEAF DRIVER.  NO SEPARATE DRUMSET OR TAPESET BLOCK LAYER
IS TO BE ADDED.

THE CURRENT DSK ROOT DISCOVERY REMAINS BOOT-SPECIFIC.  GENERIC TSFS MEMBER
DISCOVERY/CHECKSUM VALIDATION RUNS IN A TRANSIENT USERSPACE HELPER AND IS
DISCARDED AFTER MOUNT.  DRM/DTC CONSUMERS MAY BUILD THE SAME GENERIC DESCRIPTOR
WITHOUT ADDING FILESYSTEM SEMANTICS TO BLOCKSET.

CURRENT KCC MEASUREMENT OF THE 2026-09-24 ARCHIVE: KCORE+MRES IS 16094 WORDS.
A SINGLE-MEMBER ROOT HAS PERMANENT_LAST 037415 WITH 242 FREE ADDRESSES.  THE
ACTIVE MULTI-MEMBER DSK ROOT INSTALLS THE 41-WORD BLOCKSET PACKAGE AND HAS
MULTI_LAST 037466 WITH 201 FREE ADDRESSES BELOW 040000.  THESE VALUES SUPERSEDE
THE EARLIER SWAP-RESERVATION-MIGRATION SIZE CHECKPOINT.

# DAIMOS BLOCKSET LOGICAL-BLOCK SPECIFICATION

*SMALL STORAGE-SET BLOCK LAYER BELOW FILESYSTEMS*

## DOCUMENT METADATA

- STATUS: LOGICAL-BLOCK MRES IMPLEMENTED; RESIDENT SWAP/LOGSTORE SEMANTICS REMOVED
- DATE: 2026-09-22
- SCOPE: BLOCKSET ASSEMBLY, MEMBER MAPPING, BAD MEDIA, AND LOGICAL BLOCK I/O
- ENCODING: PLAIN ASCII; ALL MEDIA WORDS ARE 36-BIT PDP-10 WORDS

## 1. PURPOSE

THE DAIMOS BLOCKSET LAYER COMPOSES THE PRESENT V1 DSK270 PROFILE OF ONE THROUGH
FOUR PHYSICAL DISK MEMBERS INTO A SMALL LOGICAL BLOCK ADDRESS SPACE AND EXPORTS
GENERIC LOGICAL BLOCK/RANGE ACCESS TO CONSUMERS.  THE SAME STORAGE-SET BOUNDARY
IS ALSO THE TARGET FOR DRM236 DRUM SETS WHERE STRIPING/MAPPING IS WANTED.  IT
EXISTS BELOW D6FS, SWAP, AND LOGSTORE AND ABOVE RAW PHYSICAL DRIVERS.  THE
FOUR-MEMBER V1 LIMIT MATCHES BOTH LIVE DSK270/DRM236 HARDWARE PROFILES; A FUTURE
CONTROLLER/FORMAT MAY RAISE IT WITHOUT CHANGING D6FS.

THE DESIGN PRIORITIES ARE:

1. RESIDENT RAM SIZE;
2. EXECUTION SPEED, ALMOST AS IMPORTANT AS RAM;
3. ON-DISK SPACE;
4. ABSTRACTION ELEGANCE.

THE MOST PRAGMATIC REPRESENTATION WINS WHEN IT IS MEASURABLY SMALLER OR FASTER.
IN PARTICULAR, SWAP AND LOGSTORE ARE RAW I/O CONSUMERS RATHER THAN D6FS
FILES.  THEIR PERSISTENT LOGICAL RESERVATIONS ARE OWNED BY THE FILESYSTEM AND
REGISTERED THROUGH VFS; BLOCKSET DOES NOT OWN THEIR SEMANTIC REGION METADATA.

## 2. LAYERING

'''TEXT
D6FS --------\
SWAP ---------+--> STANDALONE BLOCKSET MRES --> STORAGE MRES --> DSK270
LOGSTORE -----/
'''

THE RUNTIME BLOCKSET MRES OWNS ONE VALIDATED SINGLETON LAYOUT.  BOOT-TIME
DESCRIPTOR DISCOVERY/DECODING IS ONE-SHOT KINIT CODE AND IS NOT KEPT IN THE
RESIDENT BLOCKSET PACKAGE.  THE RUNTIME SERVICE ABI IS DELIBERATELY SMALL: ONE
DISPATCH ENTRY AND A COMPACT REQUEST.

THE BOOT DESCRIPTOR AND MEMBER-LOCAL BOOTSTREAM ARE SPECIAL EARLY-BOOT MEDIA
LAYOUT AND ARE DESCRIBED IN 'BOOT/DBOOT.MD'.  STAGE1 MAY READ THEM BEFORE THE
FULL RUNTIME BLOCKSET OBJECT EXISTS.

D6FS DOES NOT KNOW MEMBER COUNTS, MEMBER UUIDS, STRIPE ZONES, PHYSICAL SECTORS,
BAD RUNS, OR PHYSICAL BOOTSTREAM LOCATIONS.  IT MAY OWN LOGICAL SWAP/LOGSTORE
RESERVATIONS WITHOUT KNOWING THEIR PHYSICAL MEMBER DISTRIBUTION.

THE RAW DSK270 DRIVER DOES NOT KNOW FILESYSTEMS, STRIPE ZONES, OR RAW REGION
SEMANTICS.  IT READS/WRITES PHYSICAL SECTORS AND SCHEDULES REQUESTS FOR ONE
PHYSICAL UNIT.

## 3. MEMBER IDENTITY

THE PRESENT V1 DSK270 BLOCKSET PROFILE HAS 1 THROUGH 4 MEMBERS.

EACH MEMBER DESCRIPTOR RECORDS:

- BLOCKSET UUID;
- DESCRIPTOR GENERATION;
- MEMBER MASK;
- LOGICAL MEMBER INDEX;
- MEMBER COUNT;
- MEMBER-LOCAL BOOTSTREAM LOCATION;
- BAD-RUN INFORMATION WHERE PRESENT.

LOGICAL MEMBER INDICES MAY BE SPARSE.  MEMBER MASK IS AUTHORITATIVE AND MEMBER
COUNT IS THE NUMBER OF SET BITS.  FOR EXAMPLE:

    MASK 0013, COUNT 3 -> MEMBERS 0, 1, 3

A NORMAL BLOCKSET IS ACCEPTED ONLY WHEN EVERY REQUIRED MEMBER OF THE SAME UUID,
GENERATION, AND MEMBERSHIP DESCRIPTION IS PRESENT.  THERE IS NO DEGRADED
FILESYSTEM MODE IN V1.

THE RUNTIME STATE MUST SCALE WITH THE NUMBER OF PRESENT MEMBERS; DO NOT RESERVE
FULL PER-MEMBER RAM FOR EIGHT MEMBERS WHEN FEWER ARE PRESENT.

## 4. STRIPING

THE DSK ROOT BLOCKSET DATA LAYOUT IS PURE EQUAL-SIZE INTERLEAVING.  THERE IS NO MIRRORING, PARITY,
OR GENERAL RAID POLICY.

THE NORMAL STRIPE UNIT IS ONE 128-WORD LOGICAL BLOCK.

THE BLOCKSET LAYER, NOT D6FS AND NOT DSK270, MAPS A LOGICAL BLOCKSET BLOCK TO A
MEMBER AND MEMBER-LOGICAL BLOCK.

### 4.1 UNEQUAL MEMBER SIZES

THE IMPLEMENTED INTERLEAVE POLICY REQUIRES EQUAL MEMBER LENGTHS.  THERE IS NO
UNEQUAL-MEMBER ZONE-STRIPING ALGORITHM IN THE CURRENT BLOCKSET MAPPER.  WHEN A
CONSUMER NEEDS UNEQUAL LOGICAL MEMBER WINDOWS IT MUST USE THE GENERIC CONCAT
POLICY, WHERE EACH MEMBER CONTRIBUTES ONE CONSECUTIVE LOGICAL RANGE OF ITS OWN
DECLARED LENGTH.

DO NOT DOCUMENT OR IMPLEMENT CAPACITY-PRESERVING SHRINKING-WIDTH INTERLEAVE AS
PART OF V1 UNLESS A REAL CONSUMER REQUIRES IT; IT WOULD ADD RESIDENT MAPPING
CODE AND A THIRD POLICY WITHOUT CURRENT NEED.

## 5. BAD PHYSICAL MEDIA

PHYSICAL BAD SECTORS/BLOCKS ARE NOT A FILESYSTEM FEATURE.  THE STORAGE-SET
LAYER OWNS ONE COMMON PERSISTENT EXCEPTION MAP FOR BOTH DSK270 DISKS AND DRM236
DRUMS.  RAW DRIVERS DETECT/RETRY/REPORT DEVICE ERRORS; THEY DO NOT KEEP THEIR
OWN PERSISTENT BAD-BLOCK TABLES.

THE RESULT EXPORTED ABOVE THIS LAYER IS A STABLE CLEAN LOGICAL ADDRESS SPACE.
D6FS, LOGSTORE, AND SWAP DO NOT CARRY BAD-BLOCK LISTS AND DO NOT CREATE HIDDEN
BAD-BLOCK FILES.

### 5.1 COMPACT V1 REMAP WORD

THE CURRENT PDP-6 PROFILE NEEDS AT MOST FOUR MEMBERS.  DSK270 HAS 45056
128-WORD SECTORS PER UNIT AND DRM236 HAS 8192 128-WORD BLOCKS PER UNIT, SO A
16-BIT MEMBER-LOCAL BLOCK NUMBER IS SUFFICIENT FOR BOTH.  DEFINE A PHYSICAL
LOCATOR AS:

'''TEXT
18-BIT LOCATOR = 2-BIT MEMBER | 16-BIT MEMBER-LOCAL BLOCK
'''

ONE 36-BIT WORD THEREFORE STORES ONE REMAP:

'''TEXT
LH18 = BAD/SOURCE PHYSICAL LOCATOR
RH18 = SPARE/REPLACEMENT PHYSICAL LOCATOR
'''

KEEP THE IN-CORE TABLE SORTED BY SOURCE LOCATOR AND USE A SIMPLE LINEAR SEARCH
FOR THE SMALL PDP-6 PROFILE.  THIS COSTS ONE RESIDENT WORD PER ACTUAL REMAP AND
AVOIDS A FULL-MEDIA BITMAP.  IF A LATER LARGE-MEDIA PROFILE NEEDS MORE THAN FOUR
MEMBERS OR MORE THAN 65536 BLOCKS PER MEMBER, VERSION THE LOCATOR FORMAT RATHER
THAN PENALIZING THE PDP-6 PROFILE NOW.

SPARES ARE RESERVED PHYSICAL BLOCKS OUTSIDE THE EXPORTED LOGICAL CAPACITY.
PREFER A REPLACEMENT ON THE SAME MEMBER; THE FORMAT CAN REPRESENT A DIFFERENT
MEMBER WITHOUT CHANGING THE FILESYSTEM ABI.

### 5.2 STABILITY RULE

A REMAP IS AN EXCEPTION TO A STABLE PHYSICAL MAPPING.  IT MUST NEVER INSERT OR
DELETE AN ADDRESS IN A WAY THAT SHIFTS FOLLOWING LOGICAL BLOCKS.

THEREFORE:

1. BADSCAN SHOULD RUN BEFORE A NEW STORAGE-SET GENERATION IS CREATED;
2. KNOWN DEFECTS RECEIVE STABLE SPARES IN THAT GENERATION'S REMAP TABLE;
3. NORMAL LOGICAL-TO-MEMBER STRIPING IS CALCULATED WITHOUT DEFECT-DEPENDENT
   ADDRESS SHIFTING, THEN THE PHYSICAL LOCATOR IS PASSED THROUGH THE REMAP;
4. A NEW RUNTIME FAILURE MAY ADD A REMAP ONLY THROUGH A CRASH-SAFE PERSISTENT
   MAP UPDATE; UNTIL THAT UPDATE PATH EXISTS IT REMAINS A MAINTENANCE EVENT;
5. AN UNRECOVERABLE READ STILL RETURNS DATA LOSS.  A SPARE BLOCK DOES NOT
   RECONSTRUCT CONTENT WHICH COULD NOT BE RECOVERED;
6. IF A READ SUCCEEDS ONLY AFTER RETRY, MAINTENANCE OR A FUTURE ONLINE RETIRE
   PATH MAY COPY THE RECOVERED CONTENT TO A SPARE AND RETIRE THE SOURCE;
7. A FAILED WRITE MAY BE REISSUED TO A SPARE ONCE THE REMAP IS DURABLY RECORDED.

DEVICE-SPECIFIC RETRY COUNTS, CONTROLLER RESET SEQUENCES, SEEK/ROTATION POLICY,
AND RAW ADDRESS FORMATION REMAIN IN DSK270/DRM236.  ONLY THE EXCEPTION MAP, ITS
PERSISTENCE RULES, AND THE TRANSLATION STEP ARE SHARED.

### 5.3 BOOT-TIME LEGACY BAD-RUN FORMAT

DB0/DB1 PROVIDE THE CURRENT COMPACT BOOT-TIME BAD-RUN REPRESENTATION.  KEEP IT
AS A BOOTSTRAP COMPATIBILITY FORMAT WHILE STAGE1 CANNOT CONSUME THE FULL
STORAGE-SET REMAP.  KINIT/MAINTENANCE MAY CONVERT KNOWN BOOT-TIME DEFECTS INTO
THE NORMAL STABLE REMAP REPRESENTATION FOR THE RUNTIME DATA REGION.  DO NOT
MAKE THE DBOOT BAD-RUN ENCODING THE GENERAL RUNTIME BAD-MEDIA ABI.

### 5.4 CURRENT IMPLEMENTATION

THE TRANSLATOR IS IMPLEMENTED AS THE OPTIONAL MOVABLE `BADMAP` PACKAGE.
KINIT LOADS AND VALIDATES THE PERSISTENT TABLE ONLY WHEN ITS ENTRY COUNT IS
NONZERO, THEN COPIES THE SORTED SOURCE,,SPARE WORDS INTO MANAGED CORE.  CLEAN
MEDIA INSTALL NO BADMAP PACKAGE AND ALLOCATE NO TABLE.

THE SAME MAPPER SITS BELOW D6FS, LOGSTORE, AND THE RAW SWAP-TAIL NAMESPACE.
THE PRODUCTION MAPPER REGRESSION PASSES BOTH DSK270 AND DRM236 GEOMETRIES.
A REAL PDP-6 SIMH ROOT TEST REMAPS BOTH D6FS SUPERBLOCKS, DESTROYS THE ORIGINAL
PHYSICAL SECTORS, AND STILL BOOTS THROUGH D6FS TO LOGIN.

`D6BAD` COPIES SOURCE CONTENTS TO A RESERVED PHYSICAL SPARE BEFORE PUBLISHING
THE NEW MAP.  `D6SWAP --RESIZE-TAIL` PRESERVES THE EXISTING PER-MEMBER SPARE
RESERVE SO PHYSICAL REMAP LOCATORS REMAIN STABLE ACROSS SWAP-TAIL RESIZES.
ONLINE RETIREMENT AFTER DEVICE-SPECIFIC RECOVERY REMAINS SEPARATE WORK.

## 6. LOGICAL ADDRESS SPACE AND FILESYSTEM RESERVATIONS

BLOCKSET EXPORTS A CLEAN LOGICAL BLOCK ADDRESS SPACE.  IT DOES NOT PERSIST OR
OWN SWAP/LOGSTORE SEMANTIC REGION BOUNDARIES.  THE FILESYSTEM MAY RESERVE
LOGICAL RANGES FOR THOSE SERVICES; VFS RESOLVES AND REGISTERS THE RANGES.

THE BLOCKSET LAYER EXCLUSIVELY CHOOSES HOW EVERY LOGICAL RANGE IS DISTRIBUTED
OVER MEMBER DISKS OR DRUMS.  D6FS, SWAP, AND LOGSTORE MUST NOT INFER MEMBER
NUMBER, STRIPE POSITION, CYLINDER, TRACK, OR BAD-MEDIA SUBSTITUTION FROM A
LOGICAL BLOCK NUMBER.

A LOGICALLY CONTIGUOUS SWAP OR LOGSTORE RESERVATION MAY THEREFORE BE PHYSICALLY
DISTRIBUTED ACROSS MEMBERS.  KNOWN BAD MEDIA REMAIN A BLOCKSET/MEDIA MAPPING
CONCERN AND DO NOT BREAK THE LOGICAL CONTIGUITY SEEN ABOVE THIS LAYER.

THE BOOT/DESCRIPTOR AREA REMAINS A LOWER-LAYER/MEMBER-LOCAL CONCERN.  D6FS
FORMAT/MAINTENANCE POLICY MAY USE DEVICE GEOMETRY REPORTED BY LOWER LAYERS TO
PLACE ITS LOGSTORE/SWAP RESERVATIONS, BUT BLOCKSET DOES NOT ASSIGN THEIR
SEMANTIC PURPOSE.

## 7. BLOCK/RANGE API

THE LONG-TERM BLOCKSET CONTRACT IS GENERIC LOGICAL BLOCK/RANGE I/O PLUS
WRITABILITY, FLUSH/ORDERING, AND THE GEOMETRY INFORMATION NEEDED BY FORMAT/
MAINTENANCE TOOLS.  VFS REGISTRATION CACHES A SERVICE'S BACKING LOGICAL
START/LENGTH ON ACTIVATION, SO SWAP/LOGSTORE FAST-PATH I/O DOES NOT REENTER VFS
OR D6FS.

THE RESIDENT BLOCKSET IMPLEMENTATION NO LONGER CONTAINS SWAP- OR LOGSTORE-
SPECIFIC OPERATIONS.  THE ROOT RAW TAIL USES THE SAME LOGICAL MAPPER AS NORMAL
BLOCK I/O.  DBOOT TAIL FIELDS DESCRIBE PHYSICAL TRAILING CAPACITY AND REMAIN
BOOTSTRAP/LEGACY-COMPATIBILITY METADATA; THE ACTIVE SWAP START/LENGTH ON NEW
MEDIA IS PERSISTED BY D6FS.  PERSISTENT SEMANTIC RESERVATION OWNERSHIP BELONGS
TO D6FS/VFS.

## 8. REQUEST SCHEDULING

THE BLOCKSET MAY CHOOSE WHICH MEMBER RECEIVES EACH STRIPED LOGICAL REQUEST AND
MAY ISSUE INDEPENDENT MEMBER REQUESTS IN PARALLEL WHEN THE KERNEL SUPPORTS IT.

PHYSICAL SEEK SCHEDULING WITHIN ONE MOVING-HEAD DRIVE BELONGS TO THAT DRIVE'S
DRIVER.  FOR DSK270 THE POLICY IS SPECIFIED IN 'KERNEL/DSK270.MD'.  THE BLOCKSET
MUST NOT TRACK CYLINDER POSITION OR IMPLEMENT ANOTHER SEEK ELEVATOR.

## 9. TOOLS AND MAINTENANCE

'DSKLABEL' OWNS BLOCKSET IDENTITY, MEMBERSHIP, PHYSICAL/LOGICAL MEMBER MAPPING,
AND LAYOUT GENERATION.  IT DOES NOT OWN FILESYSTEM SWAP/LOGSTORE RESERVATIONS.

'BADSCAN' OWNS PHYSICAL BAD-MEDIA DISCOVERY.  IT SHOULD BE RUN BEFORE LAYOUT
CREATION FOR A NEW GENERATION.  A NEW DEFECT ON A FORMATTED SET IS A
MAINTENANCE EVENT, NOT A D6FS HIDDEN OBJECT.

'MKFS.D6FS' RECEIVES THE LOGICAL FILESYSTEM SPACE AND MAY CREATE OPTIONAL
ALIGNED SWAP/LOGSTORE RESERVATIONS WITHIN IT.  IT DOES NOT NEED THE PHYSICAL
MEMBER MAP; LOWER-LAYER GEOMETRY IS SUFFICIENT FOR PLACEMENT/ALIGNMENT POLICY.

LOGSTORE AND SWAP CONTENT INITIALIZATION USE THEIR VFS-RESOLVED RAW LOGICAL
RANGES, NOT NORMAL D6FS FILE I/O.

## 10. EXPLICIT NON-FEATURES

BLOCKSET V1 HAS NO:

- MIRRORING;
- PARITY;
- DEGRADED-MEMBER OPERATION;
- TRANSPARENT ONLINE BAD-SECTOR INSERTION THAT SHIFTS LOGICAL ADDRESSES;
- FILESYSTEM BAD-BLOCK OBJECTS;
- D6FS-SPECIFIC PHYSICAL SEEK SCHEDULER;
- REQUIREMENT TO REPRESENT RAW REGIONS AS FILES.


## 11. CURRENT IMPLEMENTATION STATE, 2026-09-24

BLOCKSET IS A STANDALONE RUNTIME STORAGE LAYER BELOW D6FS.  RESIDENT
SWAP/LOGSTORE SEMANTIC ENTRY POINTS AND THE OLD SPECIAL SWAP DISTRIBUTION ARE
REMOVED.  BLOCKSET MAPS LOGICAL BLOCKS ONLY; D6FS V2 OWNS PERSISTENT
SWAP/LOGSTORE RESERVATIONS, VFS PINS MOUNTS WITH ACTIVE STORAGE RESERVATIONS,
AND THE FIXED SWAP FAST PATH CONSUMES THE D6FS-AUTHORITATIVE LOGICAL RANGE.
FILESYSTEM-INDEPENDENT PER-MOUNT BACKING IS IMPLEMENTED, AS IS THE COMMON
OPTIONAL BADMAP LAYER BELOW D6FS/LOGSTORE/SWAP.  DBOOT STILL DESCRIBES PHYSICAL
RAW-TAIL CAPACITY FOR MEDIA LAYOUT.

THE REMAINING PRE-USERLAND BLOCKSET/STORAGE INTEGRATION IS D6FS-ON-DRM: A
SINGLE DRM MUST BYPASS BLOCKSET, WHILE MULTI-DRM USES THE EXISTING EQUAL-SIZE
INTERLEAVE MAPPER.  BLOCKSET CONTINUES TO OWN ONLY LOGICAL-TO-PHYSICAL
DISTRIBUTION; DEVICE-SPECIFIC MECHANICAL SCHEDULING STAYS IN THE LEAF DRIVERS.

CURRENT PER-UNIT ASYNCHRONOUS QUEUES AND SHARED DCT OWNERSHIP REMAIN VALID.
THE REMAINING SCHEDULER PASS SHOULD EXPLOIT CROSS-SPINDLE MECHANICAL OVERLAP
BEFORE CHOOSING THE NEXT SHARED TRANSFER.
