# DAIMOS DISKSET LOGICAL-BLOCK SPECIFICATION

*SMALL STRIPED MULTI-DISK BLOCK LAYER BELOW FILESYSTEMS*

## DOCUMENT METADATA

- STATUS: LOGICAL-BLOCK MRES IMPLEMENTED; LEGACY SEMANTIC SWAP/LOGSTORE API TRANSITIONAL
- DATE: 2026-09-17
- SCOPE: DISKSET ASSEMBLY, MEMBER MAPPING, BAD MEDIA, AND LOGICAL BLOCK I/O
- ENCODING: PLAIN ASCII; ALL MEDIA WORDS ARE 36-BIT PDP-10 WORDS

## 1. PURPOSE

THE DAIMOS DISKSET LAYER COMPOSES THE PRESENT V1 DSK270 PROFILE OF ONE THROUGH
FOUR PHYSICAL DISK MEMBERS INTO A SMALL LOGICAL BLOCK ADDRESS SPACE AND EXPORTS
GENERIC LOGICAL BLOCK/RANGE ACCESS TO CONSUMERS.  IT EXISTS BELOW D6FS, SWAP, AND LOGSTORE AND
ABOVE RAW PHYSICAL DISK DRIVERS.  THE FOUR-MEMBER V1 LIMIT MATCHES BOTH THE LIVE
DSK270 DRIVER AND THE HISTORICAL BOOT DESCRIPTOR; A FUTURE CONTROLLER/FORMAT MAY
RAISE IT WITHOUT CHANGING D6FS.

THE DESIGN PRIORITIES ARE:

1. RESIDENT RAM SIZE;
2. EXECUTION SPEED, ALMOST AS IMPORTANT AS RAM;
3. ON-DISK SPACE;
4. ABSTRACTION ELEGANCE.

THE MOST PRAGMATIC REPRESENTATION WINS WHEN IT IS MEASURABLY SMALLER OR FASTER.
IN PARTICULAR, SWAP AND LOGSTORE ARE RAW I/O CONSUMERS RATHER THAN D6FS
FILES.  THEIR PERSISTENT LOGICAL RESERVATIONS ARE OWNED BY THE FILESYSTEM AND
REGISTERED THROUGH VFS; DISKSET DOES NOT OWN THEIR SEMANTIC REGION METADATA.

## 2. LAYERING

'''TEXT
D6FS --------\
SWAP ---------+--> STANDALONE DISKSET MRES --> STORAGE MRES --> DSK270
LOGSTORE -----/
'''

THE RUNTIME DISKSET MRES OWNS ONE VALIDATED SINGLETON LAYOUT.  BOOT-TIME
DESCRIPTOR DISCOVERY/DECODING IS ONE-SHOT KINIT CODE AND IS NOT KEPT IN THE
RESIDENT DISKSET PACKAGE.  THE RUNTIME SERVICE ABI IS DELIBERATELY SMALL: ONE
DISPATCH ENTRY AND A COMPACT REQUEST.

THE BOOT DESCRIPTOR AND MEMBER-LOCAL BOOTSTREAM ARE SPECIAL EARLY-BOOT MEDIA
LAYOUT AND ARE DESCRIBED IN 'BOOT/DBOOT.MD'.  STAGE1 MAY READ THEM BEFORE THE
FULL RUNTIME DISKSET OBJECT EXISTS.

D6FS DOES NOT KNOW MEMBER COUNTS, MEMBER UUIDS, STRIPE ZONES, PHYSICAL SECTORS,
BAD RUNS, OR PHYSICAL BOOTSTREAM LOCATIONS.  IT MAY OWN LOGICAL SWAP/LOGSTORE
RESERVATIONS WITHOUT KNOWING THEIR PHYSICAL MEMBER DISTRIBUTION.

THE RAW DSK270 DRIVER DOES NOT KNOW FILESYSTEMS, STRIPE ZONES, OR RAW REGION
SEMANTICS.  IT READS/WRITES PHYSICAL SECTORS AND SCHEDULES REQUESTS FOR ONE
PHYSICAL UNIT.

## 3. MEMBER IDENTITY

THE PRESENT V1 DSK270 DISKSET PROFILE HAS 1 THROUGH 4 MEMBERS.

EACH MEMBER DESCRIPTOR RECORDS:

- DISKSET UUID;
- DESCRIPTOR GENERATION;
- MEMBER MASK;
- LOGICAL MEMBER INDEX;
- MEMBER COUNT;
- MEMBER-LOCAL BOOTSTREAM LOCATION;
- BAD-RUN INFORMATION WHERE PRESENT.

LOGICAL MEMBER INDICES MAY BE SPARSE.  MEMBER MASK IS AUTHORITATIVE AND MEMBER
COUNT IS THE NUMBER OF SET BITS.  FOR EXAMPLE:

    MASK 0013, COUNT 3 -> MEMBERS 0, 1, 3

A NORMAL DISKSET IS ACCEPTED ONLY WHEN EVERY REQUIRED MEMBER OF THE SAME UUID,
GENERATION, AND MEMBERSHIP DESCRIPTION IS PRESENT.  THERE IS NO DEGRADED
FILESYSTEM MODE IN V1.

THE RUNTIME STATE MUST SCALE WITH THE NUMBER OF PRESENT MEMBERS; DO NOT RESERVE
FULL PER-MEMBER RAM FOR EIGHT MEMBERS WHEN FEWER ARE PRESENT.

## 4. STRIPING

THE V1 DISKSET DATA LAYOUT IS PURE STRIPING.  THERE IS NO MIRRORING, PARITY,
OR GENERAL RAID POLICY.

THE NORMAL STRIPE UNIT IS ONE 128-WORD LOGICAL BLOCK.

THE DISKSET LAYER, NOT D6FS AND NOT DSK270, MAPS A LOGICAL DISKSET BLOCK TO A
MEMBER AND MEMBER-LOGICAL BLOCK.

### 4.1 UNEQUAL MEMBER SIZES

MEMBERS MAY HAVE UNEQUAL USABLE SIZES.  CAPACITY IS NOT TRUNCATED TO THE
SHORTEST MEMBER.  THE DISKSET USES SHRINKING-WIDTH STRIPE ZONES DERIVED FROM
USABLE MEMBER CAPACITIES.

EXAMPLE FOR MEMBERS WITH 1000, 1500, AND 2000 USABLE BLOCKS:

    ZONE 0  MEMBER DEPTH    0..999     WIDTH 3: A B C
    ZONE 1  MEMBER DEPTH 1000..1499    WIDTH 2:   B C
    ZONE 2  MEMBER DEPTH 1500..1999    WIDTH 1:     C

FOR N MEMBERS THERE ARE AT MOST N ZONES.  THE ZONE TABLE IS DERIVED WHEN THE
DISKSET IS ASSEMBLED AND IS NOT STORED IN D6FS METADATA.

## 5. BAD PHYSICAL MEDIA

PHYSICAL BAD SECTORS ARE NOT A FILESYSTEM FEATURE.

PERSISTENT BAD-RUN INFORMATION BELONGS TO MEMBER/MEDIA METADATA.  DSK270
REPORTS PHYSICAL I/O FAILURES; THE MEMBER/DISKSET MAPPER USES THE PERSISTENT
BAD-RUN DESCRIPTION TO EXCLUDE KNOWN DEFECTS FROM THE USABLE MEMBER ADDRESS
SPACE.

THE RESULT EXPORTED ABOVE THIS LAYER IS A CLEAN LOGICAL ADDRESS SPACE.  D6FS,
LOGSTORE, AND SWAP DO NOT CARRY BAD-BLOCK LISTS AND DO NOT CREATE HIDDEN
BAD-BLOCK FILES.

### 5.1 STABILITY RULE

THE BAD-RUN MAP USED TO CREATE A FORMATTED DISKSET GENERATION IS PART OF THAT
GENERATION'S PHYSICAL-TO-LOGICAL MAPPING.  IT MUST NOT BE CHANGED IN PLACE IF
DOING SO WOULD SHIFT EXISTING LOGICAL BLOCKS.

THEREFORE:

1. BADSCAN SHOULD RUN BEFORE A NEW DISKSET LAYOUT/FILESYSTEM IS CREATED;
2. KNOWN BAD RUNS ARE EXCLUDED WHEN THAT GENERATION IS LAID OUT;
3. A NEW RUNTIME MEDIA FAILURE IS REPORTED AS AN I/O ERROR AND MARKS THE SET
   FOR MAINTENANCE;
4. V1 DOES NOT SILENTLY INSERT A NEW SKIPPED SECTOR INTO A LIVE MAPPING;
5. OFFLINE REBUILD/REPLACEMENT MAY CREATE A NEW GENERATION WITH A NEW BAD MAP.

THIS RULE AVOIDS A RESIDENT RELOCATION TABLE AND PREVENTS A NEW DEFECT FROM
SILENTLY REINTERPRETING EVERY LOGICAL BLOCK AFTER IT.

### 5.2 DBOOT BAD-RUN FORMAT

DB0/DB1 PROVIDE THE CURRENT COMPACT BOOT-TIME BAD-RUN REPRESENTATION.  ITS
CURRENT START-SECTOR FIELD COVERS THE 02000-SECTOR BOOTSET IMAGE PROFILE.  IT
DOES NOT BY ITSELF DESCRIBE THE FULL 45056-SECTOR RAW DSK270 GEOMETRY.
A FULL-SIZE REAL-MEDIA PROFILE REQUIRES A COMPATIBLE WIDER BAD-RUN DESCRIPTOR
BEFORE THE DISKSET FORMAT IS CONSIDERED FROZEN FOR THAT GEOMETRY.

## 6. LOGICAL ADDRESS SPACE AND FILESYSTEM RESERVATIONS

DISKSET EXPORTS A CLEAN LOGICAL BLOCK ADDRESS SPACE.  IT DOES NOT PERSIST OR
OWN SWAP/LOGSTORE SEMANTIC REGION BOUNDARIES.  THE FILESYSTEM MAY RESERVE
LOGICAL RANGES FOR THOSE SERVICES; VFS RESOLVES AND REGISTERS THE RANGES.

THE DISKSET LAYER EXCLUSIVELY CHOOSES HOW EVERY LOGICAL RANGE IS DISTRIBUTED
OVER MEMBER DISKS OR DRUMS.  D6FS, SWAP, AND LOGSTORE MUST NOT INFER MEMBER
NUMBER, STRIPE POSITION, CYLINDER, TRACK, OR BAD-MEDIA SUBSTITUTION FROM A
LOGICAL BLOCK NUMBER.

A LOGICALLY CONTIGUOUS SWAP OR LOGSTORE RESERVATION MAY THEREFORE BE PHYSICALLY
DISTRIBUTED ACROSS MEMBERS.  KNOWN BAD MEDIA REMAIN A DISKSET/MEDIA MAPPING
CONCERN AND DO NOT BREAK THE LOGICAL CONTIGUITY SEEN ABOVE THIS LAYER.

THE BOOT/DESCRIPTOR AREA REMAINS A LOWER-LAYER/MEMBER-LOCAL CONCERN.  D6FS
FORMAT/MAINTENANCE POLICY MAY USE DEVICE GEOMETRY REPORTED BY LOWER LAYERS TO
PLACE ITS LOGSTORE/SWAP RESERVATIONS, BUT DISKSET DOES NOT ASSIGN THEIR
SEMANTIC PURPOSE.

## 7. BLOCK/RANGE API

THE LONG-TERM DISKSET CONTRACT IS GENERIC LOGICAL BLOCK/RANGE I/O PLUS
WRITABILITY, FLUSH/ORDERING, AND THE GEOMETRY INFORMATION NEEDED BY FORMAT/
MAINTENANCE TOOLS.  VFS REGISTRATION CACHES A SERVICE'S BACKING LOGICAL
START/LENGTH ON ACTIVATION, SO SWAP/LOGSTORE FAST-PATH I/O DOES NOT REENTER VFS
OR D6FS.

THE CURRENT IMPLEMENTATION STILL CONTAINS HISTORICAL D6FS/SWAP/LOGSTORE
REGION-SPECIFIC ENTRY POINTS AND LAYOUT FIELDS.  THEY ARE TRANSITIONAL.  MOVE
PERSISTENT SWAP/LOGSTORE OWNERSHIP UPWARD INTO D6FS/VFS WITHOUT REGRESSING THE
EXISTING RAW RANGE FAST PATH OR ADDING FILE-I/O OVERHEAD.

## 8. REQUEST SCHEDULING

THE DISKSET MAY CHOOSE WHICH MEMBER RECEIVES EACH STRIPED LOGICAL REQUEST AND
MAY ISSUE INDEPENDENT MEMBER REQUESTS IN PARALLEL WHEN THE KERNEL SUPPORTS IT.

PHYSICAL SEEK SCHEDULING WITHIN ONE MOVING-HEAD DRIVE BELONGS TO THAT DRIVE'S
DRIVER.  FOR DSK270 THE POLICY IS SPECIFIED IN 'KERNEL/DSK270.MD'.  THE DISKSET
MUST NOT TRACK CYLINDER POSITION OR IMPLEMENT ANOTHER SEEK ELEVATOR.

## 9. TOOLS AND MAINTENANCE

'DSKLABEL' OWNS DISKSET IDENTITY, MEMBERSHIP, PHYSICAL/LOGICAL MEMBER MAPPING,
AND LAYOUT GENERATION.  IT DOES NOT OWN FILESYSTEM SWAP/LOGSTORE RESERVATIONS.

'BADSCAN' OWNS PHYSICAL BAD-MEDIA DISCOVERY.  IT SHOULD BE RUN BEFORE LAYOUT
CREATION FOR A NEW GENERATION.  A NEW DEFECT ON A FORMATTED SET IS A
MAINTENANCE EVENT, NOT A D6FS HIDDEN OBJECT.

'MKFS.D6FS' RECEIVES THE LOGICAL FILESYSTEM SPACE AND MAY CREATE OPTIONAL
ALIGNED SWAP/LOGSTORE RESERVATIONS WITHIN IT.  IT DOES NOT NEED THE PHYSICAL
MEMBER MAP; LOWER-LAYER GEOMETRY IS SUFFICIENT FOR PLACEMENT/ALIGNMENT POLICY.

LOGSTORE AND SWAP CONTENT INITIALIZATION USE THEIR VFS-RESOLVED RAW LOGICAL
RANGES, NOT NORMAL D6FS FILE I/O.

## 10. EXPLICIT NON-FEATURES

DISKSET V1 HAS NO:

- MIRRORING;
- PARITY;
- DEGRADED-MEMBER OPERATION;
- TRANSPARENT ONLINE BAD-SECTOR INSERTION THAT SHIFTS LOGICAL ADDRESSES;
- FILESYSTEM BAD-BLOCK OBJECTS;
- D6FS-SPECIFIC PHYSICAL SEEK SCHEDULER;
- REQUIREMENT TO REPRESENT RAW REGIONS AS FILES.


## 11. CURRENT IMPLEMENTATION TRANSITION, 2026-09-17

DISKSET IS A STANDALONE RUNTIME STORAGE LAYER BELOW D6FS.  THE CURRENT TREE
STILL DECODES HISTORICAL LAYOUT FIELDS AND RETAINS SEMANTIC SWAP/LOGSTORE
ENTRY POINTS, INCLUDING THE OLD SPECIAL SWAP DISTRIBUTION.  THOSE INTERFACES
ARE TRANSITIONAL AND MUST NOT BE TREATED AS THE FINAL FORMAT.

THE MIGRATION IS:

1. MOVE PERSISTENT SWAP/LOGSTORE START/LENGTH INTO D6FS METADATA;
2. LET VFS REGISTER THE RESOLVED RAW LOGICAL RANGE WITH THE SERVICE;
3. KEEP THE ACTIVE FAST PATH AS GENERIC LOGICAL RANGE I/O BELOW VFS;
4. REMOVE DISKSET SEMANTIC KNOWLEDGE OF SWAP/LOGSTORE;
5. COMPLETE COMMON BAD-MEDIA TRANSLATION BELOW D6FS/SWAP/LOGSTORE;
6. PRESERVE DISKSET OWNERSHIP OF PHYSICAL DISTRIBUTION AND SCHEDULING.

CURRENT PER-UNIT ASYNCHRONOUS QUEUES AND SHARED DCT OWNERSHIP REMAIN VALID.
A LATER SCHEDULER PASS SHOULD EXPLOIT CROSS-SPINDLE MECHANICAL OVERLAP BEFORE
CHOOSING THE NEXT SHARED TRANSFER.
