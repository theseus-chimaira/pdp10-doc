## IMPLEMENTED V1 PATH

THE CURRENT TREE IMPLEMENTS THE FIRST SYNCHRONOUS HDD PATH:

'''TEXT
PAPER TAPE OR SIMH RIM
  -> STAGE1 HDD/DBOOT V1 READER
  -> DB0/DBX OR DBC DESCRIPTOR SELECTION
  -> DAIMON BOOT STREAM READ FROM SELECTED MEMBER RUNS
  -> BOOTINFO V2 AT 073000
  -> KINIT ASSEMBLES THE DISKSET/MEMBER MAP
  -> DISKSET EXPORTS THE D6FS LOGICAL REGION
  -> DSK270 SERVICES PHYSICAL MEMBER REQUESTS
  -> D6FS MOUNTS THE EXPORTED ROOT REGION
'''

IMPLEMENTED PIECES:

'''TEXT
- DCT136 POLLED WORD TRANSFER HELPERS
- DSK270 RAW ADDRESS PACKING, PROBE, SECTOR READ, SECTOR WRITE
- DSK270 RUN READ/WRITE API THAT LOOPS ONE SECTOR AT A TIME, WITHOUT HARDWARE STREAMING
- INTERRUPT-MODE ENTRY POINTS AND PI REGISTRATION HOOKS
- STAGE1 PRIVATE DSK270 READER
- DBOOT DB0/DBX/DBC V2 PARSING
- BOOTINFO V2 DISK-SET AND REGION HANDOFF
- BOOT/MEMBER MAPPING THROUGH THE HISTORICAL P6STRIPE/BOOTDISK HELPERS
- D6FS ROOT REGION READ PATH THROUGH THAT LEGACY MAPPING
- D6FS BOOT-ROOT MOUNT ABOVE THE LOGICAL REGION
- HOST TOOLING TO CREATE CLEAN EMULATOR BOOT SETS WITH D6FS ROOTS

THE RAW DSK270 LAYER REMAINS A PHYSICAL-SECTOR DRIVER. IT DOES NOT KNOW ABOUT
D6FS FILES, DIRECTORIES, ALLOCATION POLICY, DISKSET STRIPE ZONES, SWAP,
LOGSTORE, OR FILESYSTEM REGIONS.

## CURRENT MEDIA FORMAT

THE CURRENT MEDIA DESCRIPTOR IS DBOOTX V2:

'''TEXT
DBC   ONE-SECTOR CLEAN-MEDIA DESCRIPTOR
DB0   BAD-RUN SECTOR
DBX   DESCRIPTOR PAIRED WITH DB0
'''

THE DESCRIPTOR RECORDS GENERATION, DISK-SET UUID, MEMBER MASK, MEMBER INDEX,
DISK COUNT, KINIT BOOT CONFIGURATION, AND THE MEMBER-LOCAL BOOTSTREAM RUN.
DAIMOS V2 SUPPORTS 1 THROUGH 8 DISKSET MEMBERS.  DISKSET STRIPING,
UNEQUAL-MEMBER ZONE MAPPING, BAD-RUN EXCLUSION, AND REGION BOUNDARIES LIVE
ABOVE THE RAW DSK270 ADDRESS/TRANSFER API; THE RAW DRIVER REMAINS A SINGLE-UNIT
DRIVER.  SEE 'KERNEL/DISKSET.MD'.


## SEEK SCHEDULING

FOR SEEK-BASED DISKS, EACH PHYSICAL DSK UNIT USES A SMALL BOUNDED ONE-WAY
ELEVATOR QUEUE, FOLLOWING THE SIMPLE TENEX POLICY:

1. SERVICE THE NEAREST QUEUED REQUEST AT OR ABOVE THE CURRENT TRACK/CYLINDER.
2. CONTINUE IN THE SAME DIRECTION.
3. WHEN NO REQUEST REMAINS ABOVE, WRAP TO THE LOWEST QUEUED REQUEST.
4. DO NOT IMPORT TENEX PRIORITY-CLASS COMPLEXITY UNLESS MEASUREMENT SHOWS A
   NEED.

SCHEDULING IS PER PHYSICAL MEMBER AND OCCURS BELOW DISKSET STRIPING.  QUEUE
DEPTH IS A BENCHMARKED IMPLEMENTATION PARAMETER, NOT AN ON-DISK FORMAT FIELD.

## BAD-SECTOR HANDLING

DSK270 OWNS PHYSICAL ERROR DETECTION AND REPORTING.  IT DOES NOT OWN THE
PERSISTENT BAD-RUN MAP AND MUST NOT SILENTLY CHANGE LOGICAL BLOCK MAPPINGS.

THE CURRENT DBOOT DB0/DB1 RECORDS CAN CARRY COMPACT KNOWN BAD RUNS.  THE
DISKSET/MEMBER MAPPER CONSUMES THAT INFORMATION AND EXCLUDES KNOWN DEFECTS FROM
THE USABLE MEMBER ADDRESS SPACE BEFORE D6FS, SWAP, OR LOGSTORE SEE IT.

A NEW RUNTIME SECTOR FAILURE IS REPORTED UPWARD WITH THE PHYSICAL REQUEST
CONTEXT.  V1 DOES NOT TRANSPARENTLY INSERT A NEW SKIPPED SECTOR INTO A LIVE
FORMATTED MAPPING; THAT COULD SHIFT EVERY FOLLOWING LOGICAL BLOCK.  OFFLINE
MAINTENANCE/REBUILD CREATES A NEW STABLE GENERATION WHEN REQUIRED.

NATIVE SURFACE SCAN BELONGS TO BADSCAN/MAINTENANCE TOOLING.  A FUTURE SPARE-
SECTOR REMAPPER MAY BE ADDED BELOW THE FILESYSTEM ONLY IF IT PRESERVES STABLE
LOGICAL ADDRESSES WITH ACCEPTABLE RAM/CODE COST.

## BUFFER AND CACHE POLICY

DSK270 DOES NOT OWN A FILESYSTEM BLOCK CACHE.

THE DRIVER MAY KEEP ONLY THE BOUNDED TRANSFER/REQUEST STATE NEEDED TO OPERATE A
PHYSICAL UNIT AND ITS SEEK QUEUE.  THE PDP-6 FILESYSTEM/VFS PATH TARGETS ONE
SHARED 128-WORD FULL-BLOCK WORKSPACE ABOVE THE DRIVER; D6FS AND DTFS MUST NOT
FORCE PRIVATE FULL-BLOCK ARRAYS INTO DSK270.

REQUEST QUEUES ARE SCHEDULING STATE, NOT A DATA CACHE.  A FUTURE ASYNCHRONOUS
WRITE PATH MAY REQUIRE BOUNDED IN-FLIGHT BUFFERS, BUT THEIR COUNT MUST BE
MEASURED AGAINST PDP-6 RAM AND MUST NOT BECOME AN UNBOUNDED FREE-RAM CACHE.

## PRIORITY MULTI-SECTOR OPTIMIZATION

MULTI-SECTOR STREAMING IS USEFUL AS A PRIORITY PERFORMANCE OPTIMIZATION, NOT AS A CORRECTNESS REQUIREMENT. IT MEANS
ISSUING ONE HARDWARE/CONTROLLER TRANSFER FOR A RUN OF ADJACENT SECTORS INSTEAD
OF LOOPING THROUGH 'READ_SECTOR()' OR 'WRITE_SECTOR()' ONE SECTOR AT A TIME.
THE VISIBLE API ALREADY HAS 'READ_RUN()' AND 'WRITE_RUN()', BUT THE CURRENT
IMPLEMENTATION STILL PERFORMS ONE FULL SECTOR OPERATION PER SECTOR.

STREAMING IS NOT REQUIRED FOR V1 CORRECTNESS, BUT IT SHOULD BE THE FIRST DSK270
PERFORMANCE ITEM ONCE THE REQUEST/WRITE PATH IS STABLE ENOUGH TO MEASURE. IT
MATTERS MOST WHEN BOOT LOADING OR SEQUENTIAL FILESYSTEM/RAW-REGION I/O SPENDS
TOO MUCH TIME IN PER-SECTOR SETUP.

HARD RULE FOR ANY FUTURE STREAMING:

'''TEXT
NEVER CROSS SECTOR 43 -> 0 IN ONE HARDWARE STREAMING COMMAND
UNLESS HARDWARE AND SIMULATOR BEHAVIOR ARE BOTH PROVEN SAFE
'''
