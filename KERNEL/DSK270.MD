## IMPLEMENTED V1 PATH

THE CURRENT TREE IMPLEMENTS THE FIRST SYNCHRONOUS HDD PATH:

'''TEXT
PAPER TAPE OR SIMH RIM
  -> STAGE1 HDD/DBOOT V1 READER
  -> DB0/DBX OR DBC DESCRIPTOR SELECTION
  -> DAIMON BOOT STREAM READ FROM SELECTED MEMBER RUNS
  -> BOOTINFO V2 AT 073000
  -> KINIT ASSEMBLES THE BLOCKSET/MEMBER MAP
  -> BLOCKSET EXPORTS THE D6FS LOGICAL REGION
  -> DSK270 SERVICES PHYSICAL MEMBER REQUESTS
  -> D6FS MOUNTS THE EXPORTED ROOT REGION
'''

'''TEXT

- INTERRUPT-DRIVEN DSK270 COMPLETION THROUGH THE STORAGE MRES
- FIXED BOUNDED PER-UNIT REQUEST QUEUES
- ONE-WAY ELEVATOR ORDERING
- WATCHDOG/TIMEOUT WAKEUP FOR BLOCKING CALLERS
- PERSISTED PHYSICAL-DISK ONLINE READ/WRITE REGRESSION

THE RAW DSK270 LAYER REMAINS A PHYSICAL-SECTOR DRIVER. IT DOES NOT KNOW ABOUT
D6FS FILES, DIRECTORIES, ALLOCATION POLICY, BLOCKSET STRIPE ZONES, SWAP,
LOGSTORE, OR FILESYSTEM REGIONS.

## CURRENT MEDIA FORMAT

THE CURRENT MEDIA DESCRIPTOR IS DBOOTX V2:

'''TEXT
DBC   ONE-SECTOR CLEAN-MEDIA DESCRIPTOR
DB0   BAD-RUN SECTOR
DBX   DESCRIPTOR PAIRED WITH DB0
'''

THE DESCRIPTOR RECORDS GENERATION, DISK-SET UUID, MEMBER MASK, MEMBER INDEX,
DISK COUNT, KINIT BOOT CONFIGURATION, AND THE MEMBER-LOCAL BOOTSTREAM RUN.
THE PRESENT V1 DSK270/BOOT PROFILE SUPPORTS 1 THROUGH 4 BLOCKSET MEMBERS.
BLOCKSET EQUAL-SIZE INTERLEAVING, CONCAT MAPPING, AND THE COMMON STABLE BAD-MEDIA
EXCEPTION REMAP LIVE ABOVE THE RAW DSK270 ADDRESS/TRANSFER API; FILESYSTEM
SWAP/LOGSTORE RESERVATIONS LIVE ABOVE BLOCKSET IN D6FS/VFS; THE RAW DRIVER
REMAINS A SINGLE-UNIT DRIVER.  SEE 'KERNEL/BLOCKSET.MD'.


## SEEK SCHEDULING

FOR SEEK-BASED DISKS, EACH PHYSICAL DSK UNIT USES A SMALL BOUNDED ONE-WAY
ELEVATOR QUEUE, FOLLOWING THE SIMPLE TENEX POLICY:

1. SERVICE THE NEAREST QUEUED REQUEST AT OR ABOVE THE CURRENT TRACK/CYLINDER.
2. CONTINUE IN THE SAME DIRECTION.
3. WHEN NO REQUEST REMAINS ABOVE, WRAP TO THE LOWEST QUEUED REQUEST.
4. DO NOT IMPORT TENEX PRIORITY-CLASS COMPLEXITY UNLESS MEASUREMENT SHOWS A
   NEED.

SCHEDULING IS PER PHYSICAL MEMBER AND OCCURS BELOW BLOCKSET STRIPING.  QUEUE
DEPTH IS A BENCHMARKED IMPLEMENTATION PARAMETER, NOT AN ON-DISK FORMAT FIELD.

## BAD-SECTOR HANDLING

DSK270 OWNS PHYSICAL ERROR DETECTION, BOUNDED DEVICE-SPECIFIC RETRY/RESET, AND
REPORTING.  IT DOES NOT OWN A PERSISTENT BAD-SECTOR TABLE AND MUST NOT SILENTLY
CHANGE LOGICAL BLOCK MAPPINGS.

PERSISTENT SUBSTITUTION BELONGS TO THE COMMON STORAGE-SET BAD-MEDIA MAPPER
DEFINED IN 'KERNEL/BLOCKSET.MD'.  DSK270 AND DRM236 SHARE THAT TRANSLATOR AND
ON-MEDIA EXCEPTION FORMAT; THEY DO NOT DUPLICATE RESIDENT MAPS.  FOR THE PDP-6
PROFILE ONE 36-BIT WORD HOLDS A COMPLETE SOURCE->SPARE REMAP.

THE CURRENT DRIVER DOES NOT RETRY MEDIA ERRORS OR REMAP THEM: THE PI ERROR PATH
FAILS THE ACTIVE REQUEST, AND THE BOOT POLLED PATH RETURNS FAILURE.  THE CURRENT
BLOCKSET RUNTIME ALSO DOES NOT APPLY THE BADMAP FIELDS ALREADY DECODED BY KINIT.
THE IMPLEMENTATION WORK IS THEREFORE STILL OPEN.

A NEW UNRECOVERABLE READ MUST CONTINUE TO REPORT DATA LOSS EVEN AFTER THE
PHYSICAL BLOCK IS RETIRED.  A WRITE OR A READ WHOSE DATA WAS RECOVERED BY RETRY
MAY BE MOVED TO A SPARE ONCE THE COMMON REMAP UPDATE CAN BE RECORDED CRASH-SAFELY.

NATIVE SURFACE SCAN BELONGS TO BADSCAN/MAINTENANCE TOOLING.  THE DRIVER SHOULD
EXPOSE ENOUGH PHYSICAL FAILURE CONTEXT FOR THAT TOOLING WITHOUT KEEPING A
SECOND BAD-SECTOR DATABASE.

## BUFFER AND CACHE POLICY

DSK270 DOES NOT OWN A FILESYSTEM BLOCK CACHE.

THE DRIVER MAY KEEP ONLY THE BOUNDED TRANSFER/REQUEST STATE NEEDED TO OPERATE A
PHYSICAL UNIT AND ITS SEEK QUEUE.  THE CURRENT PDP-6 FILESYSTEM/VFS PATH HAS A
SHARED 128-WORD FULL-BLOCK WORKSPACE ABOVE THE DRIVER; ACCEPTED D6FS CACHE WORK
MAY REPLACE THAT TRANSITIONAL WORKSPACE WITH RECLAIMABLE MANAGED-CORE BUFFERS.
D6FS AND DTFS MUST NOT FORCE PRIVATE FULL-BLOCK ARRAYS INTO DSK270.

REQUEST QUEUES ARE SCHEDULING STATE, NOT A DATA CACHE.  A FUTURE ASYNCHRONOUS
WRITE PATH MAY REQUIRE BOUNDED IN-FLIGHT BUFFERS, BUT THEIR COUNT MUST BE
MEASURED AGAINST PDP-6 RAM AND MUST NOT BECOME AN UNBOUNDED FREE-RAM CACHE.

REMAIN KERNEL TODOS:

'''TEXT
- TRUE HARDWARE MULTI-SECTOR STREAMING FOR SAFE ADJACENT RUNS

'/PROC' IS NOT A SEPARATE FILESYSTEM.  IT IS THE VFS ALIAS OF
'/MONITOR/PROCESSES' AND THEREFORE CONTAINS PROCESS OBJECTS ONLY.  OTHER KERNEL
STATE BELONGS IN THE APPROPRIATE MONITORFS TREE.  DIAGNOSTICS SHOULD REMAIN
SMALL NUMERIC RECORDS RATHER THAN A SECOND RESIDENT TEXT FILESYSTEM.

## DEFERRED MULTI-SECTOR OPTIMIZATION

MULTI-SECTOR STREAMING IS A POSSIBLE PERFORMANCE OPTIMIZATION, NOT A
CORRECTNESS REQUIREMENT.  IT MEANS
ISSUING ONE HARDWARE/CONTROLLER TRANSFER FOR A RUN OF ADJACENT SECTORS INSTEAD
OF LOOPING THROUGH 'READ_SECTOR()' OR 'WRITE_SECTOR()' ONE SECTOR AT A TIME.
THE VISIBLE API ALREADY HAS 'READ_RUN()' AND 'WRITE_RUN()', BUT THE CURRENT
IMPLEMENTATION STILL PERFORMS ONE FULL SECTOR OPERATION PER SECTOR.

THE FIRST CORRECT PROTOTYPE COST ABOUT 53 RESIDENT WORDS AND WAS REJECTED
WITHOUT A LIVE PROCESS-SWAP CALLER.  RECONSIDER IT ONLY AFTER REAL RUN TRAFFIC
EXISTS AND MEASUREMENT SHOWS THAT PER-SECTOR SETUP DOMINATES.  THE ACCEPTANCE
GATE IS A MATERIAL SPEEDUP AT A JUSTIFIED RESIDENT COST, WITH ALL STORAGE
ORACLES STILL GREEN.

HARD RULE FOR ANY FUTURE STREAMING:

'''TEXT
NEVER CROSS SECTOR 43 -> 0 IN ONE HARDWARE STREAMING COMMAND
UNLESS HARDWARE AND SIMULATOR BEHAVIOR ARE BOTH PROVEN SAFE
'''
