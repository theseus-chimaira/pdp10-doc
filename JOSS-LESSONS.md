# JOSS II LESSONS FOR INTERACTIVE DAIMOS

STATUS: DESIGN DIRECTION; NOT YET AN IMPLEMENTATION REQUIREMENT

## 1. PURPOSE

JOSS II IS A USEFUL REFERENCE FOR DAIMOS BECAUSE IT SOLVED INTERACTIVE
MULTIUSER COMPUTING ON A SMALL PDP-6 WITH VERY LIMITED CORE.  ITS IMPORTANT
LESSON IS NOT THAT DAIMOS SHOULD BECOME A JOSS-LIKE INTEGRATED INTERPRETER.
JOSS COULD SPECIALIZE ITS MONITOR, SCHEDULER, SWAPPING, CONSOLE SERVICE, AND
LANGUAGE AROUND ONE APPLICATION MODEL; DAIMOS MUST REMAIN A GENERAL-PURPOSE
OPERATING SYSTEM.

THE TRANSFERABLE LESSON IS THAT INTERACTIVE RESPONSIVENESS SHOULD BE AN
EXPLICIT SYSTEM DESIGN GOAL RATHER THAN AN ACCIDENTAL CONSEQUENCE OF FAIR CPU
SCHEDULING.

DAIMOS IS EXPECTED TO BE A MULTIUSER SYSTEM, BUT ITS NORMAL LOAD IS CLOSER TO
A WORKSTATION THAN TO A LARGE TIMESHARING SERVICE: A SMALL NUMBER OF
SIMULTANEOUS USERS, INTERACTIVE SHELLS AND EDITORS, DEVELOPMENT TOOLS, AND A
FEW BACKGROUND OR COMPUTE-HEAVY JOBS.  POLICY SHOULD THEREFORE FAVOR PROMPT
FOREGROUND RESPONSE WHILE PRESERVING FAIR PROGRESS FOR OTHER USERS.

THE PRIORITIES ARE:

1. KEEP HUMAN INTERACTION RESPONSIVE;
2. KEEP THE 32K PDP-6 CONFIGURATION PRACTICAL;
3. KEEP THE KERNEL SMALL AND MECHANISMS GENERAL;
4. GIVE BACKGROUND WORK GOOD THROUGHPUT AFTER INTERACTIVE LATENCY IS SATISFIED;
5. PRESERVE MULTIUSER FAIRNESS WITHOUT OPTIMIZING FOR DOZENS OF ACTIVE USERS.

## 2. WHAT JOSS II DID WELL

JOSS TREATED CONSOLE INPUT, CPU SCHEDULING, CORE ALLOCATION, DRUM SWAPPING,
OUTPUT BUFFERING, AND THE INTERPRETER AS PARTS OF ONE RESPONSE-TIME PROBLEM.
A USER WHO FINISHED TYPING WAS MOVED FROM AN INACTIVE STATE TO A HIGH-PRIORITY
REQUEST STATE; THE MONITOR COULD ARRANGE DRUM OR CORE SERVICE AND RETURN CPU
SERVICE QUICKLY.  LONGER COMPUTATION WAS ALLOWED TO PROCEED AT LOWER
INTERACTIVE URGENCY.

JOSS ALSO USED USER STATE TO MAKE MEMORY DECISIONS.  A USER WHO WAS LIKELY TO
REMAIN INACTIVE WAS A BETTER DRUM-SWAP VICTIM THAN A USER EXPECTED TO NEED THE
CPU AGAIN IMMEDIATELY.  CONSOLE OUTPUT WAS BOUNDED SO A FAST PRODUCER COULD
NOT CONSUME UNBOUNDED CORE WHILE A SLOW TERMINAL DRAINED IT.

FINALLY, JOSS MEASURED THE BEHAVIOR THAT MATTERED: RESPONSE TIME, USER STATES,
BUFFER PRESSURE, CORE COMPACTION, DRUM ACTIVITY, AND OTHER SOURCES OF DELAY.
THE IMPORTANT LESSON IS TO MEASURE COMPLETE USER-VISIBLE OPERATIONS, NOT ONLY
INDIVIDUAL KERNEL SUBSYSTEMS.

## 3. DO NOT COPY THE JOSS MONITOR MODEL

DAIMOS SHOULD NOT ADD:

- A LARGE JOSS-LIKE USER-STATE MACHINE;
- ONE SCHEDULER QUEUE FOR EACH INTERACTIVE PHASE;
- TERMINAL-SPECIFIC POLICY THROUGHOUT THE PROCESS SCHEDULER;
- A SPECIAL SHELL OR INTERPRETER PROCESS CLASS;
- LARGE PER-USER ACCOUNTING TABLES;
- A SECOND INTERACTIVE SCHEDULER;
- UNBOUNDED TERMINAL OR DISPLAY OUTPUT QUEUES.

THE EXISTING NICE + RECENT-CPU SCHEDULER REMAINS THE BASE NORMAL SCHEDULER.
THE EXISTING SINGLE-OWNER REAL-TIME MODE REMAINS SEPARATE AND IS NOT AN
INTERACTIVE-PRIORITY FACILITY.

THE JOSS LESSONS SHOULD BE EXPRESSED THROUGH SMALL GENERAL SIGNALS ALREADY
AVAILABLE TO THE DAIMOS PROCESS AND MEMORY SYSTEMS.

## 4. INTERACTIVE WAKEUP POLICY

THE MOST IMPORTANT CHANGE TO INVESTIGATE IS PROMPT SERVICE AFTER A PROCESS HAS
BEEN BLOCKED FOR A MEANINGFUL TIME.

DAIMOS ALREADY HAS MOST OF THE REQUIRED INFORMATION WITHOUT GROWING THE PROCESS
DESCRIPTOR.  THE PACKED SCHEDULER WORD CONTAINS:

- NICE;
- RECENT CPU;
- SATURATING SLEEP AGE;
- WAIT CLASS;
- PROCESS STATE.

BLOCKING WAKEUPS ALREADY CLEAR RECENT-CPU AND SLEEP-AGE ACCOUNTING BEFORE
REQUEUEING THE PROCESS.  THIS NATURALLY GIVES A WOKEN INTERACTIVE PROCESS A
GOOD SCORE AT THE NEXT NORMAL SCHEDULER SELECTION.

THE REMAINING LATENCY IS THAT AN ORDINARY WAKEUP NEED NOT PREEMPT A CURRENT
CPU-BOUND PROCESS UNTIL ITS NORMAL QUANTUM ENDS.  FOR A WORKSTATION LOAD THIS
CAN MAKE A HUMAN-VISIBLE REQUEST WAIT BEHIND COMPUTATION THAT HAS ALREADY HAD
PLENTY OF CPU.

THE PREFERRED EXTENSION IS:

    LONG-BLOCKED PROCESS BECOMES RUNNABLE
            ->
    CLEAR ITS EXISTING DYNAMIC CPU/SLEEP ACCOUNTING
            ->
    REQUEST THE EXISTING SOFTWARE PI6 RESCHEDULE
            ->
    RUN THE ORDINARY NICE + RECENT-CPU SELECTOR

THIS IS NOT A PRIORITY BOOST CLASS.  IT ONLY ASKS THE NORMAL SELECTOR TO
RECONSIDER THE RUN QUEUE PROMPTLY.  NICE STILL APPLIES, REAL-TIME OWNERSHIP
STILL WINS, AND A PROCESS WHICH CONTINUES COMPUTING IMMEDIATELY ACCUMULATES
RECENT-CPU PENALTY NORMALLY.

THE FIRST IMPLEMENTATION SHOULD USE EXISTING SLEEP AGE AS THE INTERACTIVE
PROXY.  A PROCESS BLOCKED FOR AT LEAST ONE SLEEP-AGE PERIOD IS A CANDIDATE FOR
AN IMMEDIATE RESCHEDULE REQUEST.  THIS CATCHES HUMAN THINK TIME WITHOUT
REQUIRING THE SCHEDULER TO KNOW WHETHER THE WAKEUP CAME FROM CTY, DCS, GE,
DPY, A PIPE, A CHILD, OR A FILESYSTEM.

SHORT DEVICE WAITS SHOULD NOT CAUSE A RESCHEDULE KICK MERELY BECAUSE AN I/O
COMPLETION OCCURRED.  THIS AVOIDS TURNING HIGH-RATE DISK, TAPE, PIPE, OR
TERMINAL TRAFFIC INTO EXCESSIVE SCHEDULER ACTIVITY.

IF MEASUREMENT LATER SHOWS THAT ONE SLEEP-AGE PERIOD IS TOO COARSE, CHANGE THE
AGE REPRESENTATION OR THRESHOLD ONLY AFTER MEASURING THE COST.  DO NOT ADD A
TTY-SPECIFIC PROCESS FLAG JUST TO RECOGNIZE INTERACTIVE JOBS.

## 5. WORKSTATION FAIRNESS

THE TARGET IS NOT MAXIMUM THROUGHPUT UNDER A LARGE NUMBER OF TERMINAL USERS.
THE NORMAL CASE IS A SMALL SET SUCH AS:

    LOGIN/DSH OR EDITOR        INTERACTIVE
    COMPILER/ASSEMBLER/LINKER  BURSTY OR CPU-HEAVY
    MAKE OR TEST JOB           BACKGROUND/COMPUTE
    ONE OR TWO OTHER LOGINS    MOSTLY IDLE OR INTERACTIVE

AN INTERACTIVE WAKEUP MAY THEREFORE RUN QUICKLY AHEAD OF A COMPUTE JOB, BUT IT
MUST NOT RECEIVE A PERMANENT PRIORITY ADVANTAGE.  RECENT-CPU ACCOUNTING IS THE
CORRECT DECAY MECHANISM: ONCE THE WOKEN PROCESS USES CPU, IT RETURNS NATURALLY
TO ORDINARY COMPETITION.

NICE REMAINS THE EXPLICIT ADMINISTRATIVE/USER POLICY.  AN ORDINARY USER MUST
NOT BE ABLE TO LABEL A PROCESS "INTERACTIVE" TO ESCAPE NICE OR CPU FAIRNESS.
THE KERNEL SHOULD INFER SHORT-TERM INTERACTIVITY FROM BLOCKING HISTORY.

THIS POLICY ALSO FITS MULTIPLE USERS: EACH USER WHO RETURNS AFTER THINK TIME
CAN OBTAIN QUICK SERVICE, WHILE A USER WHO RUNS CONTINUOUS COMPUTATION DOES
NOT DOMINATE THE MACHINE.

## 6. SWAP AND CORE-PRESSURE POLICY

JOSS'S SECOND IMPORTANT LESSON IS THAT THE BEST SWAP VICTIM IS OFTEN THE
PROCESS LEAST LIKELY TO NEED CPU SOON, NOT MERELY THE PROCESS THAT USED CPU
LEAST RECENTLY.

DAIMOS ALREADY IMPLEMENTS MUCH OF THIS IDEA.  SWAP-VICTIM SELECTION PREFERS
SLEEPING OR STOPPED PROCESSES, USES THE EXISTING SATURATING SLEEP AGE, AND
ONLY THEN FALLS BACK TO RUNNABLE-PROCESS PRIORITY.  THIS IS APPROPRIATE FOR
THE WORKSTATION TARGET AND SHOULD REMAIN THE BASE POLICY.

THE DESIGN RULES ARE:

- LONG-SLEEPING PROCESSES ARE STRONG SWAP-OUT CANDIDATES;
- STOPPED JOBS ARE STRONG CANDIDATES;
- LOW-PRIORITY BACKGROUND RUNNABLE JOBS ARE BETTER VICTIMS THAN ACTIVE
  INTERACTIVE WORK;
- A PROCESS WHICH HAS JUST WOKEN AFTER A LONG BLOCK SHOULD NOT BE CHOSEN FOR
  SWAP-OUT BEFORE IT GETS A CHANCE TO RUN;
- SHORT DEVICE WAITS SHOULD NOT BE MISTAKEN FOR HUMAN IDLE TIME;
- CLEAN EXECUTABLE-BACKED TEXT SHOULD CONTINUE TO BE DISCARDED AND RELOADED
  RATHER THAN WRITTEN TO BACKSTORE.

BECAUSE THE PDP-6 PROCESS TABLE IS SMALL, A LINEAR VICTIM SCAN IS ACCEPTABLE
AND OFTEN BETTER THAN MAINTAINING EXTRA ORDERED QUEUES.  DO NOT ADD JOSS-LIKE
PER-STATE QUEUES UNLESS MEASUREMENTS SHOW A REAL NEED.

THE EXISTING SLEEP-AGE/WAIT-CLASS PACKING SHOULD BE USED BEFORE ADDING ANY
PER-PROCESS MEMORY.

## 7. BOUNDED OUTPUT AND BACKPRESSURE

JOSS DELIBERATELY LIMITED CONSOLE OUTPUT BUFFERS.  WHEN A SLOW CONSOLE COULD
NOT DRAIN OUTPUT QUICKLY ENOUGH, THE PRODUCER WAITED RATHER THAN CONSUMING
ARBITRARY CORE.

DAIMOS SHOULD KEEP THE SAME GENERAL RULE:

    SLOW CONSUMER
            ->
    BOUNDED QUEUE FILLS
            ->
    PRODUCER BLOCKS
            ->
    OTHER WORK RUNS

THIS APPLIES TO TERMINALS, DISPLAY TEXT SERVICES, PIPES, AND ANY FUTURE
BUFFERED USERSPACE DISPLAY PATH.  IT DOES NOT REQUIRE ONE COMMON KERNEL
BUFFERING IMPLEMENTATION; THE IMPORTANT PROPERTY IS A SMALL, EXPLICIT BOUND.

DO NOT ADD LARGE PER-TTY OUTPUT BUFFERS TO IMPROVE BENCHMARK THROUGHPUT.
DAIMOS IS MORE CONSTRAINED BY CORE THAN BY THE COST OF OCCASIONALLY BLOCKING A
FAST WRITER BEHIND A HUMAN-SPEED DEVICE.

THE CURRENT FIXED-SIZE WORD PIPE AND LAZY/BOUNDED TERMINAL/DISPLAY STORAGE ARE
CONSISTENT WITH THIS POLICY.

## 8. END-TO-END INTERACTIVE MEASUREMENT

INTERACTIVE POLICY MUST BE VALIDATED WITH USER-VISIBLE LATENCY, NOT ONLY CPU
THROUGHPUT OR KERNEL MICROBENCHMARKS.

THE PRIMARY DSH METRICS SHOULD INCLUDE:

    COMPLETE INPUT LINE -> FIRST SHELL RESPONSE
    COMPLETE COMMAND    -> FIRST CHILD OUTPUT
    COMPLETE COMMAND    -> PROMPT RETURN
    LONG-IDLE WAKEUP    -> FIRST USER INSTRUCTION
    SWAPPED WAKEUP      -> FIRST USER INSTRUCTION

THE MEMORY-PRESSURE WORKLOAD SHOULD ALSO RECORD:

- PROCESS SWAP-OUTS AND SWAP-INS;
- WORDS WRITTEN TO AND READ FROM BACKSTORE;
- CLEAN EXECUTABLE TEXT DISCARDED/RELOADED;
- CORE COMPACTIONS;
- BCACHE/MEMFS RECLAIM BEFORE PROCESS SWAP;
- LONGEST OBSERVED INTERACTIVE WAKEUP DELAY.

THE NORMAL ACCEPTANCE WORKLOAD SHOULD REPRESENT THE INTENDED MACHINE, FOR
EXAMPLE:

    SESSION 1   INTERACTIVE DSH/EDITOR
    SESSION 2   INTERACTIVE OR MOSTLY IDLE
    BACKGROUND  MAKE/COMPILER/TEST OR CPU LOOP
    MEMORY      ENOUGH PRESSURE TO EXERCISE RECLAIM AND, IN ONE TEST, SWAP

THE TEST SHOULD VERIFY THAT BACKGROUND WORK CONTINUES TO MAKE PROGRESS WHILE
INTERACTIVE RESPONSE REMAINS SHORT.

DETAILED COUNTERS DO NOT BELONG PERMANENTLY IN THE PRODUCTION KERNEL MERELY TO
SUPPORT THESE TESTS.  PREFER TESTKIT/SIMULATOR TRACING OR A BUILD-TIME
INSTRUMENTED CONFIGURATION.  ONLY A COUNTER WHICH PROVES USEFUL FOR NORMAL
ADMINISTRATION SHOULD BE CONSIDERED FOR THE PERMANENT MONITORFS ABI.

## 9. USERSPACE INTERACTION QUALITY

JOSS ALSO SHOWS THAT AN INTERACTIVE SYSTEM BENEFITS WHEN ERRORS PRESERVE THE
USER'S PROBLEM-SOLVING CONTEXT.  FOR DAIMOS THIS BELONGS PRIMARILY IN DSH AND
OTHER USERSPACE TOOLS, NOT THE KERNEL.

DSH SHOULD PREFER STRUCTURED PARSER ERRORS SUCH AS:

    EXPECTED COMMAND AFTER PIPE
    MISSING REDIRECTION TARGET
    UNTERMINATED QUOTE

OVER AN UNQUALIFIED "SYNTAX ERROR" WHEN THE PARSER ALREADY KNOWS THE FAILURE
CONTEXT.  COMPLETION AND HELP SHOULD CONTINUE TO USE SIXMD METADATA, BUT BASIC
COMMAND EXECUTION AND ERROR REPORTING MUST NOT DEPEND ON INSTALLED HELP DATA.

THIS PROVIDES SOME OF JOSS'S "HELPFUL ASSISTANT" QUALITY WITHOUT MOVING
LANGUAGE OR SHELL POLICY INTO THE KERNEL.

## 10. IMPLEMENTATION ORDER

THIS DOCUMENT DOES NOT OVERRIDE THE CURRENT RELEASE GATES.  DO NOT GROW THE
KERNEL WHILE THE PERMANENT IMAGE IS ABOVE ITS HARD LIMIT.

AFTER THE CURRENT SIZE/CORRECTNESS GATE:

1. ADD THE END-TO-END INTERACTIVE TESTKIT WORKLOAD AND MEASURE THE UNCHANGED
   SCHEDULER FIRST.
2. MEASURE LONG-BLOCK WAKEUP LATENCY WITH A COMPETING CPU-BOUND JOB.
3. IF THE NORMAL QUANTUM IS VISIBLE IN THAT LATENCY, ADD THE MINIMAL
   LONG-BLOCK WAKEUP PI6 RESCHEDULE REQUEST USING THE EXISTING SLEEP-AGE
   FIELD.
4. RE-MEASURE THROUGHPUT, CONTEXT-SWITCH RATE, MULTIUSER FAIRNESS, AND KERNEL
   SIZE.  KEEP THE CHANGE ONLY IF THE RESPONSE-TIME BENEFIT IS CLEAR.
5. EXERCISE THE EXISTING SWAP-VICTIM POLICY UNDER THE SAME WORKSTATION LOAD.
   CHANGE IT ONLY IF TRACES SHOW A REPEATABLE BAD VICTIM CHOICE.
6. KEEP TERMINAL/DISPLAY/PIPE OUTPUT BOUNDED AS THOSE USERSPACE PATHS GROW.
7. IMPROVE DSH PARSER DIAGNOSTICS DURING SUBSTANTIAL DSH WORK; THIS SHOULD
   REQUIRE NO KERNEL SUPPORT.

## 11. ACCEPTANCE CRITERIA

THE JOSS-DERIVED WORK IS SUCCESSFUL ONLY IF:

- AN INTERACTIVE PROCESS WAKING AFTER HUMAN-SCALE IDLE TIME IS NOT FORCED TO
  WAIT FOR AN UNRELATED CPU-BOUND PROCESS TO CONSUME A FULL ADDITIONAL QUANTUM
  WHEN A CHEAP RESCHEDULE CAN AVOID IT;
- CONTINUOUSLY CPU-BOUND PROCESSES STILL MAKE FAIR FORWARD PROGRESS;
- NICE AND THE REAL-TIME OWNER RULES REMAIN AUTHORITATIVE;
- SHORT HIGH-RATE I/O DOES NOT CAUSE A RESCHEDULE STORM;
- SWAP POLICY FAVORS GENUINELY INACTIVE WORK WITHOUT THRASHING RECENTLY WOKEN
  INTERACTIVE PROCESSES;
- NO NEW PROCESS-DESCRIPTOR WORD IS REQUIRED UNLESS MEASUREMENT PROVES THE
  EXISTING PACKED STATE INSUFFICIENT;
- NO LARGE PER-USER OR PER-TTY RESIDENT TABLE IS INTRODUCED;
- PRODUCTION INSTRUMENTATION COST REMAINS NEAR ZERO;
- THE 32K PDP-6 ACCEPTANCE BUILD STILL BOOTS THROUGH NORMAL LOGIN/DSH;
- THE FULL PERMANENT IMAGE REMAINS BELOW THE PROJECT'S HARD RESIDENT LIMIT.

## 12. DESIGN SUMMARY

THE CENTRAL JOSS LESSON FOR DAIMOS IS NOT "ADD MORE PRIORITIES."  IT IS:

> USE THE INFORMATION ALREADY CREATED BY BLOCKING, WAKEUP, AND MEMORY
> PRESSURE TO REDUCE HUMAN-VISIBLE LATENCY.

FOR DAIMOS'S WORKSTATION-LIKE MULTIUSER TARGET, A SMALL EXTENSION TO THE
EXISTING SCHEDULER IS PREFERABLE TO A JOSS-LIKE FOREST OF USER STATES.  A
LONG-BLOCKED PROCESS SHOULD GET A PROMPT NORMAL SCHEDULER RECONSIDERATION,
RECENT CPU SHOULD REMOVE THAT ADVANTAGE AS SOON AS IT COMPUTES, SLEEP AGE
SHOULD CONTINUE TO GUIDE SWAP VICTIM SELECTION, AND SLOW OUTPUT SHOULD APPLY
BACKPRESSURE INSTEAD OF CONSUMING CORE.

THE RESULT SHOULD FEEL RESPONSIVE TO THE PERSON AT THE CONSOLE WHILE REMAINING
THE SAME SMALL, GENERAL-PURPOSE DAIMOS KERNEL.
