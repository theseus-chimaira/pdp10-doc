6. /CONFIG EDITING MODEL

THE LIVE "/CONFIG" STRUCTURE IS SYNTHETIC, BUT IT SHOULD BE EDITED LIKE FILES.

V0.5 RULES:

- USERS MAY EDIT CONFIG FILES WITH AN EDITOR.
- USERS MAY ALSO USE USERMODE CTL COMMANDS.
- /CONFIG STRUCTURE IS SYNTHETIC.
- /CONFIG FILES EXPOSE TYPED CONFIG RECORDS.
- CLOSING A CONFIG FILE AFTER WRITING CAUSES AN AUTOMATIC CHECK.
- IF THE CHECK FAILS, THE WRITE/CLOSE FAILS WITH ?CFG.
- FAILED CONFIG WRITES DO NOT CHANGE THE COMMITTED LIVE CONFIG.
- COMMIT CONFIG IS A USER COMMAND.
- INIT READS ONLY COMMITTED CONFIG.

THERE ARE NO COMMENTS IN NATIVE CONFIG FILES.

CONFIGURATION FILES CONTAIN DATA, NOT DOCUMENTATION.
MANUALS MUST BE GOOD ENOUGH TO EXPLAIN EVERY CONFIG TABLE AND FIELD.

RECOMMENDED COMMAND NAMES:

CHECK CONFIG
COMMIT CONFIG
ABORT CONFIG
SHOW CONFIG

OR AS EXECUTABLE COMMANDS:

CFGCHK
CFGCOMMIT
CFGABORT
CFGSHOW

THE COMMAND SPELLING CAN BE DECIDED LATER. THE IMPORTANT V0.5 RULE IS:

COMMIT CONFIG IS A COMMAND, NOT A MAGIC FILE WRITE.

7. /CONFIG STORAGE RECOMMENDATION

REASONABLE RECOMMENDATION:

- KEEP COMMITTED LIVE CONFIG TABLES DECODED IN KERNEL MEMORY.
- KEEP THE CANONICAL COMMITTED CONFIG IMAGE ON DISK.
- USE PER-OPEN IN-MEMORY STAGING BUFFERS FOR NORMAL CONFIG EDITS.
- IMPOSE SMALL EXPLICIT LIMITS ON V0.5 CONFIG TABLE SIZES.
- FOR RARE LARGE CONFIG TABLES, ALLOW D6FS-BACKED TEMPORARY STAGING.
- DO NOT MAKE LARGE MUTABLE DATASETS PART OF /CONFIG.

RATIONALE:

MOST CONFIG SHOULD BE SMALL. KEEPING COMMITTED DECODED TABLES IN MEMORY MAKES
LOOKUP FAST AND CHECKING SIMPLE. KEEPING THE CANONICAL COMMITTED COPY ON DISK
MAKES THE CONFIG PERSISTENT. PER-OPEN MEMORY STAGING AVOIDS MAKING EVERY EDIT
A DISK TRANSACTION BEFORE VALIDATION.

IF A TABLE BECOMES TOO LARGE TO STAGE IN MEMORY, IT IS PROBABLY NOT REALLY
CONFIGURATION. IT SHOULD USUALLY BE A NORMAL FILE REFERENCED FROM /CONFIG,
NOT EMBEDDED INSIDE /CONFIG.

SUGGESTED V0.5 IMPLEMENTATION:

- SMALL TABLES: MEMORY STAGING ONLY.
- COMMITTED TABLE IMAGE: ON DISK.
- DECODED COMMITTED TABLE: RESIDENT IN MEMORY.
- MAXIMUM TABLE SIZE: DOCUMENTED PER TABLE.
- OVERSIZED WRITE: ?FULL OR ?NOMEM.

SUGGESTED V1.0 EXTENSION:

- OPTIONAL D6FS-BACKED STAGING FOR LARGER TABLES.
- SAME VALIDATION AND COMMIT SEMANTICS.

8. /CONFIG CONCURRENCY MODEL

CONCURRENT EDITING SHOULD BE SIMPLE.

RULES:

- MULTIPLE USERS MAY OPEN THE SAME CONFIG FILE.
- EACH WRITER GETS A PRIVATE STAGED EDIT VIEW.
- A WRITE/CLOSE CHECKS THE STAGED EDIT.
- IF VALID, THE STAGED EDIT BECOMES THE NEWEST PENDING VERSION FOR THAT TABLE.
- IF ANOTHER EDITOR HAD AN OLDER VIEW OPEN, THAT EDITOR SHOULD SEE AN
  "OPEN FILE CHANGED" CONDITION BEFORE WRITING.
- THE LATER WRITER MAY STILL FORCE THE WRITE.
- IF FORCED AND VALID, THE LATER WRITER HAS PRIORITY.

ATOMICITY RULE:

WRITES TO A CONFIG TABLE MUST BE ATOMIC AT THE TABLE LEVEL.

SIMULTANEOUS WRITES:

- INTERNALLY SERIALIZED BY THE CONFIG SUBSYSTEM.
- ONE VALID WRITE WINS FIRST.
- ANOTHER VALID FORCED WRITE MAY REPLACE IT LATER.
- NO PARTIAL TABLE STATE MAY BECOME VISIBLE.

THIS IS CLOSE ENOUGH TO NORMAL FILESYSTEM CONFLICT BEHAVIOR, BUT WITH STRONGER TABLE-LEVEL VALIDATION.

9. /CONFIG COMMIT AND CRASH MODEL

"COMMIT CONFIG" IS ATOMIC.

RECOMMENDED MODEL:

- EACH CONFIG TABLE HAS A COMMITTED GENERATION NUMBER.
- A PENDING VALID TABLE IS WRITTEN AS A COMPLETE NEW TABLE IMAGE.
- THE TABLE HEADER CONTAINS TYPE, SIZE, GENERATION, AND CHECKSUM.
- COMMIT INSTALLS THE NEW TABLE BY A HEADER-LAST OR POINTER-SWAP OPERATION.
- ON BOOT, THE NEWEST VALID TABLE GENERATION IS SELECTED.
- IF THE NEWEST TABLE IS INVALID, THE PREVIOUS VALID GENERATION IS USED.
- IF NO VALID GENERATION EXISTS, THE TABLE DEFAULT IS USED.

CRASH DURING COMMIT:

- A CRASH DURING COMMIT MAY AFFECT ONLY THE TABLE BEING COMMITTED.
- IT MUST NOT CORRUPT UNRELATED CONFIG TABLES.
- IMPOSSIBLE OR CORRUPT TABLE DATA CAUSES FALLBACK TO THE PREVIOUS VALID
  GENERATION OR TO THE TABLE DEFAULT.
- INIT READS ONLY COMMITTED VALID CONFIG.

THIS PRESERVES THE DESIRED RULE:

COMMIT IS ATOMIC.

IF THE UNDERLYING DISK UPDATE CANNOT BE MADE TRULY ATOMIC IN ONE WRITE, THE TABLE FORMAT MUST MAKE RECOVERY DETERMINISTIC BY USING GENERATION NUMBERS AND CHECKSUMS.

10. /CONFIG TYPED RECORDS

CONFIG RECORDS SHOULD BE TYPED.

RECOMMENDED FIELD TYPES:

- WORD        36-BIT BINARY WORD
- BOOL        TRUE/FALSE
- ENUM        ONE OF A FIXED SET
- OCTAL       NUMERIC VALUE REPRESENTED CANONICALLY IN OCTAL
- SIXBIT      SIXBIT NAME
- PATH        NATIVE PATH REFERENCE
- DEVREF      /DEVICE REFERENCE
- USER        USER/SESSION REFERENCE
- MODE        PERMISSION/MODE WORD
- ADDR        MACHINE ADDRESS
- LIMIT       BOUNDED NUMERIC VALUE

BINARY WORDS:

BINARY WORDS SHOULD BE STORED AS TYPED BINARY VALUES IN THE COMMITTED CONFIG
TABLE.

FOR HUMAN EDITING, THE EDITOR OR CTL TOOL SHOULD EXPOSE A CANONICAL OCTAL
FORM. ON CLOSE, THE CONFIG SUBSYSTEM PARSES AND VALIDATES THE FIELD AND STORES
THE TYPED BINARY WORD.

THIS GIVES BOTH PROPERTIES:

- HUMAN-EDITABLE CONFIG
- MACHINE-CHECKABLE TYPED BINARY CONFIG

EXAMPLE TYPED TABLE:

TABLE BOOT
FIELD INIT     PATH   /SYSTEM/INIT
FIELD SHELL    PATH   /SYSTEM/DSH
FIELD FAILMODE ENUM   SHELL
FIELD STARTUP  PATH   /CONFIG/STARTUP/RC

EXAMPLE LOWER-LEVEL BINARY REPRESENTATION:

TABLE BOOT
INIT     = PATHREF(...)
SHELL    = PATHREF(...)
FAILMODE = ENUM(1)
STARTUP  = PATHREF(...)

THE USER DOES NOT NEED TO EDIT THE BINARY FORM DIRECTLY. THE COMMITTED STORAGE CAN STILL BE BINARY TYPED RECORDS.

17. MAKE

NATIVE DAIMOS MAKE SHOULD NOT DEPEND ON LITERAL ASCII TAB.

NATIVE RECIPE MARKER:

TARGET: DEP DEP
> COMMAND
> COMMAND

PORTABLE STANDARD MAKE DOES NOT USE ">" AS A RECIPE PREFIX. TRADITIONAL/POSIX MAKE EXPECTS TAB-PREFIXED RECIPE LINES. GNU MAKE CAN CONFIGURE ANOTHER RECIPE PREFIX, BUT THAT IS NOT PORTABLE.

THEREFORE:

- DAIMOS-NATIVE MAKE MAY USE ">" AS RECIPE MARKER.
- UNIX/POSIX MAKEFILES MUST BE CONVERTED ON IMPORT.
- DAIMOS2UNIX/UNIX2DAIMOS CAN TRANSLATE BETWEEN LEADING TAB AND LEADING ">".

V1.0 MAKE REQUIREMENTS:

- PARSE DAIMOS MAKEFILES.
- BUILD DAIMOS KERNEL AND CORE USERLAND.
- BUILD THE KCC-DERIVED COMPILER SUBSET.
- SUPPORT ENOUGH VARIABLES/MACROS FOR THE NATIVE TREE.
- SUPPORT EXPLICIT RULES.
- SUPPORT SIMPLE SUFFIX OR PATTERN RULES ONLY IF NEEDED.
