# DAIMOS RESIDENT-SIZE STATUS

DATE: 2026-10-20

## 2026-10-21 V98: PINNED SYSINFO MRES, 118 FEWER KCORE WORDS

The cold PROCINFO and MEMINFO query routines moved from the old 122-word
KCORE `syscall_info.s` object to `syscall_info_mres_v98.s`, loaded as a
mandatory, pinned `SINFO` MRES package by MINIT before runtime processes
and optional filesystem providers. KCORE retains three one-word stubs:
the two public query entries and the existing MEMFS usage-hook patch
slot. A one-word KCORE variable holds the permanent-resident word count
published by KINIT; relocated MEMINFO now reads it as data rather than
relying on a patched immediate inside movable module code. This also
preserves the existing MEMFS module-runtime binding and absence behavior.

Folded full-profile 256K KCC KCORE endpoint **022736 -> 022550 octal**,
**9646 -> 9528 words (-118)**. The original KCORE object became
**3 text + 1 data** words, and the new MRES contains 122 initialized
service words (plus its package descriptor). Full 256K disk-root image
link PASS. Targeted 256K PDP-6 SIMH native test PASS for both PROCINFO
and MEMINFO, returned process and permanent-memory information,
invalid user pointers, and recovery. No 32K, TSFS or full testkit runs.
KCORE requires **1337 more words** saved to be strictly below 8192.

Next candidate: the cold 272-word `proc_run_block` implementation, after
independent process/RUN lifetime and fixed MRES dependency auditing.


## 2026-10-21 V97: SHARED SIX-WAY USER-POINTER SYSCALL PATH

CHDIR, GETCWD, MKDIR, UNLINK, TRUNCATE and MEMINFO now select their
KCORE service in AC5 and share `native_sys_one_ptr`, retaining the
user-mapping hold/failure/release semantics and the caller's AC2 scalar.
Fresh folded KCC full-profile 256K link: `__kcore_low_end` octal
**022747 -> 022736**, **9655 -> 9646 KCORE words (-9)**. Syscall
dispatch input DOBJ **817 -> 808** text words. The new focused 256K
SIMH `test-daimos-kcore-oneptr-v97` PASSes all six syscalls and bad
logical pointer failure/recovery. No 32K, TSFS or full testkit tests.
Strictly below 8192 now requires **1455 more words**.

Comparison from the supplied historical TENEX/ITS assembler sources:
DAIMOS's primary 040..077 UUO dispatch occupies **16 packed words**;
the extension dispatch occupies **14 packed words**, total **30 words**
excluding dispatch instructions. TENEX's `128-tenex/sys.collec` builds
one `XWD FPC,handler` JSYS vector word per JSYS number up to 0777 octal
(**512 words**). ITS `src/system/its.1652` uses a UUO opcode-class
table, then numbered `.CALL` dispatch and symbolic SIXBIT name/descriptor
tables. These are **front-end tables**, not comparable complete syscall
implementations. The useful lesson is to preserve DAIMOS's packed KCORE
front-end while pursuing cold-service relocation into pinned MRES. Full
analysis and historical source paths are kept in `DAIMOS/KCORE.MD`.

## 2026-10-21 V79: DCS TRANSMIT BACKPRESSURE (SIMH PDP-6)

V78 `HELP DAS` terminal output was corrupted and stalled when the SIMH
Type 630 terminal transmit queue filled.  V79 adds an explicit DCSB CONI
`0100` transmit-ready indication in the paired PDP-6 simulator and checks
it in DAIMOS's `dcs_putchar` before DATAO.  When necessary, the simulator
polls/drains its pending TMXR output before advertising ready, preventing
both the original lost characters and the first finite-poll experiment's
premature timeouts.  On a fresh 256K KCC PDP-6 disk image, isolated HELP
DAS passes with its original assertions and full DSH conformance passes
115/115 using the paired builds.

Resident cost: DCS MRES DXR `000074` to `000105` octal = 9 decimal
additional PDP-10 words.  KCORE linked endpoint stays `024776` octal;
DSH stays `035764` octal.  These are software/simulator acceptance results,
not proof that real Type 630 hardware supplies the simulator's extra
CONI `0100` readiness bit.  Hardware compatibility remains open.

## 2026-10-20 V75: ACTUAL SLOT-0 KERNEL STACK CONSUMPTION

The original permanently pinned slot-0 idle/exit/swap-service stack occupied
`0100` octal (64 decimal) words.  This is **not enough** when a sleeping
process wakes from swap: slot 0 calls `proc_swap_service_one`, `proc_swap_in`,
aligned MM allocation and nested backing-store/I/O and cleanup routines.
The 48K live swapped-process V74 test initially stalled in this path.

An exploratory `0200`-octal (128-word) stack made the full 48K test PASS.
With the existing test-only `PROC_STACK_WATERMARK=1` canaries, the *first
untouched* stack word was at offset `0116` octal (78 decimal).  Since the
PDP-6 pushdown stack grows upward from the base, **77 words were touched**
by this test's deepest measured path.  An allocation of 78 words is the
observed minimum; it is *not* a safe general-purpose reserve.

The accepted V75 setting is `0140` octal (96 decimal) words, identically in
`system/kernel/boot/kinit.h` and `system/kernel/proc/proc_pdp6.s`.  The full
48K PDP-6 swapped MonitorFS / wake / WAIT regression PASSed again with the
96-word stack and automatic watermark assertion; the first untouched word
remained at offset 78, leaving 18 unused words.  The increase versus the
original stack is **32 resident RAM words**, rather than the **64** added
by the 128-word trial.  This is a dynamic MM allocation and does not change
the linked KCORE endpoint.  This is a measured workload peak, not a promise
about every possible future nested kernel path.  Strict 32K boot sizing
remains deferred by user request.


## 2026-10-20 V73 STARTUP RECORDS AND RESIDENT SWAP METADATA

MonitorFS no longer needs a dedicated BACKSTORE reader to display argv and
environment records for nonresident processes.  On swap-out, the V72/V73
implementation validates and preserves only the occupied startup prefix in
an exact-size, non-reclaiming dynamic allocation.  The existing stable u-area
gains one snapshot pointer at octal offset `0410`.  Snapshots are allocated
only for swapped processes, accounted in MEMINFO, and released on swap-in or
process teardown.  Process descriptors still occupy three words; the disk
swap format is unchanged.  The removed KCC swap reader occupied 691 text
words; the new snapshot implementation has 225 KCC text words and one BSS
word, excluding ordinary allocator code already in KCORE.

The V73 correction makes MonitorFS, PROCINFO COMM, and snapshot capture find
startup records from the **original** VM length, stored as the high half of
the per-process `PROC_BRK_WORD`.  `BRK` growth changes the current allocation
length in `vm_state` but does not move argc/argv/envp, so using the latter
as the origin previously made resident DSH metadata disappear.  Capturing
the snapshot also rejects an impossible original length beyond the allocated
VM.  No further per-process state is necessary.

Fresh KCC 256K link endpoints, octal (exclusive KCORE low end):

    Old BACKSTORE reader     025723
    V72 snapshot             024754  (-487 decimal words)
    V73 stable BRK origin    024776  (+18 vs V72; -469 vs old reader)

The unchanged 256K KCC LOGIN -> DSH MonitorFS live acceptance now passes
NAME, CMDLINE, ENVIRONMENT, relative path traversal and domain fields.
An independent fresh GCC low-memory 48K disk-root run passes the same oracle,
with KCORE endpoint `024454` octal.  Both GCC and KCC PDP-6 native snapshot
tests pass with deliberate post-start heap growth; the native MonitorFS word
I/O fixture passes with a grown VM and correct stable u-area.  These tests
do not yet exercise MonitorFS while its observed target process is actually
swapped.  Full fixed KCORE+MRES size acceptance must still be measured on
the relevant configuration; the figures above measure KCORE endpoints, not
the complete permanent-memory total.  Strict 32K transient image fitting
remains deliberately deferred and is not inferred from the 48K test.

## ACTIVE RULE

THE ONLY ACTIVE FIXED-SIZE ACCEPTANCE LIMIT IS THE ARCHITECTURAL REQUIREMENT
THAT FIXED RESIDENT PLUS IRREDUCIBLE SCRATCH KERNEL MEMORY REMAIN BELOW 16K
WORDS.  RECLAIMABLE MANAGED-CORE CACHE DOES NOT COUNT AS FIXED IMAGE MEMORY,
BUT ITS RESIDENT CODE AND NONRECLAIMABLE METADATA DO.

KCC IS THE ACCEPTANCE COMPILER.  GCC RESULTS MAY BE USED FOR CODE-QUALITY
COMPARISON BUT MAY NOT SUBSTITUTE FOR KCC ACCEPTANCE.
